## ★★ 两处必须说清楚的（报告纪律）

1. **`back` 的 46 是"假红修掉之后"的数。** 上一轮 20 PASS / 2 FAIL 里的 2 条 FAIL
   **是测试自己的错**——`agent2` 被错选成了 `agent_id` 本身，导致"切到第二个智能体"
   点在它已经待着的那一项上（空操作）。**不是产品缺陷。**

2. **`revert-effect-e2e.py` 不是有效反证。** 注入旧写法后 E2E **仍 46 PASS / 0 FAIL** ——
   因为常规交互下"卡片出现"与"切智能体"隔着几秒，中间那次渲染必然已提交，
   `browser.view` 的快照不会过期 ⇒ **窗口根本不开**。
   那处修复的验证依据改由 `view-race-closure.mjs` 的**场景 3** 承担，
   证据等级如实标注为「**最小化实验**」，**不是**真机 E2E。
   （不把"防御性写法"说成"已验证的修复"。）

## 两条可复用的方法论

- **"测试红了" ≠ "产品坏了"**：改产品前先证明**这条路径真被走到了**（本轮判据：`contact--on` 有没有变）。
- **"反证不红" ≠ "修复没用"**：也可能是**测试覆盖不到那个时序**；
  这时要**降到更小层面直接把条件构造出来证明**，而不是含糊写"已验证"或草率撤掉修复。
