## 0. 用户拍板的三个必须行为(各带反证,全部达成)

| 行为 | 实现 | 反证 |
|---|---|---|
| ① 名字解析不到 → **不许偷偷挑最像的**,回「没找到叫『X』的智能体,现在有:[名单]」 | 名册**精确**匹配;没点名 = 建给本轮发言人(确定性落点,不是猜) | C1:解析改成"永远拿名册第一个"→「让小王…」被建成 routine,验收红在「没找到叫『小王』的智能体」 |
| ② 同 agent + 同节奏 + 同任务已有 active routine → **不建第二个**,回「已经有一个了」 | JSONB 语义相等(键序无关)+ `enabled=true` 的 SELECT,先查后建 | C2:去重 SQL 加恒假条件 → 同句两次建出两条,验收红在「第二遍 = duplicate」 |
| ③ 回话**必须带设成了什么**(节奏 + 任务),不是「好的」、不是确认框 | `已设成:运营助手 每天 09:00 检查店铺数据,结果发这里。` 一步到位 | C3:回话换成「好的。」→ 验收红在「回话带设成了什么」 |
| (规格)解析改永远返回 null 必须红 | —— | C4:`parseRoutineIntent` 调用改恒 null → 9 条行为断言全红 |

## 1. 实现

### 1.1 `apps/server/src/orchestrator/routineCreate.ts`(新增,核心逻辑不碰 HTTP)

`createRoutineFromMessage(pool, { userId, projectId, speakerAgentId, message })` → 四选一:

- `not-a-routine`:L1 解析返回 null → chat 层走正常 LLM 路径;
- `unknown-agent`:点名了名册外的名字 → **一条都不建**,回话带现有名单(`没找到叫『小王』的智能体,现在有:『管家』、『运营助手』、『客服』。…`);
- `duplicate`:同 agent + 同 `trigger_type` + 同 `trigger_config`(JSONB 语义相等)+ 同 `task_template` 且 `enabled=true` → 回 `已经有一个了:<name>(…),没再建第二个。`;
- `created`:`createRoutine` 真 INSERT(复用批次 B 的函数,`computeNextRun` 算 `next_run_at`),回话:
  `已设成:<agentName> <scheduleLabel> <taskTemplate>,<结果去向>。`

**结果去向的诚实口径**:`triggerRoutine` 把例行结果写进**被点名智能体**的最新主会话 —— 点名的就是本轮发言人 → 说「结果发这里。」;点的是别的智能体 → 说「结果发到 <TA> 的主会话。」不撒谎。(有验收钉住。)

### 1.2 `apps/server/src/routes/chat.ts`(挂钩,与批次 E 建智能体同一口径)

在"对话式建智能体"块之后、"先读历史"之前:`createRoutineFromMessage` → 非 `not-a-routine` 时落 **user + assistant 两条消息**(assistant 记 `speaker_agent_id`、真 id、统一 `sse()`)→ 劫持 SSE 回话 → return;`not-a-routine` 或任何失败 → 只告警、回落正常聊天,**绝不把这句吃掉**。

### 1.3 顺序关系(不互相抢)

- 「建一个销售助手」→ 批次 E 的 detectBuildIntent 先命中(建智能体领地);
- L1 的守卫 2(建/创建/来个 + 助手/智能体/…)把这类句子挡在 routine 解析外;
- 「让运营助手每天9点检查店铺数据」→ 批次 E 不认(没有建动词)→ L2 接手。

## 3. 反证(拆一个机制,验收必须红)

`npm run verify:routine-create:revert`,~16s:C1~C4 如第 0 节表格,**全部咬住**,每次注入源码逐字节还原(md5 比对),还原后复跑 exit=0,最终反证失败项 0。

★ **C2 连踩两次参数个数坑**(和收尾 9 的 K3 同一课,第三次记实):
1. 第一版把 `user_id=$1` 改成 `user_id=-1` → `$1` 占位符没了、JS 还是传 5 个参数 → **整条 SQL 报错**,验收 FATAL 退出码 2 —— 红是红了,但红在参数不匹配,不是去重失效;
2. 第二版把 `agent_id=$2` 改成 `agent_id=-1` → `$2` 占位符没了,`$1→$3` 跳号 → 同样炸;
3. 第三版:**占位符原样保留,追加恒假条件** `AND user_id=-1` → 查不到任何行、参数个数不变,红的才真正落在「第二遍建出两条 = 去重失效」本身上。

## 4. 已知边界(如实说)

1. **名册匹配只认精确名字**(名册名来自 `loadProjectRoster`,含 persona 名)。说错一个字 = unknown-agent 回名单,让用户自己选——这就是"不许偷偷挑最像的"。
2. **没点名 = 建给本轮发言人**。这是确定性落点(你在跟谁说话,例行就归谁),不是猜;但用户说"每天9点提醒我喝水"时其实想的是"提醒我"而不是"让管家干"——当前口径把任务(「喝水」)记到发言人名下,回话会明说,用户一眼能纠正。
3. **去重按 (agent, 节奏, 任务) 三元组**。任务文本差一个字(「检查店铺数据」vs「检查店铺数据啊」)就是不同的 routine——不做模糊去重(宁多建,不吞掉用户意图;停用/删除入口是既有的 REST)。
4. 回话里的时刻用**规范格式**(09:00),不是用户原话("9 点")——回话带的是"设成了什么",必须和库里一致。
5. 本批**没有**真 HTTP e2e(起真服务器走 SSE 的那层):chat.ts 的 SSE 口径与批次 E 逐字同构(同样的 hijack/meta/delta/done/真 id),用静态接线断言钉住;批次 J 的 e2e 仍在全量 verify 链里跑 chat 路由,新增块在同一请求路径上(全量 243+ 条真实请求覆盖)。
