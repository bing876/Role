## 片3 原生连接器 · 高风险失败模式（动鉴权/上游输入，先列）

- GitHub PAT、飞书 App Secret 解不开 / 缺失 → 不外呼，回 `not_configured`；没有明文列，也不从全局 gh/飞书登录态偷偷拿 key。
- 外部 HTTP 401/403/5xx、返回畸形/超限 → 统一脱敏错误码，绝不把上游原文/凭据回显。
- 模型伪造 repo 路径、飞书 document_id、folder_token → 入参只认有限长度安全字符；不接任意 URL、不拼上游传入的跳转。
- 别人的连接在 `ctx.userId` 下调用 → 按 userId 查自己的密文配置，未配直接拒绝；测试覆盖两用户。
- 连接器默认只读，避免违反「不自动发送」；需要写操作时另走确认与权限授权方案。GitHub issue 列表须排除 pull_request（GitHub Issues API 会把 PR 算 issue）。飞书 tenant token 只能访问**应用有权限**的文档；无权不能宣称读取所有用户文档。
- 上游接口参考：GitHub https://docs.github.com/en/rest/issues/issues；Feishu https://open.feishu.cn/document/ukTMukTMukTM/uUDN04SN0QjL1QDN/document-docx/docx-overview 和 https://open.larkoffice.com/document/server-docs/api-call-guide/server-api-list 。

## 片2 决策与失败模式（动热路径/鉴权/密钥，先列）

- 通用桥当前仅 **MCP Streamable HTTP**；不执行用户填写的本地 shell/stdio 命令（RCE 风险），不是冒充「通用」包括任意本地进程。
- 生产注册表 append-only → 每个 MCP server rowId 全局唯一，按 `mcp__s<id>__<name>` 命名；只给当前用户的循环工具表拼当前用户工具；执行器再次校验 `user_id`。删除/重配后旧注册项仅为死条目，永不授权运行。
- URL 被恶意修改 / 重定向 → 限制 https 或 loopback http；禁止 URL 用户名/密码/查询参数；不跟跨站重定向；输入大小/工具数量/工具名限制。对于公开 server 只读外部输入视作不可信。
- auth 解不开 → 禁执行（fail-closed）；数据库只存 AES-GCM 密文，API 不返明文。
- 服务端 TCP 断、空响应、SSE 错帧、超时 → 回明确错误，密钥不进日志/错误文字；不会卡死主循环。
- 公网验收：本沙箱到 `https://mcp.deepwiki.com/mcp` 及另两处公开 endpoint TLS 失败（curl SSL_ERROR_SYSCALL），需在联网机器跑 `verify:mcp:public`；本地真 MCP server 仍保证协议与业务链完整。

官方协议参考：https://modelcontextprotocol.io/specification/2025-03-26/basic/transports （POST JSON-RPC、Accept JSON+SSE、initialize/sessionId、notifications/initialized、tools/list、tools/call）。
