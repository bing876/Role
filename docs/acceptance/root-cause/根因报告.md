# 系统性根因报告：内嵌浏览器为什么「不像一个真正的浏览器」

> 取证脚本：`scripts/verify/rootcause-browser-probe.mjs`（**不是**手抄近似实现 —— 它从
> `apps/desktop/electron/driver.ts` 里把真实的 `PAGE_HELPERS` 整段抠出来执行，
> 所以下面测到的 `find()` / `snapshot()` 就是线上跑的那一份）
> 原始输出：`docs/acceptance/root-cause/rootcause-probe.log`、`rootcause-probe.json`
> 结论：**失败项 0**（四条假设全部实测复现）

## 一、先看原始证据（用户截图里 AI 的自述）

截图（`clipboard-2026-09-19T02-37-50-204Z-caa643c0.jpg`）中 AI 自己说了三句话：

1. 「**首页视频列表没加载出来**（可能需要登录或加载中）。我回到搜索页，改用点击视频封面缩略图的方式。」
2. 「之前点击标题**无跳转**，可能是新标签打开。我尝试点击视频封面缩略图区域」
3. 「**能真的打开了新标签，只是工作台没切换**。」
4. 「一路最多走 10 步，现在已经走满了还没做完，我先停下来。」

这四句不是猜测 —— 它们是现象的直接目击。下面的探针把每一句还原成可复现的最小页面。

## 二、探测器（4 节，全部 PASS）

### ① 懒加载墙：列表在滚动之前**根本不在 DOM 里**

构造一个模仿视频站的首屏：卡片由滚动事件触发才 `append`。

| 状态 | `.card` 数量 | `snapshot().links` |
| --- | --- | --- |
| **未滚动** | 3 | 3 条（只有首屏那 3 张） |
| **滚动一遍后** | 5 | 5 条 |

→ **成立**。真实视频站的首屏通常连 3 条都没有（IntersectionObserver 懒加载）。
`read_page` 在**没滚动**的情况下拿到的快照，在模型眼里就是「列表是空的」。

**这解释了第 1 句**「视频列表没加载出来」—— 不是需要登录，是**没滚动**。

### ② iframe 墙 + ③ Shadow DOM 墙：`find()` 进不去

| 目标 | 现有 `find()` 结果 |
| --- | --- |
| 主文档按钮（基线） | ✅ 找到 `BUTTON#hostbtn` |
| iframe 里的「▶ 播放视频」 | ★ **notfound** |
| Shadow DOM 里的播放按钮 | ★ **notfound** |

但同一时刻：

- `iframe.contentDocument` **可读**（同源）
- iframe 内实际存在的按钮 = `["▶ 播放视频"]`
- `shadowRoot` **可读**
- `snapshot().buttons` 只有 `["主文档按钮（基线）"]` —— **iframe / shadow 里的东西在快照里完全不存在**

**关键判据（这条决定了修复方向）**：
拿到 iframe 内按钮的坐标后用**真鼠标**点击 → `inner hits = 1`，**点得动**。

> 所以「点不动」的成因是**「没找到元素」**，不是「点击失败」。
> `find()` 退到 `notfound` → 模型收到「没找到可点击的元素」→ 换个 target 再试 →
> 10 步预算被空转吃掉 → 触发第 4 句「走满了」。

**这解释了第 2 句**「点击标题无跳转」。

### ④ 新标签墙：`target=_blank` 被折成同页导航，渲染层不知情

线上策略（`main.ts` `setWindowOpenHandler`）：

```
if (isHttpUrl(url)) setImmediate(() => contents.loadURL(url));   // 同一个 guest 导航
return { action: 'deny' };                                       // 不创建新窗口
```

实测：点 `target=_blank` 链接 → **同一个 guest 导航走了**（`location.href` 变了）。

**这就是第 3 句「能真的打开了新标签，只是工作台没切换」的可观测形态。**

链路断点很明确：

```
页面 window.open(url)
   → 主进程 setWindowOpenHandler：deny + contents.loadURL(url)   ← 同一个 guest 换了地址
   → guest 内部触发 did-navigate
   → BrowserPanel.tsx 的 onNav 调 notePageInfo(id, {url})        ← 只更新了「这一条 tab 的 url」
   → 渲染层 tabs 数组**没有新增元素**                             ← 顶部永远不多一条 tab
```

`notePageInfo` 的逻辑是：

```ts
setBucket(t.agentId, bucketOf(t.agentId).map((x) =>
  x.id === tabId ? { ...x, ...(info.url ? { url: info.url } : {}) } : x));
```

**`map` 只改已有的那一项，从不 append。** 所以：

- 顶部 tab 数不变 → 用户觉得「没开新 tab」
- 但那一张 tab 的 **URL / 标题被静默换掉了** → 用户觉得「我的页面被换走了」

**这两件事合起来，正是「不像一个真正的浏览器」。**

## 附：顺带查出的两个真实缺陷

### A. `PAGE_HELPERS` 版本守卫写错了（无害但该修）

```js
if (window.__wbHelper && window.__wbHelper.__v === 9) return;   // ← 判 9
...
window.__wbHelper = { __v: 10, ... };                            // ← 写 10
```

守卫永远不成立 → 每次动作都把整段 helper 重新定义一遍。
功能上不出错（赋值是幂等的），但每次 `executeJavaScript` 都白跑一遍约 11 KB 的脚本，
在一个 10 步循环里就是 10 次。**探针实测 `_helperVer = 10`，证实守卫失效。**

### B. `contentTexts()` 在只有 `<a>` 的列表页返回空

探针里 `contentTexts()` 两次都是 `[]` —— 因为它只扫
`h1,h2,h3,h4,h5,p,li,td,th,dt,dd,blockquote,[role=heading],[role=listitem]`，
**不包含 `a`**。视频列表页的标题恰恰全是 `<a>`。
（`snapshot().links` 抓到了，所以正文没全丢；但「把这一页整理成列表」这类任务会少素材。）

## 三、根因收敛成一句话

> **`driver.ts` 把「页面」等同于「主文档」（`document`），
> 而真实浏览器的「页面」是 `主文档 + 所有 shadow root + 所有 frame`；
> 同时「新标签」被折成同页导航后，渲染层的 tab 列表没有对应动作。**

四道墙都是这一个假设的推论：

| # | 墙 | 真实浏览器怎么做 | 工作台现状 |
| --- | --- | --- | --- |
| ① | 懒加载 | 用户会滚动 | 没有主动滚动 |
| ② | iframe | 元素属于那一帧，坐标加偏移 | `find()` 只看主文档 |
| ③ | Shadow DOM | `shadowRoot` 是开放的就该进 | `find()` 只看主文档 |
| ④ | 新标签 | 顶部多一条 tab | deny + 同页导航，tab 不变 |

## 四、修复方案（按「像一个真正的浏览器」的目标排序）

### P0 —— 让「找得到」成立（解决 ②③，最高收益）

给 `PAGE_HELPERS` 加一层**递归穿透遍历**，产出统一的候选集合：

```js
function* walkAll(root, pathStr) {
  let all; try { all = root.querySelectorAll('*'); } catch (_) { return; }
  for (let i = 0; i < all.length; i++) {
    const el = all[i];
    const p = pathStr + '>' + el.tagName + (el.id ? '#' + el.id : '');
    yield { el, path: p };
    if (el.shadowRoot) yield* walkAll(el.shadowRoot, p + '::shadow');       // open shadow root
    if (el.tagName === 'IFRAME') {
      try { const d = el.contentDocument; if (d) yield* walkAll(d, p + '::iframe'); } catch (_) {}
    }
  }
}
```

改造面（都在 `PAGE_HELPERS` 内，**不改对外契约**）：

- `find()` / `findInput()` / `findClickable()` → 走 `walkAll`
- `visible()` → 跨 frame 时需用**该 frame 的** `getComputedStyle` / `defaultView`
- `snapshot()` / `contentTexts()` / `pageKey()` → 同上
- 点坐标：如果是 frame 内元素，**加上所属 iframe 的 rect 偏移**（探针已验证这样点得动）
- 边界：`walkAll` 加**访问节点上限**（防深站点遍历爆炸）+ `try/catch`（跨源 frame 会抛）

**跨源 iframe**（视频站最常见：`player.bilibili.com` 之类）`contentDocument` 会抛 ——
这一档需要走 CDP 的 frame 级操作，**改变「单文档」假设，是独立工作量，需要你先拍板**。

### P1 —— 让「新标签」真的开新 tab（解决 ④）

两条路，我倾向第二条：

- **P1-a**：`setWindowOpenHandler` 里 `return { action: 'allow' }` 并 `createWindow` 一个
  隐藏 BrowserWindow，再把它 attach 成工作台的第二个 guest。
  改动大、生命周期复杂。
- **P1-b（推荐）**：`deny` 之外，把 `url` 通过**已有 IPC 通道**推回渲染层，
  让 `useBrowserWorkspace` **新开一条 tab**（就是用户在「＋」时走的同一条路）。
  复用 `openUrl(agentId, url)` —— 一行主进程改动 + 一条 `bridge.on('open')` 已存在。

> 注意：`bridge.on('open')` 通道**已经存在**（`App.tsx:1460` → `browser.openFromMain`），
> 只是 `setWindowOpenHandler` 从来没往它发过。这是**最小改动、最大体验收益**的一处。

### P2 —— 主动滚动（解决 ①）

`read_page` 在快照里加一条「这一页看起来是懒加载列表（可见正文很少但容器很高）」的提示，
或让 `scroll` 工具支持 `until` 参数。**这条要先确认产品意图**：
AI 自动滚动会改变用户视图，得想清楚什么时机该滚。

## 五、需要你拍板的三件事（我不自己决定）

1. **跨源 iframe 要不要一起修？**
   视频站（B站/YouTube 播放器）几乎都是跨源 iframe。
   不修 → 视频类任务仍然点不动；修 → 要动 CDP frame 级操作，是独立一块工作量。
2. **「新标签」用 P1-b 吗？**
   我推荐 P1-b（新开一条 tab，复用现有通道）。要不要顺带把「同站复用」改成
   「`target=_blank` 一律新开」？（真浏览器就是一律新开，这样更「像浏览器」，
   但会更快撞上 `maxBrowserInstances=4` 的上限。）
3. **多窗口形态**（上一轮就挂着的三选一）：
   A 保持现状（一窗口多内嵌页）/ B 真开多个 OS 窗口 / C 单窗口内并排分屏。
   我仍倾向 C。

## 六、自动化测试测不出、需要你亲眼看的主观项

1. **点开视频站搜索页后，AI 主动滚动加载列表** —— 滚的节奏会不会让你觉得「页面在自己乱动」？
2. **真开新 tab 时的切换动画/焦点** —— 新 tab 出现后**要不要自动切过去**？
   现在的行为是不切（`focusByWebContents` 只给当前智能体的页）。
3. **iframe 里的按钮点中后，视觉反馈够不够** —— 真实鼠标点击在跨源 iframe 边界上偶发失灵的话，
   你看到的就是「高亮闪一下但没反应」，这个体感只有你能判断。
