## 一、「视频点不了」——查找进不去 iframe / Shadow DOM

### 怎么定位的

我写了个探针（`scripts/verify/rootcause-browser-probe.mjs`），
它**不是手抄一份近似实现**，而是从 `driver.ts` 里把线上那份 `PAGE_HELPERS`
整段抠出来执行，所以测的就是真实代码。

结果（修复前）：

| 目标 | `find()` 结果 |
| --- | --- |
| 主文档按钮（基线） | ✅ 找得到 |
| iframe 里的「▶ 播放视频」 | ★ **notfound** |
| Shadow DOM 里的播放按钮 | ★ **notfound** |

而同一时刻，`iframe.contentDocument` 是**可读的**、`shadowRoot` 是**可读的**，
元素**也确实存在**（`["▶ 播放视频"]`）。

**决定性判据**：拿到 iframe 内按钮的坐标后用真鼠标点击 → `inner hits = 1`，**点得动**。

> 所以缺的是「**找得到**」，不是「点得下去」。
> `find()` 返回 notfound → 模型收到「没找到元素」→ 换个 target 再试 →
> 10 步预算被空转吃光 → 触发你截图里那句「一路最多走 10 步，走满了」。

**真浏览器的「页面」= 主文档 + 所有 open shadow root + 所有同源 frame。**
工作台把「页面」等同于「主文档」——这就是根因。

### 改了什么

给 `PAGE_HELPERS` 加了一层**递归穿透遍历**，并让所有查找/快照都走它：

```js
const walkAll = (root, depth, budget) => {   // 主文档 → shadowRoot → 同源 iframe
  ... root.querySelectorAll('*') ...
  if (el.shadowRoot)  walkAll(el.shadowRoot, depth + 1, budget);
  if (el.tagName === 'IFRAME') { const d = el.contentDocument; walkAll(d, ...); }
};
const queryDeep = (selector) => /* walkAll + matches + visible */;
```

改造点（都在 `PAGE_HELPERS` 内，**对外契约没动**）：

- `find` / `findInput` / `visible` / `snapshot` / `pageKey` / `loginish` / `overlayish` / `contentTexts` 全部改走 `queryDeep`
- 新增 **`absRect(el)`**：累加各级 iframe 的偏移，给出**最顶层视口坐标** ——
  因为 CDP 的 `Input.dispatchMouseEvent` 认的是最顶层坐标。
  老的 `getBoundingClientRect` 在跨 frame 时会点**偏**到别的元素上。
- **命中测试也分层做**：元素在某级 frame 里就**用那一帧的** `elementFromPoint`。
  在老实现里拿主文档去测只会返回 `IFRAME` 本身，永远测不到里面 —— 这也是
  「人工点击也会点不中」为什么在代码上说不通的原因（引擎其实会把事件转发进去）。
- 护栏：访问节点上限 `MAX_NODES = 20000`、深度上限 `6`、跨源 `try/catch` 静默跳过
  （跨源 frame 读 `contentDocument` 会抛，不能让它把整条动作链炸掉）

### 顺带修掉的两个真实缺陷

1. **`PAGE_HELPERS` 版本守卫写错了**：判 `__v === 9` 但赋值 `__v = 10`
   → 守卫永不生效，每次动作都白跑一遍 11 KB 脚本。现统一为 `11`。
2. **`contentTexts()` 不扫 `<a>`**：纯链接列表页返回**空数组**（探针实测 `[]`），
   而视频列表的标题恰恰全是 `<a>`。已把 `a` 加进选择器。

### 验收

`rootcause-browser-probe.mjs` 已改造成**回归测试**（断言反转成「修复后应成立」）：

```

PASS ★ 修复后：iframe 里的元素**找得到**了  —— BUTTON#play
PASS ★ 修复后：Shadow DOM 里的元素**找得到**了  —— BUTTON#splay
PASS ★ 修复后：snapshot() 能看到 iframe 与 shadow 里的按钮

```

→ **4/4 目标断言变红**（`失败项：4`）；还原后回到 `0`。测试不是摆设。

## 二、「没开新 tab」——两个独立原因叠在一起

### 原因 A（更根本）：**站点根本不在登记表里**

`detectOpenUrl` 是**纯字符串**判断（脱网、不问模型）。表里没有的名字 → 返回 `null`
→ 整条开页链路**根本不启动**。

我用真代码验了一下：

```
"打开速卖通官网"  -> detectOpenUrl = null     ← ★ 什么都不开
"打开chatgpt"     -> detectOpenUrl = null     ← ★ 什么都不开
"打开淘宝"        -> detectOpenUrl = "https://www.taobao.com"   ← 有登记的才开
```

**这就是「说了第二遍还是没反应」和「chatgpt 打不开」的直接原因。**

已补进登记表：速卖通 / aliexpress / 阿里巴巴 / alibaba / 1688 / **chatgpt** / openai /
claude / gemini / gmail / outlook / youtube / 推特 / x / facebook / instagram /
linkedin / reddit / amazon / temu / shopee / lazada / wish / shein 等。

⚠️ 注意 `['x', 'https://x.com']` 这个单字母项——已验证它**不会**抢走
「打开小红书」（`xiaohongshu` 全等优先）。

### 原因 B：`target=_blank` 被折成同页导航

老行为（`main.ts`）：

```
if (isHttpUrl(url)) setImmediate(() => contents.loadURL(url));  // 同一个 guest 导航走
return { action: 'deny' };                                       // 不创建新窗口
```

实测：点 `target=_blank` → **同一个 guest 导航走了**。
但渲染层的 `tabs` 是 React state，`notePageInfo` 只做 `map` **改已有的那一项、从不 append**
→ 顶部永远不多一条 tab。

**这精确对应你截图里 AI 自己说的那句话：「能真的打开了新标签，只是工作台没切换」。**

新行为：主进程只做一件事 —— 把请求推给渲染层去**真开一条 tab**：

```ts
contents.setWindowOpenHandler(({ url }) => {
  if (isHttpUrl(url)) {
    const owner = webviewOwner.get(contents.id);   // 哪张 guest 触发的
    setImmediate(() => sendToMainWindow('workbench:browser:opentab',
      JSON.stringify({ url, agentId: owner ?? null, sourceWcId: contents.id })));
  }
  return { action: 'deny' };
});
```

渲染层新增 `openFromPage(url, preferAgentId)`，与 `openFromMain` 的两点关键差别：

1. **归属**用主进程查出的 `agentId`（哪张 guest 触发的）—— A 的页里点出来的 tab
   必须留在 A 名下，**不能**用「此刻正在聊的那个」。
2. **不复用同站页**。真浏览器点 `target=_blank` 就是**新开**，哪怕同站
   （常见：搜索结果点开第二条、列表里点开另一个商品）。
   老逻辑走 `openUrl` 的「同站复用」会**把当前页导航走** ——
   那正是你抱怨的「没开新 tab，反而把当前页换掉了」。

仍然遵守 `maxBrowserInstances`：到顶就说话、拒绝新开，**绝不偷偷关页**。

### 验收

## 三、关于「人工点击也点不了视频」

这一条我单独说明，因为**它的机理和上面不一样**，而且我**没有改它的代码**。

我做了对照实验（`scripts/verify/manual-click-probe.mjs`）：

| 场景 | `elementFromPoint` 返回 | 真鼠标点击 |
| --- | --- | --- |
| 裸元素（基线） | `BUTTON#v1` | ✅ 点得中 |
| **透明遮罩压在上面** | `DIV#shield`（**按钮被夺走**） | ★ **点不中** |
| `pointer-events:none` 的父层 | `BUTTON#v3` | ✅ 点得中（子层重新打开就没事） |

**结论**：人工点击点不中 → **主文档里有东西挡住了那一点**（透明遮罩 / 覆盖层）。
而 `iframe` 边界本身**不挡**人工点击（引擎会把事件转发进子框架，同源实测 `hits=1`）。

> 所以「视频点不了」这件事，**如果只发生在特定站点**，
> 很可能是那个站点自己在视频上盖了一层（防下载 / 整块可点）；这**不是工作台的 bug**。
> 但如果发生在**任何有 iframe 的页面**上，那就是上面第一条已修的问题。

**我需要你确认**：你点不中的那个视频，是**哪个网址**？
——如果给我网址，我可以把「是谁盖住了那一点」精确到那个元素的类名。

| 反证对象 | 怎么注入缺陷 | 红了多少条 |
| --- | --- | --- |
| 查找穿透（`driver.ts` 的 `walkAll`） | 把 shadow / iframe 两段下钻**整段注释掉**，只留主文档 | **3 条红**：iframe `notfound`、shadow `notfound`、`snapshot().buttons` 只剩主文档那一个 |
| 站点登记表（`sites.ts`） | 删掉 `chatgpt` / `速卖通` / `1688` 三条 | **13 条红** |
| 新标签 handler（`main.ts`） | 换回老行为 `deny` + `contents.loadURL(url)` | **8 条红**，证据直白：`before=data:… after=https://example.com/video/1`（当前页**真被导航走了**） |

还原后三套脚本分别回到 **失败项 0 / 0 / 0**。

> ★ 顺带记一条教训：反证注入**必须保持函数的返回类型不变，只改行为**。
> 我第一次图省事，把 `queryDeep(` 全替换成 `document.querySelectorAll(` ——
> 结果探针不是"断言变红"，而是**整段脚本 FATAL 崩掉**。
> 原因是 `queryDeep()` 返回真数组，`querySelectorAll` 返回 `NodeList`，
> 下游的 `cands.find(...)` / `els.some(...)` 在 NodeList 上不存在。
> 这种红是**语法级崩溃，不是语义级回归**，不算有效反证。

## 四、还没做：你要的「取消活页 / 空闲休眠」

你说的「**没有活页这个说法了，空闲的页面应该处于休眠状态，需要的时候唤醒**」
（像 Chrome 那样省内存）—— 这条我**还没动手**，因为它是**新功能**不是修 bug，
按我们定的规矩要先跟你确认设计。

现在的实情（我读码确认的）：

- `BrowserPanel` 的「舞台」把**所有智能体、所有 tab** 的 `<webview>` 全挂着，
  靠 z-index / opacity 分层，**从不卸载** —— 注释里写得很明白：
  「切走的那些页也必须活着」。
- 非激活页的 CSS 是 `.browserPanel__view--off { opacity:0; pointer-events:none }`，
  **不动 display、不动尺寸、不卸载**。
- 上面写着「**N 张活页**」，确实还有「活页」这个说法。

**要做成你要的样子，需要定三件事**（定了我就动手）：

1. **休眠的触发条件**：多久没被用就休眠？（比如 5 分钟没操作 / 没被驾驶）
2. **休眠的深度**：
   - 浅休眠：保留 `<webview>`，只是 `opacity:0` + 暂停它的 JS 定时器（省 CPU 不省内存）
   - 深休眠：**卸载** `<webview>`，只留「URL + 滚动位置 + 表单草稿」的快照，
     唤醒时重新加载并恢复（**真省内存**，但会有重新加载的白屏）
   —— 我倾向浅休眠打底 + 长时间（如 30 分钟）再转深休眠。
3. **唤醒时机**：切回那张 tab 时自动唤醒？还是显示「这张页已休眠，点一下恢复」让你决定？
   （自动唤醒最顺手；但如果你有正在跑的驾驶任务，自动唤醒会不会打断它，要一并定。）

另外「活页」这个词要不要从界面上拿掉（改成「N 个页面」或直接不显示个数），
也请你说一句。

## 五、需要你亲自看的主观项（自动化测不出的）

> 自动化测试全绿**不等于**用户体验没问题。以下几件只有你能判断：

# 七、第二轮（2026-09-19 下午）：认不出站点时模型自己编「已打开」

## 7.1 你的原话与症状

> 「我同时输出打开豆包打开千问这些他不会在浏览器里面展开，
> **但是消息里面已经提示打开了**，并且我输出 chatgpt 还是没有出现在浏览器里面。」

症状的关键在于**「消息里说打开了」**—— 这是全新的层次：
上一轮修的是「页没开出来」，这一轮是「**页没开，模型却告诉你开了**」。

## 7.2 根因链（决定性证据）

我先用 `detectOpenUrl()`（纯字符串判断，脱网、不问模型）逐条实测：

| 输入 | 返回 |
| --- | --- |
| `打开豆包` | ★ `null` |
| `打开千问` | ★ `null` |
| `打开deepseek` | ★ `null` |
| `打开kimi` | ★ `null` |
| `打开chatgpt` | `https://chatgpt.com` ✅ |

豆包 / 千问 / deepseek / kimi **全都不在站点登记表（`SITES`）里** → `detectOpenUrl` 返回 `null`。

**那为什么消息里还是说"打开了"？** 把链路拆开看：

```
用户：「打开豆包」
  ↓
detectOpenUrl('打开豆包') → null          ← 页没开
  ↓
★ 但这一轮**没有拦住这句话**，照样 POST /chat/stream 发给模型
  ↓
服务端 chat.ts:405：
    const browserContext = openedUrl ? '……网页已开好，别让用户点确认' : '';
                                          ↑ openedUrl 为空 → 一个字都不注入
  ↓
模型只看到「打开豆包」这个动词，**没有任何"页没开"的约束** → 自己编一句「已为你打开」
  ↓
用户：「消息里说打开了，浏览器里没有」   ← 你看到的现象
```

**这就是"AI 对自己没做过的事撒谎"的机械原因**：不是模型坏，是**我们没告诉它**。

## 7.3 三层修复

### ① 补登记表（治标，但最直接）

`sites.ts` 补了 20+ 条国产/海外 AI 站点：

```
豆包 / doubao            → https://www.doubao.com
千问 / 通义 / 通义千问 / tongyi / qwen → https://www.tongyi.com
deepseek                 → https://chat.deepseek.com
kimi / 月之暗面           → https://kimi.moonshot.cn
文心一言 / 文心           → https://yiyan.baidu.com
智谱 / chatglm           → https://chatglm.cn
讯飞星火 / 星火           → https://xinghuo.xfyun.cn
元宝 / 腾讯元宝           → https://yuanbao.tencent.com
grok / perplexity / copilot
```

### ② 认不出就**拦住模型**（治本）

新增 `detectUnknownOpenTarget(raw)`：判「像在开页、但表里没有」的情况。
App.tsx 里对应分支**直接 `return`，根本不走 `/chat/stream`**：

```tsx
const unknownTarget = openUrl === null ? detectUnknownOpenTarget(value) : null;
if (unknownTarget) {
  // 开一张起始页 + 聚焦地址栏，然后**直接结束这一轮**
  setChatNote(`我认不出「${unknownTarget}」是哪个网站，所以**没有替你打开任何真实网站** ——
               刚才没开就是没开，不糊弄你。……地址栏已经选中：直接打网址就行。`);
  return;   // ★ 模型没有机会编
}
```

**为什么这样是最优解**：与其让模型说一句漂亮的假话，不如让它**诚实地说"我认不出"**
并且**立刻给用户一条可达的路径**（起始页 + 已聚焦的地址栏，打网址回车即走）。

### ③ 防误报（这一版差点做坏）

第一版 `detectUnknownOpenTarget` 会把下面这些**误判成"认不出的站点"**：

- 「打开这个文件」→ 误报「这个文件」
- 「打开我昨天写的报告」→ 误报「我昨天写的报告」

**修**：加指示代词/助词排除 + 长度限 12 + 只允许「中文/字母数字/连字符」的干净词组：

```ts
const NOT_A_SITE = /[这个那哪些什么我的你他她它了的吗呢吧啊哦呀咿矣焉哉？!！。，、；：]/;
if (NOT_A_SITE.test(site)) return null;
if (!/^[\u4e00-\u9fa5a-zA-Z0-9][\u4e00-\u9fa5a-zA-Z0-9\-]*$/.test(site)) return null;
if (site.length > 12) return null;
```

## 7.4 测试与反证

`scripts/verify/unknown-site-tests.mts`（`npx tsx` 跑）—— 5 节：

1. 补表后认得的（豆包/千问/deepseek/kimi…）
2. 原站点防回归（chatgpt/百度/淘宝…）
3. 认不出的要识别（小红mall / 某某商城 / 某某网 / Acme官网）
4. **防误报**（打开这个文件 / 打开我昨天写的报告 / 打开我们公司内网 / 打开那个卖鞋的站）
5. 两判定互斥（`detectOpenUrl` 非空时 `detectUnknownOpenTarget` 必须为空）

**反证（证明测试不是摆设）**：

| 注入的缺陷 | 变红条数 |
| --- | --- |
| 删掉表中 3 条（豆包 / 千问 / kimi） | 2 条红 |
| 把 `NOT_A_SITE` 换成 `/(?!)/` 并去掉长度限制 | 4 条红 |

均已还原、重跑全绿。

> ★ 中途我自己**把测试用例归类错了**：把「打开那个卖鞋的站」「打开我们公司内网」

# 八、第二轮：不要百度默认页 → 工作台自己的起始页

## 8.1 你的要求

> 「然后不要百度浏览器的默认改成一个单独的浏览器，不要百度。」

（通过选项拍板：点「＋」新开 → **空白起始页**；认不出站点 → **开一张起始页让用户自己输**）

## 8.2 做法：`data:` 内联起始页（零网络请求）

`HOME_URL` 原来是 `https://www.baidu.com`，现在改成一段**内联 HTML**：

```ts
export const START_PAGE_HTML = `<!doctype html>…「新标签页」+ 6 个入口…`;
export const HOME_URL = 'data:text/html;charset=utf-8,' + encodeURIComponent(START_PAGE_HTML);
export function isStartPage(url: string): boolean {
  return typeof url === 'string' && url.startsWith('data:text/html');
}
```

**为什么用 `data:` 而不是本地 html 文件**：
- **零网络请求**（断网也能显示，不会像百度那样转圈）；
- 不用往 asar 里塞额外资源、不用处理 `file://` 的路径与权限；
- **不受**主进程 `will-navigate` 拦截影响 —— `will-navigate` 只管**后续导航**，
  初始 `loadURL` 不走它（这一点我实测确认过）。

配套改 `useBrowserWorkspace.openUrl`：起始页**直通** `toHttpUrl`（它只认 http(s)），
且**不参与同站复用**（否则两张起始页会被误判成"同一站点"合并掉）。

## 8.3 起始页长什么样

- 标题「新标签页」
- 6 个入口按钮：百度 / 淘宝 / 抖音 / ChatGPT / 豆包 / 速卖通 —— **全部 `target="_blank"`**
  （这样才能走 `setWindowOpenHandler` → `opentab` → 新开一张 tab，而不是把起始页本身导航走）
- 一行提示：「在上面地址栏输入网址，或点上面的入口。也可以直接在聊天里说『打开某网站』。」

## 8.4 测试与反证

`scripts/verify/startpage-tests.mjs` —— 用真 Electron `loadURL(dataUrl)` 验证：
加载成功 / 标题是「新标签页」/ ≥4 个入口 / 入口都是 http(s) / **都带 `target="_blank"`** / 可点。

> ★ 第一版超时 120s：隐藏窗口里用 `<webview>` 加载 data: guest 会挂住。

# 九、第二轮：Chrome 同款休眠图标

## 9.1 你的要求

> 「可以休眠的小图标就改成谷歌设计的那种。」

## 9.2 做法

新建 `apps/desktop/src/browser/SleepBadge.tsx` —— **Chrome「内存节省模式」同款图形**：

- 灰色圆底（`circle` r=6.4，`opacity .14`）
- 内存条外框（`rect` 描边）
- **颗粒：浅休眠 2 颗 / 深休眠 3 颗** ← 一眼看出睡多深
- 右侧电容（短竖条）

14×14（占 favicon 的位置，不撑开标签），颜色走 `currentColor`，
深浅由外层 `--shallow`(0.55) / `--deep`(0.85) 的 `opacity` 区分。

**为什么是"内存条"而不是"月亮 / zzz"**：Chrome 用它表达的是**内存被省下来了**，
而不是"睡着了"—— 用户真正关心的是省内存。而且颗粒数天然能表示休眠深度。

## 9.3 接进标签（不是只做个预览页）

`BrowserPanel.tsx`：

```tsx
{!ws.drivingIds.includes(t.id) && t.sleep && <SleepBadge depth={t.sleep} />}
```

两个要点：
- **放在标题前面** = 占 favicon 的位置（Chrome 就是**换掉 favicon**，不是另起角标）；
- **排除 `drivingIds`** —— 正在被驾驶的页和"休眠"语义互斥，同时出现就是 bug。

顺带把「N 张活页」改成「**N 个页面**」，并在 >0 时补一句「· N 个已休眠」
（否则用户会以为页丢了）。
