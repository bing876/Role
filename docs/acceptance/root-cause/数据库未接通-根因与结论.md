# 数据库未接通 —— 根因与结论（2026-09-19）

## 一句话结论

**不是代码 bug，是本机起不了 PostgreSQL。** 服务端代码、连接串、compose 文件全是好的；
缺的只是一个能跑 PostgreSQL 的运行时 —— 而本机唯一可行的那条路（Docker Desktop 的
Linux 引擎）依赖 `wsl.exe`，**这个程序在本机被安全策略拉黑了**，我无法绕过。

---

## 证据链

### ① 服务端本身是健康的，只有 DB 那一项是 down

```
GET http://127.0.0.1:8787/health
{"ok":true,"service":"ai-workbench-server","db":"down","sms":"mock","llm":"configured",
 "llmCalls":0,"loopMaxSteps":10,"liveLoops":0,"runningLoops":0,"pageStates":0}
```

`ok:true` + `llm:"configured"` + `sms:"mock"` 都正常 → 服务进程活着、配置读到了、
模型 key 也在。**只有 `db:"down"`。**

### ② 服务端设计上就是「库没起也让服务起」

`apps/server/src/index.ts:100-107`：

```ts
try {
  await migrate(pool);
  console.log('[server] 数据库表就绪（...）');
} catch (err) {
  console.warn('[server] 数据库暂未连通，服务照常起（/auth 会回 503 提示）：', err.message);
}
```

注释里写得很清楚：**「库没起也不让健康检查崩：桌面要能区分『后端没起』和『后端起了库没起』」**。
所以 `db:"down"` 是**被设计出来的正常降级**，不是崩溃。

### ③ 真正连不上的原因：本机没有可用的 PostgreSQL 运行时

逐项排查：

| 方案 | 状态 | 证据 |
| --- | --- | --- |
| 本机原生 PostgreSQL | ❌ 未安装 | `ls "/c/Program Files/PostgreSQL"` → 空；`which psql pg_ctl postgres` → 无 |
| Docker Desktop Linux 引擎 | ❌ 起不来 | `docker context ls` → `desktop-linux *`；`docker version` → `request returned 500 Internal Server Error ... dockerDesktopLinuxEngine` |
| Docker Desktop Windows 引擎 | ❌ 无响应 | `docker -c default info` 30 秒超时、零输出 |
| Docker Desktop 进程本身 | ✅ 在跑 | `tasklist` 里有 `Docker Desktop.exe` × 5、`com.docker.backend.exe` × 2、`com.docker.build.exe`、`docker-agent.exe` |

**关键一环**：Docker Desktop 在 Windows 上跑 Linux 容器，后端必须是 **WSL2**。
而本机：

```
PROGRAM BLOCKED BY SECURITY POLICY - The sandbox prevented a program on the
configured Program Blacklist from starting:
  - wsl.exe (C:\WINDOWS\system32\wsl.exe)
This block cannot be approved or bypassed from the current command.
Do NOT retry this program, launch it through another shell or script, or
attempt an equivalent workaround.
```

`wsl.exe` 在**安全中心 → 命令安全 → 程序黑名单**里。
这句话明确说了：**当前命令无法批准、无法绕过、不要换 shell/脚本重试。**
→ Docker 的 Linux 引擎**在本机起不来**，这不是我能修的。

### ④ 服务端对 DB 断开的处理是「说人话」，不是崩栈

`apps/server/src/routes/auth.ts:73-82`：

```ts
function dbError(reply, err) {
  if (isDbUnreachable(err)) {
    return reply.code(503).send({
      error: '数据库连不上：先跑 docker compose -f apps/server/docker-compose.yml up -d（或 npm run db:up）',
    });
  }
  ...
}
```

所以用户在界面上看到的「数据库未接通」，**就是这句话被原样贴出来了** ——
它准确地说明了原因，只是那句「先跑 docker compose」在本机跑不通。

## 我做了什么、没做什么

**做了（在权限范围内的全部）：**
1. 启动了 Docker Desktop（`Start-Process`），进程确实起来了；
2. 后台轮询 `docker info` 200 秒等引擎就绪 —— **超时**，引擎始终是 500；
3. 逐个试了 `docker version`（Linux 引擎）、`docker -c default info`（Windows 引擎）——
   都不通；
4. 确认本机没有原生 PostgreSQL；
5. 定位到最终卡点是 `wsl.exe` 被安全策略拉黑。

**没做（不能做）：**
- 绕过 `wsl.exe` 的黑名单。安全策略明确禁止，且禁止换 shell/脚本重试。
- 私自把后端从 `pg` 改成 SQLite。`apps/server/package.json` 只有 `"pg"` 依赖，
  `db.ts` 里 250 行 DDL 全是 PostgreSQL 方言（`JSONB` / `BIGSERIAL` /
  `TIMESTAMPTZ` / `CREATE INDEX ... WHERE` 部分索引）。
  换成 SQLite 等于**重写整个数据层** —— 这远超「修一个连不上」的范围，
  属于产品级架构决策，按规矩**必须先问用户**，不能自己悄悄做。

## 给用户的三条路（按推荐度）

### 路 A：把 `wsl.exe` 从黑名单里放出来（最省事，推荐）

「安全中心 → 命令安全 → 程序黑名单」里移除 `wsl.exe`，然后我重跑：

```bash
docker compose -f apps/server/docker-compose.yml up -d
```

`apps/server/docker-compose.yml` 已经写好了（`postgres:16-alpine`，
user/pass/db 都是 `workbench`，端口 5432，带 healthcheck），
`.env` 里的 `DATABASE_URL` 也已经对上。放行后应该是**一条命令就通**。

### 路 B：装一个原生 PostgreSQL（不依赖 WSL / Docker）

装完建一个 `workbench` 库、用户密码都设 `workbench`，`DATABASE_URL` 一个字都不用改。
适合「以后也不想为数据库开 Docker」的情况。

### 路 C：先不动数据库，我把功能换装进桌面端

**这一条是重点**：用户说的「你之后所有改动都同步进桌面端能够正常点开使用」，
**和数据库通不通是两件事**。

- 服务端「库连不上也照常起」→ 桌面端**能点开**、能用；
- 只有**需要落库的操作**（注册/登录、存消息、知识库）会被 503 挡住；
- 本轮改的**浏览器部分**（补站点表 / 认不出站点不再让模型瞎编 / 起始页 / 休眠图标）
  **完全不碰数据库**，换装后立刻可用。

所以：**即使数据库这条路暂时走不通，换装也该照做** —— 用户要的是「改动同步进桌面端」，
这件事我完全可以做到。这两件事我不该绑在一起等。
