## 0. 三十秒版本

一个装在 Windows/macOS 上的 Electron 桌面软件。它不是聊天框——**它内置一个原生浏览器，AI 能像人一样打开网页、点按钮、读页面、填表单，把活真的干完**。用户说一句话「建个小美，专门盯店铺数据」，它当场变出一个专职智能体；多个智能体可以派活协作；所有数据（密钥、记忆、任务）都在用户本机，加密存储。

**技术上的真正亮点**：元素定位是「读懂页面再动手」（看按钮上写的什么字），不是猜坐标、不是死记网页代码。**这比主流的 vision+坐标 方案更抗网站改版。** 有 181 条自动断言钉着。

**当前的真相**：架构是仓库最值钱的资产（别重写）；但「代码 90% 完成」只覆盖了后端与引擎；**四个最关键的验证一个都没做**（真模型准确度 / 真打包 / 真机 / 真凭据）；界面层几乎没开始；有一个已知红的检查。

```
├─────────────────────────────────────────────────────────────┤
│ 主进程 apps/desktop/electron（Node）                          │
│  职责：浏览器宿主、CDP 遥控、桌面侧驾驶循环、服务守护、JWT 内存   │

│ 服务端 apps/server（Fastify，loopback 绑定）                    │
│  职责：路由、记忆、技能、编排、工具循环、模型唯一出口 llmFetch     │
└─────────────────────────────────────────────────────────────┘
```

### 一次「帮我在淘宝改标题」的完整链路

1. **用户输入** → `App.tsx` 输入栏 → `useChat.ts` → `POST /chat/stream`
2. **大管家路由** → `chiefOfStaff.ts`：先字面打分选智能体；置信度低于 `SEMANTIC_ROUTE_CONFIDENCE = 0.35` 才调 LLM；**12 秒超时 fail-closed 回字面结果**
3. **任务开始** → `POST /agent/loop/start` → 服务端建循环，状态 `running`
4. **桌面接手** → `agent.ts` 的 `runToolLoop` 轮询 `POST /agent/loop/next`（**超时 90 秒**）
5. **模型决策** → 服务端 `toolLoop.ts` 组提示词（含 `snapshotBrief` 页面摘要）→ `llmFetch`（唯一出口）→ 返回一个工具调用
6. **翻译成动作** → `toolExecutors.ts` 的 `resolveBrowserAction`（纯查表，**刻意与 shared 重复，`tool-registry-parity.mjs` 强制两边一致**）→ `BrowserAction`
7. **真的动手** → `driver.ts` `drive()`：`resolveTarget(wcId)`（**必须显式给，多页并存禁止自动挑**）→ `ensureAttached` 打 CDP 补丁（`CDP_TIMEOUT_MS = 8000`，**防死锁硬闸，别删**）→ 发 `Input.dispatchMouseEvent` / `DOM.*` / `Runtime.*`
8. **结果回来** → `agent.ts:263 toResult()` 转成 `LoopToolResult` → `POST /agent/loop/message` 回服务端
9. **循环**：服务端 `describeToolResult` 转人话喂模型 → 下一步。直到 `stop`（`reason` 必须 ∈ `{need_user, blocked}`）
10. **三个本地安全网**（`agent.ts`，不进模型）：
    - 连续 **2** 步失败（`FAILS_BEFORE_ASK`）→ 求助卡片
    - 连点 **3** 次页面无变化（`STALE_BEFORE_ASK`）→ 求助卡片
    - 要打字但找不到输入框、目标明显是搜索 → **直接跳搜索 URL**
    - 只有 `STUCK_ASK_REASONS` 白名单内的 reason 才弹卡片

### 委派（一个智能体派多个）

```
A 的循环 running
  └─ delegate 工具 → delegation.ts
       ├─ 登记 job（deadline = DELEGATE_TIMEOUT_MS，默认 10 分钟）
       ├─ A 的循环 park 成 waiting_job，浏览器交还用户
       └─ workers.ts 起一队：最多 5 个、并发 3 个
            ├─ 每人独立 AbortController + 超时（clamp 到 ≤60_000ms）+ 受整队 budgetMs 约束
            ├─ allSettled：单个失败不影响同队，逐条给回执
            └─ 结果按输入顺序返回（确定性）
```

**⚠️ 接手最关键的一条事实**：`subLoops.ts:14` 注释原话——「**子循环没有桌面手**，被 `/next` 找到反而是漏洞」。**派出去的工人默认不操作浏览器。** 这是刻意的安全决定，不是 bug。

## 6. 不能动的红线 ★接手第一天就要背下来

来源：`docs/工程纪律.md` + 各 ADR 失败模式表。

1. **旧 6 工具的名 / 顺序 / schema 冻结**。新增只能版本化追加（如 `click_semantic`）。
2. **接口只增不破**：新字段必须可选 `?`。禁止删字段、改名、收窄可空性、改语义。任何接口增删改必须**同一 commit 更新 `docs/前端接入契约.md`**。
3. **浏览器三条路径不许碰**：不卸载内嵌页 / 不 `display:none` / 不归零（`verify:shell` 有 golden 网）。
4. **本地优先**：数据不出本机；密钥装机随机生成（0600）；`llmFetch` 用 `redirect:'error'`。
5. **fail-closed**：定位不到就停下来问人，**绝不猜坐标、绝不 CSS 猜支付/密码字段**。
6. **不引 Tailwind / shadcn**（用户定案）。
7. **降噪定案不许推翻**。
8. **不许调断言调到绿**。改标准 = 改断言，必须在注释里写清被什么取代。
9. **新文件写完立刻 `git add`**（沙箱回合会重置）。
10. **禁止 `git clean -fd` / `reset --hard` / `checkout -- <file>`**；变异前先 `cp` 原件，还原后 `md5sum -c`。
11. **不做 PR、不切分支**（会话固定在 `arena/01a0e33c-role`）。
12. **`screenshot` 只进渲染层，绝不进服务端、绝不进提示词**（当前它是死能力，见 §8）。

## 10.4 R7 修复（2026-09-29）· 关页即清该页的分片状态

**问题不是内存泄漏**（`pageState.ts` 本就有 TTL 扫描 + 64 条上限兜底），是**显示错**：
`clearPageState(wcId)` 从落地起没有任何调用点 ⇒ 用户关掉一张浏览器页后，服务端不知道，
`latestPageStateOfAgent()` 继续把那张**已关闭**页的状态当"最新"返回，
`chat.ts` 的 `mergeLatestPageState` 把它并进显示态 ⇒ `login_required` / `current_task`
最多滞留 **10 分钟**（`PAGE_STATE_TTL_MS`）。用户看到"页面都关了，界面还说需要登录/还在忙"。

**修法两处，缺一不可**：

| 位置 | 改什么 | 为什么 |
|---|---|---|
| `toolLoop.ts` `stopLoopsOfPage()` | 停掉该页全部循环后 `clearPageState(wcId)` | 清在**这个**函数而不是 `stopLoop(loopId)`：分片状态的键是 `wcId`（页）不是 `loopId`（循环），一张页可能同时有多路循环，在单路 stopLoop 里清会把同页其他路的状态一起抹掉 |
| `electron/main.ts` `workbench:browser:view-close` | 关页时 `agentPost('/agent/loop/stop', { wcId, reason:'page_closed' })` | 否则服务端根本收不到"页关了"这件事。带 `wcId` 不是 `loopId`：`stopLoopsOfPage` 会停该页**全部**循环并清页状态 |

**验收**：`scripts/verify/r7-page-state-clear.mts`（8 断言，已入主链）。
反证已跑通：删掉 `clearPageState(wcId)` → 「放下这一路后，该页的分片状态必须被清掉」红。
盖不到的一条已写明：Electron 侧只有**静态接线核对**，没有真关过一次页的证据（沙箱不起真 webview）。

## 10.5 治理（2026-09-29）· `packages/shared/dist` 整个取消跟踪

**原状**：`.gitignore` 写着 `dist/`，但 `packages/shared/dist` 下 **16 个文件**是当年 `git add -f` 进去的 —— **部分跟踪**。这就是"批次 J 事故"的根因（`mention-parse.mts` ⑩ 段有完整记录）：新增 `src/mention.ts` 后编译出的 `dist/mention.js` 被 ignore 挡住没进库，而**已跟踪**的 `dist/index.js` 里写着 `__exportStar(require("./mention"))` ⇒ 新克隆不手动 build 就起服务端 → `ERR_MODULE_NOT_FOUND`，**启动即崩**，而开发机永远复现不了。

**处置（正解：dist 整个不跟踪，靠 build 生成）**：

1. `packages/shared/package.json` 加 `"prepare": "npm run build"`。**实测 `npm install` 会触发它**，dist 从零重新生成，且与被跟踪的那份**逐字节一致**（`git status packages/shared/dist` 为空即为证）。
2. `git rm -r --cached packages/shared/dist`（16 个文件，磁盘上留着）。
3. 新增 `scripts/verify/shared-dist-fresh.mts`（4 断言，已入主链）接管两种新的失败形态：
   - **不在**：有人 `--ignore-scripts` 装依赖或 prepare 失败 → dist 没有 → 全链第一步崩。现在变成一句人话（"跑 npm install"），而不是 `ERR_MODULE_NOT_FOUND`。
   - **过期**：改了 `src/*.ts` 忘了 build → 测试和产品跑**旧代码**，现象是"我改了却没生效"。**这个比"不在"更阴**，所以逐个源文件核对产物 mtime。

三条反证都跑通、确认会红：删掉 dist → 红；`touch src/tools.ts` → 红；又 `git add -f` 回去 → 红。

> ⚠️ 为什么不能只做 `git rm --cached`：`verify:typecheck` 用的是 `tsc --noEmit`，**整条验证链从不 build shared**，而所有验收脚本 `require('@ai-workbench/shared')` 都解析到 `dist/`。没有 `prepare` 兜底就取消跟踪，等于把"批次 J 事故"从"部分跟踪"变成"一份都没有"，新克隆照样启动即崩。

## 10.6 P1-2 修复（2026-09-29）· 超时不再是「失败」，而是「不确定」

**原状**（接手报告 10.2 的 P1-2）：所有动作统一 `EXEC_TIMEOUT_MS = 20_000`，
且 `LoopToolResult` 没有 outcome/timeout 字段。「执行了但慢」与「确定失败」
不可区分，**超时后会盲目重做**。

### 两个必现 bug（不是理论）

**bug A · 超时被当成失败，于是盲目重做**

`Promise.race([hooks.exec(action), timeout])` 超时后**不会取消** `hooks.exec(action)`
—— 那一下点击照样发出去。可系统这边已经拿到 `{ok:false}` 并告诉模型「失败」。
模型于是重试。用户让 AI 买东西 / 填表 / 发消息时，这就是**下两单、发两条、提交两次**。

**bug B · `wait` 在 20~30 秒之间必然假失败，还对模型谎报时长**

driver 允许 `wait` 0~300 秒（`MAX_WAIT_SECONDS`），实际睡眠上限 30 秒；
而 race 的超时是 20 秒。于是任何 20~30 秒的 wait **都被判失败**，尽管它成功了。
附带：`detail` 报的是**模型要求的**秒数，实际只睡了 `min(seconds,30)`
—— 模型据此判断「已经等够了」，在页面还没加载完时就去点下一步。

### 修法

| # | 改哪 | 改成什么 |
|---|---|---|
| 1 | `shared` 的 `DriveResult` / `LoopToolResult` | 加 `outcome?: 'done'\|'failed'\|'unknown'`（可选字段，旧码不破） |
| 2 | `agent.ts` 新增 `execTimeoutFor(action)` | 按动作定超时：`wait` = 自己要等的 + 余量；`open_url`/`read_page`/`screenshot` 放长；`fill_form` 按字段数放大；交互类仍 20s（本地 CDP 调用，挂住就是真卡，长等没意义）。全部可配 env，有下限兜底 |
| 3 | `agent.ts` 超时路径 | 标 `outcome:'unknown'`，文案明确写「**不确定有没有生效**，先 read_page 看当前页面再决定，不要直接重试同一个动作」 |
| 4 | `agent.ts` 驾驶循环 | 独立 `unknown` 分支：**先 read_page 确认**，让模型基于当前页面决定，连 3 次不确定就停下来问人。单独计数，**不并进 `fails`**（并进去就退回盲目重做） |
| 5 | `driver.ts` 的 `wait` | 报**真实等了的**秒数；超上限时如实说明「要求 Ns，本机单次上限 30s，已按上限执行」 |

### 为什么光加字段不够

模型读的是**文本**，不是结构。所以 3 的文案必须把「下一步该干什么」说死：
先读页面、已替你读了、基于当前页面决定、目标已达成就直接 done。
只加 `outcome:'unknown'` 而文案仍写「失败」，模型照样重试。

### 验收

`scripts/verify/p1-2-exec-outcome.mts`（12 断言，已入主链）。
反证已跑通：把 `wait` 的超时改回一刀切 20 秒，「wait 20s 的超时必须大于它实际睡眠」红。

**诚实标注盖不到的两条**（需人工/端到端，脚本不假装盖到）：
1. `Promise.race` 的真实时序（要真起一个挂住的 exec 等满超时）；
2. 「模型收到 unknown 后确实没有重试」（那要真模型）。

> 写这个脚本时还踩了一个自己的坑：断言用正则查旧代码 `detail = `等待了 ${action.seconds}s``，
> 结果匹配到了**我自己注释里引用的旧代码**，代码明明是对的却判红。
> 已改成只匹配行首是空白的真赋值行（`^\s+detail = .../m`），并把注释里的旧代码示例
> 改成文字描述 —— 否则以后每次 grep 都会误报。

## 10.8 P1 二连修（2026-09-29）· #6 账本 + 怀疑 4 hijack

来源：`docs/待办清单-P2P3重排-20260920.md` §1 的两条 P1。

### #6 · `done` 集合整体清空 → 已处理过的会话被**再抽一遍**

原状：

    const done = new Set<string>();
    if (done.size > 800) done.clear();     // ← 整体清空

这是那份清单 §4 点名批评的**同一个模式**，和 #4（`if (ipHits.size > 5000) ipHits.clear()`）
是同胞：

> **「容量压力下整体清空集合」是一个会自我失效的防线。**

后果：`done` 清空后的下一秒，那些**还落在 15~60 分钟闲置窗口内**的会话又变成
「没处理过」→ 下一轮扫描**再整理一次记忆**。同一切点重复喂模型，用户完全无感，
但**计费**。而且**越是会话多、压力越大的账号越容易撞上** —— 防线恰好在最需要它时失效。

修法（照 #4 的定案：**永远不整体清空**），新文件 `apps/server/src/doneLedger.ts`：

| 步骤 | 做什么 |
|---|---|
| ① | 先淘汰**过期**的（切点对应的会话早就过了 60 分钟窗口，永远扫不到） |
| ② | 仍超上限，按最旧**逐条**淘汰少量（兜底，正常走不到） |

`markDone()` 是「不重复整理」的真正闸门：同一 key 第二次返回 false，调用方 `continue`。

**写的时候发现并修掉的一个自己的问题**：`sweepDoneLedger` 起初把 TTL 淘汰数和
兜底淘汰数合成一个返回值，`memories.ts` 据此打日志 ⇒ `expired` 是**常态**
（每分钟都有切点过 90 分钟），会**每分钟刷一行日志**。已拆成
`{ expired, capped }`，**只在 `capped > 0` 时打日志**（那才说明「热切点数顶到上限」
这个容量假设被打破了，是要留痕的信号）。

### 怀疑 4 · `hijack()` 之后还去碰 `reply` → 真因被框架报错盖掉

原状：`/chat/stream` handler 有 **6 处** `reply.hijack()`（mention 提示 / 三段不同收尾 /
页面任务开场 / `openSse()`），而**外层 catch 无条件** `return dbErr(reply, err)`。

异常抛在 hijack 之后、内层 try/catch 之外时（例如 SSE 建流阶段）：

    dbErr → errJson → reply.code(503).send(...)
      ↓ 打在「已被手写 SSE 接管」的响应上
    Fastify 抛 "Reply was already sent"
      ↓
    真实错误被盖掉，排查时看到的是框架噪音

修法：

| # | 改哪 | 改成什么 |
|---|---|---|
| 1 | 6 处 `reply.hijack()` | 统一收口到**带标志的** `hijackOnce()`（幂等） |
| 2 | 外层 catch | 分两段：没 hijack 才走 `dbErr`；hijack 了就写进 SSE + `res.end()` |
| 3 | 真因 | **无论走哪一段都先 `console.error` 落日志** |

为什么用 helper 而不是在 6 处各写一遍 `hijacked = true`：那样以后加第 7 处 hijack
时极易忘记置位，防线又漏了。

## 10.9 #7 / 怀疑 3 的**实测数字**（把"我觉得该这样改"变成证据）

两个改动都落盘了，但**没有证据就不算做完**。以下是在真 PostgreSQL 18.3
（PGlite，WASM 版）里灌 300,000 条消息、20 项目 / 2000 会话 / 60 天跨度，
用 `EXPLAIN ANALYZE` 跑出来的。

### 我原来的判断错了一条

我给复合索引写的理由是「也让闲置调度里按 conversation_id 分组求 MAX(id) 能走索引」。
实测：

| 被测对象 | 耗时 |
|---|---|
| OLD（无时间上界 + 单列索引） | 760 ms |
| NEW（有时间上界 + 复合索引） | 135 ms |
| NOB（无时间上界 + 复合索引） | 838 ms |

⇒ **提速 100% 来自时间上界；复合索引在那条 GROUP BY 上不但没帮忙，还略慢**
（索引更大，扫起来更贵）。那句理由**是错的**，已在 `db.ts` 注释里改掉。

### 但复合索引在另一条查询上是决定性的

`SELECT ... FROM messages WHERE conversation_id=$1 ORDER BY id DESC LIMIT 40`
（读历史、整理记忆各有一处）。同库，一个 20,000 条消息的会话：

| 索引 | 计划 | 耗时 |
|---|---|---|
| 只有单列 `(conversation_id)` | `Index Scan Backward using messages_pkey` + `Filter: conversation_id` + **`Rows Removed by Filter: 299700`** | 58.77 ms |
| 有复合 `(conversation_id, id)` | `Index Scan Backward using idx_messages_conversation_id` + `Index Cond` + `Buffers: shared hit=4` | **0.07 ms** |

⇒ **794x**。而且注意它的恶化方式：**与消息表总行数成正比，与会话长度无关**。
表越大，「读最近 40 条」越慢 —— 而这是每次打开历史都要跑的查询。

### 最小复现条件（为了把守卫做进主链）

坏计划**不需要** 30 万行：实测 **8,000 条消息**（一个 2,000 条的会话 + 30 个 200 条的）
就能让规划器选 `messages_pkey` 倒扫，造数据约 0.3 秒。

★ 但**长会话必须建在最前面**（拿最小 id）。坏计划的形状是「倒扫全表再过滤」，
只有当该会话的消息位于表**前段**时才复现；建在最后，它的消息就在表尾，
倒扫第一下就命中，0.07ms，什么都测不出来。
（基准脚本首版就建在最后，B 段测出 1x，白跑一趟。）

### 三个脚本的分工

| 脚本 | 进主链？ | 数据量 | 守什么 |
|---|---|---|---|
| `scripts/verify/p2-idle-scan-bounded.mts` | 是 | 小 | 加上界后**行为不变**（新旧查询逐行比对）+ CI 口径 golden |
| `scripts/verify/idx-messages-fetch.mts` | 是 | 8,000 条 | 读历史那条**必须走复合索引**、不许大批量 `Rows Removed by Filter` |
| `scripts/verify/bench-idle-scan.mts` | **否**（约 25 秒） | 300,000 条 | 可复现的实测数字；改上界/索引前先拿改前基线 |

### 诚实的边界

**绝对耗时不可迁移**：PGlite 是 WASM 单线程，比真服务器慢，也没有并行 worker。
「58.77ms / 0.07ms」这种数字**不能**拿去说"生产环境也这么快"。

可信的是两件事：
1. **执行计划的形状** —— 走哪个索引、有没有 Sort、`Rows Removed` 多少。
   这是规划器的决定，与 WASM 无关，与真服务器一致。
2. **同一环境内的比值** —— 同一个库、同一份数据、同一台机器，改前改后差多少倍。

**生产结论仍需真库实测**：真 PostgreSQL + 真数据量 + `EXPLAIN ANALYZE`。
这些脚本给的是"改动方向正确"的证据，不是"生产快了多少"的结论。

## 10.10 P1-2 补刀（2026-09-29）· 超时**真的**止住，不再是「换个说法」

### 10.6 那版只做完了半边

`c08a09c` 把超时从 `outcome:'failed'` 改成了 `outcome:'unknown'`，诚实是诚实了，
但**动作还在后台跑完**：超时那一刻系统报"这一步失败了"，可那一发点击 3 秒后照样落在
浏览器里。换句话说，上一版修的是**回执怎么说**，没修**到底停不停**。

### 修法：把取消信号一路递到真正会卡住的那一层

```
agent.ts  超时回调  ──execAbort.abort()──┐
                                         ▼
drive(action, wcId, signal?)   ← 第三参可选，既有三个调用方零改动
        │
        ├─ 形状闸之后、解析目标之前 ──→ abortIfRequested() 第一道闸
        │      （还没碰页面，退出最干净）
        │
        └─ switch 派发之前 ──→ abortIfRequested() 最后一道闸
               （决定放弃之后，绝不再下手）
```

配套改的 `sleep(ms, signal?)`：可取消，取消时**提前 resolve 而不是 reject**
（拒绝会逼每个调用点写 try/catch，而它们本来就要看 `signal.aborted` 决定回执），
并且 `clearTimeout` + `removeEventListener`，不留悬空定时器（否则进程不退出）。

`agent.ts` 每步建一个 `AbortController`，超时回调里 `abort()`；
`catch` 和 `finally` 里也 abort（抛错后不继续、正常跑完即清理）。

### ★ 诚实的边界（写进了 `driver.ts` 注释，测试第 ⑤ 组盯着它）

信号只挡**还没派发出去**的动作。那一发点击要是已经通过 CDP 发给浏览器了，
**没有任何办法收回来**。

所以这个机制的真实保证是两句：
1. 决定放弃之后，**不再继续下手**；
2. **不再傻等**自己发起的等待（`wait` 被叫停时如实报"实际只等了 0.8s"）。

**不是**"撤销已经发生的点击"。别把这条夸大成回滚能力。

### 验收：静态 + 行为，13 PASS

`scripts/verify/p1-2-exec-abort.mts`（主链第 48 步），五组：

| 组 | 查什么 |
|---|---|
| ① | `AbortController` 幂等基线（`agent.ts` 的 `finally` 依赖这一点，重复 abort 不炸） |
| ② | `sleep` 真能取消：已 aborted 立即返回且不排定时器；睡 30s 在 ~50ms 内被叫停；不传 signal 睡满 |
| ③ | `drive()` 第三参可选 + 两道闸位置 + 取消回执 `outcome:'unknown'` + `wait` 如实报"实际只等了" |
| ④ | ★ `agent.ts` 超时回调里 `timedOut = true;` 之后 400 字符内**必须**有 `execAbort.abort()` |
| ⑤ | 注释必须写明"挡不住已派发的那一下、不是撤销" |

### 反证（四条，全红才算数）

| 删掉什么 | 报什么 |
|---|---|
| A ★ 超时回调里的 `abort()` | ★ 超时回调里必须调 abort |

## 10.12 P1-5：主诉已经过时，真正坏的是"返回值撒谎"（2026-09-29）

### BUG_LIST 怎么说的，实测是什么

BUG_LIST P1-5 的主诉是：`pauseDriving()` / `resumeDriving()` 由 preload 暴露，
但渲染层**零调用**，所以**用户没有"暂停正在跑的驾驶"的 UI 入口**。

**这条主诉不成立。** 实测：

| 环节 | 实测结果 |
|---|---|
| 渲染层有没有暂停入口 | **有**。`useChat.ts:499` 调 `window.workbench?.pauseTask(wcId)`；`browserGlue.ts:165` 调 `resumeTask(wcId)` |
| 本地暂停门有没有真的生效 | **有**。`workbench:task:pause` → `pauseTask(wcId)` → `applyPaused(wcId, true)` → `t.paused = true` |
| `drive()` 有没有据此拦截 | **有**。`if (pausedOf(wcId) && PAUSED_BLOCKED.has(actionName))` 挡住 click / type / fill_form，并回一句人话 |

`pauseDriving` / `resumeDriving` 确实没人调 —— 但它们是 `pauseTask` 那条路的
**重复接口**（都通往同一个 `applyPaused` 本地门），不是"唯一入口缺失"。

### 真正坏的那一处：垫片无条件返回 `true`

`apps/desktop/src/webBridge.ts`（浏览器预览用的垫片）里原来是：

```ts
pauseDriving: async () => true,
resumeDriving: async () => true,
```

**什么都没做，却报告成功。** 调用方拿到 `true` 会以为"暂停门按住了"，
于是在预览模式里点暂停，自动操作照旧跑。

而主进程的 `setDrivingPaused()` 返回的是 `pausedOf(wcId)` —— **门的真实状态**。
同一个接口在两种环境下语义不一致，调用方没法根据返回值判断到底按没按住。

### 修法

让垫片与主进程对齐：落一份 per-target 暂停位 → 改任务状态 → 广播 →
**从状态里读出结果再返回**。没落成就返回 `false`，不骗人。

```ts
drivingPaused[wcId] = true;
const st = makeState('paused', '已暂停 — 自动操作已停止，浏览器交还给你', wcId, 'user');
taskStates[wcId] = st;
emit('state', JSON.stringify(st));
return drivingPaused[wcId] === true && taskStates[wcId]?.phase === 'paused';
```

**没有删接口**（遵守"接口只增不破"），preload 的白名单项原样保留。

### 这个测试自己撞的坑：静态正则盖不住"被禁用"

首版查暂停门写的是
`/pausedOf\(wcId\)\s*&&\s*PAUSED_BLOCKED\.has\(actionName\)/` ——
反证时把代码改成 `if (false && pausedOf(wcId) && …)`，**测试照样绿**：
正则匹配到了中间那段，看不见前面被 `false &&` 禁用了。

修法：把正则**锚在 `if (` 上**，要求 `(` 后紧跟 `pausedOf`。这样前面塞任何
字面量（`false &&` / `true ||` / 尾巴 `&& false`）都匹配不上。

这是本轮第三次撞上同一类坑（前两次在孤儿守卫里），值得记成规矩：
**静态断言要防"条件被字面量禁用"，正则必须锚到语句开头。**
