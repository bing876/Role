## 2. 三个由架构逼出来的设计判断（评审必读）

### 判断 1 · 临时工与被委派方**本批都在服务端执行**（没有「浏览器手」）

桌面执行器签名是 `drive(action, wcId)`，`wcId` 必须指向某一张真实的 `<webview>` guest，
而 lane/暂停/求助卡/partition 全按「页 + 智能体」组织。让「另一个智能体」用浏览器，
等于要新增「替某个智能体开一张页 + 起一条独立 lane + 跨进程调度」的通道，工作量与风险都不小。

所以本批的边界写死为：

* 临时工 / 被委派方能做：**联网检索（Tavily）+ 推理 + 整理 + 结构化汇报**；
* 它们**不能**打开网页、点击、填表 —— 工具表里根本没有这些工具，提示词里也明说「你没有浏览器手，
  不许说『已打开 / 已为你打开』」（这条话术是既有产品红线，见 `search/chatTool.ts` 的同类约束）。
* 需要浏览器的事，由**发起方自己**做（它本来就有浏览器手），或 `stop(reason=need_user)` 交给用户。

> 扩展点已经留好：给模型哪张工具表由 `LoopSession.toolNames` 决定（§4.2）。
> 将来做「桌面手」只需要给子循环分配 wcId + lane，不需要改本方案的其余部分。

### 判断 2 · 长耗时工具必须「**派出即返回 → 挂起 → 结果回来自动续跑**」

`/agent/loop/next` 的桌面端超时 90s（`main.ts agentPost`），服务端单次模型调用也有 90s 超时，
而委派要等 **10 分钟**。任何「在 `advance()` 里 await 子任务」的写法都会把循环打成 `brain_failed`
（R6 已证明：`/next` 传输出错就是永久杀循环）。

所以引入：

* 新循环状态 `waiting_job`（挂起等子任务，**不调模型**、不烧 token）；
* 后台任务登记表 + 完成投递（把结构化结果当作**那一格工具的正式回执**注入历史）；
* 桌面侧对 `job_pending` 的**轮询自动续跑**（§6）。

### 判断 3 · 协议上只加「可选字段 + 新 reason」，**不加新的 decision kind**

旧桌面（已安装版）遇到未知 `kind` 会掉进 `tool` 分支、把垃圾回执喂回来 → 死循环自旋。
所以「等子任务」这件事实**复用 `ask`**：

```jsonc
{ "kind": "ask", "reason": "job_pending", "question": "已派出…结果回来我会自动接着做",
  "jobId": "job_x", "jobKind": "workers", "etaMs": 120000, "step": 3 }   // 后三个字段可选
```

* 旧桌面：正常停下、把话显示给用户（不会自旋，只是不会自动续跑，用户点「继续」即可）；
* 新桌面：识别 `reason==='job_pending'` → ℹ️ 提示 + 登记 `jobWaiters` + 轮询 → 自动续跑。

## 3. 数据流（文字图）

```
用户 → 智能体 A 的循环（桌面手，浏览器）
  A 调 spawn_workers(tasks[3])
        │ 服务端 advanceInner 就地执行 spawn_workers
        ├─ 建 AgentJob(kind=workers, owner=A.loop)  → 返回 { ok:true, park:{jobId,…} }
        ├─ A 的 session.status = 'waiting_job'，/next 回 {kind:'ask', reason:'job_pending'}
        └─ 后台：3 个临时工并行跑（每个：≤2 轮 web_search + 1 次 JSON 输出）
                        完成后 deliverJobResult(jobId)
                          ├─ A.messages += tool 回执（聚合后的 WorkerReport[]，结构化）
                          ├─ A.status = 'running'（下一次 /next 就能继续）
                          └─ 桌面轮询发现 jobPending=false → resumeAgentLane(A 那张页) → A 继续

  A 调 delegate(to=母鸡, task=…)
        ├─ 闸：同项目/非自己/对方不在等结果/对方没满/深度≤2/非环
        ├─ 建 agent_delegations + 内部频道消息(kind='task')
        ├─ 建子循环（agentId=母鸡，toolNames=[web_search,spawn_workers,delegate,stop]）
        ├─ A 挂起（同 workers 那套 park）
        └─ 后台 runner 驱动子循环：
              每一步工具 → 写频道(kind='progress')  → 直到 stop(done/need_user)
              整体 ≤10 分钟；超时 → stopLoop(child) + 频道写 system + 投递 delegate_timeout
              完成 → 频道写 reply + 投递结果给 A → A 自动续跑
用户 → 「内部频道」抽屉：A ↔ 母鸡 的 task / progress / reply / system 全过程（密文落库）
```

## 5. 工具契约（三个新 server 工具，`side:'server'`、`kind:'action'`）

### 5.1 `spawn_workers` —— 临时工并行（无身份、无记忆、结构化汇报、用完即销毁）

```jsonc
// parameters
{ "type":"object", "properties": {
    "tasks": { "type":"array", "items": { "type":"object", "properties": {
        "title":       {"type":"string"},   // ≤60 字
        "instruction": {"type":"string"},   // ≤600 字，一件事，写清要什么
        "context":     {"type":"string"}    // 可选 ≤2000 字：发起方已有的资料
      }, "required":["title","instruction"] } },
    "allow_search": {"type":"boolean"}      // 默认 true；Tavily 未配置时自动降级为纯推理
  }, "required":["tasks"] }
```

* **上限硬闸**：`tasks.length` ≤ `WORKER_MAX_PER_CALL`(默认 5)；每个循环累计 ≤ `WORKER_MAX_PER_LOOP`(默认 12)。
* 单条任务 description 里**明说**："临时工没有身份、没有记忆、没有浏览器，只能查公开资料与推理；
  要打开网页/登录/下单的事不要派给他们。"
* 执行语义：建 job → 立刻返回 `{ ok:true, detail:'已派出 3 个临时工并行处理（≈XX 秒）',
  data:{ jobId, status:'pending' }, park:{ jobId, kind:'workers', etaMs, note } }`。
* 后台：`runWorkerPool` 并发上限 `WORKER_CONCURRENCY`(默认 3)，**每个工人独立超时**
  `WORKER_TIMEOUT_MS`(默认 120s)，整批预算 `WORKER_JOB_BUDGET_MS`(默认 180s)；
  单个失败**不影响**同批其他人（`Promise.allSettled` + 逐条 status）。
* 汇总投递：`data = WorkerBatchResult`（**顺序与入参一致**，确定性）；`detail` 一句话
  （"3 个临时工都回来了：2 成功 / 1 失败"）。

### 5.2 `delegate` —— 智能体间委派

```jsonc
// parameters
{ "type":"object", "properties": {
    "to":      {"type":"string"},  // 目标智能体：名字（推荐，模型看到的是名单）或 id
    "task":    {"type":"string"},  // ≤600 字：要对方做成什么、要回什么
    "context": {"type":"string"},  // 可选 ≤2000 字
    "expect":  {"type":"string"}   // 可选：你希望对方回什么结构
  }, "required":["to","task"] }
```

* description 里带上**当前项目同事名单**不是靠 description（那是静态的），而是靠
  **提示词块**：`StartLoopInput.orchestrationBlock`（§5.4）由路由在建循环时按 DB 查出来拼好，
  名单含「名字 / 职责（persona.duty） / 忙不忙」。
* 执行语义：过闸（§7）→ 建 `agent_delegations` + 频道 `task` 消息 + 启子循环 →
  返回 `{ ok:true, detail:'已交给「母鸡」，最多 10 分钟给你结果', data:{ delegationId, channelId, to },
  park:{ jobId, kind:'delegate', etaMs: DELEGATE_TIMEOUT_MS, note } }`。
* 被拒时（不 park，当场回执，让发起方自己决定下一步）：
  `{ ok:false, reason:'agent_busy_waiting' | 'agent_busy' | 'agent_not_found' | 'cross_project' |
    'delegate_self' | 'too_deep' | 'cycle' | 'too_many' | 'orchestration_off',
    detail:'人话' }` —— 且**写进频道**（kind='system'），用户在内部频道能看见"谁被拒了、为什么"。

### 5.3 `web_search`（可选，但对本功能意义大）

* 复用 `search/tavily.ts` + `search/chatTool.ts` 的定义与策略，注册成**服务端工具**：
  执行器里先过 R1 同一套 `SENSITIVE_TARGET_RE`（命中直接拒绝、不外发、日志不记原文），
  再带每循环轮数上限（`WEB_SEARCH_MAX_ROUNDS`，默认 3）。
* 挂给谁：
  * **临时工**（内部小循环，≤2 轮）：默认开（否则临时工只能瞎猜）；
  * **被委派方子循环**：默认开（这是它的主要能力）；
  * **主浏览器循环**：⚠️ **建议也挂上（默认开、可关）** —— 现在浏览器循环里问"查一下今天天气"
    只能瞎翻页（正是 R4 说的一半问题）。挂上之后，服务端就地搜一次（1~3 秒）再回答，
    不占桌面那 90s 之外的时间。开关：`AGENT_LOOP_WEB_SEARCH=0/1`（默认 1）。
    **这一条算行为变更，需要你点头**（见 §14 Q4）。

### 5.4 提示词（新文件 `apps/server/src/orchestrator/prompts.ts`）

| 常量 | 给谁 | 要点 |
|---|---|---|
| `WORKER_SYSTEM_PROMPT` | 临时工 | 你没有身份、没有记忆、不许编造来源；只输出**严格 JSON**（schema 见 §4.1 WorkerReport）；不能打开网页；敏感信息不外发 |
| `SUB_AGENT_SYSTEM_PROMPT` | 被委派方子循环 | 你是项目里的「X」，同事「Y」把一件事交给你；**你没有浏览器手**（只有 web_search / spawn_workers / delegate / stop）；做完必须 `stop(reason=done, summary=…)` 收尾；要用户拍板的一律 `stop(reason=need_user)`；不许假装打开网页 |
| `orchestrationBlock()` | 两边的第一条 user 消息追加段 | 同事名单（名字/职责/忙不忙）+ 三条硬规矩（谁能用浏览器、临时工只能干"不用浏览器"的活、委派最多 10 分钟且会被拒） |

> 名单与规矩作为**追加段**进第一条 user 消息（`firstUserMessage` 已经支持 `state` 这种追加段，
> 新增一个可选 `orchestrationBlock` 参数，默认空 = 行为零变化）。
> 循环启动点有两个：`routes/chat.ts`（任务轮）与 `routes/loop.ts`（桌面自建），
> 两处都要把 `orchestrationBlock` 一起传（**两端字段名必须一致** —— 这是踩过的坑）。

## 6. park 生命周期（时序，含"不能让任务卡死"）

1. `advanceInner` 内循环执行 server 工具 → 拿到 `LoopToolResult.park`。
2. 写回执进历史是**不能**做的（结果还没出来）——只记 assistant 的 tool_call（`pendingCallId = call.id`），
   然后 `session.jobId = park.jobId`、`session.status = 'waiting_job'`，
   返回 `{ kind:'ask', reason:'job_pending', question: park.note, jobId, jobKind, etaMs, step }`。
3. 桌面：
   * `job_pending` 不进求助卡白名单（`STUCK_ASK_REASONS` 不含它）→ **不会弹卡、不会误导**；
   * 新桌面：`emitAgent({kind:'ask', reason:'job_pending', …})` → 渲染层画 ℹ️（不是 ⚠️）+ "等 X 交活/等临时工，
     结果回来自动接着做"；主进程把 `{wcId, loopId, goal, deadlineAt}` 记进 `jobWaiters`，**lane 正常收尾**
     （浏览器交还用户，页面照常可点）。
   * 旧桌面：同一条 `ask` 分支 → 停下来等用户点「继续」（不会自旋、不会重复执行）。
4. 主进程轮询（`setInterval` 4s，只在 `jobWaiters` 非空时跑，`unref`）：
   `GET /agent/loop/job?loopId=…`（要 JWT）→ `{ status, job:{ pending, deadlineAt, resultReady } }`。
   * `pending === false` → `resumeAgentLane(wcId, goal)`（**复用既有"继续"链路**：read_page → `/agent/loop/resume`
     （对 `running` 是 no-op）→ 同一 lane / 同一 loopId 原地接着跑）。
   * 超过 `deadlineAt + 60s` 仍 pending → 停轮询 + 一条如实提示（"还没回来，稍后点「继续」也行"）。
   * 用户按「停」/ 换指令/登出/关页 → 该 wcId 的 jobWaiter 立刻清掉（`abortAllLanes`、`dropLane` 一并清）。
5. 后台任务完成（成功 / 失败 / 超时）→ `deliverJobResult(jobId, result)`：
   * 找到 owner 循环且仍挂在**同一个 jobId** 上 → 走 `ingestToolResult`（tool 消息 + 快照 + 清 pending + step+1）
     → `status='running'`、`jobId=null`、`touchedAt=now`；
   * 循环不在 / 已停在别的状态 → 只落库（委派结果在内部频道里仍可读）+ 日志；
     **绝不静默伪造回执**。
   * 幂等：同一 jobId 只投递一次（`job.status='done'` + 投递标记）。
6. 幂等重放：`waiting_job` 期间任何 `/next`（用户在旧桌面上狂点「继续」）**一律不再调模型**，
   原样回同一句 `job_pending`（保护费用与死循环）。
7. 超时熔断（10 分钟）：`DELEGATE_TIMEOUT_MS` 默认 600000；
   * 到点 → `cancel('timeout')` → 子循环 `stopLoop(child, 'delegate_timeout')`（释放 lane 无关，纯内存）→
     频道写 `system` + `reply`（"暂未完成"）；委派行 `status='timeout'`；
   * 发起方拿到 `{ ok:false, reason:'delegate_timeout', detail:'「X」暂未完成（已等 10 分钟）',
     data:{ delegationId, status:'timeout' } }` —— **如实告知，不假装完成**；
   * 释放 `busyTargets` 里对方的名额（对方可以接下一件事）。
8. 临时工超时同理（`WORKER_JOB_BUDGET_MS`）：回来的 `WorkerReport[].status='timeout'`，
   发起方看到的是"3 个里 1 个超时"，而不是整批失败。
9. TTL：`waiting_job` 归入等待档（6h），但 job 自己的 deadline（≤10 分钟）会先把它解开 → 不留僵尸。

## 7. 安全限制（逐条对应你提的三点）

| 你的要求 | 实现（**确定性闸，不靠模型自觉**） | 位置 |
|---|---|---|
| 防止死循环：正在等别人结果的智能体，不能被拉去处理新委派 | `waitingAgents: Map<agentId, delegationId>`；`delegate` 执行前查：目标在等 → **当场拒绝** `agent_busy_waiting`（并在频道留痕）。名额在投递/超时/失败时释放 | `orchestrator/delegation.ts` + `registry.ts` |
| 同上（并发面） | 每个智能体同时只处理 `DELEGATE_MAX_ACTIVE_PER_AGENT`(默认 1) 个被委派任务；超了拒收 `agent_busy`（v1 先不排队，见 §14 Q3） | 同上 |
| 委派链自环 | 拒绝 `delegate_self`；链深 ≤ `DELEGATE_MAX_DEPTH`(默认 2：A→B→C 可以，A→B→C→D 不行)；目标出现在祖先链里 → `cycle` | 同上（链信息随 job 传递） |
| 费用熔断（顺手补 R9 的一角） | 每循环 `DELEGATE_MAX_PER_LOOP`(默认 3)；全局 `ORCH_MAX_LIVE_JOBS`(默认 8)；临时工每循环上限 12；搜索每循环 ≤3 轮；每个 job 都有 deadline | `registry.ts` |
| 10 分钟超时熔断 | `DELEGATE_TIMEOUT_MS` 默认 **600000**（env 可调，夹在 60s~30min）；到点如上"如实告知 + 释放" | `delegation.ts` |
| 敏感信息不出圈 | 委派任务文本、临时工 instruction/context、频道正文、payload 一律先过 `redactSensitive()`（复用 R1/R2 同一套正则）；命中就直接拒绝该次委派/派工并说明原因 | `orchestrator/redact.ts` |
| 不越权 | 目标智能体必须：**同一 project**、属于本账号，且 `agentId ≠ 自己`；跨项目/别人的一律 `404/拒绝`（与 `/agents` 同一口径） | `delegation.ts` |

## 8. 内部频道（存储 + 接口 + UI）

### 8.1 服务端接口（`apps/server/src/routes/channels.ts`，全部要 JWT）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/agents/channels?projectId=` | 我的频道列表（对方名字、最后一句预览、时间、条数、是否有在跑的委派）。**只回自己的**（`user_id` 过滤），预览解密后截 60 字 |
| GET | `/agents/channels/:id/messages?limit=50&beforeId=` | 某个频道的对话（解密后下发）。不是自己的频道 → 404（不泄漏存在性） |
| GET | `/agents/delegations?channelId=&limit=20` | 委派记录（状态/截止/结果摘要），UI 画状态徽标用 |

### 8.2 渲染层（`apps/desktop/src/channels/`，新目录）

* `useAgentChannels.ts`：拉列表/消息（打开抽屉时每 5s 轮询一次；关掉就停），带 token。
* `ChannelsDrawer.tsx`：独立抽屉（不占用现有三栏布局）。左侧频道列表（对方名字 + 未读点 + 最后一句），
  右侧对话气泡：
  * `task` 蓝色（发起方）／`progress` 灰色小字（对方做了什么，如"已搜索：xxx"）／
    `reply` 绿色（对方交活）／`system` 黄条（被拒/超时/取消，附原因）；
  * `reply` 的 `payload` 渲染成一张结构化卡：状态、要点（findings）、来源链接、耗时、置信度；
  * 顶部一行徽标：`进行中（剩余 mm:ss）` / `已完成` / `超时未完成` / `被拒（原因）`。
* 入口：任务卡/驾驶区旁边一个「📨 内部频道」按钮 + 有未读时红点（沿用既有红点观感）。
* 聊天区同步一行：发起时 `📨 已把这件事交给「母鸡」，可在内部频道查看过程`；
  回来时 `📨 「母鸡」把结果交回来了：<摘要>`（走既有 `emitAgent`/`pushChatLineFor`，按 wcId→agentId 落回**发起方**的聊天，不串）。

### 8.3 聊天侧不做的事

不把内部频道的每条消息都灌进智能体的**对用户会话**（那会污染用户自己的聊天记录）；
用户会话里只有上面那两行摘要 —— "用户可以查看这个交流过程"由**抽屉**满足。

## 11. 验收（真机，需要你配合的部分）

1. **临时工并行**：让某智能体做"A/B/C 三家竞品各查一遍"→ 会话出现 "已派出 3 个临时工" → 到点自动继续并给结论；
   日志里 `[orc] job=… workers=3 conc=3` 证明**真并行**，完成后瞬间从 `jobs` Map 消失（销毁）。
2. **委派**：让小助把一件研究类的事交给母鸡 → 打开「内部频道」抽屉，能看到 task / progress / reply 全过程；
   母鸡的回复结构化卡上有要点与来源。
3. **死循环防护**：手工构造"母鸡在等别人结果时再被委派"→ 被拒 + 频道里有 `system` 留痕（原因写清）。
4. **10 分钟熔断**：用一件注定做不完的事（或临时把 `DELEGATE_TIMEOUT_MS` 调到 30s）→
   发起方如实收到"暂未完成"，任务**不卡死**（可继续对话 / 可重新派）。
5. **不串号**：两个智能体各开一张页同时跑，其中一路派工/委派 → 另一路完全不受影响（沿用既有 lane/agentId 双闸）。

## 13. 风险与回滚

| 风险 | 对策 |
|---|---|
| 旧桌面 + 新服务端 | 协议只用「可选字段 + 新 reason」，旧桌面行为 = "停下来告诉用户"（§2 判断 3）；服务端对"挂起期间收到的意外回执"一律忽略并重放 `job_pending`（防自旋） |
