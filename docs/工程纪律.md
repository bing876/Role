# 工程纪律

> 来源:蒸馏自 [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills)(Production-grade engineering skills for AI coding agents)六条:documentation-and-adrs、spec-driven、doubt-driven、source-driven、planning、security-and-hardening。
> 定稿:2026-09-26(用户拍板,**从本条起遵守**)。
> 性质:工程侧纪律(怎么做)。产品侧标准在 `docs/产品交互规格.md`(做成什么样),两者互补。
> 用法:每批开工前对一遍;每条写「我们现状 + 要补的动作」。对不上的先说明再继续。

## 1 重要决策写 ADR(documentation-and-adrs)

原则:影响后续代码的决策(选型、口径、红线)落成 ADR——背景 / 决定 / 后果 / 否掉的备选。别让它只活在聊天记录和 commit message 里。

我们现状:

- 没有 `docs/adr/` 目录;重要决策散在 commit message、`README.md`、`docs/智能体协同-总计划.md` 里(如:内容列加密 fail-closed 口径、输出纪律、撤回 Tailwind/shadcn 选型)。
- 有些「类 ADR」段落(README「数据与安全」、收尾 6 注释块),但混在代码注释里、检索难,且不记「否掉了什么、为什么」。

要补的动作:

- 建 `docs/adr/NNNN-短名.md`,四段:背景 / 决定 / 后果 / 备选与否因。
- 规则:任何**跨 feature、动红线、改既有口径**的决策,push 前先有 ADR。
- 历史决策**不批量补**:哪个旧决策被新批次碰到,顺手补一份(注明原 commit sha)。

## 2 先规格后代码(spec-driven)

原则:先写「什么算对」(标准 + 验收 + 反证),再写代码;验收脚本就是可执行规格。

我们现状:

- 产品侧已有规格(`产品交互规格.md` C1–C8);每批「验收 + 反证 + 全量 verify」纪律已在跑——G3/G4 都是先把标准写清才动代码,规格精神实际已生效。
- 缺口:规格留在会话记忆/聊天里,没进 repo;下个会话要对 git 历史才能还原口径。

要补的动作:

- 每批开工先写「标准表」(标准 | 验收 | 反证),随批次一起提交(commit message 或 `docs/acceptance/`)。
- 验收脚本断言与标准表行一一对应;**改标准 = 改断言,绝不「调断言到绿」**(铁律照旧)。

## 3 高风险先列「怎么会失败」(doubt-driven)

原则:高风险改动动手前,先列失败模式;每个失败模式要有对应断言兜着。

我们现状:

- 反证(revert-proof)惯例已有:每批至少一处变异证明「拆掉必红」(G1 5/5、G2 5/5、G3 2/2、G4 2/2)。
- 缺口:反证多是**事后拆**(先绿再变异,证明没过度断言);动手**前**的失败模式枚举没有制度化——如 G4 recorder 是 fire-and-forget,它的失败模式写在注释里,但没有逐条断言清单。

要补的动作:

- 高风险批次 = 碰 加密 / 鉴权 / 热路径 / 支付级数据 任一 → 动手前先列「失败模式表」(每行:会怎么坏 → 怎么验)。
- 验收时逐行覆盖;覆盖不到的行要写明理由,进「已知缺口」,不许默默跳过。

## 4 不熟先查官方(source-driven)

原则:不熟的 API / 行为 / 报错,先查官方文档或 `node_modules` 里的源码;不猜。查完把结论记下来,下次不重查。

我们现状:

- 有真实代价的记录:`npx tsc` 装错包(`tsc@2.0.4` 不是 TypeScript 的命令,「This is not the tsc command」);沙箱重置清掉 remote-tracking ref 后猜了一遍,最后靠 `git ls-remote` 才确认;`users` 表只有 `phone_hash/phone_enc` 没有明文 `phone`,照想当然写 `WHERE phone=$1` 直接报错。
- 好例子也有:G3 桩 LLM 解析 `- id=N` 候选行之前,先读了真实 prompt 的拼装再写桩——桩是对着真格式写的,不是猜的。

要补的动作:

- 报错 / 不熟行为:官方文档 → `node_modules` 源码 → 再动手;结论写进会话记忆「Errors & Dead Ends」。
- 新外部依赖第一次用时,留一行「实际行为」笔记(版本相关行为尤甚)。

## 5 计划增量更新,不覆盖(planning)

原则:计划是活文档——做完的标掉、新的追加;不整篇重写成丢掉上文(addyosmani 仓库自己就为此发过修:「never overwrite an incomplete plan」)。

我们现状:

- 长期计划 `docs/智能体协同-总计划.md` 在 repo 里,是长期口径的单一来源。
- 缺口:会话记忆的「下一步」每段整体重写,顺序写岔时会丢已完成项(实际发生过:G1/G2 的先后要靠 git log 对 parent 才校正过来)。

要补的动作:

- 会话记忆是工作层:完成项**移**进「Key Results」(带 sha),「下一步」追加/勾销,不整篇覆盖。
- 长期计划只走 `docs/智能体协同-总计划.md`;新批次与计划冲突时,**先改计划再动手**。

## 6 密钥 / 输入 / fail-closed(security-and-hardening)

原则:密钥不入库;外部输入必校验;失败时 fail-closed(拒绝,而不是降级成明文)。

我们现状(本条 repo 已做得较实,大部分「现状」即是已达标项):

- 密钥:`DATA_KEY` / `JWT_SECRET` 等只走 env;验收脚本用内联随机 key,repo 里没有任何真密钥。
- 密文:messages / memories / skills / 知识库 / checkpoints 内容列 `gcm$...`(AES-256-GCM);tasks 目标只存 `goal_enc`,`payload` 不留明文 goal、`title` 恒 NULL(收尾 6,真库复验过);步骤摘要入库前脱敏(R2)。
- 输入:路由处理一律 `authed`(JWT)+ 类型/长度/归属校验(`ownTask`、`user_id` 过滤、id 必须 integer)。
- fail-closed:加密失败 → 500 不落库;checkpoint 拿不到 cipher 不写;语义路由 LLM 不可用回落字面;G4 录制失败只 warn 不拖任务 done;确认/拒绝接口非 pending 如实 404。

要补的动作:

- 新路由上线前对清单:① 有 `authed`?② 输入类型 + 长度 + 归属都校验?③ 落库的内容是密文或脱敏?④ 失败是 500/404 还是降级明文?
- 新增敏感列 → 纳入 `verify:db` / 脱敏 verify 链。
- 发现明文残留按收尾 6 口径:加密文列 + 回填 + 读「解密优先、回退旧列」,**旧列暂不 drop**(照旧)。
