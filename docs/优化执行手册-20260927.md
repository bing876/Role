- **改动点**：新增 `.github/workflows/verify.yml`。建议先加**只读子集**，不碰打包 workflow：
  ```yaml

        - run: npm run verify:typecheck
        - run: npm run verify:gates
        - run: npm run verify:redact
        # …按 package.json 的 verify 链顺序逐条列，最后：
        - run: npm run verify:shell
        - run: npm run verify:logic
  ```
- **注意（回验结论）**：主链 41 步**全部离线可跑**——`verify:mcp:public` / `verify:connectors:live` / `eval:model:live` 都不在主链里（这是对的，别改）。**唯一需要 electron 二进制的是 `verify:release`**（`release-runtime.mts` 用 `ELECTRON_RUN_AS_NODE` 起包内二进制）；E44 起 electron 包不再 postinstall 下载、改为懒下载，所以 `npm ci` 不会自动拉 100MB，但 `verify:release` 首次 spawn 会拉。**建议：第一版 CI 不含 `verify:release`**（它已由 `package-desktop.yml` 在 Win/mac 覆盖），主链跑稳后再决定是否并入。
- **验收**：CI 对"故意改坏一处生产代码"的提交必须红（用一个临时分支试，不合入）。
- **反证**：把 workflow 里任一 `run: npm run verify:*` 删掉 → 该步的保护消失（用"改坏对应模块 + push 临时分支"证明它会红）。
- **回滚**：删 workflow 文件。

### Q2 · CORS allowlist + Host 白名单 + 登录限流（合并 E1）

- **改动点**（三处，都在服务端）：
  1. `index.ts:92`：`cors({ origin: true, ... })` → 显式 allowlist（`http://127.0.0.1:8787` / `http://localhost:8787` / dev 态 vite origin；生产安装包是 `file://` → `Origin: null`，需显式放行 `null` 或用 `origin: false` + 桌面不走 CORS）。
  2. 同处或加一个 `onRequest` 钩子：校验 `req.headers.host` ∈ `127.0.0.1:<port>` / `localhost:<port>`，否则 421/403。**这一条才是防 DNS rebinding 的正解**（origin 可被伪造/host 才是浏览器实际连的地址）。
  3. `routes/auth.ts` 的 `/auth/login/xyz`（:474）与 `/auth/sms/send`（:278）加**按标识的失败计数**：复用 `auth.ts` 已有的进程内限流表（`PHONE_HOURLY_CAP` / 按 IP 20-per-min 那套），加"同 XYZ 号连续失败 N 次（如 10）→ 冷却 M 分钟"，且**淘汰策略按 key 淘汰最旧**（别用 `clear()`——`auth.ts:70-72` 自己记着这个绕过）。
- **验收**：起真后端于随机端口（照 `r4-dispatch-acceptance.mjs` 的端口随机化做法）：
  - 带 `Origin: https://evil.example` 的 `POST /auth/login/xyz` → 被拒；
  - `Host: attacker.com` → 被拒；
  - 桌面真 origin + `Host: 127.0.0.1:<port>` → 正常登入；
  - 同 XYZ 号连续 10 次错密码 → 第 11 次返回冷却话术（**且不泄露"该号是否存在"**——文案与普通 401 一致或明确说"尝试过多"）。
- **反证**：① 删 Host 校验 → 前两条红；② 删 allowlist → 第一条红；③ 删失败计数 → 第四条红。
- **回滚**：三处都是加法，回退即恢复 `origin: true`。
- **注意**：`Origin: null`（`file://`）必须显式处理，否则**生产安装包登录页会被自己拦死**——这是最可能的回归。验收里必须有一条"安装包形态（Origin: null）能登录"。

## 3. CI 提案的取舍（为什么这样拆）

| 套件 | CI 可行性 | 理由 |
|---|---|---|
| `verify:typecheck` / `:gates` / `:redact` / `:mention` / `:tools` / `:r4` / `:orch` / `:websearch` / `:memory` / `:persona` / `:collab` / `:handoff` / `:followup` / `:routine-*` / `:output-hygiene` / `:creation` / `:semantic-*` / `:skill-recording` / `:teach-once` / `:report-once` / `:plugins` / `:mcp` / `:connectors` / `:model` / `:batches` / `:db:pglite` / `:chat-trace` / `:shell` / `:electron` / `:waitwatch` / `:tokens` / `:logic` / `:loop:kill9` / `:build-agent` | ✅ 离线可跑 | 全部用 PGlite / jsdom / 本地 HTTP 桩。`verify:electron` 只读 `node_modules/electron/package.json` 版本，不拉二进制 |
| `verify:release` | ⚠️ 需 electron 二进制（懒下载 ~100MB）+ `release:prepare`  staging | 已由 `package-desktop.yml` 在 Win/mac 覆盖；第一版 CI 不含，跑稳后再议 |
| `verify:mcp:public` / `:connectors:live` / `eval:model:live` | ❌ 需公网 + 真凭据 | **刻意不进主链**（对的），由 P0 Runbook 在联网机人工跑 |

**给每条 CI 失败加归类输出**（`env` / `flaky` / `real`）比"让 CI 全绿"更重要。已知 flaky 嫌疑：`verify:loop:kill9`（pglite 文件库 + 真 SIGKILL）、端口探测类套件（8799/8899/9333）、50 处 `setTimeout` 时序等待。第一遍 CI 大概率红在这里——**那是 CI 在立功，不是 CI 有问题**。
