# 重复执行风险审计（只读）

> 审计对象：本仓库 `arena/01a09b16-work123` 分支上的「AI 驾驶真实网页」链路。
> 审计时间：2026-09-21。
> 性质：**只读**。本轮没有修改任何产品代码、没有新建分支、没有提交。
>
> **术语速查**（首次出现时用大白话说一遍，后面不再解释）
> - **不可逆转动作**：做错了撤不回来的动作 —— 提交订单、付款、发消息、发邮件、发布内容。
> - **幂等**：同一个动作做 1 次和做 3 次结果一样（比如"读取页面"就是幂等的，"下单"不是）。
> - **回执**：桌面端（"手"）执行完一个动作后回传给服务端（"脑"）的一条消息，说明"做了什么、成了没、现在页面长什么样"。
> - **挂起 / 解挂**：把一条正在跑的任务停下来但**保留记忆**（pause），之后再**原地接上**（resume）。
> - **delta（变化判定）**：比较"挂起前那张页面"和"继续时这张页面"，判断用户在挂起期间有没有自己动过页面。
> - **CDP**：Chrome DevTools Protocol —— 我们用来真正点击网页的那套底层遥控器。
> - **TTL**：存活时间。超过这个时间没人理它，就自动回收。
> - **置信度标记**：【读到】= 代码里明明白白写着；【推断】= 代码没直接写，但从读到的代码推出来，我会写清依据；【无法确定】= 读不出来，我会写清我看到了什么。

## ⚠️ 高优先级发现

读完全部相关代码后，我确认存在**两条会造成真实损失**的路径。它们都不是"理论上可能"，而是代码里已经写明会发生。

### 发现 1（最硬）：「继续」时如果循环已过期，会**丢弃全部历史、开一轮全新的**——AI 在完全不知道自己做过什么的情况下，重跑整个目标

- **触发条件**：任务处于挂起/等待状态，**超过 10 分钟**没有动静（或者服务端重启过），此时用户点「继续」。
- **代码路径**：
  1. 服务端循环存活 10 分钟 —— `apps/server/src/toolLoop.ts:270` `const LOOP_TTL_MS = 10 * 60 * 1000;`；`sweep()` 在 `toolLoop.ts:320-328` 把超时的循环直接 `loops.delete(id)`；`getLoop()` 在 `toolLoop.ts:333-335` 也是「超时即删、返回 null」。
  2. 于是 `/agent/loop/resume` 返回 **404「这个循环不存在或已过期」** —— `apps/server/src/routes/loop.ts:323-324`。
  3. 桌面端 `resumeAgentLane()` 捕到这个失败后走兜底分支 —— `apps/desktop/electron/main.ts:586-592`：
     ```ts
     } catch (err) {
       // 解挂失败（循环过期等）→ 退回「新建一轮」，绝不让「继续」变成没反应
       lanes.delete(wcId);
       startAgentLoop(wcId, goal, false, { agentId: ... });   // ← 不带 loopId、不带 resume:true
       return;
     }
     ```
  4. `startAgentLoop` 不带 `loopId` 时会在服务端**新建一个循环**（`toolLoop.ts:384` `startLoop`），`messages` 从零开始。
- **后果**：模型拿到的上下文里**一条"我已经点过什么、页面现在是什么样"的记录都没有**（只有一句原始目标 `goal`）。如果目标里包含一个不可逆转动作（"帮我把这张订单提交掉"），模型会从第一步重新走一遍 —— **第二次提交**。
- **置信度**：【读到】（第 1~4 步的代码和注释都明写）。**"一定会重复提交"这一后果是【推断】** —— 依据是新建循环后模型上下文为空、且没有任何"已执行台账"可供它查询（见第 3 步问题 1），但模型具体会不会重走那一步，取决于它自己怎么规划，我无法从代码里读出。
- **为什么这条最硬**：它是**唯一一条在代码里被明确写成了"故意的行为"**的丢历史路径（注释写「绝不让『继续』变成没反应」），也就是说这不是 bug 而是取舍，不会被日常测试暴露 —— 用户只是"隔了十来分钟回来点了继续"。

### 发现 2：不存在「确定没执行」vs「不知道执行没执行」这个区分——**超时被一律当成"没执行"，而超时的那一次点击很可能已经落在页面上了**

这是本次审计的核心问题（OpenHands / DeepSeek 都专门为它设计了机制）。我们**没有**这个区分。

- **证据 A —— 回执缺失被当成"确定没执行"**：`apps/server/src/toolLoop.ts:979-987`
  ```ts
  } else if (session.pendingCallId) {
    // 上一格给了工具但桌面没回执就又问了一次：把它当「没执行」，让模型重选
    session.messages.push({ role: 'tool', tool_call_id: session.pendingCallId,
      content: '工具没有被执行（桌面没有回执）。请重新选下一步。' });
    session.pendingCallId = null;
  }
  ```
  这句话里**只有一种可能性**（没执行），没有"可能执行了但没回执"这个档位。
- **证据 B —— 超时**不会取消**已经发出去的点击**：`apps/desktop/electron/agent.ts:496-509` 用 `Promise.race` 给执行加 20 秒超时：
  ```ts
  res = await Promise.race([
    hooks.exec(action),
    new Promise<DriveResult>((resolve) => { setTimeout(() => resolve({ ok: false, ... }), EXEC_TIMEOUT_MS); }),
  ]);
  ```
  - 【读到】race 之后没有任何"取消 / 中止在途那次 exec"的代码（紧接着是 `catch` 和 `if (hooks.aborted())`，都没有 abort signal 传给 `hooks.exec`）。
  - 【推断】因此那次点击**仍然会在之后落地**（CDP 的 `Input.dispatchMouseEvent` 已经发出去了只是没等到结果）。依据：`Promise.race` 不会取消另一个 Promise（JS 语义），且代码里没有任何取消通道。
  - 同类还有 `apps/desktop/electron/driver.ts:750-782` 的 `CDP_TIMEOUT_MS = 8000`，同样是"不再等结果"而不是"撤销动作"。
- **证据 C —— 回执里还有"假成功"这一档，代码自己承认了**：`apps/desktop/electron/driver.ts:1393-1533` 的 `clickTarget()` 注释写明点击可能"静默失败"但仍返回 `ok: true`；执行层靠 `noChange`（`driver.ts:1962`、返回处 `driver.ts:2073`）表达"点了但页面没动"，再经由 `toolLoop.ts:710` 翻译成给模型的话：「动作执行了，但页面看不出任何变化……多半没点中」。注意：**它假设"页面没动 = 没点中"，但"页面没动"也可能是"点中了、请求正在路上"**。
- **证据 D —— 代码里有两处**主动鼓励模型重试**同一动作**：
  - `apps/desktop/electron/agent.ts:531`：「点了两次页面都没有可见变化……**我再试一次**，不行就停下来问你。」
  - `apps/desktop/electron/agent.ts:588`：「把按钮上的准确文字告诉我，**我再试一次**」
- **现有的保护层（必须说清楚，它挡住了最致命的那一类）**：
  - 服务端 `PAYMENT_TARGET_RE`（`toolLoop.ts:723`）+ `payClickGuard`（`driver.ts:1336-1346`，用 `fieldClass.ts:78` 的 `PAY_ACTION_RE`）—— 命中「立即支付 / 确认支付 / 去支付 / 提交订单 / 确认订单 / pay now / checkout / place order / 付款 / 支付」的按钮，**AI 一律不代点**。
  - **但它的覆盖面是不完整的**【读到】：
    1. `PAYMENT_TARGET_RE` 只在 `click` 分支生效（`toolLoop.ts:776`，位于 `case 'click':` 内部）；`payClickGuard` 也只在 `case 'click':` 里调用（`driver.ts:1933`）。
    2. **`type` 带 `submit: true`（打字后回车提交表单）这条路径只过敏感字段闸**（`driver.ts:1970` `typeSensitiveGuard`），**不过支付闸**。也就是说"在备注框里打完字回车"如果那个回车会触发提交，没有任何守卫。
    3. 词表里**没有**「下单 / 预订 / 发送 / 提交 / 发布 / Send / Submit / Buy now / 确认收货」这类非支付但同样不可逆转的按钮。
    4. `payClickGuard` 的前置是"先找到那个元素"（`driver.ts:1340-1344`）；元素找不到时 `hit` 为 null，守卫直接返回 null（不拦）。
- **合成后的真实损失场景**（【推断】，依据是上面 A+B+D 三条叠加）：
  用户让 AI 在某某网站点「发送」/「提交」/「下单」，页面响应慢 → 20 秒超时 → 回执"失败" → 模型按既有话术再点一次 → **第一次点击其实已经生效** → 消息发两条 / 表单提交两次 / 订单下两个。

### 发现 3（次要，但同样会在界面上骗人）：暂停期间"AI 已停手"是两道独立的门，其中一道在途动作管不住

- 【读到】`pauseOut()`（`agent.ts:361-369`）先调服务端挂起，再本地停手；注释写「挂起失败不拦本地停手：本地已经不动了，最坏结果只是『继续』时新建一轮」。
- 【读到】`resumeAgentLane` 的失败兜底（发现 1）正是这条注释里说的"新建一轮"。
- 也就是说：**"暂停失败"这件事在界面上是静默的**，用户看到的仍然是"已暂停"，但下一次「继续」会把历史丢掉。

| 11 | **页面被换掉了**（`wcId` 对不上） | 无状态变化 | HTTP 409 `page_mismatch`，回执明写「**没有执行任何动作**」（`routes/loop.ts:185-189`） | 不执行 | **否** | — |

### 关于"哪些中断不持久化"的直白回答

**除了 `task_pauses` 表里那几行"谁在什么时候暂停了哪一路"的流水账之外，没有任何中断是持久化的。**

- `task_pauses` 存的是：`loop_id / agent_id / wc_id / goal / paused_by / paused_at / resumed_at / delta_kind` —— **没有一步"做过什么动作"的内容**。
- 它有一个**部分唯一索引** `uniq_task_pauses_open ON task_pauses (loop_id) WHERE resumed_at IS NULL`（`db.ts:240-256` 附近），作用是"同一条循环同时只能有一条未解除的挂起记录"。
- 它的用途（`routes/loop.ts:354-360` 的注释写得很清楚）：**「重启后恢复显示的读口 + 验收取证口」** —— 只用来让界面显示"哪几路是暂停中"，**不用来恢复执行状态**。而且如第 7 行所说，**桌面端根本没去读它**。

## 三、第 2 步 · 逐场景追代码

### 场景 1：用户暂停 → 自己动手做完了 → 点继续

**链路**（按调用顺序）：

1. 主进程收到 `workbench:task:pause`（`main.ts:465-521`）：**先 `read_page` 拿一张基线快照**，再 `POST /agent/loop/pause` 把这张快照一起交给服务端。
2. 服务端 `pauseLoop()`（`toolLoop.ts:509-537`）：status 改 `paused`，把基线快照存进 `s.pause.snapshot`（取 `opts.page ?? s.lastSnapshot`），**messages 不动**。日志会打「已挂起……消息历史保留 N 条、已走 M 步」（`toolLoop.ts:535`）。
3. 服务端挂起期间**绝不调模型**（`toolLoop.ts:195-205` 的文档注释明写）。
4. 桌面端 `runToolLoop` 在下一格的循环头（`agent.ts:371-376`）或拿到决策后（`agent.ts:393-396`）检测到暂停 → `pauseOut()`（`agent.ts:361-369`）→ `finish('paused')`。
   - `paused` 在 `KEEP_ALIVE` 里（`agent.ts:350`）→ **不调用 `stopLoop`**，服务端循环活着。
5. 用户点「继续」→ `resumeAgentLane(wcId, goal)`（`main.ts:565-618`）：
   - `drive({action:'read_page'})` 重读当前真实页面；
   - `POST /agent/loop/resume`（带新快照）；
   - `liveLoops.has(wcId)` 为真就只是 `resumeTask(wcId)`（不开第二辆车，`main.ts:608-612`），否则 `startAgentLoop(..., { resume: true, loopId })` 原地接上。
6. 服务端 `resumeLoop()`（`toolLoop.ts:551-630`）：
   - 算出 `delta = pageDelta(暂停前, 现在)`；
   - `s.pause = null; s.status='running'; s.step = 0`（**步数从头计**）；
   - 往 `s.messages` **追加**一条 user 消息（`toolLoop.ts:601`），内容是 delta 简报 + 当前页简报 + **三条硬规矩**：
     1. 这一步只能调用 `read_page`；
     2. 禁止用 `open_url` 跳回暂停前的地址；
     3. **不重做用户已经手动完成的部分**。

**结论：有风险。**

- **安全的一面**【读到】：恢复是**追加**而不是重建，历史里每一步的回执都还在（"已用真实鼠标点击 XX"），服务端还有三条硬规矩明确禁止重做，delta 也会告诉模型"页面变了 / 没变"。
- **风险的一面**【读到 + 推断】：
  1. 那三条硬规矩是**写在提示词里的软约束**，不是代码层的拦截。模型是否遵守，取决于它自己。
  2. `pageDelta` 的粒度是**整页粗比对**（url / title / buttons / links / inputs / texts，`pageDelta.ts`），它能说"页面变了"，但**说不出"是哪一个具体动作已经做过了"**。如果用户手动完成的正好是那个不可逆转动作（比如他已经自己把订单提交了），delta 只能报 `edited`，模型要靠自己理解"这表示已提交"。
  3. **如果循环已过期（>10 分钟）**，走发现 1 的兜底 → 历史归零 → 这三条硬规矩也不存在了。

**置信度**：【读到】（链路与硬规矩）；"模型会不会照做"是【无法确定】。

### 场景 2：步数上限触发 waiting → 用户说"继续"

**链路**：

1. `toolLoop.ts:997-1012`：`if (session.step >= stepLimit) { session.status = 'waiting'; reason: 'step_budget' }`（上限来自 `env.AGENT_LOOP_MAX_STEPS`，默认 10，允许 8~12，见文件头 `toolLoop.ts:24`）。
2. `waiting` 时不调模型（`toolLoop.ts:195-205`）。
3. 恢复走 `resumeLoop`，其中 **`s.step = 0`**（步数从头计）。

**结论：有风险（较低）。**

- 历史 messages **完整保留**，模型能看到自己已经点过什么、每步的回执是什么 —— 这是它和场景 1 兜底分支最大的区别。
- `s.step = 0` 保证恢复后不会"刚接上就又撞上限"。
- **残留风险**【推断】：`s.step = 0` 意味着这一个循环**可以无限次续杯**——每撞一次上限，用户说一次"继续"，就再获得一整个步数预算。这本身不是重复执行，但它拉长了任务时间，**客观上增加了撞上 10 分钟 TTL 的概率**，从而把任务推进场景 1 的丢历史兜底里。

**置信度**：【读到】。

### 场景 3：点击后页面没反应（网络慢 / 超时）

**链路与证据**（这一节是本次审计的重心，见开头「发现 2」）：

1. 桌面端执行动作 `hooks.exec(action)`，外面套 20 秒 `Promise.race`（`agent.ts:496-509`）；driver 内部每个 CDP 命令还有 8 秒超时（`driver.ts:750-782`）。
2. 两种不同性质的失败**被合并成同一个回执**：
   - **"动作根本没下发"**（元素找不到 → `clickTarget` 返回 `kind:'notfound'` → `driver.ts:1938-1960` 返回 ok:false）—— 这是**确定没执行**。
   - **"动作下发了但没等到结果"**（20 秒 / 8 秒超时）—— 这是**不知道执行没执行**。
   两者在 `toResult()`（`agent.ts:230-239`）里长得一模一样：`{ ok: false, error: '...' }`。
3. 服务端把这条回执翻译成给模型的话（`toolLoop.ts:704-713`）：「工具 click 回执：**失败**……失败原因：……」。**没有任何一个字段标识"这次失败属于哪一种"**。
4. 如果循环在这次失败后又问了一次模型、而桌面没给回执（比如桌面卡死/连接断开），服务端还会追加一句（`toolLoop.ts:979-987`）：「**工具没有被执行**（桌面没有回执）。请重新选下一步。」—— 把不确定性**直接抹掉**。
5. 模型拿到"失败"后可能重试；而代码里有两处**主动鼓励它重试**（`agent.ts:531`、`:588`）。
6. 计数上限：`fails >= 2` 转 ask（`agent.ts:582`），`staleClicks >= 3` 转 ask（`agent.ts:534`）。**在到达上限之前，同一动作最多可能被重发 2~3 次。**

**结论：⚠️ 高优先级 · 有风险（最接近"一定会重复"的一条）。**

精确表述：**当一次点击因为超时（20s / 8s）被判为失败，且那次点击其实已经落在页面上，且目标按钮不在支付守卫词表内时，同一个不可逆转动作会被执行两次。**

现有的兜底（必须如实说明）：
- 支付/收银台最终确认按钮**不管在哪个环节都不代点**（服务端 `toolLoop.ts:776` + 桌面 `driver.ts:1933`，词表见 `fieldClass.ts:78`）。这一条挡住了最贵的那一类。
- 但词表覆盖不全（见发现 2 的「保护层」4 条），且 **`type` + 回车提交这条路径完全没有支付闸**。

**置信度**：【读到】（回执合并、超时不取消、鼓励重试、守卫只在 click 分支）；"第一次点击真的生效了"是【推断】（依据是 `Promise.race` 不取消、代码里无取消通道）；"模型会照着重试"是【无法确定】（模型是非确定性的）。

### 场景 4：客户端崩溃或重启

**链路与证据**：

1. 服务端循环在内存里，靠 TTL 存活 10 分钟（`toolLoop.ts:270/320-328`）。
2. 桌面端的所有驾驶状态都是**模块级 Map**：`lanes`、`liveLoops`（`main.ts:563`）、`pendingGoals`、`resumingWc`（`main.ts:553`）—— 进程一退全没。
3. 桌面端**没有任何代码读 `/agent/loop/pauses`**：我 grep 了整个 `apps/desktop/src/**` 与 `apps/desktop/electron/**`，`loop/pauses` **零命中**。该接口的存在位置只有：`routes/loop.ts:361`（定义）、`packages/shared/src/index.ts`（类型注释）、以及 3 个验收脚本（`scripts/verify/p1-fix-regression.py`、`p1-revert-proof.py`、`pause-resume-tests.py`）。
4. 如果服务端是**应用自己拉起**的，`before-quit` 会调 `stopOwnedServer(...)`（`main.ts:1794-1810`）一起停掉 → 内存里那份循环也没了。
5. 如果服务端是**独立启动**的（`npm run dev:server`），循环会挂在 `running` 状态、没人驱动，直到 10 分钟后被 `sweep()` 回收。服务端自己有诊断口径可以看见这种"孤儿"（`toolLoop.ts:341-351` 的 `runningLoopCount` 注释：「runningLoops=3 但 liveLoops=0」就是挂着没人驱动）。

**结论：不会重复执行，但会丢。**

- 崩溃/重启本身**不会**导致重复执行 —— 因为根本不会恢复。
- **但如果用户重新下同一条指令**，这是一条**全新的循环**、历史为零，等价于发现 1 的情形 → 可能重做已经做过的动作。

**置信度**：【读到】（零命中 grep、`before-quit`、TTL）；"完全没有其它恢复入口"是【推断】（我只 grep 了 `loop/pauses` 这一个关键词，不能排除存在别的机制，比如渲染层用 localStorage 记忆 —— 但我没有看到任何相关代码）。

### 场景 5：工具调用报错

分三种，结论不同：

| 子情形 | 谁报的 | 动作下发了吗 | 会不会重复执行 | 证据 |
|---|---|---|---|---|
| 5a. 服务端安全闸拦下（`payment_confirm` / `sensitive` / 非法参数） | 服务端 `sanitizeToolCall`（`toolLoop.ts:749-782`） | **没有** | **不会** | `toolLoop.ts:1055`「本机拒绝执行：……」直接换成一句提问塞回模型 |

**置信度**：【读到】。

### 场景 6：AI 主动求助（验证码等）→ 用户处理完 → 点继续

**链路**：

1. 服务端 `sanitizeToolCall` 命中敏感字段 → **在动作下发之前**就换成一句提问（`toolLoop.ts:785-782` 区域 + `1055`）。**动作根本没有被下发过。**
2. 桌面收到 `ask` 决策 → `agent.ts:424-446` → `finish('ask_user')`。`ask_user` 在 `KEEP_ALIVE` 里（`agent.ts:350`）→ 不 stopLoop，服务端 status 保持 `waiting`，历史完整。
3. 用户处理完，两条恢复路：

**置信度**：【读到】。

## 四、第 3 步 · 五个是/否问题

### 问题 1：有没有"这一步到底执行了没有"的记录？

**答：没有。既没有持久化的执行台账，也没有内存里的"已执行"概念。**

我看到的全部相关记录只有三类，没有一类能回答"这一步到底落地了没"：

1. **服务端内存里的 `session.messages`**（`toolLoop.ts:217`）—— 里面有 assistant 的 tool_call（**打算做什么**）和桌面的 tool 回执（**据桌面说做了什么**）。区分"AI 说要做"和"实际做了"的唯一凭据就是那一条桌面回执，而回执的可信度正是场景 3 的漏洞（超时 / 假成功）。
2. **`session.pendingCallId`**（`toolLoop.ts:1060-1095` 设置）—— 它表示的是"**已下发、待回执**"，是一个**中间态**，不是"已执行"。而且它在回执缺失时被解释成"没执行"（`toolLoop.ts:979-987`）。
3. **数据库 `task_pauses`**（`db.ts:240-256`）—— 只有暂停/解挂的元数据，**没有任何一步动作的内容**。

另外，**`toolLoop.ts` 这个文件里一次数据库调用都没有**（我 grep 了 `pool` / `INSERT INTO` / `persist`，零命中）。文件头 `toolLoop.ts:192-193` 自己写明：「会话状态（在内存里；**进程重启即丢**——本步明确不做『重启恢复』）」。

结论：**不存在"已执行"这个数据**。回执只有 `ok / detail / error / noChange / refused / userAnswer` 几个字段（`routes/loop.ts:191-202`），其中没有任何一个表示"这一下已经不可撤销地落到页面上了"。

**置信度**：【读到】。

### 问题 2：恢复时，已经执行过的动作会不会被重放？

**答：分情况，三种。**

| 情形 | 会不会重放 | 证据 |
|---|---|---|
| **正常解挂**（循环还在内存里） | **不会自动重放** —— 恢复是往 `messages` **追加**一条 user 消息（`toolLoop.ts:601`），不是重建；且追加的三条硬规矩里第 3 条明写「不重做用户已经手动完成的部分」 | `toolLoop.ts:551-630` |
| **解挂失败 / 循环已过期** | **会（从零重跑整个目标）** —— `main.ts:586-592` 删掉 lane、不带 loopId 地 `startAgentLoop` → 服务端新建循环、messages 归零 | `main.ts:586-592` + `routes/loop.ts:323-329` + `toolLoop.ts:320-335` |
| **回执缺失（pendingCallId 无回执）** | **会被当成没执行、从而可能重做** —— `toolLoop.ts:983` 原文「工具没有被执行（桌面没有回执）。请重新选下一步。」 | `toolLoop.ts:979-987` |

需要说明的一点【读到】：第一种情形里"不重放"是靠**提示词**保证的，不是靠代码拦截。服务端并没有一个"已执行动作清单"可以在下发前比对，也没有任何一处代码在下发 click/type 之前检查"这个动作刚才是不是已经做过"。

**置信度**：【读到】（三种分支的代码都在）；"模型在第一种情形下是否真的不重做"是【无法确定】。

---

### 问题 3：有没有任何地方会自动重试工具调用？在哪一层？重试前有没有检查"这一步是否已经执行过"？重试几次？

**答：没有代码层的自动重试；重试是模型自己决定的，而代码里有两处在"鼓励"它重试。重试前没有任何"是否已执行"的检查（因为问题 1 已经说了：压根没有这个数据）。次数上限是 2~3 次。**

**"没有自动重试"的证据**：我在 `apps/**` 下 grep 了 `retry|重试|reattempt|retryCount|maxRetries`，命中的只有这些，**没有一条是工具调用重试**：

- `apps/server/src/index.ts:101-156` —— 数据库**建表**的重试（每 3 秒一次、最多 40 次 ≈ 2 分钟）。
- `apps/server/src/routes/auth.ts:243/285/390` —— 短信发送限流、建号碰撞的**给用户看的话术**。
- `apps/desktop/electron/driver.ts:1413` —— **注释**，原文是「……给出『原因 + 一个下一步』，而不是无限重试」。
- `apps/desktop/src/browser/useBrowserWorkspace.ts:410` —— webview 还没 dom-ready 时重试拿句柄，与工具调用无关。
- `apps/server/src/llm.ts:10`、`search/tavily.ts:20` —— 文件头里"明确不做重试风暴"的声明。

**重试实际发生的方式与上限**：

| 触发 | 计数 | 上限 | 到上限后的动作 | 证据 |
|---|---|---|---|---|
| 动作失败 `res.ok === false` | `fails` | `FAILS_BEFORE_ASK = 2`（`agent.ts:121-134`） | 转 ask「连续失败两次」，`finish('stuck')` | `agent.ts:581-596` |
| 动作成功但页面没变化 `res.noChange` | `staleClicks` | `STALE_BEFORE_ASK = 3` | 转 ask「连点三次页面无变化」 | `agent.ts:523-548` |
| 成功后 | 两个计数**都清零** | — | — | `agent.ts:552-553` |

**代码里主动鼓励重试的两句话**：

- `agent.ts:531`：「点了两次页面都没有可见变化：…… **我再试一次**，不行就停下来问你。」
- `agent.ts:588`：「① 把按钮上的准确文字告诉我，**我再试一次**；② 你自己在卡片里点一下，然后点『继续』……」

**重试前的检查**：**没有**。我能找到的、动作下发前的检查只有三类，**都不是"这一步是否已经执行过"**：

1. 安全闸：`PAYMENT_TARGET_RE` / `SENSITIVE_TARGET_RE` / `payClickGuard` / `typeSensitiveGuard`；
2. 归属闸：`wcId` 不匹配 → 409（`routes/loop.ts:185-189`）、并发 → 409 `LoopBusyError`（`toolLoop.ts:887-903`）；
3. 暂停闸：`pausedOf(wcId) && PAUSED_BLOCKED.has(actionName)`（`driver.ts:1908-1918`）。

**置信度**：【读到】。

### 问题 4：页面快照是 unknown 的时候，是当成"没做过"还是"做过"？

**答：两种都有，而且方向是相反的 —— 快照 unknown 时是"不假设、看当前页"（这个是对的），但回执缺失时被当成"没执行"（这个是危险的）。**

- **`pageDelta` 判成 `unknown` 时**（`pageDelta.ts`）：它的 brief 原文是「没有我上次看到时的页面快照可以比对（这一路在此之前还没读过页）。请直接根据**当前**页面判断下一步，**不要假设它和之前一样**。」
  - 这是**恰当的中立处理**：既不假设"做过"也不假设"没做过"，让模型看当前真实页面决定。**但它的潜台词仍然是"你可以继续往下做"**，而不是"你不确定、先去核实/问用户"。
- **回执缺失时**（`toolLoop.ts:979-987`）：明确当成**"没执行"** —— 「工具没有被执行（桌面没有回执）。请重新选下一步。」这就是把 `TOOL_OUTCOME_UNKNOWN`（不知道执行没执行）**降级**成了 `TOOL_NOT_STARTED`（确定没执行）。
- 另外 `routes/loop.ts:315-316` 的注释也确认了 unknown 是被容忍的正常路径：「不带（page）也能继续，但 delta 会如实判成 unknown」。

**结论：快照 unknown 的处理是"中立偏继续"；回执缺失的处理是"当成没执行"。两种情况都不会触发"停下来核实/问用户"这一档。**

**置信度**：【读到】。

### 问题 5：客户端崩溃或重启后，正在跑的任务会怎样？

**答：不会恢复，静默消失。服务端那份最多再活 10 分钟（如果服务端自己还活着的话），然后被回收。**

逐条证据：

1. 服务端循环只在内存（`toolLoop.ts:312` `const loops = new Map()`），TTL 10 分钟（`toolLoop.ts:270`），`sweep()` 到点就删（`toolLoop.ts:320-328`）。
2. 桌面端**没有恢复入口** —— `apps/desktop/src/**` 与 `apps/desktop/electron/**` 里 `loop/pauses` **零命中**（grep 结果：只有服务端定义、shared 类型、3 个验收脚本）。服务端那个接口的注释写的是「重启后恢复**显示**的读口」（`routes/loop.ts:354-360`）—— 关键词是"显示"，不是"恢复执行"。
3. 若服务端由应用自己拉起，`before-quit` → `stopOwnedServer(...)`（`main.ts:1794-1810`）会把它一起停掉，内存那份也没了。
4. 服务端自己留了诊断口径能看见"孤儿循环"（`toolLoop.ts:341-351` 注释：「runningLoops=3 但 liveLoops=0」= 挂着没人驱动），但**没有任何代码去处理它们**，只是等 TTL 回收。
5. DB 里那条 `task_pauses` 记录的 `resumed_at` 会一直是 NULL —— 它变成了**一条永久开放的取证痕迹**，不会被自动闭合。

**因此：崩溃/重启不会导致重复执行（因为根本不恢复），但会导致任务丢失 + 一条永久未闭合的暂停记录。真正的重复风险来自"用户重新下同一条指令"（等价于发现 1 的全新循环）。**

**置信度**：【读到】（第 1~4 条）；"完全没有其它恢复入口"是【推断】（我只 grep 了 `loop/pauses` 这一个关键词）。

## 五、「无法确定」清单

以下这些地方我读不出来，写下我看到了什么，不做猜测。

1. **模型在实际运行中到底会不会重发同一个 click**

   - 为什么无法确定：模型是非确定性的，同一句话这次可能重试、下次可能不重试。**这需要真机跑多轮统计，不能从代码里读出来。**

2. **超时时那一次点击是否真的会落地**
   - 我看到了什么：`agent.ts:496-512` 用 `Promise.race` 做超时，race 之后**没有任何取消在途 exec 的代码**；`driver.ts:750-782` 的 CDP 超时也只是 reject，不撤销。
   - 为什么无法确定：我没有实测过"20 秒超时后那次点击是否真的生效"。这需要在真机上注入一个人为卡慢的页面来验证。**我的【推断】是"会落地"，依据是 JS 的 `Promise.race` 不取消另一个 Promise，但这不是直接读到的。**

3. **崩溃/重启后是否真的完全没有其它恢复入口**

   - 为什么无法确定：我只 grep 了 `loop/pauses` 这一个关键词，且没有逐行通读 `main.ts` 的全部启动路径。不能排除渲染层用别的方式（localStorage 等）记忆过任务。

## 六、一句话总结

**我们现在没有「确定没执行 → 可以重试 / 不知道执行没执行 → 禁止自动重试」这个区分。** 代码里只有一种失败回执，回执缺失被一律解释为"没执行"，超时不取消在途动作，重试由模型自己决定且有两处话术在鼓励它重试。最严重的两条真实损失路径是：**（1）挂起超过 10 分钟后点「继续」→ 历史归零、从头重跑；（2）点击超时被判失败 → 那一下很可能已经生效 → 模型再点一次。** 现有最强的保护是支付/收银台最终确认按钮一律不代点，但它只覆盖 `click` 分支、词表不含"发送/提交/发布/下单"这类非支付的不可逆转动作，且 `type` + 回车提交这条路径完全没有守卫。
