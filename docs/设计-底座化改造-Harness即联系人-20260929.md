## 1. 需求确认（用户原话 → 精确化）

| 用户原话 | 精确化后的需求 |
|---|---|
| 「我们平台是一个大底座，提供这些 harness 技能技术的工具和环境」 | 平台提供**统一的 agent 运行时 + 工具环境 + 授权边界**，业务逻辑不写死在底座里 |
| 「创建的每一个对应的联系人就拥有对应的 harness，像把应用装进我们里面」 | **联系人 = 人设 + 一组 harness 绑定 + 工具权限 + MCP 授权**。装一个新 harness 不改底座代码，只加配置 |
| 「需要编码 harness……比如设计了一个前端界面，那就直接接对应的开发智能体，那这个智能体背后就是这些 harness 去执行，然后终端验收」 | 场景：**设计稿 → 委派给「开发」联系人 → 编码 harness + 终端 harness 执行 → 结构化回报 → 发起方续跑/验收** |
| 「终端这些我们也最好需要，根据需求场景去配置这个基础的」 | 新增**终端 harness**；harness 组合按场景配置，不是全局一套 |
| 「核心是被委派」 | **委派是一等公民**，不是附属功能。委派必须能传递 harness 能力 |
| 「之后接入像一些其他的 MCP 能够被智能体读取去执行」 | MCP 授权粒度从 **user 级下沉到联系人级** |

### 1.1 这条需求最重要的隐含条件

用户说「**核心是被委派**」。而当前代码里，**被委派的子循环恰恰是什么都干不了的那一类**：

`toolLoop.ts:329-333` 原话：

> 被委派的子循环：`SUB_AGENT_TOOL_NAMES`（web_search/spawn_workers/delegate/stop）——**没有手**，
> 工具表里根本没有 open_url/click/type，它想开页也开不了（提示词里也明说了）。
> **将来做「桌面手」只需要给子循环分配 wcId + 换这张表，其余部分不用动。**

**所以本设计的头号任务，就是把"被委派方没有能力"这个现状，改造成"被委派方拥有自己配置的 harness 能力"。** 原作者已预留扩展点，这是改造而非重写的关键依据。

## 2. 目标架构

```
╔═══════════════════════════════════════════════════════════════════╗
║  L4  工具与技能生态                                                 ║
║      MCP 网关（已有，需下沉到联系人级授权）· 爬虫/取数 · 连接器        ╠
╠═══════════════════════════════════════════════════════════════════╣
║  L3  Harness 实现层（可插拔）                                        ║
║      ├─ 浏览器 harness   自研（已有，差异化资产，保留）              ║
║      ├─ 编码 harness     接 Codex app-server（Apache 2.0）          ║
║      ├─ 终端 harness     ★ 新建                                       ║
║      ├─ 电脑操作 harness 参考 Anthropic Computer Use（为物理设备打底） ║
║      └─ 记忆 harness     接 Mem0 / Hindsight（Apache 2.0）           ╠
╠═══════════════════════════════════════════════════════════════════╣
║  L2  ★ Harness 抽象层（本设计核心新建）                              ║
║      统一协议 Item / Turn / Thread · Harness 注册表 · 能力协商        ╠
╠═══════════════════════════════════════════════════════════════════╣
║  L1  底座（已有，**一个字不动**）                                     ║
║      三层架构（渲染层/主进程/服务端）· 本地服务端 · Electron · 加密    ╚
╚═══════════════════════════════════════════════════════════════════╝

联系人层（横切）：每个联系人 = 人设 + harness 绑定 + 工具权限 + MCP 授权
委派层（横切）：A 判断需要什么能力 → 委派给拥有该 harness 的联系人 → 结构化回报
```

### 2.1 为什么 L1 不动

**已商业验证。** Z.ai 的 ZCode（`zai-org/ZCode`）仓库结构与本仓库几乎同构：`packages/desktop`(Electron Main/Host/Renderer) / `packages/server`(HTTP/WS) / `packages/shared+rpc+client` / `packages/provider` / `apps/zcode-cli`(Agent CLI/TUI/运行时)。三层分层 + 本地服务端 + 共享协议是成熟形态，不是待修正的缺陷。

### 2.2 为什么 L2 必须新建

当前"能力"是硬编码在工具表里的：

| 循环类型 | 工具表 | 出处 |
|---|---|---|
| 桌面手循环 | `LOOP_TOOL_NAMES`（open_url/read_page/click/type/scroll/stop） | `toolLoop.ts:129` |
| 被委派子循环 | `SUB_AGENT_TOOL_NAMES`（web_search/spawn_workers/delegate/stop） | `toolLoop.ts:329` |

**两张表都是编译期常量。** 加一种能力 = 改代码 + 改 181 条对照断言。这与"装应用"的目标直接冲突。

## 3. L2 Harness 抽象层设计

### 3.1 协议原语（参照 Codex app-server，JSON-RPC over stdio/loopback）

OpenAI 的 Codex Harness 已 Apache 2.0 开源，其 app-server 协议只有三个原语，被 CLI/Web/VS Code/macOS 四个前端共用。我们采用同构设计：

| 原语 | 定义 | 映射到现有概念 |
|---|---|---|
| **Thread** | 一个持久会话容器，可 create/resume/fork/archive | 一个**联系人**的运行时实例 |
| **Turn** | 一个工作单元，从提交到产出 | 现有的一条 `loop` |
| **Item** | 一次原子 I/O，带生命周期（pending → running → done/failed） | 现有的一步 tool call + `LoopToolResult` |

**Thread 是关键**：它让"联系人"从"数据库里的一行人设"变成"一个有状态、可恢复、可被委派的运行时"。这正是原作者 `checkpoint.ts`（目标+消息加密存档）想解决但没完全解决的问题。

### 3.2 Harness 接口（要新建的注册表）

```ts
// 概念定义，非最终代码
interface Harness {
  id: string;                      // 'browser' | 'code' | 'shell' | 'computer' | 'memory'
  provides: Capability[];          // 它能干什么：['open_url','click',...] / ['run_command',...]
  requires: Environment;           // 它需要什么环境：wcId? / workdir? / sandbox?
  risk: RiskClass;                 // 'read_only' | 'write_local' | 'write_remote' | 'irreversible'

  start(thread: Thread): Promise<Handle>;     // 开工（分配 wcId / worktree / 终端会话）
  step(handle: Handle, item: Item): Promise<ItemResult>;  // 执行一步
  stop(handle: Handle): Promise<void>;        // 收尾（归还浏览器 / 关终端 / 清沙箱）
}
```

**这张表取代现在的两张硬编码工具表。** 循环启动时按"这个联系人绑定了哪些 harness"动态组装可用工具，而不是编译期决定。

### 3.3 能力协商（委派时用得上）

A 委派给 B 时，A 需要知道 B 有没有能力接这活。当前是盲派（派了才知道对方只有嘴）。改造后：

```
A: delegate(to=B, task="把这份设计稿实现成页面")
   → 查 B 的 harness 绑定：{ code: ✓, shell: ✓ }
   → 需要的能力：{ code: ✓, shell: ✓ }
   → 匹配，派活
   → 若 B 只有 { browser }，当场回「B 不会写代码，这活得给 C」而不是派出去再失败
```

## 4. 联系人 = 配置（数据模型变更）

### 4.1 现状（实测）

`agents` 表基础列只有 `id / project_id / name / kind / created_at`，后续能力全靠 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 追加（`db.ts:225-291`）：`persona JSONB`、`persona_status`、`can_create_agents`、`computer_visibility`。

**没有 harness 字段，没有工具权限字段。**

MCP 授权是 **user 级**：`mcp_servers WHERE user_id = $1`（`routes/mcp.ts:83-91`）——同一个用户下所有联系人共用一套 MCP。

### 4.2 要加的（沿用现有 schema 演进方式，不引入 migrations 目录）

```sql
-- ① Harness 注册表（底座级，不是每用户一份）
CREATE TABLE IF NOT EXISTS harness_registry (
  id           TEXT PRIMARY KEY,           -- 'browser' | 'code' | 'shell' ...
  version      TEXT NOT NULL,
  provides     JSONB NOT NULL,             -- 能力清单
  requires     JSONB NOT NULL,             -- 环境需求
  risk         TEXT NOT NULL,              -- read_only|write_local|write_remote|irreversible
  builtin      BOOLEAN NOT NULL DEFAULT true,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ② 联系人 ↔ Harness 绑定（多对多）
CREATE TABLE IF NOT EXISTS agent_harnesses (
  agent_id     BIGINT NOT NULL REFERENCES agents(id) ON DELETE CASCADE,
  harness_id   TEXT NOT NULL REFERENCES harness_registry(id),
  config       JSONB NOT NULL DEFAULT '{}', -- 该联系人对这个 harness 的专属配置
  granted_by   BIGINT REFERENCES users(id),  -- 谁授权的（审计）
  granted_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (agent_id, harness_id)
);

-- ③ 联系人 ↔ MCP 授权（把 user 级下沉到联系人级，user 级保留作默认）
CREATE TABLE IF NOT EXISTS agent_mcp_grants (
  agent_id     BIGINT NOT NULL REFERENCES agents(id) ON DELETE CASCADE,
  server_id    BIGINT NOT NULL REFERENCES mcp_servers(id) ON DELETE CASCADE,
  tool_allow   JSONB,                       -- null = 全允许；否则白名单
  granted_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (agent_id, server_id)
);

-- ④ 委派时的能力快照（审计 + 复现用）
ALTER TABLE agent_delegations ADD COLUMN IF NOT EXISTS harness_snapshot JSONB;
```

**为什么要 `harness_snapshot`**：委派发生时把 B 的能力固化下来。将来 B 的配置改了，历史委派仍然可复现、可审计。这与 `handoff.ts` 的"交接文件结构化"是同一思路。

### 4.3 schema 演进纪律（必须遵守）

现有机制是「基础 `CREATE TABLE IF NOT EXISTS` + 下方幂等 `ALTER TABLE ADD COLUMN IF NOT EXISTS`」，**没有 migrations 目录**。新增必须沿用这个方式，并且同步更新 `scripts/verify/2a-migrate-replay.mjs` 的旧 DDL 提取断言——否则那条反证会红。

## 5. 委派机制改造（本设计的核心）

### 5.1 现状（实测，可用）

| 能力 | 状态 |
|---|---|
| A→B 联系人间委派 | ✅ `delegation.ts`，`fromAgentId → toAgentId` |
| 结构化交接文件（目标/输入/产出要求/审批边界） | ✅ `handoff.ts`，注释明写"依据 Grok Bot 实战结论" |
| 共享看板 + 落库行锁（跨进程、kill -9 不丢） | ✅ `board_locks` + PG `SELECT … FOR UPDATE` + rename 原子替换 |
| 委派消息只传路径不传内容 | ✅ |
| park-and-resume（派出即返回，不等） | ✅ 10 分钟期限 |
| 一队工人并发（最多 5、并发 3、单工人 ≤60s、整队预算、allSettled） | ✅ `workers.ts` |
| 全局闸（maxLiveJobs / subLoopMaxLive，超限回人话） | ✅ `registry.ts:169`、`tools.ts:176-180` |
| **被委派方拥有 harness 能力** | ❌ **`wcId=null`、工具表没有浏览器工具** |

### 5.2 改造点（四件，都在预留扩展点上）

| # | 改什么 | 文件 | 性质 |
|---|---|---|---|
| 1 | **给子循环分配 harness**：`delegation.ts:306` 的 `toolNames: [...SUB_AGENT_TOOL_NAMES]` → 按 `agent_harnesses` 动态组装；`wcId: null` → 按需分配 | `delegation.ts`、`toolLoop.ts` | 开开关 |
| 2 | **登录态按联系人不按项目**：`view-host.ts:70-80` 的分区命名 `persist:workbench-browser-project-<projectId>` → 增加 agent 维度 | `view-host.ts`、`main.ts:1063` | 加规则 |
| 3 | **联系人 ↔ 固定浏览器页绑定表**：让"小美有她自己那一页"成为事实，而不是临时抓空页 | 新建 | 加表 |
| 4 | **淘汰留痕**：`toolLoop.ts:480-488` 的 `sweep()` 静默 `loops.delete()` → 补日志 + `/health` 计数 | `toolLoop.ts` | 补观测 |

**关于 #1 的安全边界（必须一起做）**：原作者不给子循环发手，理由是"被 `/next` 找到反而是漏洞（客户端能驱动一条不属于它的循环）"。所以发手的同时**必须**加一道"这条循环能且只能动它绑定的那个 wcId"的校验，否则是把一个已堵住的洞重新挖开。

### 5.3 委派时序（改造后）

```
A 的 Thread（harness: browser）
  │  Turn 开始
  ├─ Item: read_page            → 拿到设计稿/需求
  ├─ Item: delegate(to=B, task) 
  │     ├─ 能力协商：B 有 { code, shell }？✓
  │     ├─ 固化 harness_snapshot
  │     ├─ B 的 Thread 启动（分配 worktree + 终端会话）
  │     └─ A 的循环 park 成 waiting_job，浏览器交还用户
  │
  B 的 Thread（harness: code + shell）
  │    ├─ Item: run_command(npm install)
  │    ├─ Item: edit_file(...)          ← 敏感，可能触发审批
  │    ├─ Item: run_command(npm test)
  │    └─ Item: stop(reason=done) + 结构化回报（diff 摘要 + 测试结果 + 文件路径）
  │
  A 的循环 resume ← 结果回来
  ├─ Item: 终端验收（人话汇报"做完了，3 个文件改动，测试全过"）
  └─ Item: stop(reason=need_user)  ← 要人确认
```

## 6. 权限与安全模型（最容易被跳过、出事最贵的一块）

### 6.1 三层授权，不可互相借用

| 层 | 现在 | 改造后 |
|---|---|---|
| 用户 | JWT（主进程内存持有，不落盘） | 不变 |
| 联系人 | **无独立权限**，继承用户 | `agent_harnesses` + `agent_mcp_grants`，**显式授权** |
| Harness 动作 | 本地两道闸（payClickGuard / typeSensitiveGuard） | 保留 + 按 harness `risk` 分级 |

**铁律：A 委派给 B，B 用 B 自己的权限，绝不继承 A 的。** 否则"小美能碰支付"会通过委派链传染给所有联系人。

### 6.2 按 risk 分级的确认要求

| Harness risk | 例子 | 确认要求 |
|---|---|---|
| `read_only` | read_page / 搜索 / 读文件 | 不问，直接做 |
| `write_local` | 改文件 / 跑构建 / 写数据库 | 可配：默认不问，高风险命令进黑名单 |
| `write_remote` | git push / 发消息 / 调外部 API | **必须人确认** |
| `irreversible` | 删除 / 下单 / 部署 | **必须人确认，且不可被委派方代确认** |

### 6.3 终端 harness 的命令分级（新建，最危险）

终端是全新能力，当前仓库**零 shell 执行代码**（实测：`apps/server/src` 无 `child_process`/`execSync`/`spawn`）。必须：

- 每联系人一个**独立工作目录**（`data/workdirs/<agentId>/`），默认逃不出去
- 命令三级：白名单直接放行 / 黑名单（`rm -rf`、`git push --force`、`curl | bash`、`dd`、`mkfs`）一律拦截 / 其余进人确认
- 超时 + 输出截断（防 `yes` / 无限输出）
- 全程落审计日志（命令 + 退出码 + 截断后的输出），**这是将来唯一能查"它到底干了什么"的东西**

## 7. 各 Harness 接入方案

| Harness | 方案 | 成本 | 风险 / 取舍 |
|---|---|---|---|
| **浏览器** | **保留自研**。借 Playwright 两样：auto-wait 机制、`@playwright/cli`（比 MCP 省 4× token）[3](https://unbrowse.ai/blog/best-open-source-browser-automation-2026) | 低 | 无。这是差异化资产，别扔 |
| **编码** | 接 **Codex app-server**（`openai/codex`，Apache 2.0）。三种接入：`codex exec`（有界任务）/ Codex SDK（TS+Python）/ app-server（JSON-RPC 持久 Thread）[1](https://www.swequiz.com/articles/openai-codex-architecture)[2](https://floatboat.ai/blog/codex-harness-open-source) | 中 | Rust 二进制 → 打包体积 +100MB 级；产品稳定性开始依赖 OpenAI 发布节奏 |
| **终端** | **自建**（无合适现成物可"装上"） | 中 | 安全事故面最大，§6.3 的分级是前置条件不是可选项 |
| **电脑操作** | 参考 **Anthropic Computer Use Demo** 的截图+动作接口[6](https://github.com/ai-boost/awesome-harness-engineering) | 中 | 为将来的物理设备打底，本期可不做 |
| **记忆** | 接 **Mem0 或 Hindsight**（均 Apache 2.0） | 中 | ⚠️ **别用 Zep/Graphiti**：要额外运维图数据库（Neo4j/FalkorDB），且 Zep 社区版已废弃[4](https://hindsight.vectorize.io/blog/2026/08/11/open-source-agent-memory-systems)[5](https://www.developersdigest.tech/blog/best-ai-agent-memory-providers-2026) |
| **MCP** | 已有桥（ADR-0007：仅 Streamable HTTP、按用户鉴权、HTTPS-only、不跟随重定向、≤8 服务/≤40 工具）[7](https://github.com/openai/codex/discussions/29756) | 低 | 授权粒度下沉到联系人级即可，协议不用改 |
| **爬虫/取数** | 参考 **Unbrowse** 思路：发现网站内部 API 直接调，比 DOM 快 3.6×[3](https://unbrowse.ai/blog/best-open-source-browser-automation-2026) | 中 | 适合"读数据"场景，与浏览器 harness 互补 |

### 7.1 记忆层的 honest 对比（这是你现在最弱的一环）

| 方案 | LongMemEval | 自托管成本 |
|---|---|---|
| 现在的字面匹配（中文 bigram + Jaccard，阈值 0.25） | 无公开对标，明显低于专用系统 | 零（已在 Postgres） |
| Mem0 | 49.0% | 一个向量库 |
| Zep/Graphiti | 63.8% | 图数据库 + 50–150ms 读延迟 |
| 无记忆基线 | 20–30% | — |

**该优化，但别用 Zep 换那 14.8 分**——代价是永久多运维一个图数据库。Mem0/Hindsight 是合理中点。

## 8. 分阶段实施

> 每阶段有出口判据，未达不准开下一阶段。

### P0 · 先稳住（前置，不可跳过）

| 做 | 为什么 |
|---|---|
| CI 跑 41 步 verify 链 | 后面所有改造的安全网。现在只有打包会自动跑 |
| 修 `verify:loop:kill9`（PGlite 存储层红） | 地基有裂缝 |
| 堵 `/auth/login/xyz` 无限流 + CORS allowlist + Host 白名单 | 真安全风险 |
| 拆 `App.tsx`（3,162 行） | 后续所有功能都在这一个文件里冲突 |
| 清治理项（17 个被跟踪的构建产物、13 个孤儿脚本、5 处死代码） | 减少改造噪音 |

**出口判据**：CI 绿 · kill9 绿 · 4 条安全断言过 · App.tsx < 1,500 行。

### P1 · Harness 抽象层（本设计的地基）

建 `harness_registry` + `agent_harnesses`，把 `toolLoop.ts` 的两张硬编码工具表改成动态组装。**先把已有的浏览器 harness 装进新框架跑通**，再接新的。

**出口判据**：不写一行新 harness 代码，仅靠改 `agent_harnesses` 配置，就能让一个联系人"有手"、另一个"没手"。

### P2 · 委派传递能力 + 独立身份

§5.2 的四件事。这是"核心是被委派"的落地。

**出口判据**：界面上能同时看到「小美操作淘宝、阿开发在终端跑测试」；派给阿开发的活它真能自己执行。

### P3 · 接编码 + 终端 harness

按场景配置（用户原话：「根据需求变成的需求需要哪些场景就去配置这个基础的」）。建议第一批场景：

| 场景 | 联系人 | harness 组合 |
|---|---|---|
| 前端开发 | 阿开发 | code + shell + 浏览器（看效果） |
| 数据抓取 | 小采 | 浏览器 + 爬虫 MCP（只读） |
| 运营监控 | 小美 | 浏览器 + 连接器 MCP（只读） |

**出口判据**：「设计稿 → 委派阿开发 → 终端跑测试 → 结构化回报 → 人验收」整条链跑通一次。

### P4 · 记忆 + MCP 下沉 + 生态

Mem0/Hindsight 接入；`agent_mcp_grants` 落地；电脑操作 harness（物理设备前置）。

## 9. 风险与取舍（必须让决策者看到）

| 风险 | 严重度 | 缓解 |
|---|---|---|
| 接 Codex 后产品稳定性依赖 OpenAI 发布节奏 | 高 | 版本锁定 + 抽象层隔离，坏了能退回自研编码 harness |
| Rust 二进制让安装包 +100MB | 中 | 做成可选组件，用户不用编码 harness 就不装 |
| 终端 harness 出事（删文件、泄露） | **极高** | §6.3 的命令分级是前置条件；工作目录隔离；全程审计 |
| 委派链权限传染 | 高 | §6.1 铁律：B 只用 B 的权限 |
| 一次改太多层 | 高 | P0–P4 顺序执行，每阶段出口判据不过不开下一阶段 |
| 记忆换 Mem0 后检索质量未必更好 | 中 | 先离线评测（用现有 20 题框架加记忆组），再切 |

## 10. 需拍板（8 项）

1. **编码 harness 现在就要，还是 P3 再说？** （影响打包体积和一份外部依赖的引入时机）
2. **终端 harness 的工作目录隔离强度**：软隔离（约定路径）还是硬隔离（沙箱）？硬隔离更安全但工程量大。
3. **`write_local` 类动作默认要不要人确认？** （改文件/跑构建）——这直接决定"委派一次要问几次"。
4. **物理设备是哪一类？**（智能家居 / 机械臂 / 你的手机 / 工业仪器）——决定电脑操作 harness 方向，也决定"物理确认硬件"要不要提前立项。
5. **记忆层切 Mem0 的时机**：先离线评测再切，还是直接切？
6. **MCP 授权下沉后，user 级默认授权还保留吗？**（保留 = 方便但松；不保留 = 安全但每个联系人都要逐次授权）
7. **第一批上线哪三个场景？**（§P3 那张表只是我的建议）
8. **接 Codex 的版本锁定策略**：锁 minor 还是锁 exact？
