## 1. 用户的三条要求，逐条对应到代码与断言

### 要求 1「临时工并行」

一个智能体派 N 个并行临时工，临时工**没有身份、没有记忆**，只交结构化数据，然后销毁。

- `orchestrator/workers.ts` `runWorkerPool` —— 并发 `WORKER_CONCURRENCY=3`，单次 ≤5 个，单个 120s / 整批 180s
- 每个临时工一段全新 messages + 独立 `AbortController`；跑完 job 从表里删掉（`orc-park.mts` 断言 `liveJobCount()===0`）
- 汇报强制 JSON（`toolChoice:'none'`），`parseReport` 会**丢掉不是真搜索返回过的来源网址** —— 防编造链接
- 断言：`orc-workers.mts` 14 条（含并发峰值实测、挂死单被掐、HTTP 500 降级、敏感 query 不外发）

### 要求 2「智能体间委派」+ 内部频道可查

同项目智能体互为同事，任何智能体可委派另一个；交流存在按对（A↔B）的**内部频道**里。

- `orchestrator/delegation.ts` `executeDelegate`；频道 = `UNIQUE(user_id, agent_a_id, agent_b_id)` 且 `a<b` 归一化，所以 A→B 与 B→A 落在**同一条**双向频道
- 正文 `content_enc` 密文（与 `messages` 表同一套 AES-256-GCM）；`payload` 是明文 JSONB，所以进它之前必须过 `sanitizePayload()` 白名单
- 过程可见：`task` → `progress`（第几步、干了什么）→ `reply`；被拒时留 `system` 痕
- 只读接口 `GET /agents/channels`、`/agents/channels/:id/messages`、`/agents/channels/:id/delegations`
- **界面**：`apps/desktop/src/channels/`（顶栏「🗂 内部频道」开关 + 左列表右对话），只读
- 断言：`orc-delegate.mts` 15 条、`orc-routes.mts` 18 条（含「库里是密文、接口回明文」、「别人的频道一律 404 不是 403」）、`orc-channels-ui.mts` 11 条（jsdom 渲染真组件）

界面这块的两条硬约束（都是安全约束，不是风格偏好）：

1. **只读到底**。面板里没有任何输入框、没有写操作按钮 —— 服务端那边也只有 GET，
   前后端一致，不是一边拦一边放。断言直接查 DOM：`input, textarea, select, [contenteditable]` 必须为 0 个。
2. **超时那条要显眼**。委派 `timeout` 时界面染底色 + 红字写出原因（「超过 10 分钟未完成」）。
   这是要求 3(b)「不假装完成」在界面上的落点 —— 后端如实说了，界面也不能把它画成「已完成」。

### 要求 3「安全：不死循环 + 10 分钟熔断」

**(a) 不死循环**：正在等自己委派结果的智能体，不能被拉去接新委派。

- `isAgentWaiting(target)` → 当场拒 `agent_busy_waiting`（A 等 B、B 又委派 A 的死结就是这条挡住的）
- `agentBusyCount(target) >= 1` → 拒 `agent_busy`（v1 不排队，已确认）
- 另有 `delegate_self` / `cross_project` / `too_deep`（≤2 层）/ `cycle`（链上已有）/ `too_many` / `sensitive_content`
- 链信息随子循环下传（`chain = [发起方, …, 自己]`），否则 A→B→C→D 能无限转
- 断言：`orc-delegate.mts`（10 种原因逐个验，且每种都在频道留痕）、`orc-e2e.mts`（`chain` 真的传进子循环）

**(b) 10 分钟熔断**：到点如实说「暂未完成」，绝不挂死。

- `createJob({budgetMs: DELEGATE_TIMEOUT_MS})`，默认 **600000ms**，生产夹在 1~30 分钟
- 到点：`stopLoop`(子) + 掐掉在飞的 LLM 请求 + 委派行转 `timeout` + 频道留「按超时熔断处理」+ 投递 `delegate_timeout`
- 断言（`orc-e2e.mts` B 段，把熔断线压到 1.5s 实测）：
  - 1.5s 就回结果（子循环那一格本来要 8s）→ **没有无限挂死**
  - 回执文案含「暂未完成」，且**不含**子循环没交出来的那句结论 → 没有假装完成
  - 在飞请求确实被 abort（`stub.aborted >= 1`）→ 不在后台把 8 秒跑完、钱照烧
  - 名额释放、子循环销毁 → 被委派方能接下一件

## 2. 三条不能破的规矩（写进代码注释，改之前先读）

1. **不在 `advance()` 里 await 子任务** —— 委派最长 10 分钟，而 `/next` 只有 90s 硬超时，await 必挂（R6：传输出错即永久杀循环）。一律「派出即返回 + park + 结果回来续跑」。
2. **park 时不伪造工具回执** —— 挂起期间历史里只有 `assistant.tool_calls`、没有 `tool` 回执；`pendingCallId` 留着，由 `deliverJobResult` 补上那一条。`orc-park.mts` ③ 就是验这个。
3. **子循环没有浏览器手** —— 工具表里就没有那 5 个浏览器工具（`SUB_AGENT_TOOL_NAMES`），`wcId` 恒为 `null` 所以也不写任何页的分片状态。

另：`orchestrator` **绝不 import `toolLoop`**（ESM 循环依赖会拿到未初始化绑定，表现为「本地跑得好、打包后启动即崩」），级联取消走 `onLoopStopped` 订阅。

## 3. 实现过程中查出并修掉的 7 个问题

这一节是本报告最该看的部分 —— 都是**写完代码之后被验收脚本逮出来的**，不是设计时想到的。

| # | 问题 | 怎么发现的 | 修法 |
| --- | --- | --- | --- |
| 1 | `cross_project` 闸是死的：名字解析失败后用 `projectId=-1` 回查，而那个查询**按项目过滤**，必然查不到 → 跨项目一律报成「查无此人」 | `orc-delegate.mts` 红 | 新增 `findAgentByNameAnyProject`（只用于话术区分，不用于解析目标） |
| 2 | **收尾竞态**：熔断把委派行写成 `timeout`，被 abort 的子循环请求以 `llm_error` 正常返回，runner 顺着「模型卡住了」那支把它**覆盖成 `need_user`** → 频道说超时、接口说等用户，两个口径对不上 | `orc-e2e.mts` 红 | `finishDelegation` 加 `WHERE status IN ('pending','running')`（幂等交给 DB 行状态仲裁）+ runner 查 `signal.aborted` 后立刻退出 |
| 3 | **`browserToolNamesFor` 只挂了 `web_search`** → 主循环（用户直接对话的那一路）**根本调不到 `spawn_workers`/`delegate`**，两条核心需求在主入口上都用不了 | `orc-routes.mts` 红 | 三个工具都追加，各自过开关 + **查注册表确认真的注册了**（`toOpenAITools` 遇到未注册名会抛错，整条循环起不来） |
| 4 | ★ **桌面端断链**：`job_pending` 被当普通 `ask` 处理 → `return finish('ask_user')` → 本地驱动循环退出，**再没有人调 `/next`**。服务端把结果备好、循环也活着，任务却永远停在半路 —— 正是用户要防的「挂死」 | 读 `agent.ts:445` 时查出来的（服务端脚本看不见这半边） | 单开一格：继续驱动、2.5s 轮询一次；**不**发 `ask` 事件、**不**弹求助卡、**不** `stopLoop`；本地兜底时限 = `etaMs + 15s` |
| 5 | 叫停循环时在飞的那次 LLM 请求没被掐，会在后台把 90 秒跑完（钱照烧） | 写 S7 熔断时推出来的 | `session.abortCtl` + `AbortSignal.any([ctl, AbortSignal.timeout(90s)])`（超时保护没被削弱） |
| 6 | `sanitizePayload` 白名单没有 `outline` → 频道 `reply` 与委派 `result` 的要点提纲被静默丢掉，只剩一句话 | `orc-e2e.mts` 红 | 白名单补 `outline` / `waitedMs` / `to` / `peerAgentId` / `messageCount` |
| 7 | 用了不存在的 `level:'warn'`（`AgentEventPayload` 的 note 只有 `info | error`） | `npm run typecheck` 红 | 改用 `error`（渲染端只对 error 画 ⚠️ 并刷新驾驶状态，这件事该让用户注意到） |

**第 7 条还暴露了一个我自己的检查漏洞**：我先前只跑了 `tsc -p apps/desktop/tsconfig.json`（渲染层），
而 `electron/agent.ts` 属于 `tsconfig.electron.json` —— 所以当时看着是绿的。
**桌面端类型检查必须跑 `npm run typecheck`（根目录，三个工作区都过），不能只跑单个 tsconfig。**

## 4. 与方案的偏差（两处，都是往简单里偏）

1. **没有建 `orchestrator/index.ts` 桶文件** —— 没有任何调用方需要从桶里 import，加了只是多一层间接。
2. **没有改 `routes/agents.ts` 抽 `loadProjectAgents`** —— 名单查询放在 `orchestrator/roster.ts`
   （`loadProjectRoster` / `orchestrationBlockFor`），`/agent/loop/start` 与 `/chat` 两条入口共用同一个实现。
   好处是不必动 `agents.ts`；两条入口给的名单必然一致（否则「聊天里能委派、任务里不能」就成了玄学）。

## 5. 已知缺口（没做，说清楚）

| 缺口 | 影响 | 建议 |

| 频道界面**没有真机跑过** | 沙箱里没有显示器、没有 Electron-Chromium 二进制。界面逻辑已用 jsdom 渲染真组件验过（11/0），但**像素级观感、暗色模式、窄栏折行没验** | 真机 `npm run dev` 打开「🗂 内部频道」看一眼；样式都在 `channels/styles.css` 一个文件里，好改 |
