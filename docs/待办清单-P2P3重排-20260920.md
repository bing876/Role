## 1. P1：建议下一批就做

### 1.1 #6 `startIdleScheduler` 的 `done` 集合整体 `clear()`

- **位置**：`apps/server/src/routes/memories.ts:349`（`const done = new Set<string>()`）、
  `:369`（`if (done.size > 800) done.clear();`）
- **问题**：超 800 条就把**整个集合**清空 → 已经抽取过的会话会被**再抽一遍**（静默调模型）。
- **为什么升到 P1**：
  1. 它和刚修完的 **#4 是同一个模式** —— "容量压力下的自我失效"。刚在 #4 里把这条想清楚了，
     趁热改成本最低，也避免以后有人再写出第三份。
  2. 后果是**计费**的：重复抽取 = 重复的模型调用，而且用户完全无感。
- **顺手怎么改**：把"整体清空"换成"**逐条淘汰**"。`done` 里放的是会话 key，
  最自然的做法是记 `{key, at}`，超上限时先淘汰**已经不在候选集里的**（那些永远不会再被扫到），
  再按最旧淘汰少量。判据与 #4 一致：**永远不整体清空**。

### 1.2 怀疑 4 —— `hijack()` 之后仍走 `dbErr(reply, ...)`（**已核实为真**）

- **位置**：`apps/server/src/routes/chat.ts` —— `:489` `reply.hijack()`；
  同一个 handler 的外层 `catch` 在 `:577-578` 调 `return dbErr(reply, err)`
- **核实过程**：确认 489 与 578 **在同一个 handler 里**（两者之间没有新的 `app.post/get`，
  下一个路由注册在 `:583`）。`dbErr` 会执行 `reply.code(503).send(...)`，
  而此时响应已经 hijack 并被手写 SSE 接管 → Fastify 会抛
  "Reply was already sent"，**真实错误被掩盖**。
- **触发条件**：hijack 之后、内层 try/catch 之外抛出的任何异常（例如 SSE 建流阶段）。
- **为什么升为 P1**：这不是"可能有问题"，是**已核实的错误处理缺陷**；
  而且它的表现形式最坏 —— 排查时看到的是 Fastify 的框架报错，不是真因。
- **顺手怎么改**：hijack 之后**绝不**再碰 `reply`。把外层 catch 分成两段：
  hijack 之前用 `dbErr`，hijack 之后写进 SSE（`sse(res,'error',...)` + `res.end()`），
  并在日志里打出真因。

## 2. P2：值得排期，但不必停下手上的事

### 2.1 #7 `startIdleScheduler` 每分钟全表 `GROUP BY`

- **位置**：`apps/server/src/routes/memories.ts:359`（`GROUP BY c.id, p.user_id`），
  定时器在 `:350`
- **问题**：每分钟扫一遍 `conversations ⋈ messages`，**没有时间窗、没有 LIMIT**。
  数据量涨上来之后就是"每分钟一次全表聚合"。
- **与 #6 的关系**：**同一个函数**。改 #6 的时候顺手把查询加上
  `AND m.created_at > now() - interval 'X'` 之类的时间窗 + LIMIT，一次改完两件事。
- **顺手怎么改**：先给 `messages(conversation_id, created_at)` 或
  `conversations(updated_at)` 加索引（见 怀疑 3），再收敛扫描范围。

### 2.2 #11 CORS `origin: true` + `/health` 免认证

- **位置**：服务端 CORS 配置（`origin: true`）；`/health` 不校验 JWT
- **问题**：服务端**只监听 127.0.0.1**，所以外部网络打不到。
  但**本机浏览器里打开的任意网站**都能 `fetch('http://127.0.0.1:8787/...')`，
  而 `origin: true` 会把 `Access-Control-Allow-Origin` 反射成那个网站的源 → **响应可读**。
- **为什么升到 P2**：
  - `/health` 会泄露运营信息（`llmCalls` / `liveLoops` / `pageStates`）；
  - 发码接口 `/auth/sms/send` 是**免认证**的，可以被用来消耗短信额度（有按 IP / 按号码的限流兜着）；
  - 认证用的是 `Authorization: Bearer`（不是 cookie），所以**不构成自动 CSRF** —— 这是它没到 P1 的原因。
- **顺手怎么改**：把 `origin: true` 换成**明确白名单**
  （开发态 `http://localhost:5173`，打包态 `file://` 对应的 `null` 源）。
  注意改完要**真机验一遍**开发态与打包态都能连上，别把渲染层自己的请求拦了。

### 2.3 #9 `EXEC_TIMEOUT_MS` 只放弃等待，不中止底层动作

- **位置**：`apps/desktop/electron/agent.ts`（`EXEC_TIMEOUT_MS = 20_000` + `Promise.race`）
- **问题**：超时后调用方继续往下走，但 `drive()` 还在跑 → 页面可能**在 AI 放弃之后**才被改动，
  造成"循环以为没做、页面其实做了"的状态分叉。
- **为什么保持 P2（而且影响面比原判断小）**：`drive()` 内部有自己的 CDP 超时
  （`CDP_TIMEOUT_MS = 8000`），正常情况下远早于 20s 结束。
  所以这条 race 基本打不到 —— 但**一旦打到**（某个 CDP 调用真的挂住），后果就是分叉。
- **顺手怎么改**：把 `drive()` 的取消能力补上（传入 `AbortSignal`，
  或在超时后主动 `debugger.detach()` 让底层调用立刻失败），而不是只放弃等待。

### 2.4 #10 `driver.ts` 的 `tasks` Map 无上限无 TTL

- **位置**：`apps/desktop/electron/driver.ts:269`（`const tasks = new Map<number, TargetTask>()`）、
  `:280` 写入、`:557` 只在整体清理时 `clear()`
- **核实结论**：按 `wcId` 累积，**页面关掉之后条目不会被删** → 长会话里缓慢增长。
  说"无上限"是准确的，但增长速度是"每开一张新内页 +1"，不是每步 +1。
- **顺手怎么改**：在 webview 的 `destroyed` / `did-detach` 事件里 `tasks.delete(wcId)`。
  这是**最省事**的一条 —— 加两行事件监听即可。

## 3. P3：记录在案，顺手再处理

### 3.1 #13 `loops` 与 `pageState` 的 TTL 回收口径不一致
- **位置**：`apps/server/src/toolLoop.ts`（`LOOP_TTL_MS`）与 `apps/server/src/pageState.ts`（`PAGE_STATE_TTL_MS`）
- **问题**：两套 TTL 各自独立计时，回收时机不同步 → 会出现"循环没了但页状态还在"
  （或反过来），诊断时容易被误导。
- **顺手怎么改**：把两个 TTL 抽成同一个常量来源，或在 sweep 时一起判。

### 3.2 怀疑 3 `messages` 表缺 `(conversation_id, id)` 复合索引
- **问题**：按会话取最新 N 条会退化成扫描。
- **顺手怎么改**：加一条 migration。**这是全清单里最便宜的一条**，谁碰 `db.ts` 就顺手加上。

### 3.3 怀疑 5 `wcId` 停循环分支（**已核实：潜在隐患，非活跃 bug**）
- **位置**：`apps/server/src/routes/loop.ts:232-235`（`stopLoopsOfPage(claims.sub, wcIdRaw)`）
- **核实结论**：桌面端**所有** `/agent/loop/stop` 调用点（`main.ts` 共 5 处）
  **都传 `loopId`**，没有一处传 `wcId`。而 `loopId` 是全局唯一的，天然实例安全。
  所以这条分支在当前代码里**走不到**。
- **潜在风险**：多开应用实例时，两个实例的 `wcId` 都可能从 3 开始；
  若将来有调用方按 `wcId` 停循环，A 实例会停掉 B 实例那一程。
- **顺手怎么改**：二选一 —— 要么删掉 `wcId` 分支（没人用），
  要么把它改成"实例内作用域"（比如让客户端带上实例标识）。

### 3.4 怀疑 2 敏感轮询可叠加（**已核实：真实问题比原来判断的小**）
- **核实结论**：`startSensitiveAutoResume` **只有一个调用点** ——
  `main.ts:929`（`lane.stopWatch = startSensitiveAutoResume(...)`），
  而 `drive()` 的 `focus_sensitive_field` 分支**不启动任何 watcher**。
  所以"渲染层反复调 drive 堆起多个 10 分钟轮询"**不成立**。
- **真实问题**：`lane.stopWatch` 是**直接赋值**的 —— 如果同一路在 `notifyResume` 之前
  重复进入 `sensitiveHold`，上一个 watcher 会被覆盖而**不被停掉**（泄漏一个定时器）。
  好在它有 10 分钟上限、到点自清，属于**有界**泄漏。
- **顺手怎么改**：赋值前先 `lane.stopWatch?.()`（与 `notifyResume` 同一套清理）。

## 4. 一条值得固化的规则（本轮两次撞上同一个模式）

**「容量压力下整体清空集合」是一个会自我失效的防线模式。**

- #4：`if (ipHits.size > 5000) ipHits.clear()` → 攻击者撑满表就能把**自己的限流计数**一起清掉
- #6：`if (done.size > 800) done.clear()` → 已处理过的会话被**重新处理**（重复计费）

两次的写法看起来都像"够用就行的粗清理"，但实际效果是**防线在压力最大的时候正好失效**。
→ 建议以后凡是要写"超限就清空"，一律改成**逐条淘汰**，并且**优先淘汰那些已经没用的**
（过期 / 已不在候选集里的），**绝不整体清空**。

## 5. 本轮新产生、也建议记一笔的两条

这两条不在原审查报告里，是修 P1 批次时发现的，一并留档：

1. **`will-attach-webview` 是同步事件** —— 想在里面做"这个用户有哪些项目"的判断，
   就必须**提前把数据推到主进程**（本轮为此加了 `workbench:projects:sync`）。
   以后再往这个事件里加逻辑，先问一句"我需要的材料此刻在不在手里"。
2. **本地时序竞态测不出来** —— #5 的 TOCTOU 用"12 路并发 HTTP"在本地**撞不稳**
   （12 次跑里只有 1 次撞到），必须用**确定性手段**（外部事务先锁行）才能稳定复现。
   以后遇到并发缺陷，优先想"怎么把窗口 100% 造出来"，而不是"多跑几遍碰运气"。
