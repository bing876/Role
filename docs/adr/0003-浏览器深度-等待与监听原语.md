# ADR-0003 · 浏览器深度 第一片:wait-for / watch 两个原语

> 状态:已实施(2026-09-26)。
> 对应 GrokBot 环节:**电脑可监听 / 可教**。
>   - `wait-for`(等元素/文本出现,带超时)= 「可教」的地基:驾驶复杂页面时,智能体必须能
>     **等到预期状态再动手**(等结果渲染、等弹窗、等登录框),而不是盲点盲填。
>   - `watch`(监听 DOM 变化,新内容出现触发回调)= 「可监听」的地基:客服台这类「新消息实时
>     插进来」的页面,智能体要能**实时感知新内容**并触发回调,而不是靠轮询整页快照。
>   本片只落**原语层(地基)**;上层「客服监听智能体 / 复杂页驾驶编排」是后续片,建立在这两个
>   原语之上。

## 背景

- ADR-0002 已把内嵌页宿主从 `<webview>` 迁到主进程托管的 WebContentsView,驾驶走
  `webContents.debugger`(CDP 1.3)的 `Runtime.evaluate` / `Input.*`。
- 现有 `BrowserAction` 里只有 `{ action: 'wait'; seconds: number }` —— 一个**盲睡**(睡 N 秒,
  不看页面状态)。它没法表达「**等这个元素出现**」「**等新内容插进来**」这两类复杂页面刚需:
  - 复杂页:点「提交」后要**等结果区渲染出来**才算成功;盲睡要么睡不够(误判失败)要么睡过头(慢)。
  - 客服台:新消息是**异步插进 DOM** 的;靠 `read_page` 整页快照轮询既慢又贵,还抓不到「刚插进来」
    这一瞬。
- 缺这两个原语,后续「可监听/可教」的上层能力没有地基可踩。

## 现状(迁移前的事实基线,逐条对码核实)

- `driver.ts`:`drive()` 是唯一执行入口;`ensureAttached(wc)` 返回打过 8s 超时代补丁的
  `Electron.Debugger`;`evaluate()` 用 `Runtime.evaluate`(returnByValue)读页面;`resolveTarget(id)`
  只认 `viewHostRegistry` 里的主进程托管页。现有 `wait` 动作 = `await sleep(seconds*1000)`(盲睡)。
- Electron `Debugger` 官方类型:`Debugger extends NodeEventEmitter`,CDP 事件经
  `dbg.on('message', (event, method, params, sessionId))` 送达(含 `Runtime.bindingCalled`);
  webContents 关闭或 DevTools 打开时触发 `detach`。仓库里**尚无任何** `dbg.on('message')` 用法
  —— 本片是第一个 CDP **事件(push)** 消费者,此前的驱动全是 request/response。
- `sendToMainWindow(channel, payload)`(main.ts:409)是主进程向渲染层推事件的既有通道
  (分区闸 `workbench:browser:blocked` 就走它)。

## 决定

1. **新模块 `apps/desktop/electron/wait-watch.ts` —— 纯逻辑,零 `electron` 依赖**。
   它只依赖「一个 CDP `send` 函数」和「一个 CDP 事件源」两个**结构型接口**,不 import electron:
   - 这样它能在 node / jsdom 里被**直接驱动**(验收),而 `driver.ts` 负责把**真实的**
     `ensureAttached(wc)` debugger 接进来。**同一份 core 代码**,生产与验收共用,不是副本。
2. **`wait-for` = 页面侧谓词 + 主进程轮询**(不是盲睡):
   - 注入一个自包含 IIFE 谓词(选择器 `document.querySelector` 或 正文 `textContent` 子串),
     主进程每 `pollMs`(默认 100ms)用 `Runtime.evaluate` 求值一次,直到命中或到 `timeoutMs`。
   - 用**轮询**而非「注入 Promise + `awaitPromise`」,是**有意**的:现有 `sendCommand` 补丁对**每条**
     CDP 命令都强加 8s 超时,一个跨多秒的长 `awaitPromise` 会在 8s 被那条补丁杀掉。轮询的每次
     evaluate 都是毫秒级短命令,天然绕开这条硬闸,且跨导航鲁棒。上限沿用 `MAX_WAIT_SECONDS=300`。
   - 选择器非法(抛错)一律当**没找到**(吞掉异常),绝不当「找到」,也绝不让一次坏选择器炸掉等待。
3. **`watch` = 注入 MutationObserver + CDP `Runtime.addBinding`(push,真实时)**:
   - `Runtime.enable` → `Runtime.addBinding({name:'__wbWatchReport'})`(页里生成
     `window.__wbWatchReport`)→ 注入 observer(childList+subtree+characterData),命中新节点/文本
     变化就 `__wbWatchReport(JSON.stringify(payload))` → 主进程 `dbg.on('message')` 收
     `Runtime.bindingCalled`(name 匹配)→ `JSON.parse` 后回调 `onEvent(event)`。
   - **stop** = `dbg.off('message')` + 页内 `observer.disconnect()` + `Runtime.removeBinding`。
   - **一张页同一时刻只允许一个 watch**:重复 start = 先停旧的再挂新的(re-arm),绝不双发。
   - payload 固定为 `{ label:'insert'|'text-change', tag, text, html }`,text/html 截断(500/1000 字),
     绝不让一条巨大 DOM 把 IPC 打爆。
4. **跨进程面(全加法,不碰第四列 UI,不碰后端)**:
   - `driver.ts`:`browserWaitFor(wcId, spec)` / `browserWatch(wcId, onEvent, spec)` —— `resolveTarget`
     + `ensureAttached` 后委托 core(与 `drive` 同一套目标解析与 fail-fast)。
   - `main.ts`:IPC `workbench:browser:wait-for` / `watch-start` / `watch-stop`;watch 事件经
     `sendToMainWindow('workbench:browser:watch-event', {wcId, event})` 推渲染层。
   - `preload.ts` + `shared`(`WorkbenchBridge`)+ `webBridge.ts` 桩:加 `browserWaitFor` /
     `browserWatchStart` / `browserWatchStop` / `onBrowserWatchEvent`(Web 直测桩返回明确「不可用」)。
5. **验收 = 真驱动 core**(见下「验收口径」):本地测试页(进程内 DOM 基底)+ Node `vm` **真跑**
   注入的那段 JS;另附一条 **live 探针**(需真 Electron 二进制,机器上可跑)对真 CDP 复验。

## 失败模式表(doubt-driven:动手前列,验收逐行盖)

| # | 会怎么坏 | 怎么验(断言/反证) |
| --- | --- | --- |
| F1 | wait-for **假阳性**(没真出现却报 found=true) | 谓词对「不存在」必须回 found=false;**反证**:谓词改恒 found=true → 断言红 |
| F2 | wait-for **超时不触发**,永远挂着 | 永不出现的元素 + 短 timeout → found=false 且在 ~timeout 内返回,不挂死;**反证**:删 deadline 判断 → 看门狗红 |
| F3 | wait-for **早退**(元素真出现前就返回) | 元素 T+200ms 出现 → found=true 且 waitedMs≥150ms(证明不是拿旧状态秒回) |
| F4 | 长等待被 **8s CDP 补丁**杀掉 | 轮询每次是短 evaluate;timeout 上限 300s 但单次命令毫秒级(静态 + live 复验) |
| F5 | watch **从不触发**(binding 没挂 / observer 没 observe) | 插节点 → 回调**恰好一次**且带对 tag/text;**反证**:跳过 addBinding → 无回调 → 红 |
| F6 | watch **重复触发**(同一插入回两次) | 一次插入 → 恰好 1 个事件;**反证**:重复订阅 message → 2 个事件 → 红 |
| F7 | watch **stop 后泄漏**(继续收 / 监听没摘) | stop 后再插 → 无事件;**反证**:不 off('message')/不 removeBinding → 仍收 → 红 |
| F8 | 畸形 binding payload 把主进程**炸掉** | parse 出错只吞掉(fail-safe),不抛;**反证**:喂非法 JSON → 主进程不崩、无事件 |
| F9 | watch 与**既有驾驶循环**抢 debugger / 互踢 detach | 同一 transport 上 watch 与 read_page 并存不互斥(live 复验;沙箱静态) |
| F10 | **整页导航**后 binding/observer 失效(地基已知边界) | 已知缺口:本片只保**单文档**内有效;跨导航 re-arm 留后续片(live 探针只测单文档) |
| F11 | 同页 **start 两次** → 双发 | start×2 后插一次 → 恰好 1 个事件(re-arm 语义) |
| F12 | 目标页已关时 wait/watch 硬崩 | 未知 wcId → `resolveTarget` fail-fast 抛可读错,不崩 |

## 验收口径(真驱动,非纯函数单测)

- **基底 = 本地测试页**:`scripts/verify/wait-watch-smoke.mts` 里一个进程内 DOM(真
  `querySelector` / `textContent` / 一个**真 MutationObserver 契约**的 observer),用 Node `vm`
  **真执行** `wait-watch.ts` 导出的那两段注入 JS(同一常量,零漂移)。
- 断言逐行对应 F1–F8/F11/F12:元素/文本等到(含 waitedMs≥150 的「不早退」)、超时不挂(看门狗)、
  watch 恰一次 / stop 后静默 / 双 start 不双发 / 畸形 payload 不崩 / 未知 wcId fail-fast。
- **反证(拆掉必红)**:`wait-watch-revert.py` 对 `wait-watch.ts` 做定点变异(谓词恒 true / 删 deadline /
  跳过 addBinding / 重复订阅 / 不 off+removeBinding),每处都让 smoke 变红,还原后 sha 一致。
- **live 探针(真二进制机)**:`wait-watch-live.mjs` 开一个本地 `file://` 测试页(setTimeout 插入节点),
  走**真 CDP** 验 wait-for 等到 / watch 捕获,与沙箱 core 验收互为镜像。
- 红线:不碰第四列 UI(纯加法,零渲染层可见变化)、不碰后端、`verify:shell` golden 逐字节不变。

## 后果

- 正面:复杂页驾驶拿到「等到再动」的确定性地基;客服台类实时页拿到「新内容即回调」的实时地基;
  两个原语都是**主进程/CDP 侧**能力,后续智能体编排直接调用,无需再动宿主。
- 新增第一个 CDP **事件**消费者(此前全 request/response)—— `dbg.on('message')` 的订阅/摘除
  纪律(off 与 addBinding 成对)成为新红线,写进注释与反证。
- 纯 core 模块 `wait-watch.ts` 可单测,driver 只留薄包装 —— 以后原语增多时,测试面不再依赖 Electron。

## 备选与否因

- **注入 Promise + `Runtime.evaluate({awaitPromise:true})` 做 wait-for**:更「事件驱动」,但会被
  现有 8s 命令补丁在 8s 处杀掉(跨秒等待必死);要救就得改补丁(动硬闸,高风险)。**否**。
- **watch 用主进程轮询 `read_page` 快照 diff 找新节点**:无需 binding,但慢、贵、抓不到「刚插进来」
  那一瞬,且 diff 噪声大(重排/属性变化全混进来)。用户要的是**实时监听**。**否**。
- **watch 直接用 CDP `DOM.enable` + `DOM.documentUpdated`**:`documentUpdated` 是**粗粒度**文档级
  事件,只告诉你「文档变了」,不告诉**哪里**变了、新内容是什么 —— 拿不到「新消息文本」。**否**(用
  注入 MutationObserver 拿节点级新内容)。
- **把两个原语做成 `BrowserAction`(`wait_for` / `watch`)**:动作是「一次请求一次回执」的语义,
  `watch` 是**长生命周期 + 推事件**,塞进一次性动作会扭曲 `DriveResult` 的语义。**否**(做成独立原语)。

**实施中的 2 个坑(记下)**:
1. **re-arm 语义的落点**:「同一张页同一时刻只一个 watch」的担保在**主进程**(`watch-start` 里
   `stopWatchForWc` 先停旧的再 `browserWatch`),**不在**无状态的 `coreWatch` 里。初版验收 S7 直接
   「start 两次不停旧的」→ 两个监听都收 → 2 事件 → 红。把 S7 改成镜像生产的「先停旧再挂新」契约后绿。
   教训:跨实例的互斥约束要钉在**持有实例的那层**(main 的 activeWatches),core 只管单实例生命周期。
2. **FakeCdp 的监听容器必须用数组而非 Set**:真 `EventEmitter.on` 同一监听调两次会触发两次(不 dedupe),
   Set 会 dedupe → 反证 R4(重复订阅)测不到。改成数组 + `off` 移除全部实例后,R4 才咬得住。
   教训:模拟真实对象时,**连「不 dedupe」这种语义细节都要对齐**,否则反证会假绿。
