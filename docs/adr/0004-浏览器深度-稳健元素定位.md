# ADR-0004 · 浏览器深度 第二片:稳健元素定位(语义定位层)

> 状态:已实施(2026-09-26)。
> 对应 GrokBot 环节:**电脑「抗改版 / 可操作」**。
>   - 真实站点会改版:换 class、调 DOM 顺序、换文案。靠 class / 脆选择器定位的点击/输入
>     一改版就「找不到元素」→ 驾驶失败。要「可操作」,定位必须**先按语义解析出稳定的目标**,
>     再动手,而不是死盯一个会变的 class。
>   - 本片给 click/type 加一层**语义定位**:优先**稳定属性**(id / aria-label / name /
>     data-testid),没有则用**「文本 + tag + 结构」**生成抗改版描述,**先解析再操作**。
>   这是「抗改版」的地基:上层「改版后仍能可靠操作」的编排建立在这个定位层之上。

## 背景

- ADR-0002/0003 已把内嵌页迁到 WebContentsView、并加了 wait-for / watch 原语。但**定位**仍是
  老一套:`driver.ts` 注入的 `__wbHelper.find(target)` 是 **CSS 选择器优先 → 属性精确 → 文本兜底**
  的降级链。它**不抗改版**:
  - 选择器优先意味着「target 是个 class(如 `.submit-btn`)」时,改版把 class 换成 `.cta-primary-2025`
    → `querySelectorAll('.submit-btn')` 直接空 → 找不到元素;
  - 文本兜底能兜一部分,但**没有结构约束**(同文案的元素有多个时瞎挑)、**没有稳定属性优先**
    (有 data-testid 却不用)。
- GrokBot「电脑可操作」要求:同一**语义目标**(那颗「提交订单」按钮),站点改 class、改顺序后
  **照样点中**。缺这层,复杂/易改版的站点驾驶一改版就废。

## 现状(迁移前的事实基线,逐条对码核实)

- `driver.ts` `__wbHelper.find(target)`:① `queryDeep(target)`(当 CSS 选择器,取第一个可见)→
  ② placeholder/aria-label/name/id/title **精确**命中 → ③ 可见文字**精确** → ④ 可见文字**包含** →
  ⑤ 任意可见叶子文字包含。**选择器(含 class)排第一**,文本兜底无结构约束。
- `clickTarget` 用 `H.findClickable(target)` 拿元素 → `absRect` → CDP 真实鼠标点中心;`typeInto`
  用 `H.pick(target)`(= `findInput`)拿框,四个脚本(找框/读回/三写)靠 `window.__wbTypeTarget`
  缓存盯同一颗。
- `validateBrowserAction` 是 `drive()` 入口的形状闸(只认形状,不改语义);`BrowserAction` 的
  click/type 只有 `target: string`。

## 决定

1. **新模块 `apps/desktop/electron/semantic-locate.ts` —— 纯逻辑,零 electron 依赖**(与 wait-watch
   同一纪律):只认「一个 CDP send」+ 注入到页面里的一段**自包含**解析 JS。
   - `SEMANTIC_RESOLVE`(注入 JS 的唯一真源):在页面里按**两级**解析语义目标,返回
     `{ el, via, description }`:
     - **① 稳定属性(最抗改版)**:`id` → `data-testid` → `aria-label` → `name`,逐级 `querySelector`
       取第一个**可见**命中;
     - **② 文本 + tag + 结构**:在 `within`(可选祖先选择器)范围内,按 `tag`(可选)选候选,
       按**可见文本包含**过滤;多候选时「完全相等 > 前缀 > 包含」排序。
   - 解析 JS **自包含**(不依赖 `__wbHelper`)→ 能在 node / jsdom 里真跑验收;主文档解析,
     穿透 shadow/iframe 的语义定位留后续片(老 `find` 路径照旧覆盖非语义 target 的穿透)。
2. **`SemanticTarget` 结构**:`{ id?, testId?, ariaLabel?, name?, text?, tag?, within? }` ——
   稳定属性 + 文本/tag/结构,全是**抗改版**的维度(没有 class)。
3. **click/type 加 `semantic?` 层(加法,不破坏老 target)**:
   - `BrowserAction` 的 click/type 加可选 `semantic?: SemanticTarget`;`validateBrowserAction`
     归一化它(形状闸照旧)。
   - `clickTarget` / `typeInto` 加 `semantic?` 参数:**给了 semantic → 先按语义解析出元素(先解析),
     再对它操作(后操作)**;没给 → 老 `findClickable` / `pick` 路径一个字节不动。
   - 「先解析再操作」的落点:解析出的元素**全程盯住**(click 直接用它算坐标;type 把它存进
     `window.__wbSemanticTarget`,`pick` 优先认它),不中途换目标。
   - 解析成功的方式(`via`:id/testid/aria/name/text+tag/…)写进回执 `detail`,让模型/用户看到
     「这次是凭 data-testid 找到的」,可诊断。
4. **验收 = 改版前/后两版本地测试页**(见下);**反证** = 只认 class 的旧定位在改版页必红 +
   语义定位真被驱动(拆掉必红)。

## 失败模式表(doubt-driven)

| # | 会怎么坏 | 怎么验(断言/反证) |
| --- | --- | --- |
| F1 | 语义定位**假阳性**(匹配到错的元素,如同文案的另一颗按钮) | 同文案多按钮时,`text+tag+within` 必须命中**文案匹配**的那颗;断言命中的 el 文本==目标文本 |
| F2 | 改版(换 class)后**仍按 class 定位** → 找不到 | 改版页(无原 class)语义定位**仍命中**;**反证**:纯 class 定位在改版页**必失败**(红) |
| F3 | 改版(调顺序)后定位漂移 | 改版页(顺序对调)语义定位仍命中同一逻辑元素(不靠 DOM 顺序) |
| F4 | 有稳定属性却**不用**,浪费抗改版能力 | 目标带 data-testid → `via` 必须是 `testid`(稳定属性优先于文本) |
| F5 | 稳定属性全没有时**没有兜底** | 目标只给 text+tag(+within) → `via=text+tag(+within)`,仍命中 |
| F6 | 解析出元素但**不可见/零尺寸**也当命中 | 解析只认**可见**元素;隐藏的同名元素不命中 |
| F7 | 「先解析再操作」没兑现(操作时**又按脆 key 重解析** → 换目标) | click/type 全程用**同一颗**解析出的元素(断言操作对象==解析对象);type 的 pick 优先认语义缓存 |
| F8 | 没给 semantic 时**误伤老路径** | 不给 semantic → 老 `findClickable`/`pick` 行为逐字不变(回归:老 target 照旧命中) |
| F9 | 解析 JS 在**换页途中** `document` 为 null 炸掉 | 解析 JS 对 `document`/`querySelector` 全程 try/catch,拿不到就回 notfound,不抛 |
| F10 | semantic 形状非法(超长/类型错) | `validateBrowserAction` 归一化 + 拒绝(F12 输入校验,复用形状闸) |
| F11 | 跨 frame / shadow 的语义元素定位不到(地基边界) | 已知缺口:本片只主文档;穿透版留后续片(老 find 路径仍覆盖非语义 target) |

## 验收口径(真驱动,改版前/后两版)

- **本地测试页两版**(`semantic-locate-smoke.mts` 的进程内 DOM,Node `vm` 真跑注入解析 JS):
  - **v1 改版前**:`<form>` 里 `<button class="submit-btn" data-testid="submit-order">提交订单</button>`
    + 一颗「取消」按钮;
  - **v2 改版后**:**class 全换**(`.cta-primary-2025`)、**顺序对调**、**testid 保留**;
  - **v2b 改版后(更狠)**:class 全换、顺序对调、**连 testid 也去掉**(逼出 text+tag+within 兜底)。
- **同一语义目标** `{ text:'提交订单', tag:'button', within:'form' }`(或带 testId)**三版都点中同一颗**
  (命中 el 的文本必是「提交订单」,不是「取消」)。
- **反证(只认 class 的旧定位在改版页必红)**:纯 class `.submit-btn` 在 v1 命中、在 v2/v2b **必失败**;
  同一目标语义定位在 v2/v2b **必成功** —— 证明「抗改版」来自语义层,不是 class。
- **反证(拆掉必红)**:`semantic-locate-revert.py` 定点变异(删稳定属性级 / 删文本+tag 级)→ 相应目标
  解析失败 → 红;还原后 sha 一致。
- **live 探针**(真二进制机):`semantic-locate-live.mjs` 开本地 `file://` 改版前/后两版,走**真 CDP**
  驱动**同一份编译产物** `dist-electron/semantic-locate.js`,端到端复验「改版前后都点中」。
- 红线:不碰第四列 UI(纯加法,`semantic?` 可选,老 target 零改动)、不碰后端。

## 后果

- 正面:click/type 拿到「抗改版」的语义定位地基;稳定属性优先(有 data-testid 就用),文本+tag+结构
  兜底(没有稳定属性也能扛 class 改版);解析方式进回执,可诊断。
- 语义定位 JS 自包含、纯模块可单测(与 wait-watch 同一纪律);老 target 路径零改动(零回归面)。
- 已知边界:语义定位只主文档(穿透 shadow/iframe 留后续片);`within` 是 CSS 祖先选择器(改版若连
  结构都换,需上层给更稳的语义描述)。

## 备选与否因

- **继续用老 `find`,把 class 选择器挪到最后**:治标。class 仍会被文本兜底「碰运气」命中,没有
  稳定属性优先、没有结构约束,抗改版不彻底。**否**。
- **语义定位做成新动作(`semantic_click`)**:动作是「一次请求一次回执」,语义定位是 click/type 的
  **定位层**(换解析方式,不换操作),塞成新动作会重复 click/type 的执行逻辑。**否**(做成 click/type
  的可选 `semantic` 层)。
- **靠 CDP `Accessibility.getAXTree` / `DOM.querySelector` 做语义定位**:更「官方」,但要开额外
  域、解析 AX 树更重,且 data-testid/文本这类**页内事实**直接 `querySelector` 更快更可控。**否**(用
  注入 JS 的 `querySelector` + 文本匹配)。
- **把 class 也当抗改版维度**:class 恰恰是改版最爱换的,进「抗改版」就是自相矛盾。**否**。

  新增 `SemanticTarget` / `SemanticLocateResult` 类型。

  多候选「完全相等>前缀>包含」;全程 try/catch,只主文档,空目标 notfound)+ `semanticResolveExpr` /
  `semanticLocateJs` / `coreSemanticLocate`。
- `apps/desktop/electron/driver.ts`:`validateBrowserAction` 加 `semantic()` 归一化(对象/字符串字段/
  ≤上限/至少一非空字段,空串/纯空白视同没给);`PAGE_HELPERS` `__v` 12→13;`pick` 顶部加
  `window.__wbSemanticTarget` 优先;`clickTarget` 加 `semantic?`(IIFE 内**先内联语义解析**→
  盯住那颗算坐标走 CDP 真鼠标,`el.click()` 兜底也认语义缓存),`typeInto` 加 `semantic?`(开头预解析
  stash 进 `__wbSemanticTarget` 让既有 `pick` 盯同一颗);`via`/`description` 进回执 detail。
  **未给 semantic → 老路径逐字不变。**

**验收(真驱动 core,`semantic-locate-smoke.mts`,进程内 DOM + Node vm 真跑解析 JS)—— 28/0 PASS**
- S1 同一语义目标在 v1(改版前)/ v2(换 class+顺序对调)/ v2b(再去 testid)三版都点中「提交订单」(via=text+tag+within);
- S2 有 testid 时 `via=testid`(稳定属性优先),testid 被去掉时回落 text+tag+within;
- S3 **反证**:纯 class `.submit-btn` 在 v1 命中、在 v2/v2b **必失败**(红);同一目标语义定位在 v2/v2b 仍成功(绿);
- S4 同文案多元素 → 命中文案**精确**那颗(不瞎挑);S5 隐藏同名按钮不命中(只认可见);
- S6 换 DOM 顺序不漂移;S7 空目标/不存在 → notfound 不崩。

**反证(拆级必红 + sha 还原,`semantic-locate-revert.py`)—— 全 PASS**

- R2 拆 ② 文本匹配 → 只给文本的目标必红(S1 红),纯 testid 目标不受影响(S2 v1/v2 仍绿);
- 每步还原后 sha256 与改前一致,复跑回全绿。
