# 技术侦查报告 · 「人工介入卡片」前置评估

> 日期：2026-09-20　范围：只做侦查，**未改任何产品代码**
> 取证方式：读已验收代码（本机 agent 环境**起不了 GUI Electron 进程**，探针两次尝试均被拦，见附录 A）

---

## 零、一句话结论

| 问题 | 结论 |
| --- | --- |
| ① 浏览器组件能否"嵌进聊天消息流" | **按字面（webview 挂进聊天 DOM 子树）不能，代价极高**；**按"视觉上嵌在聊天流里"能，且全在渲染层、零主进程改动**。两条路必须分开看。 |
| ② AI 怎么判断"遇到验证码/登录墙" | **登录墙：已有信号可复用**（第 16 步 `loginLike`）；**验证码：只有字段级识别、没有页面级信号**；**滑块：零覆盖**。需要新增一个小判定层，不依赖模型。 |
| ③ 用户操作后如何被 AI 感知并继续 | **完全可复用，一行新机制都不用发明**。第 9 步已经建成并验收过整条链路（等用户 → 自动感知完成 → 重读页面 → 继续）。 |
| 工作量 | **比预想小很多**——核心链路已经在了。真正的成本集中在**展示层**和**安全回归验证**。 |

**最重要的一个发现**：这个功能不是从零开始。第 9 步已经把「AI 不代填敏感字段 → 交给用户 → 自动感知 → 继续」整条链路做完并验收了，代码注释里甚至明确写着「未来『人工介入卡片』的主场景」（`electron/agent.ts:216`）。本次要做的是**换一个呈现方式 + 扩一个触发面**，不是新建一套。

## 一、问题①：能不能嵌进聊天流

### 1.1 现状：两块区域是**物理隔离**的

```
.middle (position: relative, overflow: hidden)
├── .browserLayer      position:absolute; inset:0; z-index:20   ← 浏览器在这里
│   └── .browserPanel
│       └── .browserPanel__stage (position:relative)
│           └── <webview> × N   (position:absolute; inset:0)
└── .chat              z-index:10; overflow:auto                ← 聊天在这里
```

`apps/desktop/src/App.tsx:2643-2665`、`styles.css:194-276`、`browser/styles.css:268-293`。
这**不是**随手写的：`BrowserPanel.tsx:11-15` 明确说「它是 .middle 的兄弟节点、不在 .chat 的滚动区里 —— 所以『滚聊天不会把浏览器滚没』」。也就是说，**"不在聊天流里"是当前架构的一个刻意设计**。

### 1.2 为什么"搬进聊天流"是核心改动，而不是小改动

**（a）`<webview>` 的 guest 生命周期绑在 DOM 节点上。**

这是硬约束，本仓库自己就有第一手证据 —— 第 24 步「深休眠」就是靠**卸载 `<webview>`** 来真正释放内存的：

- `BrowserPanel.tsx:262-273`：「★ 第 24 步：**深休眠的页不渲染 `<webview>`** —— 这才是真的省内存。`<webview>` 只要挂在 DOM 上，Electron 就为它保留一个 guest 渲染进程，那份内存一分都省不下来。`display:none` / `opacity:0` 都**不省内存**。」
- `useBrowserWorkspace.ts:871`：「深休眠的页**已经不在 DOM 里**了（拿不到 wcId）」
- `useBrowserWorkspace.ts:362`：`awaitWebContentsId(tabId)` —— 唤醒后必须**轮询等一个新 id**，因为重新挂载得到的是**另一个 guest**。
- `useBrowserWorkspace.ts:469`：「把它从休眠态摘出来，React 会据此**重新挂载** `<webview>`」

⇒ **元素一旦离开 DOM，guest 就销毁；搬进聊天流 = 从舞台卸载 + 挂到消息里，回来的是另一个 `webContents`。**

**（b）`wcId` 是整条驾驶链路的主键。** 换 id 等于换主键：

| 位置 | 用途 |
| --- | --- |
| `electron/driver.ts:276` `tasks: Map<wcId, TaskState>` | 主进程状态机（phase / paused / step） |
| `electron/main.ts` `lanes: Map<wcId, Lane>` / `liveLoops` | 这一路的循环与等待 |
| `server/src/toolLoop.ts` `LoopSession.wcId` | 服务端循环归属 |
| `server/src/pageState.ts` | 任务态按 wcId 分片 |
| `server/src/routes/loop.ts:120` | `/agent/loop/next` 归属硬闸 |

⇒ **wcId 一变，正在跑的那一路当场失联**（状态机找不到、挂起挂不上、继续接不回）。

**（c）同一个 guest 不可能同时出现在两处。** 要么在聊天流里、要么在全屏浏览器里。每次切换都要重建 guest + 重新加载页面（登录态 cookie 因 `partition` 按项目固定而保留，但**页面内状态全丢**：滚动位置、已填的表单、验证码本身）。

**（d）会和已有的两条红线正面冲突**：`BrowserPanel.tsx:269-273` 写着「`drivingIds` 里的页**永远不会**是 deep —— 判定层已硬拦，这里再守一道：真出现这种数据，也**拒绝卸载**，宁可多占内存，也不能把 AI 正在跑的任务弄断」。而求助卡出现的时刻，恰恰就是**有任务在跑**的时刻。

**结论：是核心改动。** 不建议走这条路。

### 1.3 但是——有一条低成本路径能达到同样的观感

关键观察：`styles.css` 全文**没有一处 `transform` / `filter` / `will-change` / `perspective` / `contain`**（已 grep 确认），且 `.browserLayer` 是 `inset:0` 的绝对定位层、`.browserPanel__stage` 是 `position:relative`。

⇒ 可以**不搬 DOM**，只改 CSS：让目标 `<webview>` 的几何**跟随**聊天流里那个占位块的 rect，看起来就落在卡片里。

这条路**不动 guest 生命周期、不动 wcId、不动主进程一行代码**。细节见 §四·方案 B。

## 二、问题②：AI 怎么判断"需要人工介入"

### 2.1 已有的信号（可复用）

| 信号 | 位置 | 覆盖 | 现状用途 |
| --- | --- | --- | --- |
| `snapshot.loginLike` | `electron/driver.ts:1055-1069` `loginish()` | **登录墙** | 只影响提示词与失败话术：写 `pageState.login_required`（`toolLoop.ts:926`）、进 `promptPolicy.ts:175`、`failureHint()`（`driver.ts:1234`）。**不触发任何 UI** |
| `classifyField` → `otp_guess` | `electron/fieldClass.ts:36-63` | **验证码字段** | 只在「AI 试图填这个框」时**被动**生效 |
| `snapshot.overlay` | `driver.ts:1075-1090` | 疑似弹窗/遮罩 | 提示词 + 失败话术 |
| `ask(reason='sensitive_field')` | `toolLoop.ts:749` `sanitizeToolCall` | **被动触发** | 把敏感动作换成 `focus_sensitive_field`，已在用 |

`loginish()` 的判据（保守、只看不猜）：有 `input[type=password]` → 真；或同源 iframe 地址命中 `登录|login|passport|sso` → 真；或 `title + href` 命中同一组词 → 真。

### 2.2 缺口

1. **没有"页面级验证码/滑块"信号。** 现在只有「某个字段像验证码」（字段级），没有「这一页是验证码页」。
2. **滑块验证零覆盖。** 无 canvas / 滑块 / 图形验证的识别。
3. **`loginLike` 目前只进提示词，不触发 UI。** 需要把它接出来。
4. **最关键的缺口：没有"我走不下去了"的判定。** 现在 `loginLike` 只在**动作失败之后**被用作解释（`failureHint`），而不是主动求助。

### 2.3 建议的新判定层（小改动）

放在**现有快照里**、与 `loginLike` 并列，本地硬判定、不依赖模型（与 `fieldClass.ts` 的"全工程唯一判定源"风格一致）：

- `challengeLike`：页面存在 `otp_guess` 字段 **且**（有「获取验证码/发送验证码/重新发送」按钮 **或** 字段/标题文案含验证码）→ 验证码页
- `sliderLike`：可见 canvas/img + 类名或 id 命中 `captcha|verify|slider|slide|滑块|验证` 且尺寸落在小尺寸区间 → 滑块/图形验证
- 登录墙直接复用 `loginLike`

**触发策略必须保守**（这条很重要）：不要"一进登录页就弹卡"——用户可能就是让 AI 去登录页点个链接。建议 **本地信号 且 有"卡住"证据** 才弹：

- 本轮动作失败 / `noChange` 连续命中，**或**
- 服务端把动作挡下来回了 `ask`，**或**
- 模型自己回了 `ask_user` / `need_user`

否则误报会变成打扰。

## 三、问题③：用户操作后怎么衔接到"继续"

**结论：整条链路已经建好并验收过了，直接复用，不要另起一套。**

三段现成机制：

### 3.1 「AI 停下来等用户」— `sensitiveHold(lane)`
`electron/main.ts:923-941`：前置窗口 → 通知渲染层把焦点给**这一路那张页**（`browser:focus` 带 wcId）→ 挂自动恢复观察 → 返回一个 Promise，循环 `await` 它。
⇒ **AI 真的停在这一格**，不调模型、不烧 token、不发任何动作。
（服务端侧对应 `waiting` 状态，`agent.ts:214-225` 专门把 `ask_user`/`say`/`stuck` 排除出 `stopLoop`，注释里明确写着「尤其 `ask_user` 里最要紧的一支就是**敏感字段**（验证码/密码——未来『人工介入卡片』的主场景）」）

### 3.2 「用户处理完了」— `startSensitiveAutoResume`
`electron/driver.ts:2003-2059`：
- 信号：`did-navigate` / `did-navigate-in-page` / `page-title-updated` **或** 每 1.2s 轮询发现「页面上敏感输入框整体消失」
- 上限 10 分钟静默停表；另有 2 分钟提示手动兜底（`main.ts:931-937`）
- 有手动出口：`main.ts:637-640` —— lane 上有 waiter 时点「继续」直接 `notifyResume`

### 3.3 「继续 = 重新感知 + 接回原历史」— `resumeLoop`
`server/src/toolLoop.ts:551-630`：
- `pageDelta(暂停前快照, 现在快照)` 算出「用户在这段时间里动了什么」
- 把结果**append 到原有消息历史**（明确不重建，否则 AI 又不记得自己做过什么）
- 注入「恢复后三条硬规矩」：只能 `read_page`、**禁止** `open_url` 跳回旧地址、不重做用户已手动完成的部分
- 步数归零（一轮步数上限的语义）

**所以求助卡只需要做两件事**：把"等用户"这件事在聊天流里**可见化**（卡片），并把"用户点了我处理好了"作为 `notifyResume` 的**又一个信号源**（现有信号是自动感知，再加一个手动按钮更稳）。

## 四、三条候选路径

### 方案 A · 真搬 DOM（webview 元素挂进聊天卡片）
| | |
| --- | --- |
| 观感 | 最贴原始需求 |
| 代价 | guest 重建 → **wcId 变** → 主进程 `tasks`/`lanes` + 服务端 `LoopSession`/`pageState` 全部要重绑；每次进出卡片都重新加载页面 |
| 风险 | **高**。要动 driver 的按 wcId 索引、loop 归属、pageState 分片，还要解决"同一 guest 两处存在" |
| 结论 | **不建议** |

### 方案 B · 影子层几何跟随（推荐）
webview **不搬**，仍在 `.browserPanel__stage` 里；只让它"看起来"落在卡片位置上。

做法：新增**第三种浏览器层视图模式**（现有 fullscreen / background，`App.tsx:2643`）：
- 聊天流里的求助卡留一个**占位块**
- 该层切到 embed 模式：`background:transparent; pointer-events:none; z-index:30`（**不能**复用 `--bg`，因为 `opacity:0` 会让 fixed 子元素以它为包含块、且整层不可见）
- 非目标页复用已有的 `browserPanel__view--off`（`opacity:0; pointer-events:none`）
- 目标页加新类：按占位块 rect（相对 `.middle`）设 `left/top/width/height`，`pointer-events:auto`，`clip-path: inset()` 裁掉滚出视口的部分
- 监听 `.chat` 的 scroll + `ResizeObserver`，rAF 节流同步

| | |
| --- | --- |
| 优点 | **零主进程改动、零 guest 生命周期改动、零 wcId 风险**；真"嵌在聊天流里"、用户直接在真页面上操作（保住安全红线） |
| 成本 | 几何同步代码（纯渲染层）；滚动跟手有约一帧延迟；需处理卡片滚出视口时的裁剪 |
| 待验 | 需一个 ~30 分钟的 spike 确认固定定位 + 滚动跟随在本 CSS 结构下成立（已 grep 确认无 `transform` 类祖先，前景乐观） |
| 风险 | **中**，且全部集中在渲染层，可回滚 |

### 方案 C · 卡片 + 浮层（兜底）
聊天流里只放一张卡（页面截图 + 说明 + 按钮），点开在**覆盖式浮层**里展示浏览器（复用现有全屏层，尺寸必须真实、不能 0×0 —— `MEMORY.md` 记着这条红线）。

| | |
| --- | --- |
| 优点 | **风险最低**、最快拿到"逻辑正确、能正常使用" |
| 缺点 | 视觉上仍是"跳转了一下"，不完全满足"不需要跳转界面" |
| 风险 | **低** |

**我的建议**：**B 为主、C 兜底**。先花半小时做 B 的 spike；如果固定定位+滚动跟随在这个结构下不成立，再退到 C。两条路的**判定层、触发编排、继续机制、视觉区分**四块完全共用，先做后四块不会白做。

## 五、安全红线（本次必须单独回归的部分）

### 5.1 现有两道硬闸（不能弱化）
1. **执行侧**：`driver.ts:1214` `typeSensitiveGuard` —— `type` / `fill_form` 命中敏感字段**直接拒填**（不依赖模型自觉）；`driver.ts:1248` `payClickGuard` —— 支付最终确认点击一律拒。
2. **服务端侧**：`toolLoop.ts:749` `sanitizeToolCall` —— 敏感动作自动换成 `focus_sensitive_field`（值即弃）。
3. **敏感值从不进链路**：快照对敏感框 `value` 直接置空（`driver.ts:1166`）；`FieldDescriptor` 结构上就不含 value。

### 5.2 ★ 本功能自己会引入的最大风险点（要提前设计防住）

> **一旦"卡片里给用户一个输入框"，就出现了"应用把用户输入的验证码写进页面"这条路 —— 那正是红线要保护的场景。**

⇒ **卡片里绝对不能自己做一个"验证码输入框 + 提交按钮"。** 那本质上就是应用在代填验证码，只是把决策权从模型换成了用户，机制上仍然绕开了 `typeSensitiveGuard`。
⇒ **必须让用户直接在真实页面上操作**（方案 B 天然满足；方案 C 的浮层里也是真页面）。这条要写进方案作为硬约束。

### 5.3 顺带要修的一个已知隐患
`main.ts:929` `lane.stopWatch = startSensitiveAutoResume(...)` 是**直接赋值**：同一路在 `notifyResume` 之前重复进入 `sensitiveHold`，上一个 watcher 会被覆盖而**不被停掉**（泄漏一个定时器，有界 10 分钟）。
本功能会让"等待"更频繁出现，建议顺手改成赋值前先 `lane.stopWatch?.()`（`docs/待办清单-P2P3重排-20260920.md` §3.4 已记录）。

## 六、工作量评估（按改动面，不给时间承诺）

| 模块 | 改动面 | 风险 | 说明 |
| --- | --- | --- | --- |
| 展示层（卡片 + embed 视图模式） | **大** | 中（方案 B）/ 低（方案 C） | 本次唯一的大头，全在渲染层 |
| 判定层（页面级 `challengeLike` / `sliderLike`） | 小 | 低 | 加在现有快照里，本地硬判定 |
| 触发与编排（何时弹卡、状态怎么流转） | 小-中 | 中 | 要与 deep-sleep / driving / 全屏三态互斥 |
| 视觉区分（用户暂停 vs AI 求助） | 小 | 低 | **但这是核心验收点**，见下 |
| 继续机制 | **零** | — | 直接复用 §三 |
| 安全回归验证 | 中 | — | 必须单独一轮，见 §五 |

### 关于"视觉区分"这条核心验收点——根因已经定位

用户反馈的"两种情况提示文字完全一样、分不清是谁发起的"，根因是：
`App.tsx:173-179` 的 `DRIVE_PHASE_LABEL` **只按 `phase` 取文案**，而两种情况都落在 `phase='paused'`：

| 场景 | 主进程实际写的 detail | 界面显示 |
| --- | --- | --- |
| 用户主动暂停 | `agent.ts:274`「已暂停（服务端已挂起这一路）— 浏览器交还给你…」 | `paused` → **"已暂停（页面归你操作）"** |
| AI 主动求助 | `agent.ts:297`「等你输入敏感信息（值不经 AI、不落库）」 | `paused` → **"已暂停（页面归你操作）"** |

⇒ **`detail` 被丢掉了，两句话在界面上被压成同一句。** 修法是给状态机加一个"是谁发起的"维度（`pausedBy: 'user' | 'agent'`），让文案/颜色/图标三者都跟着它走，而不是只跟 `phase` 走。改动很小，但要动到 `TaskState` 的结构，属于**协议级改动**，需要一并想清楚。

## 七、需要你拍板的四个问题

1. **方案选哪个**：A（真搬 DOM，不建议）/ **B（影子层几何跟随，我推荐）** / C（卡片+浮层，兜底）
2. **求助卡出现时，是否自动从"浏览器全屏"切到"卡片模式"**（否则用户在全屏里根本看不见聊天里的卡片）
3. **触发策略**：保守（本地信号 **且** 有"卡住"证据才弹，我推荐）／ 激进（检测到验证码或登录页就弹）
4. **"用户处理完了"的信号**：只靠自动感知（敏感框消失 / 页面导航）／ 额外再加一个「我处理好了」按钮（我推荐两个都要，自动感知可能失灵）

## 附录 A · 关于本次没能跑起来的运行时探针

原计划写一个独立 Electron 探针，实测「把 `<webview>` 元素从一个父节点 appendChild 到另一个父节点，guest 会不会被销毁、`getWebContentsId()` 会不会变」。这是问题①最直接的证据。

**结果：跑不起来。** 试过四种方式（直接跑、输出重定向到文件、Python 生成 GBK `.cmd` 再执行、以及关掉沙箱），全部表现为进程被杀 / 无任何产物；连一个只写文件的"最小 Electron 脚本"都起不来，而 `electron.exe --version` 正常返回 `v33.4.11`。
⇒ 本机 agent 环境**起不了 GUI Electron 进程**（与 `MEMORY.md` 里「agent 不能替用户常驻进程」一致）。

**因此问题①的结论建立在代码证据上，而非运行时实测。** 证据强度说明：
- 「元素离开 DOM ⇒ guest 销毁」—— **强**。第 24 步深休眠就是靠它省内存的，且唤醒后必须轮询等新 wcId，两处注释互相印证。
- 「appendChild 到新父节点 == 先 detach 再 attach」—— **中高**。这是 DOM 规范行为，但 Electron 在**同一父节点内**是否有特殊优化、以及"移动后 id 是否可能复用"，**没有实测**。
- 这一条**恰好是方案 A 与方案 B 的分水岭**，所以**建议在正式开发前先补一个 spike**（可以手工双击应用、或由你在沙箱外跑一次探针脚本；脚本已放在 `scripts/verify/webview-embed-probe/main.js`，跑完会写 `probe-result.json`）。
- 方案 B **不依赖这条结论**（它根本不搬 DOM），所以即使这条没实测，B 依然成立 —— 这也是我推荐 B 的一个理由。
