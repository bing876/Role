# AI 工作台 · 系统级健康度审查报告

**审查日期**：2026-09-19
**审查范围**：全仓库（`apps/desktop`、`apps/server`、`packages/shared`、`scripts`），
含此前各阶段"已验收通过"的老代码
**审查方式**：通读代码 + 主动进攻思维（"如果我是攻击者会怎么打"、"长时间高强度使用哪里先坏"、
"多功能同时触发哪里会打架"）
**审查立场**：目标不是证明项目没问题，而是**如果我要对这个系统的健康度负责，我会担心什么**

---

## 0. 先说结论

这个项目的**工程质量明显高于同类原型**：加密边界划得很干净（messages / memories / knowledge /
phone 全部 AES-256-GCM）、权限校验几乎每一条查询都带归属条件、许多踩过的坑都有注释留痕且
对应了真实修复。"数据安全"和"权限边界"这两块，我认真找了一轮，**没有找到可以直接绕过的高危漏洞**。

**但它有一个系统性的结构风险，比任何单个 bug 都值得担心**：

> **"本地（桌面/浏览器侧）判定为不可执行"的动作，有些路径的权威闸门在客户端，而服务端是信任客户端的。**

服务端 `toolLoop` 的敏感闸（`sanitizeToolCall`）做得很好，但**它是"服务端自己决定"的闸**；
而真正决定"点哪里、往哪个框里输什么"的 `classifyField` / `typeSensitiveGuard` / `payClickGuard`
**全在桌面主进程**。如果桌面这一侧的 IPC 被绕过（渲染层被 XSS、或有人直接调 IPC），
服务端**没有任何办法发现**——它只收到一句"执行成功了"。

下面按严重等级排列。**"确定存在的真实问题"与"怀疑但未证实"分开列出。**

## 一、确定存在的真实问题

### 【严重】1. `/agent/loop/next` 的 `agentId` / `wcId` 校验可以被"不传"绕过

**在哪里**
`apps/server/src/routes/loop.ts` 第 162-173 行：

```ts
const agentIdRaw = Number(b?.agentId);
if (session.agentId !== null && Number.isInteger(agentIdRaw) && agentIdRaw !== session.agentId) {
  return errJson(reply, 409, ..., { code: 'agent_mismatch' });
}
const wcIdRaw = Number(b?.wcId);
if (session.wcId !== null && Number.isInteger(wcIdRaw) && wcIdRaw !== session.wcId) {
  return errJson(reply, 409, ..., { code: 'page_mismatch' });
}
```

**是什么问题**
两处校验都要求 `Number.isInteger(...)` **为真才比较**。也就是说：

- 不传 `agentId` → `Number(undefined)` = `NaN` → `Number.isInteger(NaN)` = **false** → 整个条件短路，**校验被跳过**；
- 传 `agentId: "abc"` / `null` / `{}` → 同样 `NaN` → **跳过**；
- 传 `wcId` 不传 → 同样跳过。

代码注释写着"不串 bot 的硬闸……对不上直接 409，绝不让 A 智能体的循环把动作打到 B 智能体那张页上"，
但**这道闸只在"调用方主动报了一个数字且报错了"时才生效**。调用方只要干脆不报，就完全不受约束。

**为什么重要**
这条闸是"同一账号下多智能体/多页并行时不串台"的**唯一服务端防线**。
它挡的其实不是外部攻击者（外部攻击者拿不到别人的 loopId——`getLoop` 后还有 `userId` 校验），
而是**本机桌面端的逻辑错误**：比如某个 lane 的 wcId 变量被置空、或某段代码忘了传参，
服务端就会照常推进它，返回一个"下一步工具"，而桌面会拿这个工具在**另一张页**上执行。
设计意图（"对不上直接拒"）与实际行为（"不报就放行"）不一致 —— 这正是那种
"将来一定会出事，但当时图省事先这么写了"的地方。

**建议怎么修**
把校验改成**必须显式对上**：

```ts
// 循环记了 agentId/wcId 时，调用方必须报出同一个值；不报 = 不匹配
if (session.agentId !== null && agentIdRaw !== session.agentId) { /* 409 */ }
if (session.wcId !== null && wcIdRaw !== session.wcId) { /* 409 */ }
```

即去掉 `Number.isInteger(...)` 这个前置条件（`NaN !== 5` 天然为真 → 会正确拒掉）。
**注意这会让"不传"从"放行"变成"409"，所以要先确认桌面的所有调用点都确实传了值**
（`main.ts` 的 `agentPost('/agent/loop/next', ...)` 那一处，以及 `agent.ts` 的 next 钩子）。
如果确实存在"合法地不传"的场景，就改成**单独一条**：循环有 wcId 时 `wcId` 必填，
缺参数给一个**明确的**错误而不是静默放行 —— 而不是像现在这样让 `NaN` 悄悄通过。

### 【严重】2. `workbench:doc:download` 接受渲染层传入的 `apiBase` + `token`，构成任意地址请求与数据外带面

**在哪里**
`apps/desktop/electron/main.ts` 第 1153-1181 行：

```ts
ipcMain.handle('workbench:doc:download', async (_event, taskIdRaw, apiBaseRaw, tokenRaw) => {
  const apiBase = typeof apiBaseRaw === 'string' && apiBaseRaw ? apiBaseRaw : agentApiBase;
  const token   = typeof tokenRaw === 'string' && tokenRaw ? tokenRaw : agentJwt;
  ...
  const res = await fetch(`${apiBase.replace(/\/+$/, '')}/agent/task/doc?taskId=${taskId}`, {
    headers: { authorization: `Bearer ${token}` },
  });
```

**是什么问题**
`apiBase` 和 `token` **完全由渲染层提供，主进程不做任何校验**：
不校验 `apiBase` 是不是 `127.0.0.1`/`localhost`，不校验 `token` 是不是本机登录得到的那一个。
主进程会拿任意 `apiBase` + 任意 `token` 去发 HTTP 请求，**把响应体写进用户通过系统对话框选择的文件**。

这条链路上：
1. `apiBase` 可以是任意主机（`http://evil.example.com`）→ 主进程成为**不受同源策略约束的请求发起方**
   （SSRF 面：可以打内网地址、打本机其它端口，且响应内容会被写进文件）；
2. `token` 可以是任意字符串 → 可以把用户的 JWT **外带到第三方地址**（请求头里的
   `authorization: Bearer <token>`）；
3. 写文件用的是用户真实点击"保存"选出来的路径 → 但**内容来自渲染层指定的任意地址**。

渲染层目前是自家的 React 代码，正常不会这么干。但这个 IPC 的**存在本身**把
"渲染层被控 ⇒ 只能干渲染层能干的事"这条边界打破了：`contextIsolation` + `sandbox: true` +
preload 白名单本来是为了让**渲染层出事时主进程兜底**，而这里主进程反过来**无条件信任了渲染层的输入**。

**为什么重要**
这是整份报告里我认为**最该优先修**的一条。它的性质是"权限边界是否真的封死"——
而这个口子把一条**已经封死的边界重新打开了**。触发条件不需要"用户被骗"，只需要
"渲染层里任何一个 XSS 或第三方依赖被投毒"。

**建议怎么修**
主进程自己持有权威（它本来就有 `agentApiBase` / `agentJwt` 两个变量）：

```ts
// ① apiBase 只允许本机回环
const ok = /^https?:\/\/(127\.0\.0\.1|localhost|\[::1\])(:\d+)?$/i.test(apiBaseRaw ?? '');
const apiBase = ok ? String(apiBaseRaw) : agentApiBase;   // 不合法就忽略渲染层的值
// ② token 不接受渲染层传的：一律用主进程内存里那份
const token = agentJwt;
```

如果"刷新后主进程没会话"这个场景（注释里写的理由）确实存在，正确做法是
**让渲染层重新把凭证同步给主进程**（走一个显式的、只在登录成功后调用的通道），
而不是让每一个下载请求都能自带一个新地址和新凭证。

### 【一般】3. 桌面 `workbench:drive` IPC 不校验 `action` 形状

**在哪里**
`apps/desktop/electron/main.ts` 第 372-376 行：

```ts
ipcMain.handle('workbench:drive',
  (_event, action: BrowserAction, targetWebContentsId?: number) =>
    drive(action, targetWebContentsId));
```

**是什么问题**
`action` 被直接当成 `BrowserAction` 透传给 `driver.drive()`，**没有任何形状校验**
（`drive()` 内部是 `switch (action.action)`，未知分支走 default）。类型标注
`action: BrowserAction` 只是编译期的，**运行时没有任何约束**。

真正执行侧的闸门（`typeSensitiveGuard` / `payClickGuard` / `classifyField`）在 `driver.ts` 里，
所以**敏感字段仍然填不进去**——这一点是好的。但 `action` 的其余部分（比如
`open_url` 的 url、`type` 的 text）是原样使用的，而 `driver` 的 url 校验只有
`navigate()` 里那一层。

**为什么重要**
比第 2 条轻，因为下游（driver）确实还有敏感闸。但它是同一类问题：
**渲染层 → 主进程的每一个入口都应该是"白名单 + 形状校验"**，而这里只有"白名单"。
另外注意 `drive()` 里 `SENSITIVE_WATCH_CAP_MS = 10 * 60_000` 那套"等用户自己输完"的轮询，
如果渲染层能反复下发 `focus_sensitive_field`，可以堆起多个 10 分钟的轮询。

**建议怎么修**
在 IPC 边界加一个 `sanitizeAction()`（可以在 `driver.ts` 里导出一个和
`toolLoop.sanitizeToolCall` 同构的校验器），对 `action.action` 做枚举比对、
对每个分支的字段做类型 + 长度检查，不合法的**当场拒绝并回 `{ ok: false, error }`**。

### 【一般】4. IP 限流表 `ipHits` 的清理逻辑会**整体清空**，攻击者可以借此重置限流

**在哪里**
`apps/server/src/routes/auth.ts` 第 60-71 行：

```ts
const ipHits = new Map<string, { windowStart: number; count: number }>();
function ipRateLimited(ip: string): boolean {
  const nowMinute = Math.floor(Date.now() / 60_000);
  const hit = ipHits.get(ip);
  if (!hit || hit.windowStart !== nowMinute) {
    ipHits.set(ip, { windowStart: nowMinute, count: 1 });
    return false;
  }
  hit.count += 1;
  if (ipHits.size > 5000) ipHits.clear();   // ← 这里
  return hit.count > 20;
}
```

**是什么问题**
三个叠加的缺陷：

1. **只在"同一个 IP 同一分钟内的第 2 次及以后"才检查 size** —— 第一分支直接 `return false`，
   不走 size 检查；
2. **清空是全局的**：一旦触发，**所有** IP 的计数归零，包括那个已经被限流的攻击者；
3. **没有过期驱逐**：只有 `size > 5000` 这一条出口，所以正常跑久了表里会积压大量
   "上一分钟的陈旧 IP"，把 5000 这个水位**稀释掉**（真正被限流的那个 IP 反而可能因为
   表被清空而解禁）。

**为什么重要**
这条限流是 `/auth/sms/send` 的**第一道闸**，作用注释里写得很清楚："防脚本乱扫"。
它被绕过的后果不是直接入侵，而是**短信通道被别人当免费短信平台用**（成本攻击），
同时也是配合"手机号 1 小时 10 条上限"的补充。目前这道闸在压力下会自己失效。

**建议怎么修**
改成**按时间窗口驱逐**，而不是整体清空：

```ts
// 每分钟最多保留最近 2 个窗口的条目；删掉的只是过期 IP
if (ipHits.size > 5000) {
  const cutoff = nowMinute - 2;
  for (const [k, v] of ipHits) if (v.windowStart < cutoff) ipHits.delete(k);
  // 仍超上限再考虑拒绝新 IP（不要 clear —— 那会把正在生效的限流一起清掉）
}
```

另外建议**把 size 检查提到 `return false` 之前**（否则"每分钟只有 1 次的 IP"永远不触发清理）。

### 【一般】5. 短信验证码校验路径的 `attempts` 累加与 `used = true` 不是原子的

**在哪里**
`apps/server/src/routes/auth.ts` 第 214-226 行：

```ts
const c = await pool.query(`SELECT id, code_hash, salt FROM sms_codes
   WHERE phone_hash = $1 AND used = false AND attempts < $2 AND expires_at > now()
   ORDER BY created_at DESC LIMIT 1`, [hash, VERIFY_MAX_ATTEMPTS]);
if (c.rowCount !== 1 || !verifyCode(code, c.rows[0].salt, c.rows[0].code_hash)) {
  if (c.rowCount === 1) {
    await pool.query('UPDATE sms_codes SET attempts = attempts + 1 WHERE id = $1', [c.rows[0].id]);
  }
  return reply.code(401).send(...);
}
await pool.query('UPDATE sms_codes SET used = true WHERE id = $1', [c.rows[0].id]);
```

**是什么问题**
`SELECT` → 判断 → `UPDATE` 之间没有事务、没有行锁，是典型的 TOCTOU。

- **并发爆破**：同一个手机号 + 同一批验证码猜测并发发出，所有请求都会 SELECT 到同一行
  （`attempts = 0`），各自 `verifyCode` 失败、各自 `attempts + 1`。因为"5 次作废"
  是在 **SELECT 里**判断的（`attempts < 5`），所以并发 N 个请求时，
  **N 个都可能通过门槛**（都在 attempts 还是 0 的时候通过了 SELECT）。
  也就是说"错 5 次作废"这个防线在并发下会被放大到"并发度 × 5"。
- **并发重放**：验证码正确时，两个并发请求都能 SELECT 到 `used = false`，
  **两个都成功**。后者只是多建一次会话（同一手机号两次登录问题不大），
  但语义上"一次性验证码"被用掉两次。

**为什么重要**
6 位数字验证码的空间是 10^6。如果"5 次作废"被放大 10 倍（并发 10），
再加上 60 秒限频 / 1 小时 10 条，实际可猜次数提高了约一个数量级。
**这不是"能不能被攻破"的问题，而是"这道防线的实际强度比设计意图弱"。**
对一个明确写了"5 次尝试"安全策略的系统，这个偏差必须修。

**建议怎么修**
用一条**原子语句**完成"消费"：

```sql
UPDATE sms_codes SET used = true
 WHERE id = $1 AND used = false AND attempts < 5 AND expires_at > now()
RETURNING id;
```

`rowCount === 1` 才算本次成功消费这个码（失败分支走另一条原子语句 `attempts = attempts + 1`，
并带 `AND used = false` 条件）。这样并发下**只有一个**请求能拿到 `RETURNING`，
其余全部落到失败分支。改完请按用户的规矩做一次**反证**（见文末）。

### 【一般】6. `startIdleScheduler` 的 `done` 集合超 800 会整体 `clear()`，导致已处理过的会话被重复抽取

**在哪里**
`apps/server/src/routes/memories.ts` 第 349、366-369 行：

```ts
const done = new Set<string>();
...
const key = `c${row.conv_id}:${row.last_id}`;
if (done.has(key)) continue;
done.add(key);
if (done.size > 800) done.clear();     // ← 整体清空
```

**是什么问题**
`done` 是"这个会话的这一条消息我已经整理过了"的去重集合。
一旦超过 800 条就**整个清空**，于是所有历史切点都变回"未处理"。
而外层条件是"最后一条消息距今 15 分钟 ~ 1 小时"，所以**只要那段时间窗口内的会话还在窗口里，
它们就会被重新整理一遍**。

**为什么重要**
两条独立的影响：

1. **成本**：每次重新整理都会**真调一次模型**（`extractCore` → `llmFetch`）。
   这是后台无人触发的调用，用户看不到、也不会预期到，属于"静默烧 token"。
2. **数据**：虽然 `mem_key` 唯一 + `ON CONFLICT DO NOTHING` 能挡住重复行，
   但**更新已有记忆的路径**（`extractCore` 里的 `UPDATE`）可能会用旧内容覆盖新内容。

**建议怎么修**
和 #4 同类，改成按时间/容量**只驱逐最旧的**，不要 `clear()`。
因为 `done` 里的 key 带 `last_id`，天然只需要保留"最近一段时间"的条目：

```ts
// 用 Map<key, at> 记时间，驱逐超过 2 小时窗口的条目
// 上限用一个明显大于"1 小时窗口内可能出现的会话数"的值（比如 5000），而不是 800
```

### 【一般】7. `startIdleScheduler` 每分钟 `GROUP BY` 全表扫 `conversations ⋈ messages`

**在哪里**
`apps/server/src/routes/memories.ts` 第 353-360 行：

```sql
SELECT c.id AS conv_id, p.user_id, MAX(m.id) AS last_id, MAX(m.created_at) AS last_at
  FROM conversations c
  JOIN projects p ON p.id = c.project_id
  LEFT JOIN messages m ON m.conversation_id = c.id
 WHERE COALESCE(c.keepalive, false) = false
 GROUP BY c.id, p.user_id
```

**是什么问题**
**每分钟一次、不带时间范围、不带 LIMIT 的全表聚合**。
`messages` 表只有 `idx_messages_conversation (conversation_id)` 单列索引，
`MAX(m.created_at)` 用不上它（需要 `(conversation_id, created_at)` 或 `(conversation_id, id)`）。
所以这基本是一次**全量索引扫 + 按会话分组**。

**为什么重要**
这是**典型的"上线初期跑得很好、数据量上来后第一个塌的地方"**。
现在数据少（开发机），每分钟几十毫秒没人注意；等 `messages` 到十万/百万级，
这条 `setInterval` 会变成持续的后台负载，而且它**只查最后一个消息时间**，
本来可以只用 `conversations` 上的一列解决。

**建议怎么修**
两步：
1. **短修**：加 `AND COALESCE(c.keepalive, false) = false` 已经有了，再补一个
   `AND c.id IN (SELECT ...)` 或直接在 `conversations` 上加一列
   `last_message_at`（写入消息时顺手更新），把这个查询降成单表扫描；
2. **索引**：`CREATE INDEX ... ON messages (conversation_id, created_at DESC)`
   （或 `id DESC`），至少让 `MAX` 能走索引。

另外 `setInterval(60_000)` 里没有"上一轮没跑完就跳过"的守卫——
如果某轮因为库慢跑了 90 秒，会**并发叠上第二轮**。建议加一个 `running` 标志。

### 【一般】8. 服务端 `loops` 是纯内存态，重启后与 `task_pauses` 表必然不一致

**在哪里**
`apps/server/src/toolLoop.ts`（`const loops = new Map<string, LoopSession>()`）
与 `routes/loop.ts` 第 345-405 行（`GET /agent/loop/pauses` 的回填逻辑）。

**是什么问题**
循环的全部状态（消息历史、步数、`pendingCallId`、`pause`）**只在内存里**，
而"暂停"却**落了库**（`task_pauses` 表）。两者靠 `routes/loop.ts` 里那段注释
精心处理过的回填逻辑去"猜"一致性：

```ts
for (const rec of records) {
  if (!rec.resumed && hasLoop(rec.loopId) && !isLoopPaused(rec.loopId)) rec.resumed = true;
}
```

注释写得很清楚（这一点做得好），但**它仍然只是"猜"**：服务端重启后，
内存里所有循环消失，于是"库里 `resumed_at IS NULL`"会被维持成"还暂停着"——
**而那个循环其实已经彻底不存在了，用户点"继续"会得到 404**。

**为什么重要**
这是**跨重启的数据一致性**问题。当前阶段能接受（内存态循环 + 10 分钟 TTL 本来就是
"短生命周期"的设计），但从产品角度看：
- 用户重启服务端后，UI 可能显示"3 路任务暂停中"，点下去全是 404；
- `task_pauses` 表会持续增长（每次暂停一行，没有任何清理），
  `uniq_task_pauses_open` 只保证"同一 loopId 只有一条未闭合"，不清理已闭合的。

**建议怎么修**
不需要把循环持久化（那会改变架构）。建议**在 UI / 接口层诚实反映"内存里还在才算数"**：
`GET /agent/loop/pauses?open=1` 增加一个字段明确告诉前端"这条记录对应的循环**已经不在内存里**"
（`hasLoop(loopId)` 为 false），让前端显示成"已失效的暂停记录（服务端重启过）"而不是
"暂停中"。同时给 `task_pauses` 加一个保留期清理（比如 7 天前的已闭合记录删掉）。

### 【一般】9. `agent.ts` 的 `EXEC_TIMEOUT_MS` 只是放弃等待，**没有中止底层动作**

**在哪里**
`apps/desktop/electron/agent.ts`（`EXEC_TIMEOUT_MS = 20_000`，用 `Promise.race` 包住执行）。

**是什么问题**
`Promise.race` 只决定"我这边等不等"，**不会取消**已经发出的 `drive()` 调用。
超时之后：桌面认为"这一步失败了，报给服务端"，但**浏览器里的动作可能还在继续**
（尤其是 `navigate()` 的 30 秒超时、`scrollPage()` 的 CDP + JS 双层兜底、
`typeInto()` 的四层兜底 —— 这些内部都有各自的等待）。

**为什么重要**
后果是**状态分叉**：服务端收到"失败"→ 让模型重选下一步 → 桌面同时还在跑上一个动作。
两个动作打在同一个页面上，可能造成"AI 报告说没点中，但其实点中了"这类难以复现的行为，
也正是 `noChange` 判定容易失准的来源。同时这是**资源泄漏面**：
超时后无人引用的动作仍然持有 CDP session / 定时器。

**建议怎么修**
给 `drive()` 传一个 `AbortSignal`，让它内部的长等待（`navigate` 的 30s、
`scrollPage` 的兜底等待、`typeInto` 的逐层重试）都检查 `signal.aborted` 并提前退出。
这是比调大超时更根本的修法。

### 【轻微】10. `driver.ts` 的 `tasks` Map 没有上限也没有 TTL

**在哪里**
`apps/desktop/electron/driver.ts` 第 73 行 `const tasks = new Map<number, TargetTask>()`，
只有第 361 行的 `tasks.clear()`（全局复位时）。

**是什么问题**
`driver` 里其它几种状态都做了生命周期管理：

### 【轻微】11. CORS `origin: true` + `/health` 免认证暴露运营信息

**在哪里**
`apps/server/src/index.ts` 第 46 行（`cors({ origin: true, ... })`）
与第 52-82 行（`GET /health` 无 JWT）。

**是什么问题**
`/health` 回 `llmCalls` / `liveLoops` / `runningLoops` / `pageStates` / `sms` 模式 / `llm` 是否配置。
这些是**调试信息，但对攻击者有用**：能判断服务是否在用真短信通道、模型是否配好、
当前有多少任务在跑（配合时间可推断用户行为）。
同时 `origin: true` 会**回显任意来源**。

**为什么重要**
服务只监听 `127.0.0.1`，所以外部网络打不到 —— 这一层风险是**本机其它程序**
（任何本地进程 / 用户浏览器里打开的任意网页）可以：
1. 直接 `fetch('http://127.0.0.1:8787/health')` 读到运营数据（不需要 CORS，因为是简单请求，
   只是读不到响应体——但 `origin: true` 让**任意网页**都能读到）；
2. CORS 放行任意 Origin 意味着**任何用户浏览的网页**都能对 `127.0.0.1:8787` 发起带凭证的
   跨域请求（如果它能拿到 token）。注意 token 在 `localStorage`，网页拿不到；
   但 `/auth/*` 的 POST 不需要预检就能发（`application/json` 会预检，这里配了 methods 所以放行）。

**建议怎么修**
`/health` 拆成两个：免认证的只回 `{ ok, db }`；带 `llmCalls` 等运营指标的挪到一个
**带 JWT** 的 `/health/detail`（验收脚本改成带 token 调用）。
CORS 白名单收紧到 `['http://localhost:5173', 'file://']` 之类的确定来源。
（这两条都不是高危，但属于"把面收干净"，成本很低。）

### 【轻微】12. `phonePepper` 缺省回退到 `dataKey`，密钥复用

**在哪里**
`apps/server/src/env.ts` 第 80 行：
```ts
phonePepper: (process.env.PHONE_PEPPER || '').trim() || dataKey,
```
`.env.example` 也明写了"留空则退回 DATA_KEY"。

**是什么问题**
`dataKey` 是 **AES-256-GCM 的加密密钥**，`phonePepper` 是 **HMAC 的密钥**。
同一份密钥同时用于"加密"和"哈希"，违反了密钥分离原则。
GCM 内部是 CTR + GHASH，HMAC-SHA256 与它的数学结构不同，**不是直接可攻击的**，
但一旦 `dataKey` 泄漏，攻击者**同时**获得了"解所有密文"和"枚举手机号做彩虹表"的能力。

**为什么重要**
它的严重性取决于 `DATA_KEY` 的保密强度。目前 `DATA_KEY` 只来自环境变量、代码里无兜底，
这一点做得对。但**默认回退**意味着"用户什么都不配"也能跑起来——
这正是安全设计里最不该有的便利。而且 `phone_hash` 上有 **UNIQUE 索引**，
反过来说攻击者拿着 pepper 可以对任意手机号直接查"这个号注册过没有"。

**建议怎么修**
把 `PHONE_PEPPER` 也列进必填（和 `DATABASE_URL` / `JWT_SECRET` / `DATA_KEY` 同一档），
缺失就**拒绝启动**并给出生成命令。`env.ts` 里 `isProduction` 时的注释也说清了
"缺了就拒启/拒发（这是特性）"—— 这里恰好是那条原则的一个例外，补上就一致了。

### 【轻微】13. `loops` 的 TTL 回收与 `pageState` 的 TTL 回收口径不一致

**在哪里**
`toolLoop.sweep()`（TTL 10 分钟 + 超 32 个按 `touchedAt` 最旧回收）
vs `pageState.sweep()`（TTL 10 分钟 + 上限 64）。

**是什么问题**
两者都是"按 wcId 建状态"，但**回收顺序和上限不同**：
`loops` 是"先 TTL 再按最旧淘汰"，`pageState` 也是。看起来一致——
但 `pageState` 的 `pageStateOf()` 里有**兜底补归属**逻辑（"只有 `userId <= 0` 才认新 userId"），
而 `bindPageLoop()` 会把 `loopId` 写进去。当一个循环被 TTL 回收、但它绑定的 pageState
还活着时，`pageState.loopId` 就指向一个**不存在的循环**。

**为什么重要**
这是**软状态之间的悬挂引用**。目前没有代码依赖 `pageState.loopId` 去找循环，
所以是"潜在"问题；但 `pageState` 的 TTL 和 `loops` 的 TTL 都是 10 分钟却**各自独立计时**，
两者几乎必然不同步。建议在报告里记为"需要确认的耦合点"（我也列进了第二节）。

**建议怎么修**
统一由一个 `sweep()` 驱动两者的回收（或至少在回收 loop 时顺手清掉 `pageState.loopId`），
避免"两个 10 分钟不是同一个 10 分钟"。

### 怀疑 1. 渲染层可以改 `partition`，绕过按项目共享登录态的隔离

`apps/desktop/src/browser/url.ts` 的 `partitionFor()` 生成
`persist:workbench-browser-project-<projectId>`，而 `<webview partition=...>` 的值
**由渲染层字符串决定**。主进程只用 `PROJECT_PARTITION_RE` 去**读**项目号，
不做**写**方向的校验（`main.ts` 里那几处都是在 `web-contents-created` 之后取分区名）。
所以理论上渲染层（或被投毒的第三方脚本）可以给 webview 一个**别的项目**的 partition，
从而读到那个项目的登录态。

**严重性判断**：同一账号内的项目，所以不是"跨用户越权"。但"登录态按项目隔离"
是 Phase 3 明确的产品设计（写在工作区 MEMORY 里），绕过它是设计失效。
**怎么验证**：在 dev 环境往 `useBrowserWorkspace` 里注入一行，把 `partition` 改成另一个
项目的值，看能否读到那个项目的 cookie。

### 怀疑 2. `workbench:drive` 可以被用来堆起多个 10 分钟轮询

`driver.ts` 的 `startSensitiveAutoResume()` 有 `SENSITIVE_WATCH_CAP_MS = 10 * 60_000`，
每次 `focus_sensitive_field` 动作都可能起一个。如果渲染层能反复下发这个动作（见问题 #3），
每个都挂一个最长 10 分钟的 `setTimeout` / 轮询。**怎么验证**：
数一下 `SENSITIVE_WATCH_*` 相关的定时器有没有"同一 wcId 只允许一个"的守卫。

### 怀疑 3. `messages` 表缺少面向"按会话取最新 N 条"的复合索引

`/chat/history` 用 `WHERE conversation_id = ? ORDER BY id DESC LIMIT 200`，
`/chat/stream` 用 `ORDER BY id DESC LIMIT 24`。表上只有
`idx_messages_conversation (conversation_id)` 单列索引。
PG 能用它定位分区，但 `ORDER BY id DESC` 需要**排序**（除非走 `(conversation_id, id)` 复合索引）。
**怎么验证**：`EXPLAIN ANALYZE` 看有没有 `Sort` 节点；数据量大时这是长会话每次加载的开销。

### 怀疑 4. `cache-control` / `hijack` 之后 Fastify 的错误处理路径是否还会被走到

`chat.ts` 在 `reply.hijack()` 之后手写 SSE。劫持之后如果抛错，
`dbErr(reply, err)` 会尝试 `reply.code().send()` —— 在 hijacked reply 上这**可能报
"Reply was already sent"** 并产生未捕获异常。**怎么验证**：在 `hijack()` 之后
的那段 `try` 里人为抛一个错，看服务端日志有没有额外的 Fastify 警告。

### 怀疑 5. `resumingWc` / `liveLoops` 的去重是**进程内**的，多窗口场景下不成立

`main.ts` 的 `resumingWc = new Set<number>()` 和 `liveLoops = new Map<number, Lane>()`
都在主进程内存里。同一份应用如果被多开（工作区 MEMORY 里记录过 WorkBuddy 的多开方法），
两个实例**各自**有一份 `liveLoops`，但服务端的 `loops` 是**共享**的
（都连同一个 8787、同一个账号）。所以"同一条循环被两个桌面实例同时驱动"
在服务端只会撞到 `LoopBusyError`（409），不会串台 —— 这一点是安全的。
但 `wcId` 在两个实例里会**撞号**（都是本机 Electron 分配的 guest id），
于是 `stopLoopsOfPage(userId, wcId)` 可能停掉**另一个实例**的那一路。
**怎么验证**：需要多开环境，成本较高；先记为"已知风险"。
