# 待办：R2 残留 - tasks.payload.goal 明文存储

- 发现时间：2026-09-22 独立验收
- **状态：已修（2026-09-23，收尾 6 / 重建 1）** —— 验收报告见 `docs/acceptance/收尾6-goal加密-验收报告.md`
- 原位置：
  - `apps/server/src/routes/agent.ts` `POST /agent/task/start`：`payload = { goal, steps: [] }` 明文 JSONB
  - `apps/server/src/routes/agent.ts` `buildFallbackDoc`：`## 目标` 直接使用 goal
  - `apps/server/src/routes/agent.ts` `GET /agent/task/current` 返回 goal 明文
- 现象：用户在聊天里说“帮我在页面备注框里填入：我的密码是Secret123” -> goal 含密码，明文进 tasks 表和任务文档（加密存储 result_enc，但 goal 本身明文，且文档解密后可见）
- 影响：密码/卡号等敏感信息以任务目标形式明文躺在 PG JSONB 字段，备份可见；任务文档展示时也会显示明文

## 当初记的「建议后续方案」逐条对账

| 建议 | 落地情况 |
| --- | --- |
| 1. tasks.payload.goal 加密存储或仅存脱敏版本 | **已做（选了加密，不是脱敏）**：新增 `tasks.goal_enc`（AES-256-GCM，同一把 `DATA_KEY`），payload 里**删掉 goal 键**；`task_pauses` 同样新增 `goal_enc`、明文列恒写 NULL。历史行由启动时的 `migrateTaskGoalEncryption` 幂等回填。 |
| 2. 任务文档“目标”字段脱敏或截断 | **未做，且刻意不做**：文档是给人看的，`## 目标` 必须是原文才有用。落库那头本来就是密文列 `result_enc`，解密后可见属设计如此（报告「查到但没修」第 2 条）。 |
| 3. `GET /agent/task/current` 返回脱敏 goal | **未做，且刻意不做**：脱敏会让桌面刷新后的任务卡变成「****」，那是把功能吃掉。改成**解密优先、回退旧列**，用户看到的还是原话；传输靠本机回环 + JWT（报告第 3 条）。 |
| 4. 评估是否需要对存量数据做清理/加密迁移 | **已做**：`migrateTaskGoalEncryption(pool, cipher)` 每次启动跑（幂等 + 带重试）。fail-closed：拿不到 cipher 就跳过打 warn，下次再试，绝不写明文兜底。 |

## 比原建议多做的一件事（真库验收逼出来的）

- **`tasks.title` 一并停用**（新任务恒写 NULL、回填时清空）：它存的是 `goal.slice(0,80)`，
  是同一个明文目标的**第二份副本**。不清它，对不到 80 字的目标（绝大多数）等于没加密。
  核查过 title 只被服务端当作 goal 的兜底读，没有任何界面直接展示它。
- **回填条件不能用 `WHERE goal_enc IS NULL`**：真库里存在「`goal_enc` 已有值 + 明文列也还有值」的
  残行（灰度/回滚期间新旧代码各写一半），那种行永远轮不到 → 明文永远清不掉，而只造「纯老行」的
  验收照样全绿。已改成按「明文还在不在」扫描，两边都有值时保留已有密文、只清明文
  （明文那份可能是 title 的 80 字截断值，拿它覆盖密文会丢内容）。

## 2026-09-24 用户拍板：两件推迟的事（写清方案，别只写「以后再说」）

收尾 6 的条件验收（报告第 9 节）过完之后，用户明确拍板下面两件**本批不做**，
但要求把方案记在这里，免得下次开工时重新想一遍。

### 1. 老明文列暂不 DROP（`tasks.title`、`task_pauses.goal`）

- **现状**：两列都恒写 NULL，读路径也不再依赖它们（`taskGoalFromRow` 是
  `goal_enc` 解密 → `payload.goal`（老行）→ `title`（更老的行）三级兜底）。
- **为什么不 DROP**：DROP 之后回滚到收尾 6 之前的代码会**直接报错**（旧代码 INSERT 带 title / goal 列）。
  留着这两列的成本是「库里有两个恒 NULL 的列」，几乎为零；换来的是随时能回滚。
- **什么时候做**：**批次 K 落地并跑稳之后**再议（用户的原话口径）。届时顺序建议：
  1. 先确认线上没有回滚需求（批次 K 稳定运行一段时间）；
  2. 先把读路径里最后一级兜底（`title`）摘掉，跑一轮 `verify:db`；
  3. 再 `ALTER TABLE ... DROP COLUMN`，**单独一个提交**，配一次真库验收（含重启回填幂等）；
  4. 备份先行（`pg_dump` 留一份带旧列的），DROP 是不可逆的。
- **验收要补的断言**：DROP 之后 `migrateTaskGoalEncryption` 不能再 SELECT 那两列
  （否则启动直接抛结构性错误 → 走重试 → 永远失败）。这条现在没有断言，因为列还在。

### 2. 启动回填的全表扫描优化（水位线方案）

- **现状**：`migrateTaskGoalEncryption` 每次启动都扫
  `task_pauses WHERE goal IS NOT NULL` 与 `tasks WHERE (payload->>'goal') IS NOT NULL OR title IS NOT NULL`。
  JSONB 表达式用不上索引 → 几十万行时每次启动都是一次全表扫。
  现在库里行数是几十条量级，开销可忽略，所以用户拍板**本批不做**。
- **水位线方案（记下来，别重想）**：
  - 在已有的 `schema_meta`（键值表）里存两个键：
    `task_goal_backfill_done_pauses` / `task_goal_backfill_done_tasks`，值是「已确认无明文的最大 id」。
  - 启动回填改成两段：
    ① **增量段**：只扫 `id > 水位` 的行（新代码写的行本来就没明文，这段基本是空转）；
    ② **全量段**：仅当 `schema_meta` 里没有水位键（首次升级）或
    `--force-full-backfill` 时才跑一次全表，跑完把水位写进去。
  - **水位只能单调前进**，且必须在「这一段真的零失败（`failed === 0`）」时才推进 ——
    有失败行就把水位停在最小失败 id 之前，下次启动重试那些行。
  - **不一致行（条件3）永远不进水位**：它们要每次启动都重报，不能被水位吃掉。
    实现上就是水位只按「已处置（加密或清明文）」的行推进，`mismatched` 的行单独每次都扫。
  - 验收要补：水位存在时**不全表扫**（用 `EXPLAIN` 或行数计数断言）、
    水位缺失时退回全表、失败行不被水位跳过、不一致行每次仍被报出来。
- **触发条件**：`tasks` 或 `task_pauses` 行数上到 ~5 万，或启动日志里回填那段耗时肉眼可见（>1s）。
  在那之前不要做 —— 加了水位就多一个「水位与实际不符」的新故障面。
