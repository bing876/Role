## 1. #3 桌面 `workbench:drive` 不校验 action 形状

### 问题复现（为什么"不校验"是真问题）

`workbench:drive` 的入参来自渲染层，运行时**什么都能传**。没有闸的时候有两类后果：

1. `action` 传成 `null` / 字符串 / 数组 → `drive()` 第一行 `action.action` **当场抛 TypeError**，
   而且是在 `try` 之外 → IPC 直接 reject，调用方拿到的是**栈**而不是人话；
2. `action` 是对象但字段类型不对（`{action:'wait', seconds:'abc'}`）→ 各分支拿着
   `undefined`/`NaN` 继续跑：`wait` 会 `Math.min(Math.max(NaN,0),30)` → NaN →
   `setTimeout(NaN)` **立刻返回**（静默变成"没等"）。这类"不报错、只是行为不对"最难查。

### 改了什么

- `apps/desktop/electron/driver.ts` 新增 `validateBrowserAction()` + `ActionShapeCheck`：
  按动作类型逐项校验字段的**存在性与类型**，并给每个上限（url 2000 / target 1000 / text 20000 /
  fields 100 条 / wait 1~300 秒 / outline 100 项）。
- 闸放在 **`drive()` 入口**，不是各个 IPC 处理器里 —— `drive()` 是**唯一**的执行入口
  （`workbench:drive`、`workbench:read-page`、驾驶循环的 `exec` 钩子都走它），
  放一处覆盖三个调用方。
- `packages/shared`：`DriveResult.action` 的类型从 `BrowserActionType` 放宽为
  新增的 `DriveActionLabel`（= `BrowserActionType | 'invalid'`）——
  形状不合法时连"这是哪个动作"都答不上来，如实说 `'invalid'` 比硬塞一个假动作名诚实。

### 校验口径（刻意宽松，这是关键设计）

- **只查形状，不查业务语义**：`open_url` 传空串**仍然放行** ——
  空地址该由 `navigate()` 给出它自己那句人话错误，提前拦掉会把既有错误文案换掉
  （agent 侧的 `NO_INPUT_FOUND` 之类判断会跟着失灵）。
- **允许未知的额外字段**（忽略）：将来给某个动作加可选参数时，老版本主进程不该因为多了字段就拒收。

### 验证 & 反证

- `scripts/verify/drive-shape-probe.mjs`：**103 条断言 / 0 失败**。
  - [A] 真值表 17 条放行 + 26 条拒绝（每条拒绝还额外断言"给了人话"）；
  - [B] 拿 8 种畸形入参调**真的 `drive()`**，断言"**没有抛异常** + 返回 ok=false + 带可读 error"。
- 反证（`scripts/verify/p2-revert-proof.py` 的 A 段）：关掉形状闸后
  **10 条变红**（`drive(null)`/`drive(undefined)` 抛异常、5 条"拒绝"断言失效），还原后回到 0。

## 2. #4 IP 限流表的 `clear()` 缺陷

### 2.1 两个缺陷

| # | 缺陷 | 后果 |
| --- | --- | --- |
| ① | `if (ipHits.size > 5000) ipHits.clear()` 写在**"同 IP 同窗口第 2 次及以后"**的分支里 | **每个 IP 只来一次**的扫描（最典型的分布式扫描）**永远不触发清理** → 表无限涨 |
| ② | 触发时**整表 `clear()`** | 把**正在生效的限流**一起放掉 —— 攻击者撑满表就能让自己的计数归零，下一轮又是干净的 20 次。**这是绕过，不只是内存问题** |

### 2.2 ★ 我自己的第一版修复有残留漏洞（反证时才发现）

第一版我改成"超上限时先清过期、再按最旧淘汰"。看着对，但：

> 攻击者往往是**第一个**来的 → 它天然是"最旧"的那条 →
> 表满时**无差别按最旧淘汰**会**优先把它踢掉** → 计数归零 → **绕过依然成立**。

改法：淘汰时**避开正在承担保护职责的条目**（`count > maxPerMinute`），
优先淘汰"还没超限的"那些；只有连它们都淘汰光了（意味着同一分钟有 5 万个以上 IP 各自超限，
真实部署该在网关层拦）才退回按最旧淘汰。

同时把软上限从 5000 提到 **50000**（≈3 MB）：淘汰是有代价的，与其把上限压低频繁淘汰，
不如让它足够宽，正常情况下根本走不到淘汰那一步。

### 2.3 改了什么（可测试性也一起改了）

- 把限流器改成**工厂** `makeIpRateLimiter({ maxPerMinute, softCap, windowMs, now })`，
  线上仍用同一个默认实例（`ipRateLimited()` 调用点不变）。
- 注入时钟/阈值**不是为了方便，而是必须**：真等一分钟才能验"窗口翻篇"、
  真造 5 万个 IP 才能验"表满时的淘汰" —— 两者都不现实。

### 2.4 验证 & 反证

- `scripts/verify/ip-rate-probe.mjs`：**22 条断言 / 0 失败**（跑的是编译产物 `dist/routes/auth.js`）。
  含：基本口径 / 窗口翻篇 / **只来一次的扫描不涨表** / **撑满表后攻击者仍被限流** /
  过期条目优先清理 / 默认阈值是 20。
- 反证：注入旧写法后 **3 条变红**（扫描涨表、攻击者被 `clear` 放掉、过期条目没被优先清理），还原后回到 0。
- **★ 反证又揪出我测试的弱点**：第一版测试只让噪声 IP"各来一次"——
  而旧代码的 `clear()` 在**重复 IP 分支**里，**根本走不到**，所以第一版测试区分不出新旧代码。
  补上"让某个 IP 再来一次"这一步之后才变红。（见 §6 教训）

## 3. #5 验证码消费非原子（TOCTOU）

### 问题

原来是「先 `SELECT` 判 `used`，再 `UPDATE SET used = true`」。
两个并发请求会**双双通过**那句 SELECT（都读到 `used = false`），
然后各自置 `used = true` 并各自发一份 token —— **一个验证码被消费两次**。
6 位码 + 5 分钟有效期，重放一次就是多一个会话。

### 改了什么

把"是否还能用"和"标记已用"**压进同一条语句的 WHERE**：

```sql
UPDATE sms_codes SET used = true
 WHERE id = $1 AND used = false AND attempts < $2 AND expires_at > now()
 RETURNING id
```

判据是 **`rowCount`**，不是"语句有没有报错"—— 抢输的那次不会报错，只是影响 0 行。
计错次数的 `UPDATE` 也补上了同样的条件（不再给已消费的行加计数）。

### 验证 & 反证

- `scripts/verify/sms-code-race-probe.py`：**19 条断言 / 0 失败**。四个场景：
  1. **★ 确定性锁竞争**：外部事务先 `SELECT ... FOR UPDATE` 锁住那一行，
     逼两个请求**同时**读到 `used=false` 并**双双卡在 UPDATE 上**，再放行 →
     断言**恰好 1 次成功**。（实测"放行前仍卡在 UPDATE 上的请求数：2 / 2"）
  2. 真并发 12 路提交同一个码 → 恰好 1 次 200、11 次 401；
  3. 直接查库：该行 `used=true` 且 `attempts` 没被加（成功消费不算猜错）；
  4. 串行重放失败 + 猜错 5 次后正确的码也失效。
- 反证：注入非原子写法后**变红**，还原后回到 0。

### ★ 这里有个重要的方法论收获

**本地时序竞态是"撞不稳"的**：我第一版只用"12 路并发 HTTP"，
注入旧代码后**跑了两轮，只有一轮撞到**（12 路里撞中的概率很低 —— 本地 DB 太快，
`SELECT → verifyCode → UPDATE` 的窗口是微秒级）。

所以补了**确定性手段**：用外部事务把行锁住，**把窗口 100% 造出来**。
补上之后每次都能稳定复现。

> 结论：遇到并发缺陷，**优先想"怎么把窗口 100% 造出来"**，不要"多跑几遍碰运气"。

## 4. 怀疑 1：渲染层改 `partition` 绕过项目隔离

### 4.1 先复核原报告的修复建议 —— **它是错的（会改坏已设计好的行为）**

报告建议「加 `will-attach-webview` **强制改写** `webPreferences.partition`」。
但 `BrowserPanel.tsx:302-304` 明确写着：

> 「注意 `t.projectId` 是**开页那一刻**定下的（不是现在的项目），
> **所以切项目不会让已开的页换一套登录态**。」

也就是说 **页可以跨项目共存**。统一"强制改写"会让旧页突然换成另一套 cookie
—— **等于把用户登出**。这跟 #1 那次是同一类问题：**报告的建议没考虑合法路径**。

### 4.2 还有一个更根本的定性问题

`browser/url.ts` 的注释写得很清楚：

> 「⚠️ 这一层**只管登录态**。标签页归属、任务执行状态、暂停/继续，全部照旧**按 agentId 隔离**」

**分区在本产品里的定位是「登录态隔离」（功能），不是安全边界。**
渲染层本来就是**同一个信任域**，它合法地同时承载所有项目的标签页 ——
所以"渲染层能访问自己所有项目的分区"**在设计上是必然的**，不是越权。

### 4.3 那真正该收的是什么？

复核我上一批的实测结论（`partition-isolation-probe.mjs`）：
分区之间**确实隔离**；`session.fromPartition(name)` **无任何访问控制**；分区名**可猜**
（`persist:workbench-browser-project-<自增 id>`）；主进程**没有** `will-attach-webview`。

于是真正能收、且**不会误伤**的是这两条：

1. **形状**：分区名必须是 `persist:workbench-browser-project-<正整数>`（或兜底 `-none`）。
   其它一律隔离 —— 包括**空分区**（那会落到**默认 session**，和主窗口共用一套 cookie）
   和任意自造名字（`persist:evil`）。
2. **归属**：项目号必须是**当前登录用户名下**的项目 —— 够不到"别的账号在这台机器上留下的分区"。

### 4.4 改了什么

- `main.ts` 新增**纯判定函数** `decideWebviewPartition(raw, owned, synced)`，
  由 `will-attach-webview` 调用（抽成纯函数是为了能单独验证）。
- **处置方式是"改写到隔离的兜底分区"，不是 `preventDefault()`**：
  后者会让这张页**根本没有 guest** → 用户看到一张**永远空白的卡片**且**没有任何解释**，
  正是我们一直在修的那种"静默失败"。改写后页面照常能开，只是**没有任何项目的登录态**
  （独立空分区）—— **安全性不打折，体验好得多**。
- 新增 **`workbench:projects:sync`** 通道（渲染层拿到 `/projects` 后推给主进程）+
  登出时清空（否则下一位登录者继承上一位的白名单）。
  为什么必须显式推：`will-attach-webview` 是**同步**事件，`preventDefault()` 必须当场调用，
  **没机会 await 一次 HTTP**。
- 未同步项目列表时**放行但告警**：那时主进程确实不知道这个用户有哪些项目，
  "不知道就拦"会把启动瞬间的合法标签页全打成隔离分区。

### 4.5 验证 & 反证（**含内置对照实验**）

`scripts/verify/partition-guard-probe.mjs`：**28 条断言 / 0 失败**，四段：

- [A] 判定逻辑真值表 11 条（跑的是从 `main.ts` **抽出的函数原文**，不是抄的副本）；
- [B] **真机**：请求项目 999（不在名下）→ 断言 guest **没有**用 999 的 session、**用的是隔离分区**；
  请求 101（在自己名下）→ 断言**没被误伤**；
- [C] **对照实验（这就是反证）**：同样请求 999，但**不加闸**（= 修复前的行为）→
  断言 guest **确实**用了 999 的 session，并断言"加闸 vs 不加闸 guest 用的 session **不同**"。
  → **漏洞是真的 + 闸确实在起作用**，两件事一次证完；
- [D] 静态：`main.ts` 真的注册了这道闸、用的是纯判定函数、确实改写了 `partition`、
  `projects:sync` 通道在、preload 暴露了、渲染层两个调用点都在。

> 这个对照实验的设计意图：光证明"现在挡住了"不够 ——
> 还要证明"**不加闸就挡不住**"，否则无法排除"这个请求本来就无害"的可能。
