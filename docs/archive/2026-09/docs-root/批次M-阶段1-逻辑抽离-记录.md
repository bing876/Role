## 片 3 · `app/browserGlue`（跨 chat × browser 的胶水）

推：`e7c96a9`（remote head，已 `ls-remote` 确认）

### 为什么单独一层

这三样东西**同时**属于聊天与浏览器两侧：

| 东西 | 聊天侧的一面 | 浏览器侧的一面 |
|---|---|---|
| 求助卡 `helpCards` / `curHelp` | 卡片长在聊天流里，按**智能体**分桶 | 触发时要把 `browser.view` 切到 `embed`（露出那一张页） |
| 「上下文没了」`loopGone` | 画在聊天区上方的确认卡 | 决定通过 `loopGoneChoice(wcId, …)` 回主进程 |
| 窗口几何 `embedRect` | HelpCard 每帧量一次、上报 | 交给 BrowserPanel 写进那个**一直挂着的** webview 的内联样式 |

放进任何一侧的 feature 都会形成 `features/A → features/B` 的横切依赖 —— 所以按用户拍板归 **`app/`**：
`apps/desktop/src/app/browserGlue.ts`（`useBrowserGlue`）。

> ★ **形态说明（要跟用户对一下）**：拍板写的是「`app/BrowserGlue` **Provider**」，
> 但本阶段铁律是「JSX 一行都不许动」，而 Provider 必须在 JSX 里加一层包裹 ——
> 所以这一片先落成**同名 hook**（对外契约就是这一份 `BrowserGlueApi`），
> 等阶段 2 允许动 JSX 时原样翻成 Provider 即可（`features/**` 不许依赖 `app/**` 这条已经满足了）。

### 搬了什么（只搬逻辑；JSX 35615 字符、CSS md5 都没变）

- `loopGone` state + `answerLoopGone`；
- `helpCards` state + `curHelp` + 那个「切智能体时跟着切视图」的 effect（含 `exitEmbed` 那条**真机时序破口**的注释与写法）；
- `embedRect` / `onEmbedRect`；
- `helpCardAct`（两个按钮走 `resumeTask` / `agentDrop`）；
- 给主进程事件分发用的三个写入口：`showHelp` / `clearHelp` / `clearEmbed` / `askLoopGone`（`clearHelp` 保留原来的「没有就别造新对象」引用稳定守卫）；
- `HelpCardView` 类型从 App 移到本文件并导出。

**App 侧只改三处调用**（名字全部没变）：
`setHelpCards({...})` → `showHelp({...})`；两处 `clear` 分支 → `clearHelp(ownerAgent)` + `clearEmbed()`；
`setLoopGone(…)` → `askLoopGone(p.wcId, p.question)`。

### ★ 本片最值钱的一条：反证抓到一个**假绿**

我先写的 hook 级断言只看 `browser.enterEmbed/exitEmbed` 的调用序列 —— 结果注入
「`curHelp` 改成 `Object.values(helpCards)[0]`（**跨对话泄漏**）」
时**验收网全绿通过**（假绿！）。原因：那个 effect 是直接读 `helpCards[curAgentId]` 的，
`curHelp` 只影响**渲染**，而我的 Host 当时 `return null` —— 渲染结果没人看。

修法：让 Host 把 `curHelp` **渲染出来**（`卡:4242` / `没卡`）并断言 —— 现在注入立刻变红：
`97 号的求助卡漏到 98 号对话里了：卡:4242`。
**教训：只断言副作用（函数被调）会漏掉"值算错了"这类抽错，能渲染出来的东西就要渲染出来断言。**

### 验收（`npm run verify:logic`：12 → 17 PASS / 0 FAIL）

新增 5 条：

1. 主进程 `help` 事件 → `.helpCard` 出现在 DOM，问题/提示文案与 `helpCard--captcha` 都对；
2. 点「我处理好了，继续」→ `resumeTask(4242)`（**唯一**一次调用）、卡片立刻收起；

`sendChat`（HEAD 块口径 **486 行**）一按下去要同时驱动**三个 feature**：聊天（落桶 / 打字机 / 提示）、
浏览器（开页 / 叫醒睡着的页 / 「停」 / 刷驾驶横幅）、任务（熄红点）+ 一个主进程循环号。
如果让它去 `import` 那些 feature，立刻就是双向依赖（`useBrowserWorkspace` 自己还要拿
`setChatNote`）。所以这里的做法是：**正文逐字搬，依赖一律从组合层注入**。

### 搬了什么

| 类别 | 内容 |
|---|---|
| 函数 | `sendChat`、`onSend`、`startAgentTask` |
| state | `runningLoopId` / `runningLoopWcId`（+ 两个**最新值镜像** ref）、`searchHint` |
| 注入（新增端口） | `session` / `input` / `setInput`、`browserRef`、`setHasUnread`、`agentsRef`、`lastUserWasOpenRef`、`lastUserGoalBeforeConfirm`、`loadAgentStateRef`、`resume`（「等继续」四件套）、`askInfo`（「驾驶员问资料」四件套）、`shouldFallbackLaunch`、`intent`（8 个纯本地判定） |

**两个最新值镜像**（都是"定义排在 `useChat(...)` 之后"造成的，不是新发明）：

- `browserRef` ← `useBrowserWorkspace(...)`（它排在 `useChat` 之后，因为要用 `setChatNote`）；
- `loadAgentStateRef` ← `loadAgentState`（定义在下面，一轮结束要回刷状态行）。

两者都按本仓库既有规矩「渲染期赋值、调用期读取」（与 `chatsRef` / `agentsRef` / `curAgentRef` 同一条）。

### 建智能体的意图检测：**现在在哪儿**（批次 L 要用，用户点名）

- **桌面这一侧没有**任何"建智能体"的本地判定。本地闸只有五处：敏感值 / `detectStopIntent` /
  `detectOpenUrl` / `detectUnknownOpenTarget` / 待确认继续（`CONTINUE_*_RE`）。
- **实现在服务端**：`apps/server/src/orchestrator/agentBuilder.ts` ——
  `getPendingBuildIntent:29` / `setPendingBuildIntent:32` / `isConfirmMessage:39` /
  `isQuestionAboutBuilding:47`（**问句不建**：含"是什么/怎么建/吗/？"的一律不建）/
  `detectBuildIntent:74`（建+角色的正则 + 「我是…」自我介绍排除 + 过短排除）/
  `buildAgentImmediately:127`。
- **调用点在** `apps/server/src/routes/chat.ts:491–550`（`/chat/stream` 里）：
  ① 有 pending 且 `isConfirmMessage(message)` → 建号（491–503）；
  ② 否则 `detectBuildIntent(message)` → 存 pending + 回**确认话术**
  「要建一个「X」，职责：…，确认就建？（回"确认/可以/建吧"）」（548–551）。
  确认话术与"已建好"都是**普通 SSE `delta` + `done`**（不新开帧类型）。
- **桌面这侧的接入点**：`features/chat/useChat.ts:703` 那一段——
  注释「所有用户输入统一发送到服务端，服务端自主判定是否进入任务模式，不依赖本地正则白名单」，
  即 `fetch(`${API_BASE()}/chat/stream`)` 的请求体里 **`message: value`（用户原话，逐字不改）**。
  桌面对"建智能体"**没有任何本地判定**（唯一的相关痕迹是输入框 placeholder 里的例子文案）。
- **给批次 L 的一条提醒**：`CONTINUE_STRONG_RE`（本地的「继续/可以」判定）与服务端的
  `isConfirmMessage`（「确认/可以/建吧」）有**语义重叠**。若用户在中栏开着页时回一句「可以」，
  桌面会把它当"在当前页上干活"预备给驾驶员（`browseGoal` 非空 → 兜底发车闸可能真的发车）。
  服务端的确认话术是「要建一个「X」，职责：…，确认就建？（回"确认/可以/建吧"）」，
  而桌面的 `CONFIRM_ASK_RE` = `/(确认后我开始操作|需要我用工作台浏览器|要我帮你…|要我打开|要不要我用浏览器)/`
  —— **匹配不上**这句，所以现行代码不会把这种轮次当成"等确认"，**不会拦**。
  批次 L 落地时要么让服务端在 `meta` 里带一个"这轮是建号确认"的标记、要么在桌面侧按同一位置加一道本地闸。
