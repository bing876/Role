# 修复 P0「静默重开」—— 2026-09-21

> 一句话：**处于"等待用户"状态的循环不再被闲置超时悄悄回收；万一循环确实不在了，
> 绝对不许静默开新的一轮，必须先明确告诉用户代价，由用户点过确认才新建。**
>
> 基线（Harness 动手前）：tag `pre-harness-baseline` → commit `80c6348`
> 本次只改这一处。**「不可逆动作守卫」本轮未做，等用户拍板。**

---

## 0. 为什么要做这个（背景，一句话）

只读审计 `docs/审计-重复执行风险-20260921.md` 的「⚠️ 高优先级发现 1」：

```
任务暂停 → 超过 10 分钟（LOOP_TTL_MS）→ 循环被闲置超时回收
        → /agent/loop/resume 返回 404
        → 桌面端兜底「静默新建一轮」
        → 消息历史归零，模型完全不知道自己做过什么
        → 从头重跑整个目标
        → 目标里若有不可逆转动作（提交 / 下单 / 发送），就再执行一次
```

我们是在**真实网站**上点**真实按钮**的。所以最怕的不是"白跑几趟"，而是
**同一个不可逆的动作被执行了两次**。行业里两个独立项目（OpenHands、DeepSeek Harness）
都专门为这件事设计了机制，核心是一个区分：

> 确定没执行 → 可以重试 / 不知道执行没执行 → 禁止自动重试，必须去核实或问用户。

本轮做的是这条链路上的**止血**：把"悄悄重来"变成"先说清楚，再让用户决定"。

## 1. 改了什么（逐文件、逐处）

### 改动点 1 · 等待中的循环不该被当成"闲置"
**文件**：`apps/server/src/toolLoop.ts`（+28/−2）

| 位置 | 改动 |
|---|---|
| L270–292（新增） | `WAITING_STATUSES = new Set(['paused','waiting'])`、`WAITING_TTL_MS = 6 * 60 * 60 * 1000`、函数 `ttlOf(s)` |
| L346 `sweep()` | `now - s.touchedAt > LOOP_TTL_MS` → `> ttlOf(s)` |
| L357 `getLoop()` | 同上 |

**为什么不是把 TTL 调大或删掉**：`LOOP_TTL_MS`（10 分钟）是**活跃**循环的空转回收闸，
删了就真的会堆积。等待态语义完全不同——它本来就在等人，不是没人理。
所以给等待态一个**更长但有界**的窗口（6 小时）：跨天不管、隔夜一定回收，不是"永久保留"。

**内存上界仍然成立**：等待态**照旧参与** `MAX_LIVE_LOOPS`（32）的"从旧到新"淘汰，
只是不再被"闲置"这一条单独杀掉。这一条专门写了断言（见 §2 的第 ⑥ 条）。

### 改动点 2 · 循环真不在了 → 明确提示 + 一键确认（不许静默重开）
**文件**：`apps/desktop/electron/main.ts`（+113）

| 位置 | 改动 |
|---|---|
| L565–571（新增） | 常量 `LOOP_GONE_QUESTION`，文案逐字为简报指定那句 |
| L595–627 `resumeAgentLane` 的 catch | **删掉**原来那三行（`lanes.delete` + `startAgentLoop` + `return`），改为按 `code` 分流 |
| L719–772（新增 IPC） | `workbench:task:loop-gone`，两个出口 `restart` / `giveup` |
| L1142–1156 `agentPost` | 把服务端响应里的 `code` 挂到抛出的 Error 上（`err.code`） |

**catch 的两条分支**：

* `code === 'loop_gone'` → `emitAgent({ kind:'loop-gone', question })`，**不重开**，
  等用户在界面上点「重新开始」。
* 其它任何原因 → `emitAgent({ kind:'note', level:'error', text:'暂时接不上后端…请稍后再点一次「继续」' })`，
  **同样不重开**。

**「算了」必须收干净**（用户 2026-09-21 补的一条）：
`giveup` 出口会 `lane.aborted = true` + `lanes.delete` + `lastLoopByWc.delete`
+ `pendingGoals/pendingAnswers/lastAgentByWc` 清掉 + `resetTask` +
`setExternalPhase(wcId,'idle','已停止（这一轮的上下文不在了，按你的选择收尾）',0)`。
不留半死不活的状态——否则「继续」还会去 resume 一个已经不存在的循环，用户会以为按钮坏了。

### 改动点 3 · `/resume` 要能返回"可区分的语义原因"
**文件**：`apps/server/src/routes/loop.ts`（+17）

`/agent/loop/resume` 的两处 404（找不到循环、`resumeLoop` 返回空）现在带
`{ code: 'loop_gone' }`；**`userId` 不匹配的那个 404 不带**——那不是"过期"，
是"这不是你的循环"，不该引导用户去重新开始。

> 这一条一开始我建议"本轮不做"，用户推翻了我的判断，理由（原文）：
> 「现在桌面端是笼统 catch。如果不区分原因，那么只要网络抖动、服务端繁忙、或其它非"过期"原因，
> 也会弹出"上下文没了，要重新开始吗"。这种误报的代价不是"多一次打扰"，而是：
> **用户会被训练成不看内容就点「重新开始」**。等到某次真的丢了历史，用户照样无脑点下去——
> 安全网直接失效。所以"能区分原因"不是顺手优化，它是让那个确认弹窗可信的前提条件。」
>
> 范围按用户要求压到最小：**没有**做通用错误码重构，只加这一处的码传递。

### 改动点 4 · 界面（把这两个出口做出来）
| 文件 | 改动 |
|---|---|
| `packages/shared/src/index.ts` | `AgentEventPayload` 加 `{ kind:'loop-gone'; question:string }`；`WorkbenchBridge` 加 `loopGoneChoice(wcId, 'restart'|'giveup')` |
| `apps/desktop/electron/preload.ts` | 暴露 `loopGoneChoice` |
| `apps/desktop/src/App.tsx` | 接 `loop-gone` 事件 → `loopGone` 状态；渲染确认条：问话 +「重新开始」+「算了」 |
| `apps/desktop/src/styles.css` | `.loopGone` / `.loopGone__q` / `.loopGone__warn` / `.loopGone__giveup` 四条规则 |

### 改动点 5 · S4 的断言（验收脚本，不是产品代码）
`scripts/verify/help-card/help-card-e2e.py`：`HC_MODE=manual` 分支末尾加一条——
求助卡的「继续」**不能**误弹「上下文没了」确认条（`.loopGone__q` 必须不存在）。
防的正是上面那个"误报会把用户训练成无脑点重新开始"。

## 3. 【无法确定】清单

1. **「6 小时」这个数是不是对的**——没有真实使用数据支撑（没人真的挂起过 6 小时）。
   它是"跨天不管、隔夜一定回收"这个意图的第一次取值，可能需要按实测调。
2. **`wait` 状态和 `paused` 一起被放进长窗口是否都合适**——`waiting` 是"AI 在等用户回答"，
   `paused` 是"用户按了暂停"，两者语义接近但**没有**分别验证过各自的真实停留时长分布。
3. **服务端重启**依然会让所有循环消失（循环只存内存 `Map`，本步**明确不做**重启恢复）。
   重启后走的就是 `loop_gone` 那条路——会问用户，不会静默重开，但历史确实没了。
4. **S1 里"等超过 TTL"是靠临时把 TTL 压到 45 秒验的**，不是真等 6 小时。
   压小 TTL 只改变了常量值，不改变 `ttlOf()` 的分档逻辑，但"6 小时那个值本身"
   没有被真机验证过。
5. **S3 的前提**：用户 2026-09-20 已拍板「默认不再按步数打断」
   （`AGENT_LOOP_MAX_STEPS` 默认 0 = 不限步数），所以**默认配置下步数打断不会触发**。
   脚本是把服务端配成 `AGENT_LOOP_MAX_STEPS=6` 复现的旧行为——是**配置复现**，
   不等于"默认配置下会走到"。
6. **S4 用的是本地 `/captcha` 页面**，真实只读站上无法触发求助卡（§4）。
   所以它证明的是"求助卡 → 继续"这条链路没被本轮改动弄坏，
   **不等于**"真实网站上出现验证码时行为已验证"。

## 4. 本轮**没有**做的事（明确列出，等拍板）

* **「不可逆动作守卫」本轮未做。** 也就是"同一个动作到底执行了没有"的判定、
  以及"不知道执行没执行时禁止自动重试"那条闸。本轮只做到"不静默重开 +
  真要重开必须先问用户"，**没有**解决"工具超时了但动作其实生效了"这另一半问题
  （阶段2 的实验 A 就是在量这半边的现状）。
* 没有碰支付守卫、词表、`type`+回车路径；没有重构 `toolLoop.ts`；没有改数据存储方式
  （循环仍然只存内存）。
* 没有做通用错误码重构（用户明确要求范围最小）。
