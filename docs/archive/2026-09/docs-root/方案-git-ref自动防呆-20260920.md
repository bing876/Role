# 设计方案：git「提交后 ref 丢失」的自动防呆机制

> 状态：**✅ 已实施并验证通过**（2026-09-20）

## 0. 实施结果（先看这个）

采纳的选项：**sh 实现** + **只做守卫、不改分支名** + **安装脚本检查已有钩子**。

| 交付物 | 说明 |
| --- | --- |
| `scripts/git/ref-guard.sh` | 守卫本体（POSIX sh，无 node/python 依赖） |
| `scripts/git/hooks/post-commit` | 提交后立刻查 + 修 |
| `scripts/git/hooks/pre-commit` | 下次提交前再查一次（兜"万一提交后才丢"） |
| `scripts/git/install-hooks.sh` | 一键安装（写**绝对路径** + 检查 `.git/hooks/` 里的既有钩子） |
| `scripts/verify/git-ref-guard-probe.py` | 6 场景 + 反证，**27 条断言 / 0 失败** |

**真机演练（最关键的一条证据）**：安装钩子后做了一次真实提交，
`git commit` 输出里**自动多出了**：

```
[ref-guard] ⚠️  检测到 ref 丢失，已自动修复：refs/heads/arena/01a09b16-work123
[ref-guard]    修复前 = （文件不存在）
[ref-guard]    修复后 = 0f96c77edd56d0e60aaaa23760222f8d9c0cfb08
```

`.git/ref-guard.log` 同步落了一条 `FIXED` 记录，`git log -1` 立即恢复正常。
**全程零人工介入** —— 这正是要消除的"万一哪次忘记检查就没发现代码丢失"的风险。

三条设计声明也逐条验过：

| 声明 | 结果 |
| --- | --- |
| 正常时（`--quiet`）完全静默、零输出 | ✔ |
| 修复提示**不受 `--quiet` 影响**，永远打印 | ✔（钩子用 `--quiet`，修复信息照样出现） |
| 不改历史：41 条提交 / 根提交 1 个，HEAD 未被移动 | ✔ |

> 一处**与设计略有出入**、如实记录：修复提示实际出现在 **stderr**（git 把 post-commit 的钩子输出汇到了 stderr）。
> 不影响可见性 —— 它是**显示出来**的，这才是重点。原方案里写的"走 stdout"不准确，已按实际行为更正。

## 一、先说诊断结果（这次实测出来的新事实）

我做了一次带计时观察的提交，结果是：

| 观察时刻 | ref 状态 |
| --- | --- |
| `git commit` 返回后**立刻** | ❌ **已经没了** |
| +1 秒 | ❌ 没了 |
| +3 秒 | ❌ 没了 |

**结论：ref 是在「提交那一刻」就没的，不是过一会儿才被什么东西删掉的。**

这个事实很关键 —— 它决定了方案可行性：
**`post-commit` 钩子在提交结束时运行，那时 ref 已经丢了，所以它看得到、也修得了。**
（如果 ref 是提交后很久才丢的，钩子就会"看到一切正常"然后事后丢失，那得换方案。）

已确认的环境事实：
- 分支名 `arena/01a09b16-work123` 含 `/`，**已连续 4 次 100% 复现**（本次会话内）
- `.git/hooks/` 里**没有任何自定义钩子** → 改 `core.hooksPath` 不会覆盖掉谁
- `core.hooksPath` 当前**未设置**
- 恢复所需信息**一直都在**：`.git/logs/HEAD` 的末行永远记着新 sha（git 的 reflog 不受这个 bug 影响）

## 二、方案：仓库内版本化的 git 钩子（**不依赖"记得用某个包装命令"**）

### 为什么不用"包装 `git commit` 的脚本"

包装脚本要靠**人记得用它** —— 而这正是你要消除的风险点
（IDE、`/commit` 技能、任何直接调 `git commit` 的路径都会绕过它）。

`post-commit` 是 **git 自己调用**的：无论谁、用什么方式提交，都会经过它。

### 三个文件

```
scripts/git/
├── ref-guard.sh          ← 守卫本体（POSIX sh，无 Node/Python 依赖）
└── hooks/
    ├── post-commit       ← 提交后立刻查 + 修
    └── pre-commit        ← 下次提交前再查一次（兜"万一哪次是提交后才丢"）
```

**为什么用 sh 而不是 Node/Python**：钩子在 Windows 上由 Git 自带的 sh 执行，
**sh 一定存在**；而 node/python 要依赖 PATH，钩子里 PATH 不保证和交互 shell 一致。
恢复逻辑本身只有"读一行、mkdir、写一行"，用 sh 完全够，还少一个失败点。

### `ref-guard.sh` 做什么

```
1. 定位 .git 目录（git rev-parse --git-dir）
2. 从 .git/logs/HEAD 末行取「刚刚提交的 sha」  ← 这是权威来源，reflog 不受 bug 影响
3. 解析 .git/HEAD 得到分支 ref 路径（detached HEAD 则跳过）
4. 比对 ref 文件内容与那个 sha：
   ├─ 一致  → 静默通过（退出 0）
   └─ 不一致/文件缺失 → mkdir -p 目录 + 写回 sha
5. 复查写回结果：
   ├─ 成功 → stdout 打印一行醒目提示 + 追加进 .git/ref-guard.log
   └─ 失败 → stderr 报警 + 退出码 1（git 会把 stderr 显示出来）
6. 附带体检：根提交数应为 1；>1 说明历史可能塌陷 → 报警（不自动修）
```

### 安装方式

```bash
git config core.hooksPath "<repo>/scripts/git/hooks"     # 用绝对路径，避免相对路径解析歧义
```

配一个 `npm run hooks:install`（或 `scripts/git/install-hooks.mjs`）一键完成，
**这样钩子随仓库版本化** —— 换机器/重新克隆后跑一次即可，不需要手工拷进 `.git/hooks/`。

> ⚠️ `core.hooksPath` 是**相对 `$GIT_DIR` 还是工作区**在文档里说法绕，所以安装时**一律写绝对路径**，
> 并在安装脚本里打印实际生效路径 + 自检一次。

### 报警强度（分三档，不搞"狼来了"）

| 情况 | 表现 |
| --- | --- |
| 一切正常 | **完全静默**（不打扰） |
| 检测到丢失、**自动修复成功** | stdout 一行：`[ref-guard] ⚠️ 检测到 ref 丢失并已自动修复：refs/heads/... → <sha>`；同时写 `.git/ref-guard.log` |
| **修复失败**（需人工介入） | stderr 红字 + 退出码 1 + 写日志 + 打印手工恢复命令 |

## 三、验证方案（你要求的"故意模拟 ref 丢失"）

写成 `scripts/verify/git-ref-guard-probe.sh`，**逐条断言**：

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | 正常提交后跑守卫 | 静默通过、退出 0、ref 未被动过 |
| 2 | **删掉 ref 文件** | 检测到 + 修复 + 输出提示 + 日志有记录 |
| 3 | **把 ref 写成旧 sha**（模拟"提交没落盘，还停在上一次"） | 检测到 + 修到正确 sha |
| 4 | **删掉整个 `refs/heads/arena/` 目录**（**真实故障形态**） | 重建目录 + 写回正确 sha |
| 5 | 模拟历史塌陷（根提交数 > 1） | **报警**（但不自动改历史） |
| 6 | detached HEAD | 跳过（不误报） |

**外加反证**（证明这套测试不是摆设）：
把守卫的「写回」那一步关掉（只检测不修），
则 **场景 2/3/4 必须变红** —— 否则说明断言根本没打到修复路径。

**真实演练**：最后再做**一次真提交**，确认 `post-commit` 钩子自动跑、自动修，
而不是只在手工调用守卫时有效。

## 四、这个方案不做什么（划清边界）

- **不改分支名**：把 `arena/xxx` 改名能绕开，但那是"回避"不是"防呆"，
  而且会打乱既有 remote 跟踪配置（`branch.arena/01a09217-work123.*` 已存在）。
  如果你更倾向"改名 + 保留守卫"，我也可以两条一起做 —— 请告诉我。
- **不自动改历史**：发现根提交数异常只报警，绝不自动 `reset`/`rebase`
  （今天已经有过一次"裸 `git reset` 把 34 条历史搞成根提交"的事故）。
- **不动 `.git/logs/HEAD`**：它是恢复的唯一权威来源，只读不写。

## 五、实施时采纳的选项（原为待确认项）

| 问题 | 采纳 |
| --- | --- |
| 1. 方向：`core.hooksPath` + 仓库内钩子 | ✅ 采纳 |
| 2. 语言：sh 还是 Node | ✅ **sh**（少依赖、更稳；恢复逻辑只有"读一行、mkdir、写一行"，sh 完全够） |
| 3. 要不要同时改分支名 | ❌ **不改**（改名属另一件事，会动 remote 跟踪配置 `branch.arena/*`）。守卫已能覆盖 |
| 4. 安装脚本检查既有钩子 | ✅ 已加（检测到就提示"设了 core.hooksPath 后它们不会再被调用"） |

> 如果后来发现 `pre-commit` 在某个工作流里碍事，可以单独删掉它 ——
> **`post-commit` 才是主力**，`pre-commit` 只是便宜的兜底。
