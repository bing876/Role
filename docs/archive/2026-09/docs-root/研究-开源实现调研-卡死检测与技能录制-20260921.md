## 术语速查

| 词 | 大白话解释 |
|---|---|
| **Agent（智能体）** | 一个会自己连续做多步操作的程序。它会「想一步 → 做个动作 → 看结果 → 再想下一步」这样循环。 |
| **卡死检测（Stuck Detector）** | 一个盯着智能体看它有没有在原地打转的哨兵。发现打转就喊停，避免它把时间/钱烧光。 |
| **事件（Event）** | 智能体每一步留下的记录。比如「我说了一句话」「我调用了 read_file」「工具返回了错误」。所有事件连起来就是这次任务的完整历史。 |
| **阈值（Threshold）** | 触发报警的数字门槛。比如「重复 4 次就判定卡住」。 |
| **会话日志（Session Log）** | 把上面那些事件按顺序写进文件，关掉程序再打开还能接着看。相当于智能体的「记事本」。 |
| **持久化（Persistence）** | 把数据真正落到硬盘上，而不是只放在内存里。断电/崩溃后数据还在。 |
| **flush（落盘屏障）** | 「强制把内存里攒着的数据立刻写到硬盘」这个动作。只有写完这一下，才算真的保险。 |
| **回放（Replay）/ 恢复（Resume）** | 重新打开一次历史会话，让它接着上次的位置继续跑，而不是从头再来。 |
| **脱敏 / 遮蔽（Redaction）** | 把敏感内容（密码、卡号）盖住或替换掉，让别人看不到原文。 |
| **MIT 许可证** | 一种非常宽松的开源许可。可以商用、可以改、可以闭源发布，只要保留版权声明。**对我们友好。** |
| **AGPL 许可证** | 一种强传染性许可。只要你在网络上提供服务用了它，就必须把你自己整套代码也开源。**对我们不友好。** |
| **OCR** | 让程序「看图认字」——把图片里的文字识别成可编辑的文字。 |

## 1.3 一共几种「卡住」的判定模式

**官方文档宣传 5 种，但源码里只有 4 种真正生效，第 5 种是被注释掉的空壳。**

这一点很重要，我逐项说清楚（出处：`stuck_detector.py` 的 `StuckDetector` docstring 和 `is_stuck()` 方法体）：

| # | 模式名（中/英） | 源码里是否真的生效 | 出处位置 |
|---|---|---|---|
| 1 | 重复「动作-结果」循环 / Repeating Action-Observation | ✅ **生效** | `_is_stuck_repeating_action_observation()` |
| 2 | 重复「动作-报错」循环 / Repeating Action-Error | ✅ **生效** | `_is_stuck_repeating_action_error()` |
| 3 | 自言自语 / Agent Monologue | ✅ **生效** | `_is_stuck_monologue()` |
| 4 | 交替循环 / Alternating Patterns | ✅ **生效** | `_is_stuck_alternating_action_observation()` |
| 5 | 上下文窗口报错 / Context Window Errors | ❌ **未生效（空实现，直接 return False）** | `_is_stuck_context_window_error()` |

第 5 种的原话是：

```python
def _is_stuck_context_window_error(self, _events: list[Event]) -> bool:
    # TODO: blocked by https://github.com/OpenHands/agent-sdk/issues/282
    return False
```

**注意**：它的 `is_stuck()` 里确实写了 `if len(events) >= 10:` 再调这个函数（这个 `10` 是个裸数字，没有在 `StuckDetectionThresholds` 里定义），但因为函数体恒返回 `False`，**这一段永远不会触发**。如果你想抄第 5 种，等于要从零自己设计——它没有可抄的判定逻辑。

## 1.4 判定条件与阈值总表

### 阈值定义（出处：`types.py` 的 `StuckDetectionThresholds` 类）

| 参数名 | 默认值 | 含义 |
|---|---|---|
| `action_observation` | **4** | 重复「同一个动作 + 同一个结果」多少次后判卡住 |
| `action_error` | **3** | 重复「同一个动作 + 同一个报错」多少次后判卡住 |
| `monologue` | **3** | 连续多少条智能体消息（中间没有用户插话）后判卡住 |
| `alternating_pattern` | **6** | 两种「动作-结果」对交替出现多少个周期后判卡住 |

### 判定细节（出处：`stuck_detector.py` 各 `_is_stuck_*` 方法）

| # | 模式 | 触发条件（精确） | 阈值 | 源码依据 |
|---|---|---|---|---|
| 1 | 重复动作-结果 | 最近的 N 个 action **两两相等**，且最近的 N 个 observation **也两两相等**（N = 阈值） | **4** | `if actions_equal and observations_equal: return True` |
| 2 | 重复动作-报错 | 尾部连续出现「同一个 action + `AgentErrorEvent`」的连续段长度 **> 阈值**（注意是**严格大于**，实际要 4 次） | **3** | `if self._action_error_streak(...) > threshold:` |
| 3 | 自言自语 | 从最新往前数，连续 `source == "agent"` 的 `MessageEvent` 数量 **>= 阈值** | **3** | `return agent_message_count >= threshold` |
| 4 | 交替循环 | 最近 N 个 action 满足 `action[i] == action[i+2]`，且 N 个 observation 也满足 `obs[i] == obs[i+2]`（即 A-B-A-B-A-B 形状） | **6** | `for i in range(threshold - 2)` |
| 5 | 上下文窗口报错 | 恒 False，未实现 | 无（裸数字 10 是调用处的门槛） | `return False` |

**几个容易踩的点，值得你特别记住**：

1. **模式 2 的「阈值 3」实际需要 4 次重复才会触发**。因为它写的是 `> threshold`，不是 `>= threshold`。源码里还专门解释了为什么：
   > `# action_error needs one extra pair to tell a fresh streak from one that already continued past the nudge`
   —— 这是为了区分「刚踩到 3 次的崭新连败」和「已经收到提醒后还继续踩」的连败。**你抄的时候千万别顺手改成 `>=`，会把「先提醒、再判停」这两段逻辑压塌。**

2. **`is_stuck()` 有前置短路**：先算 `min(4, 3, 3) = 3`，事件总数不足 3 条直接返回 False（出处：`min_threshold = min(...)` 那几行）。所以极小会话不会被误判。

3. **只看「最后一条用户消息之后」的事件**（出处：`_events_since_last_user_message()`）。用户一插话，卡死计数清零重来。

4. **扫描窗口上限 20 条事件**（出处：`MAX_EVENTS_TO_SCAN_FOR_STUCK_DETECTION: int = 20`）。源码注释写明理由是**避免把整个历史日志（可能是大文件）全文载入内存**——这是个很实在的工程考虑。

5. **比较事件时「忽略无关细节」**（出处：`_event_eq()`）。比的是语义内容，不是对象身份：
   - Action 比 `source` + `thought` + `action` + `tool_name`
   - Observation 比 `source` + `observation` + `tool_name`
   - Error 比 `source` + `error`
   - Message 比 `source` + `llm_message`
   - **刻意忽略** `id`、`tool_call_id`、`llm_response_id`、`action_id`、`metrics`（时间戳、指标等每次都不同，不能参与比较）

6. **还有一个「先提醒、再判停」的温和机制**（出处：`get_action_error_nudge()`）：连败**刚好等于**阈值（3 次）时，生成一段提醒文本给模型看，劝它「别再用同样的参数调同一个工具了，看看报错改改参数或者换个思路」。等它踩到第 4 次才真正判卡死。而且有个 `_last_nudged_error_event_id` 去重，防止「模型卡住不产出新动作」时反复刷同一条提醒。

## 1.5 一句话总结

OpenHands 的卡死检测是**「只看最近 20 条事件、只看最后一条用户消息之后、用 4 个数字阈值（4/3/3/6）、忽略 ID 只比语义」**的一套轻量哨兵；第 5 种模式是个被 issue 卡住的空壳，不要指望。**它的设计最值钱的地方不是那 4 个数字，而是「先 nudge 提醒、再硬停」这个两段式，以及「忽略 ID 只比语义」这个比较口径。**

## 2.3 三个模块的「该抄 / 不该抄 / 存疑」对照表

### 模块 ①：会话日志（Session Log）

**它的做法是什么**（出处：`packages/session/README.md`、`packages/session/session-persistence/README.md`、`packages/session/session-persistence-jsonl/README.md`）

一句话：**「追加写、永不改历史」的单一真相日志 + 一套明确的落盘屏障规则 + 崩溃后补写「收尾事件」。**

具体拆开：

1. **只追加，不改写（append-only）**。`append` 的批次第一条 `seq` 必须等于已存的下一序号，**有空洞就拒绝**。出处：`session-persistence/README.md` 不变量表 —— 「Append-only, contiguous `seq`. Committed events are never rewritten」。
2. **磁盘格式是「每会话一个文件」**，默认用 Zstandard 压缩（可关掉变纯文本行）。出处：`session-persistence-jsonl/README.md` 的 `compression` 字段（默认 `'zstd'`，可选 `'none'`），以及「On-disk layout」一节。
3. **落盘屏障（flush）是唯一的保险承诺**。`append` 只是「尽力而为」；**只有 `flush` 成功返回，才敢说「崩了也不丢」**。出处：`session-persistence/README.md` — 「only a resolved `flush` promises it survives a crash」。
4. **「撕尾」永远不暴露给读方**。所谓撕尾，就是写到一半断电留下的半截记录。写路径会在第一次新追加之前，把这段残留**持久地截掉**。出处：不变量表「A torn physical tail never reaches a reader.」
5. **同一会话同时只允许一个写者**。第二个写者打开会直接报错 `SessionAlreadyOwnedError`。出处：`session-persistence/README.md` 的「Ownership and visibility」。
6. **崩溃恢复靠「事后补写收尾事件」**。这条是**你最关心的「暂停/恢复/回放」的答案**，我单独展开——

**⭐⭐ 它是怎么做到「任务可以暂停后恢复 / 回放」的**

机制的原文是（出处：`session-persistence/README.md` 的「Resuming and crash recovery」一节）：

> Resume (agent-loop) reads the stored log through its write handle, computes `interruptedTurnClosers` — synthetic `tool/result` errors, any open `step/end`, and `turn/end {interrupted}` — and appends them through the same handle as an ordinary batch.

翻译成大白话：

- 崩溃时，日志里可能留着一个**没写完的回合**（比如「我调了工具，但结果还没回来」）。
- **它不删也不改**这些记录（因为日志「只追加不改写」是铁律）。
- 它改为**追加几条「补写出来的假事件」把它封口**：
  - 一条**假的「工具结果」错误**（因为工具到底跑没跑完，只有天知道）；
  - 任何还「开着」的 `step/end`（把「步骤」这个框关掉）；
  - 一条 `turn/end {interrupted}`（明确标记：这一回合是被打断的）。
- 补完之后，日志就「语法完整」了，可以正常继续跑了。

**回放时的两条关键标记**（出处同上）：

| 遇到的情况 | 标记成什么 | 大白话 |
|---|---|---|
| 有「请求」记录，但连「我调了工具」都没记上 | `TOOL_NOT_STARTED` | 确定没跑过，可以重试 |
| 有「我调了工具」记录，但没结果 | `TOOL_OUTCOME_UNKNOWN` | **不知道跑没跑**，所以不敢自动重试 |

`TOOL_OUTCOME_UNKNOWN` 的处理策略非常克制，原文是：让模型**可以重试「只读或幂等」的操作**（幂等 = 重复做一次结果一样，比如「读文件」），但**对有副作用的操作，必须去核实或问用户，不许瞎重试**。

**值不值得我们抄？**

| 判断 | 内容 |
|---|---|
| ✅ **该抄** | **「只追加不改写 + 崩溃后补写收尾事件」这个模式本身**。这是最值得抄的一条。理由：我们的「暂停/继续」如果靠「就地改日志」，一旦中途崩了就是脏数据；而「补写封口」既保住了日志的不可变语义，又让恢复变得确定。**而且「不确定就别自动重试，去问用户」这条，和我们已有的产品原则高度一致**（我们的原则里有一条「判定分不清的东西，话术不能说死」）。 |
| ✅ **该抄** | **`TOOL_NOT_STARTED` / `TOOL_OUTCOME_UNKNOWN` 这个「两档区分」**。它把「确定没做」和「不确定做没做」分开，这个二分非常干净，比「一律重试」或「一律不重试」都强。 |
| ❌ **不该抄** | **按「项目目录」分文件夹的存储布局**（`--<normalized-cwd>--/<sessionId>/`，出处 `session-persistence-jsonl/README.md` 的 on-disk layout）。理由：我们已经有了 PG（PostgreSQL 数据库，出处见我们自己的 `MEMORY.md` 第二节表结构部分）作为会话/项目的权威存储。再引入一套文件系统的目录约定，会出现「两套真相」，且和我们的 `projects` 表重复。**它的文件布局是为「没有数据库、只有文件系统」的 CLI 场景设计的。** |
| ⚠️ **存疑** | **19 个子包拆得这么细**（`session-format-v0-to-v1`、`session-format-v1-to-v2`、`session-projection-cache`……）。**存疑理由**：这是为「给外部人按需挑选」设计的（原文：`Start with the shipped JSONL storage, then add checkpointing and only the projections... your deployment needs`）。我们是一个自用的产品，不是给第三方搭积木的平台，**照抄这个拆分粒度会显著增加维护面**。可以借鉴它的「分成持久化/投影/标题/遥测四族」的思路，**但不要照搬包的数量**。 |
| ⚠️ **存疑** | **`session-log-deepseek` 会上传日志给官方做请求元数据**（出处：`packages/session/README.md` 的 Persistence 表 —— 「Uploads the incremental canonical log as optional official DeepSeek request metadata」）。**存疑理由**：这是可选项，但它意味着**对话原文会被送到厂商**。我们要不要这么做，得单独拍板，不能顺手抄。 |

**特别值得单独记一功的一条**（出处：`packages/session/session-checkpoint-policy/README.md`）：

它把「什么时候必须落盘」定义成**三个语义节点**，而不是按时间/条数：

1. **模型请求之前**必须落盘 —— 「so a crash before a response cannot replay an unpersisted request」
2. **顶层工具真正执行之前**必须落盘 —— 「a recorded call is durable before any external side effect」
3. **每个 `agent/pre-step` 边界**必须落盘 —— 把上一步的回复和工具结果都存好，再进入下一步

而且它是 **fail-closed（失败就停，不放行）**的：原文「a model adapter or top-level tool body does not run until the durable write succeeds」。

> **这条我认为是本任务里最值得抄的单点。** 它的洞察是：**落盘的时机应该跟着「不可逆的边界」走，而不是跟着时间走**。工具一旦真的执行了就有了外部副作用（比如真的发了邮件），再也退不回来；所以在「副作用发生前」这一个瞬间落盘，是最划算的。这比「每 5 秒存一次」精确得多，也便宜得多。

**同时它也很诚实地说清了自己的边界**（出处：同文件的 Known Limitations）：
> 「Durable execution intent, not exactly-once effects」—— **它保证的是「记下了你要做」，不是「保证只做一次」**。真正的「只做一次」要靠工具自己把 `exec.callId` 当幂等键传给下游。

**这一点我们必须记住**：别把「有日志」误当成「不会重复执行」。

### 模块 ②：工具执行流水线（tools）

**它的做法是什么**（出处：`packages/core/tools/README.md`）

一句话：**一条固定六段的流水线，前两段管「能不能做」，中间一段管「怎么做」，后三段管「做完怎么记」。**

**流水线的固定顺序**（出处：「Design concept」一节原文）：

```
tools/pre-execute → 已注册的单调守卫 → tools/execute → tools/post-execute
→ 定义自带的 finalizeContent → tools/result（只读观察）
```

逐段说：

| 段 | 作用 | 关键约束 |
|---|---|---|
| `tools/pre-execute` | 决定 **allow / deny / ask**（放行 / 拒绝 / 要先问用户） | **故意不许改写 `exec.arguments`**（原文理由：改了就导致「记下来的参数」和「真跑的参数」不一致，日志和界面渲染全都会错位） |
| 单调守卫（guard） | `ctx.tools.guard()` 注册 | **单调** = 一旦某个守卫拒绝了，**后面的任何监听器都不能把它翻回「允许」** |
| `tools/execute` | 环绕派发的包装层，用于**超时 / 重试 / 埋点** | **只有这一层可以替换 signal**，之后注册表会把调用方的 signal 重新合回去 |
| `tools/post-execute` | 可以**替换结果内容**、**带反馈地阻塞**、或**挂载额外上下文** | — |
| `finalizeContent` | 由工具定义自己产出最终内容 | — |
| `tools/result` | **只读**观察冻结后的最终结果 | 不许改 |

**几个我认为设计得很聪明的点**：

1. **「单调」守卫**（原文：`no later listener can turn that denial back into permission`）。这个设计**排除了「权限被后续插件悄悄放开」这一类漏洞**。我们自己的安全边界里，「本地判定为不可执行的动作必须在本地下游阻断」是同样的思路，但它是**用类型/顺序保证**的，比我们用文案约定更硬。

2. **工具失败不结束整个回合**（原文：`so a call fails without ending the turn`）。未知工具或抛异常的工具会变成结构化错误 `UNKNOWN_TOOL`，**回合继续**。这个对我们很有参考价值——我们现在有时会因为一次工具失败就把整个任务停掉。

3. **取消是「协作式」的**（出处：「Execution and cancellation」一节）：
   - 每个工具拿到的都是**调用方持有的那个 signal**，必须自己盯着它；
   - **调用前**取消 → 结果是 `ABORTED_BEFORE_DISPATCH`（明确知道没跑）；
   - **调用后**取消 → 只把「成功」结果换成 `ABORTED`（因为已经跑了，性质不同）；
   - 「被拒绝」「包装失败」「工具失败」「策略失败」「超时」**都保留更具体的错误码**，不被笼统的 `ABORTED` 盖掉。

   > 这个「**取消也要分前后**」的设计很精细。它和任务一 OpenHands 的 `TOOL_NOT_STARTED` / `TOOL_OUTCOME_UNKNOWN` 是**同一个洞察的两个版本**——都在解决「到底跑没跑」这个致命问题。

4. **公告面 = 可调用面**（原文：`the announced surface and the callable surface stay the same`）。在 PTC 模式下，如果模型直接调一个「虽然存在但不在本次公告里」的工具，会在策略之前就解析成 `UNKNOWN_TOOL`。**这从根上排除了「模型调用了一个它没被告知可以用的工具」这种越界。**

5. **工具注册即可用，schema 自动进提示词**（原文：`Registering a tool is enough to make it visible — the registry feeds its schemas into the system-prompt assembly automatically`）。这个「注册即接线」省掉了一整类「忘了把工具写进提示词」的 bug。

**值不值得我们抄？**

| 判断 | 内容 |
|---|---|
| ✅ **该抄** | **「固定顺序的六段流水线 + 明确谁在哪一段能改什么」这个骨架**。理由：我们现在工具执行的前后钩子散落各处，容易互相覆盖。一个**固定的、有名字的阶段顺序**能让「谁能改什么」变成可检查的规则。 |
| ✅ **该抄** | **「单调守卫」这个概念**：拒绝一旦发生，后续不许翻案。**这条直接加强安全边界，且实现成本极低**（就是在拒绝时打一个不可翻转的标记）。 |
| ✅ **该抄** | **工具失败不结束回合 + `UNKNOWN_TOOL` 结构化错误**。理由：能显著提升长任务的韧性。 |
| ✅ **该抄** | **取消分「调用前 / 调用后」两种结果**。和我们已有的「本地判定分不清就别说死」是同一套哲学，值得补齐到工具层。 |
| ⚠️ **存疑** | **PTC 模式**（让模型写一段代码，在代码里 `await tools.xxx(...)` 去调工具；出处：README 的「PTC mode」整节）。**存疑理由**：① 它假设模型能可靠地写代码，**对我们当前的模型能力是个赌注**；② 官方自己列了硬伤 —— 「PTC mode intermediate values are execution-local and unbounded by bytes」**中间结果无法从会话日志回放重建，而且没有字节上限，可能把内存撑爆**；③ `run_code` 每次运行状态全新（它们明确拒绝了持久 REPL 内核，理由正是「跨调用状态对日志不可见」）。**这三点加起来，我认为现阶段不值得抄。建议只作为「未来可能」记录。** |
| ❌ **不该抄** | **`mode: 'native' | 'ptc' | 'both'` 这种「呈现模式按 agent 整体切换」的设计**。出处：Known Limitations —— 「a presentation is per agent rather than per tool」，**同一个 agent 内没法让 A 工具走 native、B 工具走 ptc**。理由：这个粒度太粗，对我们这种「有的工具适合直接调、有的适合写代码调」的混合场景是硬约束。**要抄就抄到「按工具」的粒度，别抄它的现状。** |
| ❌ **不该抄** | **`timeoutMs` 只是「声明式」**。出处：Known Limitations —— 「`timeoutMs` on a definition is declarative only — the registry never enforces deadlines」。理由：**写了个超时值却根本不生效，这是最容易骗到人的坑**。我们要么真做，要么就别放这个字段。 |
| ⚠️ **存疑** | **`maxParallelSubCalls` 默认 10**。出处：配置表。存疑理由：这是个**对我们没有对应场景的数字**（它是为 PTC 子调用设计的）。但配套的那句并发契约很值得学：**「安全的调用可以并发跑；会改数据的调用必须单独跑，按提交顺序」**（原文：`safe calls run concurrently; mutating calls run alone, in submission order`）。**这句规则本身该抄，数字不用抄。** |

### 模块 ③：提示词组装（system-prompt）

**它的做法是什么**（出处：`packages/core/system-prompt/README.md`）

一句话：**一个「注册表 + 协作式组装管线」，所有提示词片段带着排序号进来，按序拼成一段，工具清单是组装的正式成员而不是外挂。**

**关键设计**：

1. **一切都是「带 order 的 section（片段）」**，升序拼接；**order 相同就按名字的字符序**（原文：`concatenated in ascending order and equal orders use code-unit name order`）。
   - 固定开场白在 **-1000**（默认 `You are an AI agent powered by DeepSeek Harness.`）
   - 全局 persona 前缀在 **0**
   - 第一方「环境信息」段在 **10000 / 10100**
   - persona 后缀在 **10200**
   - 工具 SDK 段在 **5000**
2. **变量用 `{{variable}}` 引用，每次组装时解析**。内置提供 `model` 和 `cwd`，任何插件都能注册自己拥有的事实。
3. **工具 schema 是组装的一部分**（原文：`Tool schemas are part of the assembly by design — "what the model is told it can do" is one coherent thing`）。**这句话是本模块的核心主张**：尽管适配器在传输时把工具 schema 放在单独字段里，但在设计上，**「被告知能做什么」和「被告知是谁」应该被视为一个整体**。
4. **有作用域（scope）**：通过 `agent.ctx` 注册的东西只影响那个 agent，并**遮蔽（shadow）**同名的全局项。
5. **报错比发坏提示词好**（原文：`an unknown reference, a registered-but-valueless reference, or a malformed complete group throws, because a malformed prompt is worse than a loud failure`）。**变量没解析出来就抛错，绝不放行一个残缺的提示词。**
6. **有「完全体」逃生舱**：某个 section 标记 `complete: true` 时，**它自己就是完整提示词**。但**超过一个生效的 complete section 会让组装失败**。

**它拿来处理「缓存友好」的做法**（出处：「KV Cache effect」小节）——这一段我觉得是最有工程智慧的：

> KV Cache「键值缓存」大白话：模型服务端会把「你已经发过的前半段提示词」算好的中间结果存起来，下次只算新增部分，省钱又省时间。**但前提是前半段一个字符都不能变。**

它的做法：
- **默认情况下，改动过的提示词会在「第一个 system 节点」处就地合并改写** → 从改动点往后，缓存全部失效。
- 但如果这次请求声明了 `systemPromptUpdate: 'in-history'`，**它会把新提示词追加在缓存过的历史后面**，而不是回头改前面 → **前面的缓存依然能用**。
- 并且明确指出：**只要「同一个模型 + 同样的 persona 前缀 + 同样的工具 + 同样的前置指令」，那么换一个源文件路径、换一个本地 Web 地址、换一个 persona 后缀，都不会破坏那段可复用的前缀。**

**值不值得我们抄？**

| 判断 | 内容 |
|---|---|
| ✅ **该抄** | **「提示词 = 带排序号的片段集合」这个模型**。理由：我们现在的提示词如果还是拼接字符串，改一处容易影响全局。**带 order 的片段化让「谁贡献了哪段、排在第几」变成可读、可测、可排序的**，也天然支持「不同 agent 用不同片段」。 |
| ✅ **该抄** | **「变量未解析就抛错，不发残缺提示词」**。这条和我们已有的一条产品原则完全同源（「判定分不清的东西，话术不能说死」），**而且它更硬**：直接让它构建失败。 |
| ✅ **该抄** | **「工具 schema 是组装的一部分」这个观念**。理由：这能结构性消灭「工具注册了但没写进提示词」这类 bug（和任务二模块②里「注册即可用」是同一件事的两面）。 |
| ✅ **该抄** | **缓存友好的「追加而非回改」策略**。理由：这是**真金白银的成本优化**，而且思路可以独立于它的实现来借鉴：**能追加就不要回改历史。** |
| ⚠️ **存疑** | **order 号全部靠「中央分配 + `getSectionOrder(name)`」**。出处：`Repository-owned contributors resolve centrally allocated positions through ctx.systemPrompt.getSectionOrder(name)`。**存疑理由**：这解决了「大家乱抢号」的问题，但**引入了一个中央协调点**。对「第一方插件很多」的它很合适；**对我们，如果只有几个贡献方，可能过度设计**。建议先用「留出 100 的间隔手写」这种土办法，等真的撞号了再上中央分配。 |
| ❌ **不该抄** | **「部署方写死提示词、没有终端用户编辑 API」**。出处：Known Limitations —— 「Deployment-authored prompt text is config/composition only... there is no end-user prompt-editing API」。理由：**这是它的定位决定的（它是给开发者搭 AI 产品的框架），不是我们想要的**。我们面向的是终端用户，如果照抄，用户将完全无法调整提示词。 |
| ⚠️ **存疑** | **`toolOrder` 的报错时机**。出处：Known Limitations —— 「`toolOrder` misconfiguration surfaces at prompt assembly (the first turn), not at boot — only shape violations throw at config load」。**存疑理由**：**这是它自己承认的一个缺陷**——配错了不会在启动时报错，要等第一轮对话才炸。**我们要抄这个功能的话，必须把校验提前到启动时**，别把「第一轮对话才崩」这个体验带进我们的产品。 |
| ⚠️ **存疑** | **`interpolate: false` 这种「整段关闭变量替换」的开关**。出处：Known Limitations —— 「No inline escape syntax in interpolated text — use `interpolate: false` when a whole section must preserve literal braces」。**存疑理由**：**粒度太粗**。它自己也承认「没有行内转义语法」。如果我们要抄，建议直接做成行内转义（比如 `\{{`），比整段关闭好用得多。 |

## 3.5 怎么变成一份技能文件

出处：`electron/skillbuilder/builder.ts`、`electron/skillbuilder/instructions.ts`、`electron/skillbuilder/tools.ts`

**分两个回合（两次 AI 对话）**：

**第一回合：出计划**
- 给 AI 一段 `KICKOFF_PROMPT`，让它先调 `get_analysis`（必要时调 `get_timeline` 找工具证据），然后调 `propose_plan` 交出一个**计划**（`SkillPlan`）。
- 计划里必须有：**怎么泛化这个任务**、**固定值列表**（每个值有 `id` + `name` + `value`）、**有顺序的步骤列表**（每步有标题、说明、以及调用的原生工具）。
- **出完计划就停下**，等用户审阅和编辑。

**第二回合：按计划写正文**
- 给 AI 一段 `CREATE_PROMPT`，要求它**严格**按用户定稿的计划写 SKILL.md —— 「不增、不删、不重排、不重命名其 values 或 steps」。
- 关键设计：**正文里所有具体值都必须写成 `{{id}}` 令牌，绝不许内联字面量**。真实值由后期渲染时替换。
- 最后调用 `submit_skill` 交稿。

**落盘结构**（出处：`builder.ts` 的落盘逻辑 + `skill-placement.ts`）：

```
<目标目录>/<技能名>/SKILL.md     ← 最终技能文件
<会话目录>/skill.json            ← 持久化的 BuiltSkill JSON
```

**两种去处**（出处：`SkillTarget` 类型）：

| 类型 | 路径 | 说明 |
|---|---|---|
| `install` | `skillsRoot()`（默认 `~/.copilot/skills`，可由环境变量 `SKILL_RECORDER_SKILLS_DIR` 覆盖） | 装进 agent 的技能目录，立刻可用 |
| `export` | 用户自己选的目录 | 导出给别处用 |

**SKILL.md 的 frontmatter（文件头部的元数据）字段**（出处：`builder.ts` 的 `finalSubmission` 拼装）：

| 字段 | 来源 | 说明 |
|---|---|---|
| `name` | **强制取自计划**（`finalSubmission.name = plan.name`） | AI 改不了 |
| `description` | **强制取自计划** | AI 改不了 |
| `allowed-tools` | AI 可「收紧」，但**不能清空到计划声明之下** | 代码：`submission.allowedTools.length ? submission.allowedTools : plan.allowedTools` |

**一个设计原则值得记**（出处：`builder.ts` 的落盘逻辑）：**计划（SkillPlan）是唯一权威来源**——名字、描述、固定值、步骤全由「用户编辑过的计划」定；**AI 只负责写正文散文**。这是个很干净的「人定框架、AI 填肉」分工。

**还有一个细节**：单回合超时 `TURN_TIMEOUT_MS = 180_000`（3 分钟）；同时用 `active` 集合防止同一个会话被并发构建两次。

## 3.6 ⭐⭐ 它怎么处理密码、验证码这类敏感信息（我们的安全红线）

**这一节是重点，我拆成「四层防线 + 一条它自己的诚实边界」来说。**

### 大局：数据什么时候离开你的电脑

出处：`README.md` 的「What gets captured」开头：

> 录制、存储、抽帧、可选的语音转写**全部在你电脑上完成；录制期间什么都不往外发**。**只有当你点 Analyze 时**，才把「事件时间线 + 抽出的屏幕图 + 语音文本 + 有界的终端输出片段」发给 GitHub 云端给 Copilot 处理。

**这一点极其重要**：它把「采集」和「上传」拆成了两个时刻，**中间那段时间可以在本地做扫描和遮蔽**。这就是它整套脱敏方案能成立的前提。

### 第一层：上传**前**的本地文本扫描（文字）

出处：`electron/sensitive/scanner.ts` 的 `scanSession()`

- **扫描范围**：**整个事件 payload 的每一个字符串字段**，不是挑几个重要字段。源码里的原话解释了这个选择：
  > 「Scans the ENTIRE payload — not a hand-picked subset — so any value `get_events` could surface (a path in `cwd`, a `host`, a window `path`, or future PTY output) is covered ... **so there is no curated allow-list to silently drift out of sync with the outgoing data.**」
  —— 大白话：**「我宁可多扫，也不搞白名单」**。因为白名单总有一天会忘记更新，然后就漏了。
- 还要扫：**语音转写文本**、**终端完整输出**。
- 终端输出是**流式读**的（不会把无上限的记录全载进内存），每行上限 16,384 字符，超长行保留 12,288 字符重叠区（防止一个 token 被 PTY 切断导致漏检）。**这个细节很扎实。**

### 第二层：两套检测器

**A. 密钥/凭证检测**（出处：`electron/sensitive/secrets.ts`）
- 用 `@secretlint/core`（**离线、进程内**的 linter）+ 官方推荐规则集 `@secretlint/secretlint-rule-preset-recommend` + 自定义模式规则。
- **动态 import，只在第一次真扫描时才加载**（避免拖慢启动）。
- **非抛错设计**：引擎挂了就返回空结果，日志记一笔，**不阻断流程**（因为还有第二套兜底）。
- 产出的类别（出处：`common/sensitive.ts` 的 `SensitiveCategory`）：`private-key`、`api-key`、`jwt`、`password`。

**B. 结构化 PII 检测**（出处：`common/sensitive.ts` 的 `STRUCTURED_PII`）

| 类别 | 标签 | 严重度 | 正则/校验 | 大白话 |
|---|---|---|---|---|
| `credit-card` | Payment card number | **high** | `\b\d(?:[ -]?\d){12,18}\b` + **Luhn 校验** | 卡号，**要过校验位才算** |
| `ssn` | US Social Security number | **high** | `\b(\d{3})-(\d{2})-(\d{4})\b` + 排除 `000`/`666`/首位 `9`/`00`/`0000` | 美国社保号，**排掉明显无效的号段** |
| `phone` | Phone number | low | 北美 3-3-4 分组 + E.164 国际格式，两套 | 电话 |
| `email` | Email address | medium | `\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}\b` | 邮箱 |

**设计原则**（源码注释原话）：**「High precision on purpose」**——故意追求高精度，每个检测器要么形状很独特，要么带校验位，**就是为了让普通文章、哈希值、版本号、一串裸数字不会误报**。比如电话那条正则有个 `(?<!\d)` 的负向断言，注释解释得特别细：防止可选的国家码「1」咬住前一个号码的最后一位数字，**否则匹配会膨胀到重叠、被 `resolveOverlaps` 丢掉，结果反而把电话悄悄漏了**。**这种「为了防止漏报而修误报」的注释，是真正踩过坑才写得出来的。**

### 第三层：遮蔽的具体形状（**这一层和我们的红线最相关**）

出处：`common/sensitive.ts` 的 `maskValue()`

```js
export function maskValue(value: string): string {
  const MASK = "••••";
  if (!value) return "";
  if (value.length <= 6) return MASK;      // 短值：整个盖掉
  const head = value.slice(0, 2);
  const tail = value.slice(-2);
  return `${head}${MASK}${tail}`;          // 长值：留头 2 尾 2
}
```

**关键点，逐条对照我们的红线**：

| 做法 | 为什么这对我们重要 |
|---|---|
| **短值（≤6 字符）整个盖成 `••••`** | 短密码不会被「留头尾」泄露 |
| **长值只留头 2 尾 2** | 刚好够用户认出「哦这是那个 GitHub token」，但**不足以还原** |
| **`MASK` 是定宽（永远 4 个点）** | 源码注释写明理由：**「so the true length isn't leaked」**——**连长度都不暴露**。这是很讲究的一手。 |
| **报告里永不含原始值**（`SensitiveReport` 只带遮蔽值 + 计数） | 原文：`The report NEVER carries raw values; the values array stays in the main process and is never persisted or sent to the renderer.` |
| **`sensitive-report.json` 落盘时也只有遮蔽值** | 原文：`The report already carries only masked values + counts, so this never writes raw secrets.` |
| **给用户看的上下文片段也是遮蔽过的**（`redactedSnippet()`） | 而且会把**窗口内其他所有匹配项一并遮蔽**，防止「旁边的敏感值从这段截取的上下文里原样漏出去」 |
| **不需要的旧报告会被删掉** | `saveSensitiveReport(undefined)` 时 `rmSync`，避免「上次的旧报告」在本次「什么都没发现」时又冒出来，制造误导 |
| **屏蔽用的最小长度是 3**（`MIN_REDACT_LEN = 3`） | 注释理由：**太短的字符串做字面替换会误伤正文里大量无关子串** |

**还有一个「双向」设计**（出处：`buildRedactor()`）：把所有检测到的原始值收集起来（**只留在主进程，不进渲染层**），排序时**长者优先**（`sort((a,b) => b.length - a.length)`），这样「URL 里嵌着一个 token」时，会先把整个 URL/长值替换掉，不会留下残片。**这个「最长优先」的排序，是这类字面替换的必经之路，我们抄的时候别忘了。**

### 第四层：屏幕图像上的遮蔽（OCR + 打码）

出处：`electron/sensitive/frame-redact.ts`、`electron/sensitive/frame-heuristics.ts`、`electron/sensitive/ocr.ts`

- 屏幕图在**离开本机前**先做 OCR，认出每个词及其像素框。
- 对识别出的文字跑**同一套检测器**（密钥 + PII），**再加一项**：字面搜索「本次会话文字里已经发现过的值」（这叫 **cross-feed blur，交叉喂料遮蔽**——文字里发现的密码，如果出现在屏幕上，也会被盖住）。
- 命中的词，**画一个不透明的实心方块盖上去**。原文注释：
  > 「Boxes are solid and irreversible (**safer than a reversible blur**)」
  —— **「实心且不可逆，比可还原的模糊更安全」**。用色 `{r:17, g:17, b:17}`（近黑），并向外扩 4 像素 padding。
- **三层失败保护（这一点特别值得学）**：
  - `INACTIVE_FRAME_REDACTOR`：保护关着 → 原图直出（基线行为）
  - `WITHHOLD_FRAME_REDACTOR`：保护开着但扫描**没跑成**（比如抛异常）→ **`ready: false`，直接扣住所有帧不发**，而不是「发原图」
  - `OcrFrameRedactor`：正常运行 → 逐帧打码
  - 原文：`the caller then withholds that frame rather than risk serving raw pixels`
- **还有一项「读不出字也能拦」的补充检测**（`frame-heuristics.ts` 的 `frameSecretMatches`）：**只看形状不看具体字符**——高熵字符串、`xxx=` 这种「凭证赋值」的样子。因为它假设**「OCR 可能把字认错，但『这里有个像密钥的东西』这个形状还在」**。注释明确这是 **recall-first（优先不漏）** 的取舍。

### 它的诚实边界（我们必须知道）

出处：`README.md` 里反复出现的加粗警告，以及 `SensitiveReview.tsx` 的组件注释。

1. **它明确说：不要录密码。**
   > ⚠️ 「**Keep secrets out of your recordings.** Don't record, type, paste, or narrate passwords, tokens, API keys, or other confidential info.」
   —— **它把「用户自己别录」放在第一道防线**，而不是宣称「我能帮你兜住一切」。每次录制前都会提醒。
2. **它明确说：这是「best-effort（尽力而为）」。**
   出处：`scanner.ts` 注释 —— `Best-effort and non-throwing`；`SensitiveReview.tsx` 的注释 —— `Informational, non-blocking result`。
   —— UI 上也写死是 **`role="status"`、非阻断、可关闭的提示条**，**不是拦截弹窗**。
3. **OCR 那条路它自己承认是「优先不漏」的取舍**，也就是说**会有误报**（多盖了一些不该盖的）。源码注释原文：`Recall-first — see frame-heuristics.ts for the trade-off.`
4. **它遮的是「文字和屏幕」，不是「行为」。** 比如你在终端里敲的密码如果**回显没有被遮蔽**……实际上它靠的是终端记录脱敏 + 完整 transcript 进入同一套扫描（出处：README —— `terminal commands and the complete local terminal transcript participate in the same on-device secret/PII scan`）。

### 对我们的直接启示（对照我们的红线）

**我们的红线是：求助卡里绝不能有任何输入控件、任何提交/验证类按钮——用户必须在真实页面上操作。**

Skill Recorder 的做法给我们的启发是**它的分层顺序**：

| 它的层 | 我们能对应的做法 |
|---|---|
| ① 「用户别录」的前置提醒 | 我们已有：**让用户在真实页面操作**（而不是在我们的卡片里输） |
| ② 上传前本地扫描 | 我们可以：在**把页面内容/截图交给模型之前**，先在本地扫一遍 |
| ③ 遮蔽（短值全遮、定宽不泄露长度、不落盘原文、报告只带遮蔽值） | **这套遮蔽规则可以直接照搬**，尤其是「定宽不泄露长度」和「最长优先替换」两条 |
| ④ 失败就扣住不发（fail-closed） | **这条最该学**：扫描失败时**宁可什么都不发**，也不能「因为没扫成所以原样发出去」 |

**⚠️ 但有一条我们要比它更严**：它把整个机制定位为 **「尽力而为、非阻断、可关闭」**（用户能在设置里关掉）。**我们的红线是不可弱化的**——所以如果我们做类似的扫描，**不能给它一个「用户可以关掉」的开关**，也不能让它在失败时「静默放行」。这两点和它的产品定位不同，抄的时候要**明确改掉**，不能连定位一起抄过来。

## 3.7 任务三总结（一页）

| 问题 | 答案 |
|---|---|
| **记了什么** | 窗口切换、浏览器 URL（仅 macOS）、屏幕抽帧、剪贴板短预览、语音转写（可选）、**它自己的终端**的命令+完整输出。**不搞全局钩子、不看别人的终端。** |
| **什么格式** | `events.jsonl`（事件流）+ `session.json`（元数据）+ 语音 JSON + 终端 transcript（JSONL）+ `bundle.json`/`description.md`（分析结果）+ `sensitive-report.json`（**只有遮蔽值**）。 |
| **怎么变技能** | 两回合：① AI 出「计划」（泛化方式 + 固定值 + 有序步骤）→ 用户审阅编辑；② AI 按定稿计划写正文，具体值写成 `{{id}}` 令牌；③ 渲染时替换令牌，写 `<目录>/<技能名>/SKILL.md`；frontmatter 的 name/description 强制取自用户定稿的计划。 |
| **敏感信息怎么处理** | **四层**：① 录制本地化（只有点 Analyze 才上传）；② 上传前本地全 payload 扫描（secretlint + 结构化 PII）；③ 遮蔽（短值全遮 / 长值留头 2 尾 2 / **定宽不泄露长度** / 报告与落盘都不含原文 / **最长优先替换**）；④ 屏幕图 OCR 打**实心不可逆方块** + 交叉喂料 + **扫描失败就扣住不发**。 |
| **它的诚实边界** | 自称 **best-effort / 非阻断 / 用户可关**；明确要求「用户不要录密码」。**这两点我们不能照抄**——我们的红线不可弱化，所以既不能有关闭开关，也不能静默放行。 |

3. **`packages/session/` 下的 19 个子目录名**（供你复核）：`session-checkpoint-policy`、`session-format`、`session-format-catalog`、`session-format-v0-to-v1`、`session-format-v1-to-v2`、`session-format-v2-to-v3`、`session-log-deepseek`、`session-persistence`、`session-persistence-jsonl`、`session-projection`、`session-projection-cache`、`session-stats`、`session-telemetry`、`session-telemetry-otel`、`session-title`、`session-title-all-prompts-llm`、`session-title-first-prompt-llm`、`session-title-llm`、`session-turn-outline`。
4. **Skill Recorder 里没有 `src/` 下的「事件捕获」独立文件**。捕获逻辑在 `electron/collectors/`（`active-window`、`url-provider`、`clipboard`、`terminal` 等）与 `electron/recorder/`，不在 `src/`。**这是实际位置，我按实际位置给结论。**
5. **Skill Recorder 没有「密码字段」专用检测器**。`SensitiveCategory` 里的 `"password"` 类别是**被复用**的：screen 帧那里用它给「已知敏感值」打标签（`frame-redact.ts` 里 `known.push({ category: "password", label: "Known sensitive value", ... })`）。**它没有一个专门找「密码输入框」的检测器**，我不替它补这个功能描述。

## 一句话收尾

**三个仓库全部 MIT，都可放心参考。** 最值得抄的**单点**依次是：① DeepSeek 的「**落盘时机跟着不可逆边界走 + 失败就不放行**」；② OpenHands 的「**先提醒、再硬停**」两段式卡死处理；③ Skill Recorder 的「**扫描失败就宁可什么都不发**」以及遮蔽规则里的「**定宽不泄露长度**」。最需要**提防**的是 DeepSeek 的 PTC 模式（中间值不可回放、无字节上限）和 Skill Recorder 的「可关闭」定位——**后者和我们的不可弱化红线冲突，抄机制时必须连定位一起改掉。**
