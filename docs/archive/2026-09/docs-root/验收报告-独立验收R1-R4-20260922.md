## 逐项证据

### 1. 正常聊天对话 ✅

- 「今天过得怎么样」→ 普通聊天分支，流式回复正常，SSE 无 `loop` 事件。
- 「北京今天天气怎么样」→ 模型发起 `web_search`，Tavily 桩收到查询「北京今天天气」（`evidence/tavily-requests.jsonl`），
  `done` 事件携带 2 个来源（`searches: 1`）—— 聊天 + 联网搜索主链正常，R1 的闸没有误伤正常搜索。

### 2. 敏感信息不外发外部搜索（R1）✅

两条真实路径都验证：

1. **聊天路径（R1 闸本体）**：「这张银行卡尾号是几」→ 模型发起 `web_search`（查询含「银行卡」）
   → `chatLoop.ts` 敏感闸命中 → `blocked_sensitive`，**Tavily 桩 0 条查询**；服务端日志
   `[search] 已拦截敏感查询（未外发，未记原文）` + `[chat] 本轮联网搜索 1 次：[已拦截·敏感查询](0条/blocked_sensitive)`
   —— 日志脱敏也在（不再打印原查询）；模型改口引导用户走官方渠道。
2. **完整卡号句式**：「我的银行卡号是6222 0202 1234 5678 9012，帮我看看这张卡是哪家银行的」
   → 被服务端判任务模式（含「看」+ ≥15 字）→ 浏览器循环工具表**没有** `web_search`，结构上不可能外发搜索；
   跑完整循环后 Tavily 桩依然 0 条含卡号查询。

全轮次第三方搜索桩收到的查询全集 = `["北京今天天气", "北京今天天气", "北京今天天气"]`（三轮运行），
**没有任何一条含卡号/密码/尾号**。

> 残留（并入第 3 项 goal 通道）：含卡号消息若被判成任务，原文作为 goal 明文进 `tasks.payload.goal` 与任务文档。

### 3. 敏感输入值不明文存储/显示（R2）❌

**已修复并验证的部分**（真 `runToolLoop` + 真服务端 + 真 `/task/step`）：

- 模型下发 `type(target=备注, text="我的密码是Secret123")`：
  - 浏览器面板步骤流（`emit`，`workbench:browser:agent` 通道）= 「步 1：在「备注」输入了 14 个字符 —— 已向 备注 写入 14 个字符（方式：keyboard）」—— 无原文 ✅
  - `tasks.payload.steps`（经收尾兜底文档直拼落库内容取证）= 同上，无原文 ✅
  - 旧客户端/第三方客户端兼容：直接 POST 旧形状摘要「在「备注」输入「我的密码是Secret123」」到 `/task/step`
    → 入库被清洗为「在「备注」输入「[已脱敏·14字]」」✅

**未修复（实测打屏）**——任务轮聊天长连（P0-2 通道，`/chat/stream` 任务分支保持长连、
`/next` 经 `broadcastLoopEvent` 推 delta/step）：

```
好，我在当前这张页上动手了，做完把结果给你。

**步骤 1**：在「备注」中输入 "我的密码是Secret123"   ← 明文密码出现在聊天气泡

🎉 **任务完成**
已在「备注」框完成输入。
```

- 实测：`evidence/r2-ui-leak.json`：`气泡含明文密码=true`、`step事件载荷含明文=true`
  （`step` 事件的 `call.args.text` 也是原文）、`驾驶员emit含明文=false`。
- 根因：`apps/server/src/routes/loop.ts:615` `formatToolDesc` 对 `type` 用 `args.text` **原文**拼描述，
  而 `loop.ts:220-223` 把它广播到聊天长连；客户端 `App.tsx` 对 `j.delta` 逐段渲染进助手气泡并留档会话。
  R2 提交只修了 driver/label/taskStep 通道，漏了这条**更早存在、但任务轮才接上**的长连通道。
- 同源残留：任务 **goal 明文落库** —— `tasks.payload.goal`（JSONB 明文）+ 任务文档「## 目标」
  + 服务端 notify 日志打 goal 前 30 字（`agent.ts:310`）。用户消息本体在 `messages` 表是密文（`content_enc`），
  但一旦它成为任务 goal，就有一条明文副本躺在任务表与可下载文档里（卡号场景同样命中，见 task #1 文档实证）。

**判定：用户第 3 条口径「不会明文存储/不会明文显示在界面」不成立 —— 主界面（聊天）会显示明文。不通过。**

### 4. 暂停-继续同一操作不执行两次（R3）✅

精确复现 S7 窗口（exec 完成 → 下一次 `/next` 之间用户按暂停）：

| 路径 | 暂停响应 | 「提交」总执行次数 | 续程行为 |
|---|---|---|---|
| 主路径（修复后桌面：暂停刷回执） | `receiptIngested=true`（日志「回执已认领」） | **1** | 模型看到真实回执 → 直接 done，无多余动作 |
| 对照组（模拟修复前旧桌面：不刷回执） | `receiptIngested=false` | **1** | 服务端「回执缺失」话术 → 模型先 `read_page` 核验 → done（不盲重做） |

- 真 `runToolLoop` 两程共用同一 `loopId`（与 `main.ts` 的「继续 = 接回原循环」一致），
  计数的是驱动执行器的真实调用记录，非服务端状态推断。
- 双层防护都生效：① 暂停前刷回执（`pauseOut({result})` + `/pause` 先认领再挂起）；
  ② 回执缺失 ≠ 确认没执行（话术改为先读页核验）。

### 5. 稍长闲聊不被误判成任务（R4）❌

- 「今天天气真舒服，早上出门遛弯的时候楼下花坛开了好多月季，心情特别好，你那边天气怎么样啊」
  （43 字、无任何动作词、无打开页）→ **SSE 出现 `loop` 事件，被发车成浏览器任务**。
- 典型例句「帮我查一下今天北京的天气怎么样」→ 同样被发车。该循环工具表没有联网搜索，
  简单问题被开浏览器瞎翻页（正是复查报告 R4 记录的体验伤害）。
- **代码核对**：最新提交 `e9ec00b` 的提交信息只覆盖 R1+R2+R3；`shouldEnterTaskMode`
  （`apps/server/src/routes/chat.ts:327-346`）中：
  - `:344` `if (t.length >= 15) return true;` —— 「≥15 字一票发车」**仍在**；
  - `:341` 动作词正则仍含 `查|搜|看` 等单字；
  - `:339` `if (hasPage) return true;` —— 有活页时**所有**消息发车。
  复查报告给 R4 的修复口径（「要求动作词+有活页/开页意图才发车；纯提问走聊天搜；删 length>=15 一票发车」）**未见实施**。

**判定：不通过。这一项不是「修得不够好」，是修复本身不在最新代码里。**

### 6. 正常浏览器任务仍正常触发（回归）✅

- 「打开百度，搜索一下今天的新闻，把前三条标题读给我」：
  - 客户端真实 `detectOpenUrl` 认出 `https://www.baidu.com` 并（在真机里）开页；
  - 服务端判任务模式，SSE 下发 `loop` 事件（`wcId=3`）；
  - 真 `runToolLoop` 接上循环：`read_page` → `done`，收尾「已打开页面并读取内容，任务完成。」
- 结论：聊天→发车→循环→执行→收尾的整条链路完好，**没有被 R1–R3 的闸误伤**。

## 总评：这 4 项修复能否作为后续开发的健康基线？

**结论：尚不能作为健康基线。建议状态：R1 ✅ 可入基线；R3 ✅ 可入基线；R2 🟠 部分入基线（补 2 个点）；R4 ❌ 未实施，需补齐后重验。**

1. **R1（聊天搜索敏感闸）**：修复完整、真跑通过、日志同步脱敏、未误伤正常搜索。可作为基线。
2. **R3（暂停吞回执）**：修复完整且是双层防护（刷回执 + 回执缺失话术），精确窗口复现不重做。可作为基线。
3. **R2（敏感输入值）**：主口径（步骤摘要 + 任务账本 + 旧客户端清洗）通过，但**任务轮聊天长连会把明文值打进聊天气泡**（`formatToolDesc` 原文 + `/next` 广播），goal 通道（任务表/文档/notify 日志）仍有明文副本。补齐建议：
   - `loop.ts:615` `formatToolDesc` 对 `type` 只记 `target + 字数`（与 driver/label 同口径），`step` 事件的 `call.args` 同步脱敏；
   - goal 的明文副本：任务表 goal 加密或截断 + 文档「## 目标」脱敏 + notify 日志不打 goal 原文。
4. **R4（发车过触发）**：**未实施**。`length>=15 一票发车`与宽松动作词正则仍在，长闲聊/简单提问一律被开浏览器（且该循环没有联网搜索，比「不误判」的体验伤害更大）。建议按复查报告口径收紧后重新走验收 5/6 两条。

**风险提示**：在 R2 的长连通道修掉之前，任何「让 AI 往页面里填密码/验证码」的任务都会在用户的聊天记录里留下明文——这比修复前的问题暴露面更大（因为任务轮长连是近期才接上的新通道，等于新功能把旧漏点重新激活了）。建议**优先修 R2 长连 + R4 发车**，其余两项可先行。
