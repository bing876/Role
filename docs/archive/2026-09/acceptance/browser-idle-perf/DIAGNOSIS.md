## 0. 结论速览

**先说最重要的一句：就 CPU / 内存 / GPU 的绝对量而言，我在这台真机上没能复现出"1 个闲置浏览器会把整机拖卡"的证据。**

| | 0 张页 | 1 张页·全屏·闲置 | 1 张页·后台·闲置 |
| --- | --- | --- | --- |
| 整机 CPU（12 核口径） | 0.097% | **0.230%** | 0.063% |
| 折合"占几个核" | 0.012 核 | **0.028 核** | 0.008 核 |
| 应用内存 | 570 MB | **681 MB** | 678 MB |
| GPU 进程 CPU | 0.011% | 0.010% | 0.010% |
| GPU 加速 | 正常（ANGLE / NVIDIA GTX 1060 3GB / D3D11） | 同左 | 同左 |
| **主窗口帧率** | 60.1 fps | **60.0 fps** | 60.0 fps |
| **掉帧（>33ms 的帧）** | 0 | **0** | 0 |
| **长任务** | 0 | **0** | 0 |
| **打字延迟 p95** | 34.1 ms | **33.6 ms** | 33.4 ms |

> 换算基准：本机 12 个逻辑核，`percentCPUUsage` 已是"占整机"口径 ⇒ **1 个核跑满 = 8.33%**。
> 0.230% ≈ 一台 12 核机器上 **1/40 个核**。

**四个环节逐一排除：CPU 不是（0.028 个核）、内存量小（+111 MB）、GPU 正常（硬件加速 + 0.010%）、
帧时间也没问题（锁 60fps、零掉帧、零长任务、打字延迟贴测量下限 —— 详见 §10）。**

**多实例（§12）：每加一张页 ≈ +101 MB（线性），4 张 = 1011 MB；1~4 张页在静止 / 滚动下全部零掉帧。**

**长聊天记录（§15）：200 条消息把 DOM 从 59 个节点推到 458 个（8×），帧 p95 与打字延迟仍**完全不变**、零掉帧、零长任务。**

**任务后闲置态（§16）：真跑完一个任务后再量，`agentLanes()` 已清空、帧时间与"从未跑任务"完全一致、零掉帧零长任务。**

**内存悬崖（§17）：把上限设成 20、一路加到硬上限 20 张页（应用内存 2694 MB），帧率仍 60fps 零掉帧、系统可用内存只降 253 MB。**

**另外做了 5 分钟闲置 soak（§11）**：零掉帧、DOM 节点恒定、Layout/RecalcStyle 零增量、
JS 堆持平；对照组（不注入动画）内存**完全持平在 683~685 MB、CPU 0.03~0.06%**
⇒ **"越用越卡"与泄漏也排除了。**

**但排查过程中确认了一个真问题、并否掉了三个猜测：**

1. ★★ **后台降频只做了一半**：`opacity:0` 时 rAF 确实从 60 帧/秒降到 **1 帧/秒**（出帧节流生效），
   但 **`setInterval` 完全没被钳**（仍 62.5 次/秒）—— 因为 guest 自报 `visibilityState=visible`，
   Chromium 的「后台标签定时器钳制」**不触发**。⇒ 页面里靠 `setInterval` 跑的
   轮播 / 实时行情 / 倒计时，在后台**照跑**。整机 CPU 只降 9%（0.80% → 0.73%）。
   （另：我们**自己那套节流开关实测是空转**，见 §4.2。）
   ⚠️ **这一条我改正过**：第一版写成"完全不降频"是**错的**，起因是窗口被别的窗口遮挡，过程见 §4.3。

2. ⚠️ **本机内存确实紧张，但"内存压力导致卡顿"这条已被 §14 实测否掉**：
   物理内存 15.8 GB 只剩 **2.0 GB**（87%），370 个进程合计 20.8 GB，我们应用只排第 8（685 MB）——
   看着很像原因。**但实测**：应用 +1 张页确实把硬换页从 29.6 抬到 107.8 次/秒（峰 2353），
   然而 **磁盘忙只有 0.54%、磁盘队列 0.01、同段应用帧时间仍是 60fps 零掉帧** ⇒
   **换页没有转化成可感知的卡顿**。详见 §14。（GPU 启动崩溃那条**已排除**，见 §5.3。）

**所以下一步不是急着改代码** —— 需要你先确认"卡顿"的具体感受和复现环境（见 §7）。

## 1. 复现方式（可重复）

不是"打开应用随便点点"，而是**受控三段对照**：同一进程、同一轮，唯一变量是"有没有那张页"。

```
Phase 0  0 张页              → 应用自身基线
Phase 1  1 张页 · 全屏       → 用户报的场景（面板默认就是全屏）
Phase 2  1 张页 · 后台       → 切「退出全屏」，同一张页、同一时刻
```

- 开页走 `window.workbench.openBrowser(url)` —— **只开页、不起任何任务**（`openUrl` 不写 `drivingIds`，所以是纯粹的"闲置"）。
- 数据源 = 主进程 `app.getAppMetrics()`，**与代码里资源哨兵（`resource-guard.ts`）同源同口径**。
- 采样间隔设为 **1 秒**（`workbench-settings.json` 的 `resourceSampleMs: 1000`，`SETTINGS_RANGE` 允许的合法值）。
  为什么必须压到 1 秒：`percentCPUUsage` 是"距上一次调用之间的平均"，**5 秒的粗采样会把 1.2 秒级的尖峰平均掉**。
- 打开 `WB_RESOURCE_GUARD_RAW=1`，哨兵把**每一点、含按进程明细**写进 `raw-*.jsonl`，探针最后读文件切片，不额外轮询（避免采样本身干扰）。
- 只写临时 profile，**不动仓库代码、不动真实数据目录**。

## 4. ★★ 降频 / 节流：**rAF 已降频，但 JS 定时器没降；我们自己的开关是空转**

> ⚠️ **本节是我改正过的。** 第一版结论写的是"后台态**完全**没降频"，**那是错的** ——
> 起因是当时没控制"应用窗口有没有被别的窗口盖住"这个变量（过程见 §4.3）。
> 下面是加了控制变量后的结论，**两轮一致**。

### 4.1 受控实测（窗口确认可见，两轮一致）

把持续动画注入**内嵌页自己**，量它真实的帧率与定时器频率。
**每次测量前都先读 `document.hidden`，确认为 `false`（即窗口真的可见）**：

| 指标 | 全屏 | 后台（`opacity:0`） |
| --- | --- | --- |
| 内嵌页 rAF | **60.0 / 60.0** 帧/秒 | **1.0 / 1.1** 帧/秒 |
| 内嵌页 `setInterval(…,16)` | 62.5 次/秒 | **62.5 次/秒**（一点没被钳） |
| 内嵌页 `visibilityState` | `visible` | `visible`（`hidden = False`） |
| 主窗口 `document.hidden` | **False**（已确认可见） | **False**（已确认可见） |
| 整机 CPU（带动画页） | 0.80% | 0.73%（只降 9%） |
| （对照）后台 + 无动画 | — | 0.48% |

**⇒ 真实结论：`opacity:0` 确实让 rAF 降到了 ~1 帧/秒档；但 `setInterval` 完全不受影响。**

**为什么 rAF 降了、定时器没降** —— Chromium 有**两套独立**的机制：

| 机制 | 触发条件 | 我们这里 |
| --- | --- | --- |
| **出帧节流**（合成器层面） | 没有新帧要画（元素全透明 / 不可见） | ✅ **生效**：rAF 60 → 1 |
| **后台标签定时器钳制** | `document.visibilityState === 'hidden'` | ❌ **不触发**：guest 自报 `visible` |

```css
.browserLayer--bg      { opacity: 0; pointer-events: none; z-index: 0 }   /* 整层后台态 */
.browserPanel__view--off { opacity: 0 }                                    /* 别家智能体的页 */
```

> 第 25 步那条红线（**"绝不能 `display:none` / 绝不能 0 尺寸"** —— 因为 CDP 驾驶靠页内 rect 算坐标，
> 0 尺寸会让点击失灵）换来了"驾驶可用"；代价就是 `visibilityState` 永远是 `visible`，
> **定时器钳制这一路拿不到**。所以页面里靠 `setInterval` 跑的轮播 / 实时行情 / 倒计时
> 在后台**照跑**（实测 62.5 次/秒，与全屏完全一致）。

### 4.2 我们自己的节流开关：真调产品 API 裁决 —— **完全空转**

机制是有的，而且写得很谨慎：

```
main.ts:1401        ipcMain.handle('workbench:browser:throttle')  →  wc.setBackgroundThrottling(throttle)
                    （且明确拒绝正在被驾驶的页：throttle && isDriving ⇒ { ok:false, error:'driving' }）
preload.ts:86       browserThrottle(webContentsId, throttle)
useBrowserWorkspace.ts:875   唯一的渲染层调用点
```

但渲染层唯一的调用点是：

```ts
const want = t.sleep === 'shallow';          // ← 只有"浅休眠"才节流
void window.workbench?.browserThrottle?.(wcId, want);
```

而 `t.sleep === 'shallow'` 要求 `decideSleep`（`sleepPolicy.ts:81`）把它判成浅休眠。
`decideSleep` 的判定顺序第 ② 条是：

```ts
// ② 前台正在看的那张 —— 永不休眠
if (input.activeTabId !== null && t.id === input.activeTabId) continue;
```

**只有 1 张页时，它必然是"前台正在看的那张" ⇒ 永不休眠 ⇒ `want` 恒为 `false`。**

**★ 我直接调真实产品 API 做了裁决**（不是手抄近似实现 —— `window.workbench.browserThrottle(wcId, true)`）：

| 调用 | 返回值 | guest rAF |
| --- | --- | --- |
| 后台 + `throttle(true)` | `{ ok: true }` | 1.0 帧/秒 |
| 全屏 + `throttle(true)` | `{ ok: true }` | **60.0 帧/秒** |
| （不调用时）后台 | — | 1.0 帧/秒 |

**⇒ `setBackgroundThrottling(true)` 对 rAF 毫无影响**：后台本来就是 1/s（出帧节流已经生效），
全屏传 `true` 也仍是 60/s。所以这套机制当前**是空转** —— 既不会让后台更省，也不会让全屏变差。

**结论：`want` 恒为 `false` 的原因查对了（`decideSleep` 第 ② 条"前台页永不休眠"），
但因为 `setBackgroundThrottling` 本身无效，去改这条规则不会带来任何收益。**

### 4.3 ★ 我是怎么发现第一版结论是错的（过程留证）

同一条件两次测出**相反**结果：

- `browser-idle-throttle-probe.py`：后台 rAF **60.0/s**
- `browser-idle-throttle-options-probe.py`：后台 rAF **1.0/s**

于是做重复性实验（3 轮 × 全屏 / 后台 / 后台提前台），把控制变量揪了出来：
**guest 的 rAF 与它自己的 `document.hidden` 一一对应**（`False`→60/s，`True`→1/s）。
而 `document.hidden` 受 **Chromium 的遮挡检测（occlusion）**支配 ——
那一轮里 `主窗口 hidden=True` **从头到尾都是 True**，说明**应用窗口被我的宿主窗口盖住了**，
于是整个应用（含 guest）被标成 hidden，rAF 掉到 1/s。

最后用 Win32 把应用窗口提到前台、并**回读 `document.hidden=False` 确认**，再跑两轮全屏/后台，
得到 §4.1 那张表（两轮完全一致）。判别实验：`browser-idle-window-occlusion-probe.py`。

**⇒ 教训：测 Electron 渲染性能前必须先确认窗口真的可见（读 `document.hidden`），
否则测到的是"被遮挡"，不是代码行为；同一状态至少测 2~3 轮，不一致就说明有未控变量。**

## 5. GPU 层面

### 5.1 本机 GPU 进程**每次启动都崩**

`electron.log`（每次启动都复现）：

```
[13736:...] ERROR:gpu_process_host.cc(982)] GPU process exited unexpectedly: exit_code=1   × 9~10 次
[13736:...] FATAL:gpu_data_manager_impl_private.cc(423)] GPU process isn't usable. Goodbye.

[launch] ⚠️  当前环境无法初始化 Chromium 的进程沙箱（常见于虚拟机 / 远程桌面 / 容器）。
[launch]    自动回退 --no-sandbox 重试 …
```

`start-electron.mjs` 会自动回退 `--no-sandbox` 重启（日志里 `DevTools listening` 出现 2 次 = 启动了 2 次），
**第二次能正常跑**。这是**本机环境问题，不是我们代码的问题**（同一现象在之前几轮也记过）。

### 5.2 GPU 利用率

- `app.getAppMetrics()` **拿不到真正的 GPU 引擎利用率**（只有每个进程的 CPU / 内存）。
- 走 Windows 性能计数器 `\GPU Engine(pid_*)\Utilization Percentage` 实测时发现：
  **本应用那几个 `electron.exe` 进程一条 GPU Engine 计数器都没有**（其他进程有）。
  这既可能表示"没在用 GPU"，也可能只是"此刻没有活跃 GPU 上下文"，**单凭它不足以定论**。
- 权威判据（`SystemInfo.getInfo` + 渲染层自报 WebGL 渲染器）见下方 **§5.3**。

### 5.3 加速状态判定：**GPU 加速是正常的**

`featureStatus` 与 GPU 进程崩溃日志互相矛盾（前者说 `enabled`、后者每次崩），
所以用**渲染层实际拿到手的 WebGL 渲染器**一锤定音：

```
WebGL UNMASKED_RENDERER = ANGLE (NVIDIA, NVIDIA GeForce GTX 1060 3GB (0x00001C02)
                                  Direct3D11 vs_5_0 ps_5_0, D3D11)
UNMASKED_VENDOR         = Google Inc. (NVIDIA)
featureStatus.gpu_compositing = enabled
featureStatus.rasterization   = enabled
webgl / webgl2                = ok / ok
```

**⇒ 确认是硬件加速（NVIDIA GTX 1060 3GB + ANGLE/D3D11），不是软件渲染（SwiftShader）。**

这也反过来解释了 §5.2 那个"本应用进程没有 GPU Engine 计数器"的观察：
那只是**空闲时没有活跃的 GPU 上下文**，**不能**推出"没在用 GPU"。
（所以那条观察在报告里不作为结论，只作为"为什么改用了 SystemInfo 判据"的记录。）

**⇒ GPU 这一环节可以排除：加速正常、GPU 进程 CPU 只有 0.010%。**

## 6. 诊断结论

**卡顿到底是因为 CPU / 内存 / GPU 哪个环节？**

1. **CPU：不是。** 1 张闲置页只占 **0.230%**（12 核口径 ≈ 0.028 个核）。
   没有周期性尖峰，没有失控的定时器，主窗口渲染进程 99.99% idle。
2. **内存：是"这个浏览器实例"的主要成本，但绝对量不足以拖垮整机。**
   1 张页 = **+111 MB**（guest 渲染进程 ~103~109 MB + GPU/其它增长）。
   注意 `maxBrowserInstances` 默认 **4**（设置里最大可调到 20），**成本随实例数线性增长**。
3. **GPU / 渲染：GPU 本身正常（NVIDIA GTX 1060 + ANGLE/D3D11 硬件加速，GPU 进程 CPU 0.010%）。**
   唯一实测到"与预期不符"的是**后台降频只做了一半**（§4.1）——
   rAF 降了，但 **JS 定时器没降**；带动画页在后台仍花掉全屏 91% 的 CPU（0.80% → 0.73%）。
   绝对量依然很小。
4. **★ 帧时间（"卡顿"的直接度量）：也没有问题。** 锁 60fps、**零掉帧**（>33ms 的帧在三个阶段都是 0）、
   **零长任务**、主线程只忙 2%，**打字延迟 p95 三个阶段几乎一样（34.1 / 33.6 / 33.4ms）**
   —— 开一个浏览器页**没让它变差**。详见 §10。
5. **★ 5 分钟闲置 soak：也没有"越用越卡"。** 零掉帧、p95 前后半段一致（16.9→16.9ms）、
   DOM 节点恒定 177、**Layout/RecalcStyle 增量 = 0**、JS 堆持平；
   对照组（不注入动画）内存**持平在 683~685 MB**、CPU 0.03~0.06%。
   主 soak 那点 +2.49 MB/分经对照证明**来自注入的动画与我的采样**，不是产品泄漏。详见 §11。
6. **★ 多实例也不解释：** 每加一张页 ≈ **+101 MB**（线性，4 张 = 1011 MB），
   但 **1~4 张页在「静止 / 滚应用 UI / 滚内嵌页」三种场景下全部零掉帧**（p95 16.8~17.0ms）。详见 §12。
7. ⚠️ **"系统级内存压力"这条我实测过，也站不住**（§14）：
   本机内存确实紧张，应用 +1 张页也确实把硬换页从 29.6 抬到 107.8 次/秒（峰 2353），
   **但磁盘忙只有 0.54%、磁盘队列 0.01、同段应用帧时间 60fps 零掉帧** ⇒
   **换页没有转化成卡顿**。所以"内存压力"**不是**答案。

> **本机环境事实（供参考，都不是"卡顿"的解释）**：
> - 物理内存 15.8 GB / 可用 **2.0 GB**（87%）；370 进程合计 20.8 GB（超物理内存，靠压缩/换页撑着）。
>   前 7 名：WorkBuddyAI 3457 MB、chrome 2894、WorkBuddy 2100、svchost 1548、
>   msedgewebview2 1523、douyin 1200、msedge 1173；**我们应用 685 MB 只排第 8**。
> - C: 盘 192G 已用 / 剩 7.4G（97%）。
> - GPU 进程**每次启动**都要崩一次再回退 `--no-sandbox`（仅启动瞬间，之后加速正常，见 §5.1/§5.3）。

8. **★ 长聊天记录（200 条）也不解释**（§15）：DOM 节点从 59 涨到 458（8×），
   但**帧 p95 变化 +0.0ms、打字 p95 变化 −0.1ms、掉帧与长任务都是 0** ⇒
   "每 1.2 秒重渲染 200 条消息"的代价小到测不出来。

9. **★ "任务跑完之后"的闲置态（真实用户真正所处的状态）也正常**（§16）：
   真跑一个任务再等它结束，`agentLanes()` **已清空**（收尾摘干净了）、
   帧 p50/p95 与"从未跑任务"**完全一致**、**零掉帧零长任务**。
   ⚠️ 唯一差异是 CPU 0.05% → 0.50%（≈0.06 个核），已如实记录，**不影响帧时间**。

10. **★ 内存悬崖：一路加到硬上限 20 张也没找到**（§17）。把 `maxBrowserInstances` 上限设成 20、
   逐档加到 **20 张页**（默认上限 4 的 5 倍）：应用内存涨到 **2694 MB**（+104 MB/张），
   但**系统可用内存只降 253 MB**、**帧率始终 60fps、零掉帧零长任务** ⇒
   "内存压力导致卡顿"这条在**把内存用到产品允许的最大值**之后依然没被复现。

**所以我必须诚实说：在这台机器上，我拿到的数据不支持"1 个闲置浏览器导致整机卡顿"这个结论，
而且我连"可能的解释"也一个都没验证成立。**
**十个方向**（CPU / 内存 / GPU / 帧时间 / 5 分钟闲置 soak / 多实例与滚动 /
**系统级压力** / **长聊天记录** / **任务后闲置态** / **内存悬崖**）都测过，
**全部正常、或已被实测排除**。剩下的只能靠你提供具体信息（见 §7）。

## 8. 修复方案（**等你确认后再动手，我没有擅自改**）

### 方案 A —— 要不要把后台页的 **JS 定时器**也钳住（治 §4.1 剩下那一半）

**前提已经变了**：rAF 那一路 **Chromium 已经帮我们做了**（60 → 1 帧/秒），不需要我们动手。
剩下的缺口只有一个：**`setInterval` 在后台照跑**（实测 62.5 次/秒）。

| 子方案 | 做法 | 收益 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A1** | **不动**（保持现状） | 切回来瞬时、零风险 | 页面自己的轮播 / 行情在后台继续跑（实测：带动画页后台 0.73% vs 无动画 0.48%，差 **0.25%**） |
| **A2** | 冻结「**没有任务在跑**」的后台页的 JS | 后台 JS 全停 | ⚠️ **实测手段不成立**：`Page.setWebLifecycleState('frozen')` 返回 `{}`，**什么都没冻住**（定时器仍 62.5 次/秒、CDP 驾驶点击仍成功）。且冻结会**把任务冻住**，必须加"正在被驾驶就不冻"的硬闸 |
| **A3** | 后台页改 `visibility:hidden`（**仍保真实尺寸**）以触发定时器钳制 | 若成立，最干净 | ⚠️ **实测无效**：改完 guest 的 `visibilityState` 仍是 `visible`、定时器仍 62.5 次/秒（rAF 本来就已是 1 帧/秒）。**排除** |

**这一轮实测把 A2 / A3 两条都堵掉了**：

- `Page.setWebLifecycleState('frozen')` → 返回 `{}`，**没有冻住任何东西**
  （16ms 定时器仍 62.5 次/秒；冻结后 CDP 驾驶点击**仍然成功**，说明 JS 根本没停）
- `visibility:hidden`（保尺寸，**驾驶仍可用**：rect 48×40、点击生效）→ **`visibilityState` 不变**

⇒ **在"1 张页闲置"这个场景里，我没有找到既安全又有效的"定时器钳制"手段。**
建议按 **A1（不动）**。如果一定要继续查，下一步需要实测别的 CDP 生命周期手段
（本次**未测**，属于"新功能开发"，要你确认是否值得投入）。

> ⚠️ 顺带说明：`visibility:hidden` 与离屏 `transform: translate(-100000px,0)` 这两条
> **都保住了真实尺寸、CDP 驾驶都仍然可用**（实测点击成功）—— 也就是说，
> **如果**将来真需要更强的隐藏手段，这两条比 `display:none` 安全得多。本次不需要，仅作记录。

### 方案 B —— 修「活跃页永不休眠」（**实测：改了也没收益，不建议做**）

`decideSleep` 第 ② 条"前台页永不休眠"确实让 `want` 恒为 `false`，但 §4.2 已实测
**`setBackgroundThrottling` 本身完全无效**（后台本来就 1 帧/秒、全屏传 `true` 也不变）
⇒ **改这条规则不会带来任何收益**，除非先换掉底层手段。
⚠️ 另外浅休眠的前提本来就是"5 分钟没被用过"：**如果你说的"闲置"不足 5 分钟，改了也不生效。**

### 方案 C —— 给那个 1.2 秒轮询加条件（优先级低）

没有任务时降到 5 秒或直接停。**实测成本≈0**，纯粹是为了"逻辑干净"。
代价：「临时测试条」的相位显示会变慢（那条本来就是为了肉眼看相位变化）。

### 方案 D —— 先排除环境（**建议先做这个**，零风险）

在同一台机器上关掉其它大内存进程后复测；同时确认卡顿时任务管理器里「AI 工作台.exe」的真实 CPU。
**如果那行只有零点几，就不该改浏览器代码。**

## 11. ★★ 补充测量：**5 分钟闲置 soak** —— 排除"越用越卡"

> 前面所有测量只有 60~75 秒。而"**闲置时会卡**"往往意味着**随时间累积**

### 11.1 主 soak：1 张页 + 内嵌页持续动画（每 5 秒采一点）

## 16. ★ "任务跑完之后"的闲置态实测 —— 这是**真实用户真正所处的状态**

## 18. ★ 补充：**静态审查**闲置路径 —— 也没有"随数据量增长的热路径"

> 上面全是**动态测量**。测量有个天然局限：**我的测试库只有 1 个项目 / 1 个智能体 / 空会话**，
> 所以任何**随数据量增长**的渲染期计算都不会显形。于是补一次**静态审查**：
> 那个 1.2 秒轮询会让 `App.tsx`（2700+ 行）的 **render body 整体重跑**，
> 所以「render body 里有没有非 memo 的 O(n) 计算」是关键问题。

### 查法与结果

```bash
# ① render body / JSX 里直接做的数组运算（.map/.filter/.sort/.reduce/JSON.parse/new Date…）
grep -n "\.sort(\|\.filter(\|\.reduce(\|JSON.parse\|JSON.stringify\|new Date(" apps/desktop/src/App.tsx
# ② JSX 表达式里的 .map(（这些渲染期真的会跑）
grep -n "{[a-zA-Z_.]*\.map(" apps/desktop/src/App.tsx
```

| 位置 | 是什么 | 判定 |
| --- | --- | --- |
| `App.tsx` 里的 `JSON.parse/stringify` | 全在 **fetch body / IPC 回调**里 | ✅ 不在渲染期 |
| `2393` `userMem.map` | 用户记忆列表 | ✅ 在 `{userMemOpen && …}` 里，**面板展开才跑** |
| `2409` `projMem.map` | 项目记忆列表 | ✅ 在 `{projMemOpen && …}` 里 |
| `2457` `knowledgeDocs.map` | 知识库文档列表 | ✅ 在知识库面板里 |
| `2575` `curTask.outline.slice(0,4).join()` | 任务大纲 | ✅ 固定 4 项，O(1) |
| **`2616` `messages.map`** | **聊天消息列表** | ⚠️ **每次渲染都跑**，但**上限 200 条**，已实测零影响（§15） |
| `2643` `[...messages.slice(0, idx)].reverse().find(...)` | 找"这条确认对应的用户原话" | ✅ **在 `onClick` 里**，只有点按钮才跑 —— **不是渲染期**（一开始看它在 `map` 回调里，容易误判成 O(n²)） |

### 结论

**`App.tsx` 的 render body 里没有"随数据量增长的未 memo 热路径"。**
每次 1.2 秒重渲染实际会做的数组运算只有 `messages.map()`（≤200 条），
而这一条已经在 §15 实测过：**DOM 从 59 涨到 458 个节点，帧时间与打字延迟完全不变**。

> **教训（值得记）**：看到 `[...arr.slice(0, idx)].reverse().find(...)` 出现在 `arr.map()` 的
> 回调里，第一反应会判成 **O(n²)** —— 但它其实在 `onClick` 里。
> **判定"这段代码在渲染期跑吗"必须看它所在的闭包层级，不能只看它在哪个 `map` 里。**
