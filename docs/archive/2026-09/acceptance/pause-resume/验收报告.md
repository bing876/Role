## 2. 三个问题的答复（已实现，与答复一致）

### Q1 怎么判断页面变没变？
**结构化快照集合比对 + 两层判定**，不是截图比像素、不是整页 DOM 字符串 diff。

- 比的是本来就在每条工具回执里流动的 `PageSnapshot`（url / title / buttons / links / inputs / texts），**零额外采集成本**，而且人能读得懂；
- 代码只判「变没变、哪一类」（`unchanged` / `moved` / `edited` / `unknown`），**语义交给模型**；
- URL 归一化忽略协议 / 末尾斜杠 / `#hash`，避免「同一页刷新一下」被误判成换页。
- 为什么不用截图：base64 体积大、像素 diff 说不出「变了什么」、轮播/懒加载/秒表会天天误报。

### Q2 变了之后 AI 怎么调整？
**`replan-from-current`（就地重判）** —— 既不整份重规划，也不 naive 地「跳过用户做过的步骤」：

1. 这一步**只能** `read_page`；
2. **禁止** `open_url` 跳回暂停前的地址（会覆盖用户刚做的操作）；
3. 对照目标判当前页：已达成就 `stop(done)`；更近了就从当前位置继续且**不重做用户手动完成的部分**；明显偏离就 `stop(need_user)` 问人，不擅自导航。

实现上是往**原有消息历史 append 一条**，不是重建系统提示词 —— 既保留主提示词的全部规矩，又天然满足「最新指令优先」，且不用再维护第二套提示词。

### Q3 会不会大改现有执行逻辑？
不会。改动范围就是上表 7 处，循环引擎主体没动。最容易被改坏的 `advance()` 重入锁已单独复验（⑥）：同一 loopId 并发两次 `next` 仍是「一次 200、一次 409 `loop_busy`」。

> 另外：不能在「快跑到步数上限」的循环上点暂停 —— 它会先自己终态收尾，服务端根本收不到挂起请求。
> 脚本改成先给 B 重新发车（步数充足）再暂停，并**等 DB 真的落行**而不是睡固定几秒。

### ⑦ 服务端也重启（比"桌面端重启"更硬的情况）

循环只活在**内存**里。桌面端重启时服务端没重启，循环还在，所以 ④ 并没有验到最坏情况。
真把服务端也杀掉重开，内存里的循环一条不剩 —— 这时如果接口拿「内存里查不到」当「已恢复」，
用户从没点过继续的那条暂停就会凭空消失。

```
[PASS] 服务端重启后重新起来            —— db up
[PASS] 重启后内存里的循环确实已清空     —— live=0 running=0
[PASS] 服务端重启后仍未解除的暂停还在   —— HTTP 200 count=1
[PASS] 且没有被误报成「已恢复」         —— [false]
```

**这里修掉了一个真 bug**（`routes/loop.ts` 的 `resumed` 回填）：

```ts
// 旧：循环不在内存（重启 / TTL 到期）时 isLoopPaused 也是 false → 一律报「已恢复」
for (const rec of records) rec.resumed = rec.resumed || !isLoopPaused(rec.loopId);

// 新：只有「循环还在内存里且不是挂起态」才能断定已恢复；内存里查不到就维持库里的结论
for (const rec of records) {
  if (!rec.resumed && hasLoop(rec.loopId) && !isLoopPaused(rec.loopId)) rec.resumed = true;
}
```
（`toolLoop.ts` 新增 `hasLoop()` —— `isLoopPaused()` 无法区分「不存在」和「没挂起」，这是根因。）

**★ 这条断言不是空断言，已做反证**：把代码临时回退成旧逻辑重跑一轮，
整轮 70 条里**只有这一条变红**（`resumed: true`），其余 69 条仍 PASS
（`docs/acceptance/pause-resume/run6-revert.log`，退出码 1）→ 断言精确命中这个 bug。

## 5. 顺手修掉的遗留问题

1. **旧行为把暂停当终态**：`finish()` 里 `stopLoop('ended:paused')` 会销毁消息历史，
   「继续」只能另起一条空历史的循环 → 必然从头再来一遍。已改为挂起。
2. **`main.ts` 从不给 `/agent/loop/start` 传 `pageUrl`**：模型第一句听到的永远是
   「当前这张页：（还没打开，需要时用 open_url）」—— 配合上面那条，恢复后极可能 `open_url` 跳回旧页，
   **正好覆盖用户刚做的操作**（验收②明令禁止）。已在状态机层面用「挂起 + 强制重新读页 + 禁跳回」堵死。
3. **`finishLane` 会在暂停时把 lane 删掉**，loopId 随之丢失 → 「原地继续」名存实亡。已加 `lastLoopByWc`。
4. **`driver.ts` 的 `applyPaused()` 里还留着第 4 步演示循环 `beginRun()` 的调用**，恢复时会显示
   「正在跑」但其实没有任何一步被驱动。已删。
5. **两处注释与代码不符**：`main.ts` / `driver.ts` 写着「并发上限默认 1」，实际默认 20。已改。
6. **`GET /agent/loop/pauses` 的 `resumed` 回填把「循环不在内存」当成「已恢复」**：
   服务端重启 / 循环 TTL 到期后，用户没点过继续的暂停会被报成「已恢复」。已改（见 ⑦）。

## 7. 临时测试条 + 换装 + sha256 校验

### 7.1 为什么要有这个章节

阶段简报里明确写着「**正式的暂停/继续 UI 不在本阶段做（本阶段只用临时按钮）**」。
但 UI-1.6 回滚把右栏驾驶台（开始任务 / 暂停 / 继续 / 我来操作 / 复位）整块撤掉了，
源码里**没有任何**能让用户点一下就触发暂停/继续的入口——光标在桥接那层。
为了让你能亲手走通「暂停 → 自己操作 → 继续 → AI 重新感知」这条核心链，
**在 `App.tsx` 加了一条黄底虚框的「临时测试条」**：

- 挂在中栏 `<main className="middle">` 内部、`<BrowserPanel>` 正上方，
  只在**已经开过至少一张页**时渲染（DOM 里测试条和按钮都在位，截图见
  `docs/acceptance/pause-resume/installed-ui-annotated.png`）。
- 两个按钮直接走主进程已有的 per-target IPC：`workbench:task:pause` / `:resume`，
  点名当前这张页的 `wcId`，所以**暂停这一路不会碰到别的页**。
- 边上每秒轮询 `getTaskState(wcId)` 反射相位（idle / running / paused / done / failed），
  肉眼能立刻看到「暂停后是不是真停了」「继续后是不是真回到 running」。
