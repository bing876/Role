> 本报告只做**侦查与方案**，**未修改任何产品代码**。

## 结论速览

1. **问题 100% 复现**，且原因不是"AI 没听懂"，而是**这条路径从头到尾就没有接线**。
2. 「步数上限自动停」和「用户主动点暂停」是**两套不同状态**：前者服务端进 `waiting`，后者进 `paused`。
3. 服务端**其实已经为这个场景写好了完整的恢复能力**（`resumeLoop` 支持 `waiting` 态、步数归零、恢复前重新感知），
   主进程也已有 `resumeAgentLane` 这条完整驱动 —— **缺的只是"用户在对话里说『继续』"这一根线没接到上面**。
4. 诊断定性：**不是逻辑 bug，是"这个场景从未被开发 / 从未被测试覆盖"**。
   已验收的「暂停/继续」只覆盖了 `paused` 态，`waiting` + `step_budget` 这一支连存在性断言都没有。

## 第二步：这走的是哪套逻辑？和已验收的「暂停/继续」是同一套吗？

### 问题 1：项目里是否存在"最大执行步数"限制？在哪？

**存在**，三处：

| 位置 | 内容 |
|---|---|
| `apps/server/src/env.ts:30-55,135` | 配置项 `AGENT_LOOP_MAX_STEPS`，**默认 10**，只接受 8~12（越界夹取），注入成 `env.agentLoopMaxSteps` |
| `apps/server/src/toolLoop.ts:398,443-448` | 建循环时写入 `session.maxSteps`；并把"一轮最多走 N 步（超过就停下来问用户）"写进提示词 |
| **`apps/server/src/toolLoop.ts:976-984`** | **判定点**：`if (session.step >= session.maxSteps)` → `status='waiting'`，返回 `{kind:'ask', reason:'step_budget'}`，话术正是"要我接着做就点「继续」" |

`/health` 可直接读到现在的值（本轮实测 `loopMaxSteps=10`）。

### 问题 2：和用户主动暂停是同一套逻辑吗？

**不是同一套。** 它们只在服务端**最后一小段**共用一处代码（`resumeLoop`），前面的触发、状态、入口全都不同：

| | 用户主动点「暂停」 | 步数上限自动停（本次） |
|---|---|---|
| 触发方 | 用户点按钮 → IPC `workbench:task:pause` → `POST /agent/loop/pause` | **服务端自己判定**（`toolLoop.ts:976`） |
| 服务端状态 | `paused`（带 `pause` 记录、落 `task_pauses` 表） | **`waiting`**（无记录、不落表） |
| 回到桌面端 | `decision.kind === 'paused'` → 明确走暂停分支（`agent.ts:273`） | `kind === 'ask'`，`reason='step_budget'` → 只 emit 一句 ⚠️ 文本（`agent.ts:293`） |
| 渲染层是否置"等待答复" | 是 | **否**——`agentAwaitInfo` 只在 `reason === 'need_info'` 时置位（`App.tsx:1689`），`step_budget` 不在此列 |
| 「继续」的入口 | 点按钮 → `workbench:task:resume` → `resumeAgentLane`（读页 → 解挂 → 发车） | **没有任何入口** |

**关键发现（这部分决定了修复成本）**：服务端 `resumeLoop`（`toolLoop.ts:538-617`）**已经为这个场景做好了完整支持**：

- `const answering = s.status === 'waiting';` —— 明确接受 `waiting` 态；
- 恢复简报里写的是"【我刚才停下来问了你一个问题，现在继续 —— 先重新看一遍当前页面】"；
- 注释直接点名本场景（"场景 s20 实测"）：*任务跑到步数上限时……用户真点了「继续」，下一个 `advance()` 立刻又撞同一道上限、把同一句话再问一遍 —— 一步活都没干*，并已修掉：**`s.step = 0`（继续 = 新的一轮，步数从头计）**。

**即：能力已具备且已修过坑，缺的是"把用户这句话接到 resume 上"这一根线。**

### 问题 3：用户说「继续」这句话，系统是怎么识别和处理的？

**被当成了一句全新的、无关的普通聊天。** 判定在 `apps/desktop/src/App.tsx:1820-1961`，只有三条"发车"路径，「继续」一条都不命中：

| 路径 | 条件 | 「继续」是否命中 | 为什么 |
|---|---|---|---|
| `openUrl` | `detectOpenUrl(value)` | ❌ | 句子里没有网址 |
| `goNow` | `pendingConfirm && pendingGoal`，其中 `pendingConfirm` 要求**最后一条助手消息**匹配 `CONFIRM_ASK_RE`（`intent.ts:136`）：`(确认后我开始操作｜需要我用工作台浏览器｜要我帮你(打开/操作/查/看)｜要我打开｜要不要我用浏览器)` | ❌ | 步数上限那句"要我接着做就点「继续」"**不匹配这个正则**（它本来是给"要不要我用浏览器帮你打开"这类**开页确认**用的） |
| `browseGoal` | `detectBrowseIntent(value)` | ❌ | 「继续」没有任何动作动词 |

三条全空 ⇒ `drive` 保持 `null` ⇒ `/chat/stream` **不带 `taskMode`**（`App.tsx:1961`）
⇒ 服务端走 `chat.ts:336` 之后的**普通聊天分支**。

而按设计，**普通聊天这一支根本不给浏览器工具**（`chat.ts:29-34`、第 26 步：闲聊轮唯一的工具是 `web_search`）——
它在**结构上就不可能操作浏览器**。这就是"嘴上回应了但没有真实动作"的根因：不是模型偷懒，是**那条路上没有手**。

同时，`agentAwaitInfo` 为 false（`App.tsx:2077` 那个"把答复转给驾驶员"的通道）也不触发 ⇒ 主进程完全不知道用户说了这句话。

## 第三步：根因诊断与修复方案（**待确认后再动手**）

### 根因定位

断在**渲染层"这句话要不要接回驾驶"的判定**这一层。三层各自的实情：

| 层 | 状态 |
|---|---|
| 服务端（`toolLoop.ts` 的 `resumeLoop`） | ✅ **已支持**（waiting 态 + 步数归零 + 重新感知），不用改逻辑 |
| 主进程（`main.ts` 的 `resumeAgentLane`） | ✅ **已完整**（读页 → 解挂 → 原地接上），但它只被 IPC `workbench:task:resume`（按钮）触发 |
| **渲染层（`App.tsx` 的发送判定）** | ❌ **断点在这里**：没有"当前有任务因步数上限停住"这一支 |

定性：**不是代码写错了，是这个场景从未接线、也从未被测试覆盖**。
已验收的「暂停/继续」（70+ 断言）只覆盖了 `status='paused'`；`waiting` + `step_budget` 这一支的存在性都没有断言。

### 推荐方案 A（最小改动、复用已验收链路）★推荐

把"步数上限停住"也置成等待态，让「继续」这句话走**已有的 `resumeAgentLane`**，从而自动继承
"恢复前先读当前页""不盲目跳回旧地址""步数归零"这些已验收的设计。

| # | 文件 | 改动 | 是否核心驾驶逻辑 |
|---|---|---|---|
| 1 | `apps/server/src/toolLoop.ts:981` | 只改**话术**：把"点「继续」"改成"说一声「继续」，或点「继续」按钮"（逻辑不动） | 否 |
| 2 | `apps/desktop/electron/agent.ts:293` | `ask` 分支里对 `reason === 'step_budget'` 加一个分支：除 emit 提问外，额外 `hooks.pauseLoop('system:step_budget')`（保住历史、让服务端可恢复），并在 lane 上记"这一路是因步数上限停住的" | **是（需谨慎，见风险控制）** |

| 4 | `apps/desktop/src/App.tsx:1820-1961` | 发送判定里新增一支：当前处于"因步数上限等待"且这句命中**已有的** `CONTINUE_STRONG_RE`（intent.ts:137，**不要新造正则**）→ **不发给聊天**，直接 `window.workbench.resumeTask(wcId)`（与点按钮同一条路）。用户说的是别的内容（如"先点第一个结果"）则照旧当新指令/答复处理 | 否 |

**不动**：`driver.ts`、循环体的推进逻辑、`/agent/loop/next|resume` 的服务端实现。

### 备选方案 B：放宽 / 取消步数上限

不推荐。上限存在的意义是"到顶就停下来问用户，不空转烧 token"（`toolLoop.ts:24` 的设计注释），直接放宽等于把这个设计意图改掉。

# 实施结果（用户拍板后已实施并验证）

## 用户追加决策：**不要限制步数，让它直接跑完整个环节**

于是做了两件事：**主线取消步数打断** + **保留"说『继续』能接回"作为兜底**。

## 改了什么（4 个文件，主进程 / driver.ts / agent.ts 一行未动）

### A. 主线：默认不限步数

| 文件 | 改动 |
|---|---|
| `apps/server/src/env.ts` | `AGENT_LOOP_MAX_STEPS_DEFAULT` **10 → 0（不限）**；新增 `AGENT_LOOP_STEPS_HARD_CAP = 50`（硬兜底，2026-09-20 用户拍板从 200 调到 50）；新增 `effectiveStepLimit()` |
| `apps/server/src/toolLoop.ts` 判定处 | `session.step >= session.maxSteps` → `session.step >= effectiveStepLimit(session.maxSteps)` |
| `apps/server/src/toolLoop.ts` 首轮提示词 | 不限时改为「步数不设限：一路做到任务完成为止，中途不要因为走了很多步就停下来问用户」 |
| `apps/server/src/toolLoop.ts` 系统提示词 | 删掉「一轮最多走若干步」——**留着这句模型就会自己提前收尾** |
| `apps/server/src/toolLoop.ts` 上限话术 | 改为「已经走了 N 步还没做完（这是防空转的兜底上限）…说『继续』或点『继续』按钮都行」 |

**为什么留硬兜底、为什么是 50**：模型一旦陷入 `read_page → read_page` 这类**成功的**死循环，
本地那两张安全网（连败 2 次 / 连点 3 次无变化）**拦不住**（每步都 ok、也没"没变化"），
那就是一路烧 token。

数值由用户拍板 **200 → 50**：正常任务实测 10~30 步就完成（验收跑过 14 步、30 步），
50 步留了足够余量；而 200 步容错空间太大，真死循环时要白白多烧 150 次模型调用才停。
想放宽就配 `AGENT_LOOP_MAX_STEPS`，或直接调 `AGENT_LOOP_STEPS_HARD_CAP` 这个常量。

### B. 兜底：步数真的被打断时，说「继续」能接回（原 bug 的修复，保留）

最关键的一处 —— `apps/desktop/src/App.tsx:1911`：

```tsx

  ...

  pushChatLineFor(myAgent, '好，我接着刚才那一步往下做 —— 先重新看一眼你现在这个页面。');
  return;                                     // ★ 不发给聊天
}
```

配套三处：新增 `awaitResume/awaitResumeAgent/awaitResumeWc` 三个状态（718-720 行）、
`ask` 分支里 `reason==='step_budget'` 时置等待态（1719 行）、`done` 时清掉（1732 行）。

## 附注：侦查过程中的两个附带发现（不属于本次问题，仅记录）

1. **「在 X 上/里」会被当成开站指令**：指令里写"在商城里搜索…"，桌面端会去查内置站点表，表里没有"商城"
   ⇒ 直接回"我认不出「商城」是哪个网站"、**不发车**。写指令时要用绝对网址。
   （第一版探针就栽在这里，不是本次 bug，但值得知道。）
2. **验收后端与真实库共用**：闲置记忆扫描（`memories.ts:350-395`）扫的是全库会话，
   所以验收环境的假模型日志里会出现真实会话的抽取请求。已在探针里归类为 `memory` 噪声排除，
   不是数据泄漏（写入的 owner 仍是会话自己的 user_id）。
