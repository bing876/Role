# 概览：闲置浏览器性能诊断（只诊断，零产品代码改动）

## 任务
用户报「只开 1 个浏览器、不做任何操作（闲置）时，应用整体也卡」。
要求**先只做诊断**：拿真实数据定位是 CPU / 内存 / GPU 哪个环节、哪一块代码，再谈修法。

## 结论
**十个方向全部测过：CPU / 内存 / GPU / 帧时间 / 5 分钟闲置 / 多实例与滚动 /
系统级压力 / 长聊天记录 / 任务后闲置态 / 内存悬崖（一路加到硬上限 20 张页）。
全部正常，或已被实测排除 —— 在真机上没能复现"1 个闲置浏览器拖卡整机"。**

> **下一步（已备好工具）**：在**出问题的那台机器**上、让应用处于觉得卡的状态时跑
> `python scripts/verify/collect-lag-report.py`，把生成的 txt 发回。
> 它只读、自包含（只用 stdlib + Windows 自带 typeperf/tasklist）、不需要登录、不起环境。

| | 0 张页 | 1 张页·全屏·闲置 | 1 张页·后台·闲置 |
|---|---|---|---|
| 整机 CPU（12 核口径） | 0.097% | **0.230%**（≈0.028 个核） | 0.063% |
| 应用内存 | 570 MB | **681 MB（+111 MB）** | 678 MB |
| GPU | 硬件加速正常（ANGLE / NVIDIA GTX 1060 3GB / D3D11），GPU 进程 CPU 0.010% | | |
| **帧率 / 掉帧 / 长任务** | 60.1fps / 0 / 0 | **60.0fps / 0 / 0** | 60.0fps / 0 / 0 |
| **打字延迟 p95** | 34.1 ms | **33.6 ms** | 33.4 ms |

无内存泄漏（斜率≈0）、无周期尖峰（扫 2~40 秒无 1.2s 峰）、
主窗口渲染进程 30 秒 Profile **99.99% idle**、主线程 10 秒内只忙 **2.1~2.4%**。

> ★ **"卡顿"的正确指标是帧时间，不是 CPU%** —— CPU 0.2% 也可能掉帧。
> 实测：锁 60fps、**零掉帧**（>33ms 的帧在三个阶段都是 0）、**零长任务**、
> **开页前后打字延迟几乎不变（开页甚至没让它变差）**。
> ⚠️ 33ms 是**测量下限**（脚本"写入→等 2 帧→记录" = 2×16.67ms）⇒ 真实提交 < 1 帧。

### 内存悬崖探测（§17）—— 一路加到**硬上限 20 张**也没找到

§14 之所以没测出"内存压力→卡顿"，是因为我**从没把内存压到那么狠**。于是把
`maxBrowserInstances` 上限设成 20、逐档加页（带**安全阀**：可用内存 < 900 MB 立刻中止）：

| 张数 | 系统可用MB | 应用MB | fps | 帧p95 | **>33ms** |
|---|---|---|---|---|---|
| 4 | 1907 | 1027 | 60 | 16.8 | **0** |
| 8 | 1772 | 1453 | 60 | 16.8 | **0** |
| 12 | 1869 | 1859 | 60 | 16.8 | **0** |
| 16 | 1815 | 2282 | 60 | 16.8 | **0** |
| **20** | **1654** | **2694** | **60** | **16.8** | **0** |

- 应用内存严格线性 **+104 MB/张**（1027 → **2694 MB**）
- **系统可用内存只降 253 MB**（应用涨 1.67 GB 而系统可用几乎没动）
  ⇒ 渲染进程内存**大部分被页面文件/可回收缓存吸收**，**没有"耗尽→疯狂换页"的拐点**
- **一路到硬上限 20 张 / 2.7 GB，帧率始终 60fps、零掉帧、零长任务**
- ⇒ **把内存用到产品允许的最大值，仍然没有复现卡顿**（安全阀未触发）

### "任务跑完之后"的闲置态（§16）—— 真实用户真正所处的状态

前面所有测量里那张页都是我用 `openBrowser()` **手动**开的 —— **从没跑过任务**。
真实用户的页是 AI 在任务里开的，他看到的"闲置"是**任务刚跑完**的状态。
若 `drivingIds` 没刷新，那张页会被 `decideSleep` 第①条**永久跳过（永不休眠）**。
代码注释说处理了 —— **但本轮的规矩就是"别信注释，去量"**。

| 指标 | A 从未跑任务 | B 任务跑完后 |
|---|---|---|
| fps | 60 | 60 |
| 帧 p50 / p95 / max | 16.7 / 16.8 / 18.2 | **16.7 / 16.8 / 17.4** |
| **>33ms 掉帧 / 长任务** | 0 / 0 | **0 / 0** |
| **`agentLanes()`** | `[]` | **`[]`** ✅ |
| 整机 CPU | 0.05% | 0.50% |

⇒ **收尾把这一路摘干净了**（`refreshDriving` 的 1200ms 补刷确实起作用），
"任务后仍被当成 driving、永不休眠"**不成立**；帧时间与"从未跑任务"完全一致。
⚠️ CPU 有 0.05%→0.50% 的小差异（≈0.06 个核），已如实记录，**不影响帧时间**。

### 长聊天记录 200 条（§15）—— **最后一个假设，也被否掉了**

**读代码推出的怀疑**（不是猜）：`App.tsx` 的 1.2s 轮询每次 `setDriveBar(新对象)` ⇒ 整棵 App 重渲染；
消息是 `{messages.map(...)}` **平铺渲染**、全文件无 `React.memo`/`useMemo`/虚拟列表；
服务端 `/chat/history` 一次返回**最新 200 条** ⇒ 每 1.2 秒重渲染 200 条。
而**前面所有测量都在空库（0 条消息）里跑** —— 这条路径压根没被走到。

| 指标 | A 空会话 | B **200 条** |
|---|---|---|
| `.msg` / 全部 DOM 节点 | 0 / 59 | **200 / 458** |
| 帧 p50 / p95 / p99 | 16.7 / 16.8 / 16.9 | **16.7 / 16.8 / 16.9** |
| **>33ms 掉帧 / 长任务** | 0 / 0 | **0 / 0** |
| 打字延迟 p50 / p95 | 33.3 / 33.6 | **33.3 / 33.5** |

⇒ **DOM 涨 8×，帧时间与打字延迟完全不变** ⇒ "聊天记录长 → 闲置时卡"**不成立**。

> 附带产出可复用工具 `scripts/verify/seed-messages.mjs`（用服务端自己的 `makeCipher`
> 加密后写入，一键灌任意条数消息），以后做"长历史"类测试不用手工造数据。

**A = 应用完全没开**（基线）；**B = 应用 + 1 张闲置页**。

### 安装版实测（§13）—— 补掉我自己的一个测量偏差

前面所有测量都跑在 **dev 模式**，而 dev 会**自动打开 DevTools**
（`main.ts`: `if (isDev) openDevTools({ mode: 'detach' })`）—— 探针日志里一直有个
`Developer Tools - …` 窗口。**DevTools 自己就吃 CPU/内存**，所以那些数字是**偏悲观的上界**，
而且和你实际在用的**安装版**不是同一份东西。

| 指标 | **安装版** | dev |
|---|---|---|
| 0 / 1 张页 · 帧 p95 / >33ms | 16.8ms / **0** | 16.8~16.9ms / 0 |
| 打字延迟 p95 | **33.5ms** | 33.6~34.1ms |
| 1 张页 · 内存 | **494 MB** | 681 MB（**少 187 MB** = DevTools + vite dev 开销） |
| 0 张页 · 整机 CPU / 内存 | **0.03% / 386 MB** | — |

- 确认安装版里**没有 DevTools**（CDP 目标只有 1 个 page，可见窗口无 DevTools）✔
- ⚠️ CPU 那一行**不可直接比较**（安装版测的是"页内带动画"，dev 的 0.230% 是"假站点无动画"），
  报告里已标注，**没有拿它下结论**

## 两个需要你知道的发现

**1. 后台降频只做了一半（★ 这一条我改正过）**
- `opacity:0` 时 rAF 确实从 60 帧/秒降到 **1 帧/秒**（Chromium 出帧节流生效）
- 但 **`setInterval` 完全没被钳**（仍 62.5 次/秒）—— 因为 guest 自报 `visibilityState=visible`，
  「后台标签定时器钳制」不触发。⇒ 页面里的轮播/实时行情/倒计时在后台**照跑**
- 我们**自己那套节流开关实测完全空转**（真调 `browserThrottle(wcId, true)`：后台 1.0/s、
  全屏 60.0/s，返回 `{ok:true}` 但帧率毫无变化）
- ⚠️ 上一版报告写的"后台完全不降频"是**错的**：起因是应用窗口被别的窗口盖住，
  Chromium 遮挡检测把 rAF 压到 1/s。提前台并回读 `document.hidden=False` 后两轮结论一致

**2. 本机存在足以单独解释"卡顿"的环境因素**
15.8 GB 内存只剩 **2.0 GB 可用**（87% 占用），370 个进程合计 20.8 GB；
我们的应用 685 MB 只排第 8（前面是 WorkBuddyAI 3.4GB、chrome 2.9GB、WorkBuddy 2.1GB…）。

## 方法论教训（已写进记忆）
1. **测 Electron 渲染/性能前必须先读 `document.hidden` 确认窗口真的可见** ——
   被遮挡时 rAF 会从 60/s 掉到 1/s，测到的是遮挡而不是代码行为；
   **同一状态至少测 2~3 轮**，不一致就说明有未控变量。这条直接救回了一个错误结论。
2. **"卡顿"要看帧时间，不是 CPU%**；量"体感延迟"时**要减掉自己方法里的等待帧数**
   （否则会把"测量下限"误读成"性能差"）。
3. **性能 soak 必须带"去掉被测负载"的对照组** —— 否则会把"测试自己造的负载"
   当成产品缺陷（这次差点把 +2.49 MB/分 报成泄漏，对照组证明是 −2.53 MB/分）。
4. **起 Electron 前必须严格确认 DB 就绪**（连续 2 次 `/health` `db=up`），
   否则 Electron 的 pg-supervisor 会自己再拉一个 PG，两个 postmaster 撞死。
