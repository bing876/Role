## 关键教训

1. **截图工具的默认坑**：CDP `Page.captureScreenshot` 在本机窗口被遮挡 / 不前台
   时**永久挂住**（实测 40~60s 超时、无任何返回）。稳定做法是
   「`SetWindowPos(TOPMOST)` → 1.8s → 从**桌面 DC**（`WindowDC(0)`）BitBlt
   窗口矩形」——拿到的是屏幕上真实显示的像素，**不需要 CDP**。
2. **像素扫描比肉眼准**：要找测试条这种自定义样式组件的位置，
   先在截图里扫描其特征色（这里是 `#fff8e1`）的包围盒，
   再用「DOM 里的 rect → 截图里的 rect」的偏移量换算子元素（按钮）。
   比「用 `(outer-inner)/2` 估算偏移」精确。
3. **asar 换装的功能指纹自检**至关重要：单纯做整体 sha256 比对只能证明
   「刚放进去的就是这个包」，证明不了里面的功能代码真的存在。必加 token
   自检（如 `lastLoopByWc` / `driveBar` / `pauseTask`）—— 自检不过就回退。
4. **JSX className 在打包后是字符串字面量**：`driveBar` 这种纯字符串类名
   在 minified 产物里依然是 `'driveBar'`，所以「grep `driveBar` 是否在
   dist/assets/*.js 里」可以可靠地自检。本轮吃了这条的甜头。
5. **本机 Electron 必须 `--no-sandbox`**（之前踩过）：`GPU process isn't
   usable. Goodbye.` 退出码 0x80000003。截图脚本里给安装版自己带上了。

### 跑场景才暴露出的三个真 bug（都已修 + 已反证）

1. **`apps/server/src/pageDelta.ts`**：`urlChanged || titleChanged ? 'moved'` →
   只改标题被判成"换了一张页面"，AI 会说"你已经不在原来那个页面了"（用户明明没换网址）。
   改成 `urlChanged ? 'moved' : (titleChanged||elementChanged) ? 'edited' : 'unchanged'`。
2. **`apps/desktop/electron/agent.ts`**：`finish()` 对 `ask_user` 也 `stopLoop` →
   AI 停下问用户时服务端循环直接进终态，导致「暂停挂不起 / 继续只能 stopped」，
   验证码场景整条链断掉。加 `KEEP_ALIVE` 白名单（done/aborted/paused/ask_user/say/stuck）。
3. **`apps/desktop/electron/main.ts`**：连点「暂停/继续」时上一路还在等模型返回，
   新车对同一 loopId 再发 next → 409 `LoopBusyError` → 被当致命错误 → 任务永久 failed。
   加 `liveLoops: Map<wcId, Lane>`（车还在路上就只解门不发车）+ `resumingWc` 去重。

反证：把三处改回旧代码重编译 → 定点用例②回退成 moved(exit=1)、s2 回退 delta=moved、
s5 第 2 轮起全 failed，三条故障全部复现。

### 修完之后（第二轮）的实测结果

## ★ 第 4 个真 bug（边界场景 s8 跑出来的，最严重）

## ★ 第 8 个真 bug（连跑 13 场才抓到）：暂停基线过时 → 冤枉用户

- 症状：s4（暂停后**什么都没做**、晾 150 秒）被判 `delta=edited`，
  AI 说「应该是你自己操作过」—— 用户根本没动。**唯一的症状就是"冤枉用户"**，
  所以只有"我什么都不做"这一场能抓到。
- 根因：`pauseLoop` 用 `s.lastSnapshot`（循环最后一次读到的页面）当基线；
  AI 最后一步常已改了页面却还没重读 → 基线旧一拍 → AI 自己造成的变化算到用户头上。
- 修：桌面端 `/agent/loop/pause` 前先 `read_page`，把真实页面放 `page` 字段带上；
  服务端 `pauseLoop(loopId,{by,page})` 用 `opts.page ?? s.lastSnapshot`。

## ★★ 最严重的一个坑：Electron 里 `process.execPath` 是 electron.exe，不是 node

第一版用 `spawn(process.execPath, [dist/index.js])` 起服务端 ——
**在 Electron 进程里 `process.execPath` 指向 electron.exe 自己**，
于是"起服务端"实际是"又起了一个 Electron 实例"，那个实例在本机
GPU 沙箱必崩（`FATAL:gpu_data_process... Goodbye`，退出码 2147483651），

**正确做法**：Electron 里用 `electron.exe + ELECTRON_RUN_AS_NODE=1`
（同一个可执行文件以纯 node 模式跑，不初始化 Chromium），
这样不依赖用户机器装没装 node。见 `findNodeBinary()`。

**为什么单测没抓到这个（教训）**：
单测是在**纯 Node** 下 require 模块的，那时 `process.execPath` 确实是 node.exe ——
**环境不同、行为不同**。凡是依赖 `process.execPath` / `process.versions.electron`
这类「运行宿主相关」的值，**单测必须补一条"在 Electron 里跑"的真机验证**。

## 空闲自动休眠（取消活页）+ 换装 idle-sleep-r4

### 做了什么

用户拍板方向：「取消活页，不需要活页这个选项；只在静默或长时间不用时自己判断，
改成后台存活但不占内存的优化，就跟谷歌浏览器一样」。

落地成**三层状态机**（纯函数 `sleepPolicy.ts`，判定与 UI 解耦）：

```
清醒 ──闲置 5 分钟──▶ 浅休眠（省 CPU） ──累计 30 分钟──▶ 深休眠（省内存）
```

- **浅休眠** = `setBackgroundThrottling(true)`，页不卸载、唤醒瞬时；
- **深休眠** = 不渲染 `<webview>`（React 卸载 → guest 渲染进程真的没了），
  显示不透明占位卡 + 「唤醒」按钮；
- **红线**：`drivingIds` 里的页**永不休眠**（节流会让 CDP 查找/点击失灵 —— 那正是前几轮在修的 bug）。
  这条在**三层**都守：判定层 `continue`、渲染层 `!ws.drivingIds.includes()`、
  主进程 `throttle && isDriving → 拒绝`。
- 手工唤醒给 2 分钟宽限（`WAKE_GRACE_MS`），否则刚醒又被判睡、图标会闪；
  系统唤醒（派任务前）**不**记宽限 —— 干活需要它醒，干完照常睡回去。

## ★★ 本机 PG 的两个硬事实（这轮踩实）

### 1. `postmaster.pid` 残留会让 PG **拒绝启动**，而且不报错

`data/postmaster.pid` 里留着旧 PID（9348，进程早没了）。

### 2. ★★ agent 工具调用结束会**回收全部派生进程** —— 我无法替用户常驻 PG

→ 结论：**PG 与开发服务端必须由用户自己启动**，我这边只能"起一次、验一次"，

（用户启动的进程树不属于 agent 沙箱，不会被回收）。

判重口径（本机踩了两个坑）：
- ❌ 窗口标题判重：本机 console 窗口标题读出来是**乱码**，
  `tasklist /FI "WINDOWTITLE eq pgwatchdog"` 恒为"没有匹配"；
- ❌ 光看锁文件：重启后锁还在、看门狗没了 → 误判"已在运行"；
- ✅ 「锁文件 + **PG 是否活着**」双判：PG 活+有锁 → 跳过；PG 死+有锁 → 清锁重启看门狗。

★ 另一个坑：`subprocess.run(capture_output=True)` 调 launcher 会**卡死**
（`start` 起的新窗口继承了管道，父进程一直等它关闭 → 30s TimeoutExpired）。
→ 必须 `stdout=DEVNULL, stderr=DEVNULL, stdin=DEVNULL`。

### ★★ 本轮新学到的（都已写进 MEMORY.md）
1. **`/health` 的 `db:"up"` ≠ 建表完成。** db 字段只跑 `SELECT 1`，
   它在 PG 崩溃恢复期**就会先变 up**（实测 db 变 up 是 +38.3s，建表成功是 +40.1s，
   第 10 次尝试）。第一版 e2e 拿 `db=up` 当"库好了"就断言建表日志 → **假红**
   （代码对、用例错）。**判"库真的可用"必须看「数据库表就绪」这条日志。**
2. **测试里的「跳过」等于没测。** 第一版单元测试直接探 5432，本机 5432 恰好开着 →
   「找不到便携包 / 逃生开关 / 并发去重」**三条最重要的分支全被跳过**（18 条只真跑 14 条）。
   改法：给端口加 `WORKBENCH_PG_PORT` 覆盖，用**自己控制的临时端口**驱动每条分支
   （默认关着、需要时再开），彻底摆脱"本机 5432 开不开"这种偶然。
   ★ 为此 `getPgPort()` 必须**每次调用重读**环境变量，不能固化成模块级常量 ——
   否则同进程内换不了端口，而 `pgInflight` 又必须同进程才能验并发去重。
3. **反证要挑"能区分对错"的注入点**：本轮 5 个注入分别命中 1 / 3 / 3 / 13 / 2 条断言，
   说明断言不是摆设。注入 `clearStalePid` 那两条时特意做了**一对反向用例**
   （陈旧 pid 要清 / 活着的 pid 不许动），单点注入两边各红一边。
4. **环境相关的观察不能当判据。** 「关应用后 PG 还在不在」同脚本上一轮 PASS、这一轮 FAIL。
   查下来是 agent 沙箱杀进程时会**连带回收整棵进程树**（含 detached 子进程），
   而代码里根本没有杀 PG 的路径。改成**确定性的代码级断言**（⑧a–⑧d），运行期观察只记录。
5. **`fs.readFileSync` 读 `.env` 的 pepper 要按服务端真实优先级**：
   真实环境变量 → `PHONE_PEPPER` → `DATA_KEY`。第一版硬编码旧回落值，
   pepper 轮换后反推验证码直接落空 → 假红。
