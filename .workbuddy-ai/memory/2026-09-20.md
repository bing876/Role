### ★★ git 事故复盘：我自己用了裸 `git reset`，把 34 条历史搞成"根提交"

**经过**：为了让"只提交我这轮的文件"，我用了 `git reset -q` 清暂存区 ——
**而 MEMORY 里明明白白写着「不要裸 `git reset`（会重写层级 ref）」**。
后果链：
1. 裸 `git reset` 把 `arena/01a09b16-work123` 这个**层级 ref** 搞掉了 →
   下一次 `git commit` 变成 **`commit (initial)`（根提交，parent = 0000…）**，
   `git rev-list --count HEAD` 从 **34 变成 1**。
2. 我把分支 `git update-ref` 指回 `d7ea782`，但**索引还停在那个根提交的树**（只有 8 个文件）→
   再 commit 时，索引 vs HEAD 的差异被记成 **491 个文件被删除**（工作区文件其实都在）。
3. 最后用 **`git read-tree HEAD`** 把索引重建为 HEAD 的树，再只 `git add` 我那 8 个文件 → 提交正确。

**正确的做法（以后照这个来）**：
- **清暂存区**：`git restore --staged <path>`（或 `git rm --cached -r <path>`），**永远不要裸 `git reset`**。
- **索引乱了**：`git read-tree HEAD`（plumbing，只动索引，不碰 refs）。
- **历史"变短了"**：先看 `.git/logs/HEAD` 的 reflog 拿到上一个 sha，再
  `git update-ref refs/heads/arena/<name> <sha>` **并且**手动 `mkdir -p .git/refs/heads/arena`
  + `printf` 写回 ref 文件（`/` 分支名的老坑，见 MEMORY 第四节）。
- **每次 commit 后无条件** `git log -1 --oneline` + `git rev-list --count HEAD` 复查。
- **提交前**先 `git diff --cached --name-only` 看一眼"到底要提交什么" ——
  这次的 491 文件删除就是没看这一步。

★ 另一条重要发现：**本仓库有另一个 agent 会话在并发改动**（未提交的 `driver.ts` +217、

`drive-shape-probe.mjs` / `ip-rate-probe.mjs` 等），而且**并发跑 git 操作**。

### ★ 环境：PG 崩溃循环的真根因（前台跑 postgres 才看到）
```
LOG:  background worker "logical replication launcher" (PID x) exited with exit code 143
LOG:  terminating any other active server processes
LOG:  all server processes terminated; reinitializing
```
**143 = SIGTERM** → postgres 的**后台 worker 被外部杀掉**，
而 PG 对"worker 死了"的反应是**终止全部进程 + 重新初始化**（走一遍恢复，本机 ~40 秒）。
→ 现象：端口先通、查询报 `57P03`，能查几十秒又被杀一轮。**不是数据损坏、不是配置问题。**
**排查手段**：`postgres.exe` **前台**跑一次就能看到日志（用 `start` 起的话输出进那个窗口，日志文件里什么都没有）。

### 环境：进程活不过工具调用边界（再次确认，含新细节）
- 派生进程（含 `start ""` 起的 postgres）**在工具调用结束时被回收** →
  **跨调用的"上一步起环境、下一步跑测试"必然失败**。一次调用里跑完全程才行。
- `subprocess.run(capture_output=True)` 起 `start "" postgres.exe` **会永久挂住**：
  被拉起的 postgres **继承 stdout 管道并一直持有**，cmd 退出后管道等不到 EOF。
  → **必须用 `stdout=DEVNULL`**。
- **PG 崩溃恢复期端口就已经在监听** → `if not port_busy(5432): 启动` 会误判并**再起一个实例**，
  两个 postmaster 抢同一 data 目录 → 互相撞死 → 数据目录写脏 → 死循环。
  → **正确做法：先 `taskkill /F /IM postgres.exe` 全杀干净，再起唯一一个**。
- **不能删正在运行的 postmaster.pid**（会报 `could not open file "./postmaster.pid"`）。

### 本机杂项（新增）
- **`process.exit()` 会丢掉还没落盘的 stdout**（Windows 管道异步）→
  现象"脚本跑完了但日志只剩开头几行"。**用 `process.exitCode = n` 代替。**
- **`tasklist` 输出是 GBK** → `subprocess.run(capture_output=True, text=True)` 不指定
  `encoding/errors` 会在内部 reader 线程抛 `UnicodeDecodeError`。
- **`urlopen` 碰到 URL 里的非 ASCII 直接抛异常** → 被兜底成 status=0，
  看起来像"服务端没回 404"，其实请求根本没发出去。测试里的 id 用纯 ASCII。
- **写测试的 `chk()` 必须 `return cond`** —— 漏了它，`if (!chk(...))` 永远为真，
  脚本在第一条断言后就静默退出（本轮踩了一次）。
- 断言 `dist-electron/main.js` 里的处理器时，**要锚在 `ipcMain.handle('通道名'` 上**，
  不能用裸通道名 `indexOf` —— tsc 保留注释，注释里也会提到同一通道名，会命中注释导致集体假失败。

### 怀疑 1 验证结论：**证实为真**（未修，待拍板）
`partition` 由渲染层在 `<webview>` 上直接指定，主进程**没有 `will-attach-webview`**、
只**读**分区名不校验写方向；`session.fromPartition(name)` 无任何鉴权，分区名可猜
（`persist:workbench-browser-project-<自增 projectId>`）。
→ 渲染层指定别的项目分区 = 拿到那个项目的登录态。
**性质**：跨项目（同一用户），需渲染层先被攻破；**放大**既有入侵收益，不是全新入侵类别。

2. 即使传 true，`setBackgroundThrottling(true)` 也救不了 —— guest 自报 `visible`。
   因为"隐藏"是靠 **`opacity:0`**（`.browserLayer--bg` / `.browserPanel__view--off`），
   **Chromium 仍认为它可见**。这是"绝不能 display:none / 绝不能 0 尺寸"那条红线的代价。

### 工具教训（都踩过）
1. ★★ **`contextBridge` 暴露的对象属性是只读的** ⇒ `window.workbench.getTaskState = wrapper`
   **静默失败**（非严格模式不报错），计数器永远 0 —— 差点被它骗成"这个轮询根本没跑"。
   判据改成读「临时测试条」DOM（`当前页：空闲 · wcId 3` ⇒ 轮询确实拿到了数据）。
2. ★★ **`percentCPUUsage` 是"距上次调用之间的平均"** ⇒ 想看 1.2 秒级尖峰，
   采样间隔必须 ≤1 秒（5 秒采样会把尖峰平均掉）。改 `resourceSampleMs=1000` 即可（合法区间 1000~60000）。
3. ★★ **`typeperf` 一次查全部 866 条 GPU 计数器会返回垃圾值**（实测 7.4e19%）⇒
   只查自己那几个 pid；且 CSV 是「表头行(以 `(PDH-CSV` 开头) + 时间戳数据行」，
   不能按 `startswith('\\GPU Engine(')` 找数据行。
4. ★ **判 GPU 加速状态用渲染层自报的 WebGL `UNMASKED_RENDERER`**（一锤定音）；
   `SystemInfo.getInfo` 的 `featureStatus` 会与"GPU 进程崩溃日志"互相矛盾，不可单用。
5. `app.getAppMetrics()` **拿不到真正的 GPU 利用率**（只有每进程 CPU/内存）。
6. ★ **按 pid 归因，别按 (type,name) 分组** —— 两个 `Tab` 进程 name 都是空 ⇒ 会被合并成一条。

### ★ 新坑：PG 启动前"清陈旧 pid"会被 safe-delete 拦下 ⇒ 整轮验证直接失败
症状（跑候选降频实验时撞上）：
```
[safe-delete][SAFE_DELETE_FAIL_CLOSED] {"target": "...\\pg2\\data\\postmaster.pid", "reason": "trash-failed", ...}
  [pg] 清 pid 失败： ...   ★ 数据库起不来
```
根因：那一刻 PG **正在周期性重启**（端口还没监听）⇒ `ensure_pg()` 判定 pid 陈旧 ⇒ 去 trash，
被安全删除闸拦下（FAIL_CLOSED）⇒ 直接判失败。
**但 PG 其实活得好好的**（pid 文件里的 pid 与 `tasklist` 里的一致、5432 稍后就在听）。

**规矩**：遇到"清 pid 失败"**先独立确认 PG 到底在不在跑**（比 `postmaster.pid` 第一行与
`tasklist /FI "IMAGENAME eq postgres.exe"` 的 pid，并看 5432 是否监听），
**别信 `ensure_pg()` 那一次判定** —— 它会把"PG 正在重启"误判成"pid 陈旧"。
端口在听就直接重跑，不要动 pid 文件。

### ★★★ 方法论级教训：**窗口被遮挡会改掉渲染性能结论**（差点让我误判）
同一条件（内嵌页后台 `opacity:0`）两次测出**相反**结果：
- `browser-idle-throttle-probe.py`：后台 rAF **60.0/s**（"没降频"）
- `browser-idle-throttle-options-probe.py`：后台 rAF **1.0/s**（"降了"）

重复性实验（3 轮 × 全屏/后台/后台提前台）把控制变量揪出来了：
**guest 自己的 `document.hidden` 与 rAF 一一对应**（`False`→60/s，`True`→1/s）。
而 `document.hidden` 受 **Chromium 的遮挡检测（occlusion）**支配 ——
**我的宿主窗口（终端 / WorkBuddy）盖住应用窗口时，整个应用被标成 hidden，rAF 掉到 1/s**。
那一轮里 `主窗口 hidden=True` 从头到尾都是 True，就是遮挡的铁证。

**规矩（以后所有 Electron 渲染/性能实验都必须做）**：
1. 测之前先读 `document.hidden`（主窗口**和** guest 各读一次）；
   **`hidden=True` 时测出来的 rAF/帧率一律不可用** —— 那是遮挡造成的，不是代码行为。
2. 需要窗口真的可见时，用 Win32 把窗口提到前台（`ShowWindow(SW_RESTORE)` +
   `SetWindowPos(HWND_TOP, SWP_NOMOVE|SWP_NOSIZE|SWP_SHOWWINDOW)` + `SetForegroundWindow`），
   并**回读 `document.hidden` 确认**（提前台可能失败，不能假定成功）。
3. ★ 单次测量结论不可信：**同一状态至少测 2~3 轮**，不一致就说明有未控变量，必须先找出来。
   这条这次直接救了一个错误结论（我一度要写进报告说"后台完全不降频"）。

探针：`browser-idle-raf-repeat-probe.py`（重复性 + 提前台控制变量）、
`browser-idle-window-occlusion-probe.py`（决定性判别 A/B 假设）。

### ★★ 新坑：起探针环境时**没等 PG 真就绪就启动 Electron** ⇒ 两个 postmaster 撞死
症状：探针一路正常（后端 `/health` 报 `db=up`），但 Electron 起来后**登录不进工作台**，
`wait_until('退出登录')` 超时 60 秒。查 `electron.log` 看到：
```
[pg-supervisor] 5432 不通，自动拉起 PostgreSQL：... postgres.exe -D ...\pg2\data
[pg-supervisor] ✅ PostgreSQL 已就绪（5432 已监听）
[server-supervisor] 8787 不通，自动拉起：electron.exe + ELECTRON_RUN_AS_NODE=1 跑 dist/index.js
```
根因：探针的 `ensure_pg()` 会在"端口刚通、PG 还在 `starting up`"时就返回 True；
紧接着 Electron 启动，它的 `pg-supervisor` 探到 5432 不通 ⇒ **又拉了一个 postmaster** ⇒
两个 postmaster 抢同一 data 目录（MEMORY 里记过的那条）⇒ DB 反复不稳 ⇒ 登录链路失败。

**规矩**：起 Electron **之前**必须严格确认 DB 就绪 ——
**连续 2 次** `/health` 都报 `db=up`（间隔 3 秒），而不是只等一次。
（已实现在 `browser-idle-jank-probe.py` 的 `wait_db_ready()`。）

### ★ 另一个坑：应用自己拉起的服务端会变成**孤儿**
应用被杀后，它 supervisor 拉起的服务端**仍在 8787 监听**。
下一轮探针的日志就会出现「8787 已有服务端在跑，直接用（不接管）」——
这个"外部服务端"其实是我们自己上一次留下的，连的还可能是已经死掉的 DB。
**清理**：`netstat -ano -p TCP | findstr :8787` 拿 pid → `taskkill /F /PID <pid>`。

### ★ 探针早退会泄漏进程
`main()` 里 `return 2` 会跳过收尾段 ⇒ electron/node 全留着（实测漏 6 个）。
已改成 `__main__` 里 `try/finally: cleanup_all()`，**早退也保证收干净**。

### ★★ 帧时间实测：**完全没有卡顿**（"卡顿"的正确指标不是 CPU%）
用户说的是"卡顿"，而卡顿的本质是**帧时间** —— CPU 只有 0.2% 也可能照样掉帧。
所以补了 `browser-idle-jank-probe.py`（每段前先提前台 + 回读 `document.hidden === false`）：

| 阶段 | fps | p50 | p95 | >33ms 掉帧 | 长任务 | 打字延迟 p95 |
|---|---|---|---|---|---|---|
| A 0 张页 | 60.1 | 16.7ms | 16.8ms | **0** | **0** | 34.1ms |
| B 1张·全屏 | 60.0 | 16.7ms | 16.9ms | **0** | **0** | 33.6ms |
| C 1张·后台 | 60.0 | 16.7ms | 16.9ms | **0** | **0** | 33.4ms |

主线程 10 秒内只忙 **2.1~2.4%**（ScriptDuration 0.5~0.6%，Layout/RecalcStyle ≈ 0）。
**⇒ 锁 60fps、零掉帧、零长任务；开页前后打字延迟几乎不变（开页甚至没让它变差）。**

★ **测量口径的坑**：打字延迟是"写入 → 等 **2 帧** → 记录"，所以 **33.3ms 就是测量下限**
（2×16.67ms）。测出 33.4~34.1ms 说明真实提交耗时 **< 1 帧**，不是"33ms 很慢"。

**结论**：CPU / 内存 / GPU / 帧时间四个环节都测过且都正常 ⇒ 在这台机器上不支持
"1 个闲置浏览器导致整机卡顿"。最可能的解释仍是系统级内存压力（15.8GB 只剩 2.0GB）。

## 第 27 步 · 补第 4 条真机路径：「用户已退出全屏 → 求助 → 收卡后回后台」

### 发现的第二个体验缺陷：收卡后**一律回全屏**会把用户正在看的聊天盖住
规格只写了"**弹卡那一刻**要自动切回聊天视图"，**没写收卡那一刻回哪**。顺着想下去：
> 用户自己点「退出全屏」（浏览器转后台，他在聊天里看消息）→ AI 求助 → 卡片弹出（自动 embed，对）
> → 他处理完 → **收卡后那张页被顶成全屏**，聊天当场被盖住，还得再点一次「退出全屏」。
等于事办完了反而多欠一步。

**修法（`useBrowserWorkspace.ts`）：从哪来回哪去。**
- `enterEmbed` 先记 `viewBeforeEmbedRef = viewRef.current`（**只在还没进 embed 时记** ——
  同一张卡的重复事件会把它覆盖成 `'embed'`，那就只能兜底回全屏了）；
- `exitEmbed` 按记录恢复，原先 `background` 就回 `background`；
- `showFullscreen` / `exitFullscreen` / `closeAllTabs` 里把记录**清掉**
  （用户主动离开 embed 后，旧记录不该再影响下一次收卡）；
- 兜底仍是 `fullscreen` —— 记不上时给"看得见"的态，不留一个"什么都没有"的界面。

### 两条真机反证打的是**不同的修复**（别混）
| 脚本 | 撤掉什么 | 出问题的**时刻** |
| --- | --- | --- |
| `revert-activate-e2e.py` | `activate()` 的 `keepEmbed` | **弹卡那一刻**（`browser:focus` 冲掉 embed） |
| `revert-back-e2e.py` | `exitEmbed()` 的 `viewBeforeEmbedRef` 恢复 | **收卡那一刻**（一律回全屏盖住聊天） |
两条都表现为"视图态不对"但时刻相反 ⇒ **必须各有一条**，否则一个坏了会被另一个的绿掩盖。
`revert-back-e2e.log`：注入后 30 PASS / **2 FAIL**（红的正是那两条"回后台"断言）→ 恢复后 32 PASS / 0 FAIL。

## 追加（第 27 步收尾）：`browser.view` 闭包快照 —— 真 bug，但**真机 E2E 抓不到**

> ⚠️ 这条结论**纠正过一次**：初版写成"真机逼出这个 bug"，
> 后来反证（注入旧写法 → E2E 仍 46 PASS / 0 FAIL）**推翻了说法**。
> 记录时请用下面这版（有实验支撑）。

### ① 真 bug（`App.tsx` 切智能体 effect）
`else if (browser.view === 'embed') browser.exitEmbed()` 里的 `browser.view` 是
**渲染时的闭包快照**，而该 effect 依赖只有 `[curAgentId, helpCards]`、**不含 `view`**
⇒ 若"卡片出现（`setView('embed')`）"与"切走对话（`setCurAgentId`）"落在**同一 commit 批次之前**，
闭包里的 `browser.view` 仍是上一帧 `'fullscreen'` ⇒ 那道 `if` 为假 ⇒ **`exitEmbed()` 没被调用**
⇒ 浏览器层停在 embed，聊天旁露出一块**别人的网页**。
**修**：去掉那道 `if`，**恒调 `browser.exitEmbed()`**（内部函数式更新永远读最新值）。
★★ **通用规律：判断该由"知道最新值的那一层"做，而不是由拿着快照的调用方做。**

### ② ★★ 但它**不是真机 E2E 抓到的**
反证 `revert-effect-e2e.py` 注入旧写法后 **46 PASS / 0 FAIL** ⇒ **打不到**。
按铁律「反证 0 条变红 = 断言太弱 / 结论不成立」，做了最小化实验
**`view-race-closure.mjs`**（把该 effect 语义搬进最小 React 组件，真实 `react-dom` 渲染）：
| 场景 | 时序 | 旧 | 新 |
| --- | --- | --- | --- |
| 1 | 跨批次（＝常规交互） | ✅ | ✅ |
| 2 | 同批次但 view 从未是 embed | ✅ | ✅ |
| 3 | **闭包快照过期** | ❌ 停 embed | ✅ 正确退出 |
⇒ **bug 真实（场景3）+ 常规交互走不到那个窗口（场景1/2）**。
该修复**保留**，但**证据等级 = "最小化实验"**，**不许说"已被真机反证验证"**。

### ③ 真机那几轮 FAIL 全是**测试自己的错**
1. **JS `.click()` 不产生真实指针序列** ⇒ React `onClick` 收不到 ⇒ **静默不生效**。
   判据：`layerClass` 12 次采样全 `embed` + **`contact--on` 一直停在原智能体**。
   且**时好时坏**（更早某轮 PASS 是页面自己变化触发收卡 = **假通过**）。
   修：CDP 完整鼠标序列（`mousePressed`+`mouseReleased`，坐标取 `getBoundingClientRect()` 中心）。
2. **"目标现在是当前"证明不了切过去了**：传入 id 恰好=当前项时空操作也返 True。
   修：先读**点击前**的 `contact--on`，要求"**变了且等于目标**"。
3. **`agent2` 忘排除 `agent_id` 本身**：`addAgent()` 结尾把新智能体设为当前 ⇒
   旧逻辑把 **`agent_id`** 当"另一个" ⇒ 点在**它已待着的项**上 ⇒ 空操作 ⇒ 假红。
   修：**集合差** `ids_ui - {agent_id}`，断言里印出 `agent_id` 与 `ids_ui`。

### ★★★ 两条可复用铁律
- **"测试红了" ≠ "产品坏了"**：改产品前先证明**这条路径真被走到了**（判据 `contact--on`）。
- **"反证不红" ≠ "修复没用"**：也可能是**测试覆盖不到那个时序**；
  这时要在**更小层面直接把条件构造出来证明**，不含糊写"已验证"、也不草率撤修复。
- 扩展：**任何靠 React 合成事件的点击都该用真鼠标序列**（原铁律 6 只写了 target=_blank/新开 tab）。
