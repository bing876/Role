## 二、★★★ 最大的坑：MSYS 的 `find.exe` 会毁掉 start-dev.cmd

从 **agent 的 bash 里** 运行 `cmd //c start-dev.cmd`，PATH 带着 MSYS 目录 ⇒
`start-dev.cmd` / `watchdog.cmd` 里的 `tasklist | find "..."` 调用到 **Unix `find`**（报 `find: '22312': No such file or directory`）⇒ 全部误判：

- start-dev.cmd 以为「PG 进程已不存在」→ **删掉 postmaster.pid**
- watchdog.cmd 每 10 秒以为「PG 没在跑」→ **反复删 postmaster.pid + 反复起第二个 postgres.exe**

后果：postmaster.pid 长期缺失，两个 postmaster 指向同一数据目录（PG 官方明令禁止）。
实测旧 PG 最后被打死，`pg.log` 记 `database system was interrupted` / `not properly shut down; automatic recovery in progress`。
**PG 靠 WAL 自动恢复成功**（redo done，无错误），数据核对无误：users 6 / projects 6 / agents 9 / conversations 9 / messages 7 / tasks 1。

★ 正确姿势：给 cmd **干净 PATH**（`PATH="/c/Windows/System32:/c/Windows:/c/Windows/System32/Wbem:/c/Program Files/nodejs" cmd //c start-dev.cmd`），
这样 `find` 落到 `C:\Windows\System32\find.exe`，脚本行为正常。
★ 但**这只是为了验证**；用户**双击**运行天然就是干净 PATH，不受影响。

## 三、其它 Windows/bash 互操作坑（本次新增）

| 坑 | 现象 | 解法 |
|---|---|---|
| `MSYS_NO_PATHCONV=1` + `cmd //c` | cmd 收到字面 `//c` → 静默 exit 1、无任何输出 | 二者不能同用：要么 `cmd //c`（不要 NO_PATHCONV），要么 `MSYS_NO_PATHCONV=1 cmd /c` |
| `MSYS_NO_PATHCONV=1 cmd /c` | 被安全策略拦（"Invoking cmd.exe from Bash bypasses all command validation"） | 只能走 `cmd //c` |
| `cmd.exe /c "..."`（带引号） | 同上被拦 | 同上 |
| `tasklist /FI` 从 bash 调 | `/FI` 被转成 `C:/…/PortableGit/…/FI` | `MSYS_NO_PATHCONV=1 tasklist /FI ...`（这次反而必须加） |
| `cmd //c start "" /MIN x.cmd` | `/MIN` 被转成 `C:/…/MIN` | 去掉 `/MIN`，或换干净 PATH 直跑 |
| 用 Write 写 `.cmd`（UTF-8） | cmd 按 GBK 读 → 乱码，`watchdog.cmd` 被读成 `atchdog.cmd`，REM 行被当命令执行 | **`.cmd` 只写纯 ASCII**，或写 GBK |
| `schtasks` | **被安全策略明确禁止**（Program Blacklist），不可重试/绕过 | 放弃这条路 |
| `explorer.exe <x.cmd>` | rc=1，什么也没发生 | 不可用 |
| PowerShell 工具 | `sandbox-center cmd decisionRecord missing actual resource subject` / 空输出 | 本会话不可用，改用 bash + `tasklist`/`netstat` |
