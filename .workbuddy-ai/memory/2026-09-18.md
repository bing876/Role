## ★★ 补充：长驻栈在本机的**进程生命周期**硬坑（血泪，务必先读）

用户要「保持窗口开着」时，踩了一串坑，**根因只有一个**：
> **本机 agent 工具会话回收后台任务时，会连带杀掉该任务派生的所有子进程。**
> 表现为「服务/窗口跑 60~80 秒后自己 code=1 退出」，极像程序崩溃，其实是生命周期。

按尝试顺序记录**全都失败**的方案（不要再试）：
1. `nohup ... &` → 父 Bash 调用结束即回收。
2. 工具 `run_in_background=true` → 该任务被回收时子进程一起死（约 60~80s）。
3. Windows `cmd /c start /B`（bat 里）→ 没留住，日志 0 字节。
4. Node `spawn(cmd, {detached:true}).unref()` → 同样没留住。
5. 反过来「一条 Python 脚本内 Popen 全部子进程 + 脚本自己 while True sleep」→
   **栈能跑起来、登录也成功**，但脚本本身仍是后台任务，任务一回收整个栈（含用户要的窗口）全没。

**结论（选路线）**：
- 要「跑完就退出」的验收/截图：用**一条脚本内管全部子进程**（`scripts/verify/live-demo.py --no-keep`），
  最省事、可复现。
- 要「给用户留一个常驻窗口」：**必须让用户自己起**（或让宿主 GUI 进程起），
  agent 侧无论怎么 spawn 都留不住。so 不要承诺「我帮你开着」，而是给一条命令让用户跑。
- `taskkill /IM electron.exe /T` 会**连带杀掉 vite**（同一进程树），排查时注意。

## ★ 另外两个 CDP 侧的真坑

- **dev 模式主进程自动 `openDevTools({mode:'detach'})`** →
  devtools:// 窗口附着到同一渲染进程后，CDP 的 **`Page.captureScreenshot` 永久挂住**
  （同一条 ws 上 `Runtime.evaluate` 完全正常，所以极易误判成「脚本写错了」）。
  已给主进程加 `WORKBENCH_NO_DEVTOOLS=1` 开关（`apps/desktop/electron/main.ts`），

- **填输入框按 placeholder 定位，不要按 `input[1]`**：重渲染瞬间会取到 null，

```python
stripped = re.sub(r'(data:[a-z/+.-]+;base64,)[A-Za-z0-9+/=]{100,}', r'\1<BASE64>', src)
# 2. 按 <style> 块切分并单独存盘，再 grep —— 比全文 grep 精确（能定位覆盖层）
blocks = re.findall(r'<style[^>]*>(.*?)</style>', src, re.S)
# 3. 判「最终生效值」：base → 补丁块 → !important 覆盖层，逐层取最后命中
```

之前一直用 computed style 数值比对，用户明确指出「那不能证明看到的效果 1:1」。
改用 PIL+numpy 真像素比对后，结论完全变了 —— 差异是**结构性**的，不是细节偏差。

全局统计（1400×900，两图同尺寸同 dpr）：

### 逐条对照（原型 → 桌面端）

| 位置 | 原型 `workbench.work.html` | 桌面端 | 判定 |

### 为什么 heatmap 大面积发红 —— 三个层次的原因（不要只归因抗锯齿）

1. **主因（占差异绝大部分）：布局骨架不同**。列1 顶部「搜索框 vs 智能体标题」、
   列2「空白 vs 消息流」、底部「胶囊 composer vs input 行」——
   这些区域在原型里和桌面端是**不同的元素占位**，像素自然逐点不等。
   典型证据：`y=330-360` 整行平均差 120.3，就是输入栏所在行。
2. **次因：文字渲染差异**。同一段中文在单文件 HTML 里用系统字体栈，
   在 Electron 里走另一套 fontconfig，字形宽度/字重/hinting 不同 →
   文字区域会出现**沿字形轮廓的橙色描边**（在 `小助`/`卡布`/`电商小助手` 三张卡片上最明显）。
   这类差异是**无法消除**的，也不该消除。
3. **再次：抗锯齿 / 亚像素**。圆角边缘、1px 分隔线、渐变过渡带天生有半像素差，
   放大 3 倍后呈绿色-青色细线。这部分**可忽略**。

### 结论（要如实告诉用户）

桌面端**不是**原型 HTML 的 1:1 复刻，而是「另一套 UI」。
不是"某个属性漏改了"，是**信息架构和组件选型都不同**：
- 原型 = 搜索式联系人 + 空白工作区 + 胶囊输入；桌面端 = 项目/智能体列表 + 消息流 + 普通输入栏
- 因此**不可能靠改 CSS 补齐**，只能二选一：
  (a) 承认桌面端是独立产品，各栏目各自设计；或
  (b) 把原型的结构搬过来（列1 改搜索框+单卡片、列2 改空白+胶囊 composer、整窗改圆角玻璃面板）

### 浏览器面板：原型里**根本不存在**（重要澄清）

用户问「浏览器正常情况是隐藏的…原型里点什么东西触发」。实测答案：

- 原型文件里 **`browser` 这个词只出现在注释里**（第 37、3552 行的 CSS 说明），没有任何浏览器面板 DOM。
- 原型 `列0` 实测可点元素只有 4 个（CDP 枚举 + 逐个点击验证）：
  1. `button.menu-btn`（U 头像，27×27 @25,23）
  2. `button.tab.tab-msg.selected`（消息气泡，28×28 @25,61）— **默认为选中态**
  3. `button#railKb.rail-kb`（27×27 @25,90）— **点击后：给 `.frame` 加 `kb-open`，整个列2 被 `.kb-view` 覆盖**，显示「知识库」：左 `产品文档/团队 Wiki/个人笔记/研报与资讯`，右 4 张卡片（快速上手指南 / 快捷键速查 / 主题与外观 / 发布与分享），右上 `＋新建`）。**再点一次收回。这就是列0 第 2 个图标的真实功能 —— 资料库/知识库，不是浏览器。**
  4. `button#railSettings.hamburger`（汉堡，13×9 @32,581）
- 原型里**唯一**有个 iframe 的地方是 `.blk-lightbox-inner iframe`（消息里 HTML 块的放大预览）和 `html-preview`，都是**消息内容渲染**，与"浏览器工作区"无关。
- 所以：**原型的「浏览器隐藏态」在文件里没有实现，也没有触发点**。用户说的"隐藏"是产品意图，不是原型已画的机制。

### 桌面端现状（代码事实）

`App.tsx:2099` — `<BrowserPanel>` 被 `{browser.allTabs.length > 0 && ...}` 包裹：
**一个 tab 都没有时，DOM 里一个节点都不产生** —— 即"完全不渲染、不占空间"。
`browser.allTabs` 是所有智能体桶合并后的活页（不是当前智能体那一桶），
所以只要任意智能体还有页，面板就一直挂着、切智能体也不会卸载（保活）。
→ 桌面端**当前实现的是 (a) 完全不渲染**，正好对应下面清单里的默认选项。

## 底层功能 #2：方案 B · 暂停/继续硬控制（允许暂停期间人工操作）—— 真机 66/66 通过

报告：`docs/acceptance/pause-resume/验收报告.md`；脚本 `scripts/verify/pause-resume-tests.py`
（自带端口 8791 / 8891·8892·8893 / 5178 / 9341，约 110 秒，自己起自己收）。

### 核心设计（三个问题的答复，已实现）
1. **怎么判断页面变没变**：比**结构化快照 `PageSnapshot` 的集合差**（url/title/buttons/links/inputs/texts），
   不是截图比像素、不是整页 DOM diff。代码只判 `unchanged/moved/edited/unknown`，语义交给模型。
   URL 归一化忽略协议/末尾斜杠/`#hash`。纯函数 `apps/server/src/pageDelta.ts`（13 条单测
   `apps/server/scripts/pageDelta.check.mjs`）。
2. **变了之后怎么调整**：`replan-from-current` —— 追加（**不是重建**）一条 user 消息，含
   暂停时长 + delta 人话 + 重新读到的当前页 + 三条硬规矩（这一步只能 read_page /
   **禁止 open_url 跳回暂停前地址** / 对照目标判 done·继续·need_user）。
   为什么不重建系统提示词：`LOOP_SYSTEM_PROMPT` 是全局唯一那份，再造一份要同步维护。
3. **改动范围**：7 处局部改动，循环引擎主体没动。→ 不点暂停时行为**完全等于没改**。

### 最关键的两个状态机判断
- **`paused` 是挂起态，不是终态**。旧代码 `finish()` 调 `stopLoop('ended:paused')`，
  stop 是终态 + 新循环历史为空 → 「继续」等于从头再来一遍。
- **`finishLane` 在暂停时会把 lane 删掉**，loopId 随之丢失 → 「原地继续」名存实亡。
  新增 `lastLoopByWc: Map<wcId, loopId>` 兜住。

### 顺手修掉的 5 个遗留问题
1. 旧的 `stopLoop('ended:paused')`（上面那条）
2. `main.ts` 从不给 `/agent/loop/start` 传 `pageUrl` → 模型第一句永远听到「还没打开，需要时用 open_url」，
   配合上条，恢复后极可能 `open_url` 跳回旧页**覆盖用户刚做的操作**
3. lane 被删导致 loopId 丢失
4. `driver.ts` 的 `applyPaused()` 还留着第 4 步演示循环 `beginRun()` 的调用（显示"在跑"但没驱动任何一步）
5. `main.ts` / `driver.ts` 注释写「并发上限默认 1」，实际 `maxConcurrentAgentTasks` 默认 **20**

### ★ 取证口径上踩的 5 个坑（都是"看着 PASS/FAIL 其实是假证据"）
1. **用全局模型调用计数衡量"AI 停没停"** → 3→12 看着像没停，涨的全是 B/C。
   必须**按路过滤**（假模型把 goal 写进了每条日志，正好当分路标签）。
2. **`delta=unknown`**：暂停前那一路还没走过一个工具步，服务端没有基线快照，如实判 unknown。
   要先等它提问 ≥2 次（= 第一次工具回执已喂回）再暂停。
3. **按整条 URL 找内嵌页**：②里 A 页被手动导航走了，再用 `.../page-a` 找 guest 就找不到。
   改成按 **`host:port`** 认页。
4. **DB 查询不带 `user_id`**：④查到的"未解除暂停记录"是**上一轮另一个账号**的残留行，假 PASS。
   库查询必须带本次登录的 user_id，并额外断言 `wc_id` 正是被暂停的那张页。
5. **在快跑到步数上限的循环上点暂停**：它会先自己终态收尾，服务端根本收不到挂起请求。
   ④改成先给那一路重新发车（步数充足），并**等 DB 真的落行**而不是睡固定几秒。

### ⑦ 补验：服务端也重启（顺带修掉一个真 bug）
④只重开 Electron，服务端没重启 → 循环还在内存，没验到最坏情况。补了 ⑦：杀服务端重开，
断言 `live=0 running=0` 且 `?open=1` 仍 `count=1 / resumed=false`。

**根因**：`routes/loop.ts` 的 `resumed` 回填写成 `rec.resumed || !isLoopPaused(rec.loopId)`，

一律被报成「已恢复」。修法：新增 `toolLoop.hasLoop()`，只有「循环还在内存且不是挂起态」才判已恢复。
